Compressed swap cache (zswap)

Control Plane Reservation

				

					How much of this machine is held back for the daemon itself (issue #86).

Control-plane stalls

				

					Times this daemon's event loop stopped going round (issue #100). Recorded by a
					separate watchdog process, because the loop cannot report its own silence —
					a real multi-minute outage on the production host left nothing in the log
					store for exactly that reason, and could not be analysed afterwards at all.
				

				

					wchan is the kernel function the daemon was sleeping in, read
					from /proc by the watchdog: the single most useful fact about a wedge,
					and the one thing unavailable from inside it. state is the process
					state — D is uninterruptible sleep, the kind that cannot even be
					killed. activity is the request being served when the loop went
					quiet, so a stall names the thing that did not come back.

Boot Entries (ESP)

				

					What this machine will actually boot next, and why. Will boot
					is computed the way systemd-boot itself chooses: entries whose boot counter has
					run out sort last, then by sort-key and version
					descending — so a freshly staged update outranks an older entry whatever
					its slot letter (ADR-0202).
				

				

					Default is a glob pattern, not a name. That is what made a real
					host reboot into the image it was already running, repeatedly, with no error
					anywhere: a stale thinc-* written at install time went on matching
					six obsolete entries and outranking every correctly staged one (issue #128).
					Leave it as cix-* unless you have a specific reason — pinning
					it to one slot breaks the next update, which stages the other one.

Install a key pair

				

					Paste both PEM blocks. The DER .cer that mokutil
					needs is derived from the certificate here, so there is no third thing to
					keep in step. The certificate is checked against the private key before
					anything is written: a mismatched pair is refused outright rather than
					discovered later as an image that signs cleanly and then will not boot.
				

				

				

					
				


				
Release Signing Key

				

					A separate key, and deliberately so (ADR-0220). The pair
					above is RSA because UEFI mandates RSA, and answers “may this firmware
					boot this image?” This one is Ed25519 because
					minisign mandates Ed25519, and answers “did Cix publish
					these bytes?” One key for both would mean whoever can sign a download
					can also sign a bootloader — and the two have very different blast
					radii: republishing a public key, versus re-enrolling firmware on every host.
				

				

					Installer ISOs built here are signed with it. Anyone who downloads one
					verifies with stock minisign against the public key below
					— no Cix software required on their side, which is the point: the last
					check between a substituted ISO and a machine should not be code from the
					project that produced the ISO.

Install a release key

				

					Generate one with
					openssl genpkey -algorithm ed25519 and paste it here. The key is
					validated by deriving its public half before anything is written, so an RSA
					key — the realistic mistake, given the pair sitting right above —
					is refused now rather than at signing time on a real release.

ADR-0157: how many pkg install/pkg hostbuild jobs may genuinely run at once, each in its own build container. Lowering this doesn't disrupt jobs already in flight -- only future ones once the new, lower ceiling is reached.

			
Issue #85: these are an aggregate budget, carried by one parent cgroup every build container is a leaf of -- not a per-build ceiling. A per-build number is not a budget: with max concurrent jobs at 10 it silently meant ten times what it said, and on a real 2-CPU box four concurrent builds at 1.5 CPU each demanded 6 CPUs, starved the daemon off the run queue and took the machine out of reach entirely. Whatever this says is now what all builds together can use.

			
cix#558: a recipe can declare the memory its whole build needs (CPDL resources { memory "4GiB" }, cbs v0.1.100). While such a build runs, the budget above is raised to that need, up to the ceiling; it returns to the budget once no build is running. A recipe that declares more than the ceiling is refused before it starts, with both numbers in the error. The ceiling is never below the budget, and equal to it means no recipe can raise anything.

			
ADR-0165 (superseded in shape by the above): the memory/CPU ceiling applied to build containers -- the same cgroup mechanism a regular container's own --memory-max=/--cpu-max= already uses. Found missing the hard way: a burst of concurrent installs with no ceiling hung a real box's daemon entirely. CPU quota is microseconds of CPU time per 100000-microsecond period -- "100000 100000" is one full CPU's worth, "50000 100000" is half a CPU.

Owner

			

			

			

				A volume is a directory this daemon creates as root (issue #102), so a
				workload that does not run as root cannot write to its own volume — found the plain
				way, by an operator logging into the jump box and finding their home directory owned by
				root. These are the ids as the container sees them.
			

			

				Recursion is off by default on purpose: a volume that has been in use holds files whose
				ownership someone may have set deliberately, and rewriting all of them because the
				top-level owner changed is a quiet kind of data loss.
			


			
Size limit

			

			

			
A real, kernel-enforced hard limit — a write past it fails at the
				filesystem level rather than being noticed afterwards. Without one a volume can grow until
				the disk it sits on is full, which also makes it an unbounded thing to copy when scheduled
				backups run. On a btrfs-backed volume this is refused rather than accepted and left
				unenforced: there the limit needs the volume to be its own subvolume, which is a change to
				how volumes are created rather than another call.


			
Backups

			

			

			

				
			

			

				
			

			
Snapshots go to the disk carrying the backup role, configured
				under System > Maintenance > Volume Backups.
				Restoring replaces everything currently in the volume, and is always
				refused while a container mounting it is running.

			
The middle setting above decides whether this volume is ever actually
				backed up. A service container is normally restart: always and never stops, so
				skip means it is never snapshotted — quietly, forever.
				Pause freezes every container using the volume for the length of the copy
				and then resumes them: nothing can write while it runs, so the snapshot is genuinely
				consistent, at the cost of real downtime for that time. Copy live takes a
				crash-consistent snapshot — it sees whatever was on disk at that moment, so a file
				being written mid-copy is caught half-written. That is normally fine for a home or config
				tree and is what an ordinary filesystem backup has always given you; for a database it is
				not, and that wants its own dump from something that understands its format.


			
Move it

			

			

			
The data is copied to the new location and the volume repointed only
				once the copy succeeds, so a failure at any point leaves the volume still pointing at
				data that exists. Refused while a container mounting it is running — a bind mount
				resolves to a host path when the container starts, so moving the data underneath a live
				container would leave it writing to the old location with nothing to show for it.
