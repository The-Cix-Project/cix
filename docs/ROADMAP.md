**API-first, no exceptions (added after Phase 2):** the REST daemon is the only process with direct access to the runtime library or any host/network/DNS/PKI primitive. ## Locked-in technical decisions (apply to every phase)

- Dynamic linking against **system glibc** always — never `-static`, never TCC's bundled headers.
- `pivot_root` and `clone3` have no glibc wrappers — call via `syscall(SYS_pivot_root, ...)` / `syscall(SYS_clone3, ...)`; `struct clone_args` is declared ourselves in `include/linux_compat.h` (never `#include <linux/sched.h>`, it clashes with glibc's `<sched.h>`).
- The REST daemon's event loop uses `epoll`, not `io_uring` (no glibc wrapper, heavier hand-rolled-uapi lift — an explicit future optimization, not a baseline requirement).
- Networking phases talk to the kernel via rtnetlink sockets directly in C — never shell out to `ip`/iproute2.
- Build: `tcc -Wall -Werror -D_GNU_SOURCE -D_FORTIFY_SOURCE=0 -Iinclude ...` — zero warnings is a hard gate, not a suggestion.
- **TCC ignores `__attribute__((packed))` entirely** (confirmed on both the system `<sys/epoll.h>` struct and a minimal struct we wrote ourselves with the attribute) but *does* honor `#pragma pack`. Any kernel-ABI struct that relies on packing (`struct epoll_event` is the one hit so far: real ABI is 12 bytes/data at offset 4, TCC's default-aligned version is 16 bytes/data at offset 8) needs its own `#pragma pack`-based replacement in `include/linux_compat.h` rather than the system header's type — see `struct kx_epoll_event` / `kx_epoll_ctl()` / `kx_epoll_wait()`. Watch for this on every future struct pulled from a Linux uapi/glibc header before assuming its layout is safe under TCC.
- **Every fd the daemon opens for its own bookkeeping is `CLOEXEC` from creation** (`SOCK_CLOEXEC`/`EPOLL_CLOEXEC`/`O_CLOEXEC`, never patched on afterward). Any process built on `container_create()` routinely `clone3()`s new children from inside request-handling code, and an inherited non-CLOEXEC fd (a client connection socket, in the bug this caught) silently stalls that request until the spawned container itself exits — no crash, no error, just a severe, easy-to-miss latency regression. See ADR-0009.

## Phase 0 — Toolchain smoke test (done)

Confirmed TCC compiles and dynamically links against host glibc with `-Wall -Werror`, and every header family later phases need (`sched.h`, `sys/mount.h`, `sys/prctl.h`, `sys/wait.h`, `linux/netlink.h`, `sys/epoll.h`) parses clean. `test/test_toolchain.c`. See ADR-0001.

## Phase 1 — Namespace + cgroup v2 container harness (done)

Clone a child into new PID+MNT+UTS+NET(+CGROUP) namespaces, place it into a cgroup v2 leaf with memory/pids limits atomically at creation (`clone3` + `CLONE_INTO_CGROUP`, no TOCTOU write to `cgroup.procs`), pivot_root into a bind-mounted copy of host `/`, exec a target, reap race-free via pidfd. User-namespace/rootless support deferred to a later "Phase 1b." See ADR-0002 and ADR-0003 for why.

Implementation: `include/container.h`, `include/linux_compat.h`, `include/internal.h`, `src/cgroup.c`, `src/ns_create.c`, `src/mountns.c`, `src/container.c`. Verified end to end by `test/test_harness.c` (`test/harness_child.c` is its exec target) — all of:

1. No nesting/seccomp-blocked syscalls.
2. Child exit status `7` — `execve` ran inside the new namespaces.
3. Child PID `1` — PID namespace isolation.
4. Child hostname `container-test`, host hostname unchanged — UTS isolation without global mutation.
5. `/sys/class/net` (and `/proc/net/dev`) inside the child shows only `lo` — NET namespace isolation.
6. `cgroup.procs` has exactly one PID, matching clone3's return value — atomic cgroup placement, no race window.
7. Zero warnings under `-Wall -Werror`.

Runs only on a **privileged** LXC container/host — an unprivileged nested LXC container blocks the final `mount("proc", ...)` with `EPERM`/"VFS: Mount too revealing" regardless of mount flags or namespace combination tried (confirmed by elimination, not guesswork; resolved by converting this dev container to privileged).

## Phase 2 — OverlayFS root construction (done)

Real OverlayFS layering (lowerdir/upperdir/workdir) replaces Phase 1's bind-mount-of-live-host-root: `overlay_create()` mounts `mount("overlay", merged, "overlay", 0, "lowerdir=...,upperdir=...,workdir=...")` inside the child's own mount namespace, before `mountns_pivot()` pivots into `merged`. `lowerdir` must already exist and be populated — never auto-created, since a silently-empty lowerdir would mean a silently-broken container. The propagation-privatizing remount (`MS_REC|MS_PRIVATE`) was split out of `mountns_pivot()` into its own `mountns_make_private()` and now runs *before* the overlay mount, not after — otherwise the overlay mount could propagate back onto the host. See ADR-0004 for why the lowerdir is a dedicated tree rather than the live host root.

Implementation: `struct overlay_spec` + `overlay_create()` in `include/container.h`/`src/overlay.c`; `mountns_pivot()` in `src/mountns.c` no longer populates the root itself, it only requires `new_root` already be a mount point. `struct mount_spec.root_source` was removed (folded into `overlay_spec.merged`) to eliminate a duplicate-state footgun. Verified end to end by `test/test_overlay.c` (`test/overlay_child.c` is its exec target), against a minimal, purpose-built lowerdir (just the exec binary + the dynamic linker/libc it needs + a marker file — no debootstrap, no full userland):

1. Container `c1` runs against a fresh upperdir over the shared lowerdir, exits `42`.
2. `c1`'s upperdir has `status.txt` showing it saw the lowerdir's marker content correctly and no pre-existing file — proves shared-lowerdir visibility.
3. The lowerdir itself has no `status.txt` afterward — proves the shared lowerdir is never mutated by a container's writes (copy-up lands only in upperdir).
4. Container `c2` runs against a second fresh upperdir over the *same* lowerdir, exits `42`, and its `status.txt` also shows no pre-existing file — proves `c2` never saw `c1`'s diff (per-container upperdir isolation over a shared base).
5. Zero warnings under `-Wall -Werror`.
6. Phase 1's `test_harness` re-verified to still fully pass after this shared-code refactor (its `ov.lowerdir` is `/`, preserving its original full-host-visible content, now routed through the same real overlay mechanism instead of a raw bind mount — its result file now reads from upperdir's copy-up path rather than the bare host path, since containers can no longer write straight to the live host).

## Phase 3 — REST API spec + daemon: host + container lifecycle (done)

The API contract lives at `docs/api/openapi.yaml` (OpenAPI 3.0), written before any handler code: `GET /v1/health`, `GET/POST /v1/containers`, `GET/DELETE /v1/containers/{name}`. The daemon (`daemon/src/main.c`, binary `kanxeod`) is a single-threaded, non-blocking, `epoll`-driven reactor with no external libraries — its own minimal HTTP/1.1 parser (`daemon/src/http.c`, request-line + headers + fixed-length body, `Connection: close` only, no keep-alive/chunked — a deliberate v1 scope boundary) and its own minimal generic JSON parser/writer (`daemon/src/json.c`; `\uXXXX` escapes unsupported, also a deliberate boundary — no field in this API needs one). Containers live in a fixed-size in-memory table (`daemon/src/registry.c`) keyed by client-supplied name; safe to be in-memory-only (no restart persistence) because `container.c`'s existing `PR_SET_PDEATHSIG` means every running container dies automatically if the daemon exits, so there's no orphan/restart-reconciliation problem to solve.

New durable storage convention (first time this project needed one, versus `/tmp` test scratch): `/var/lib/kanxeo/images/<image>/rootfs` (a lowerdir — never auto-created by the daemon, same Phase-2 rule) and `/var/lib/kanxeo/containers/<name>/{upper,work,merged}`.

**A real, non-obvious bug found and fixed here, not just a test gap:** `epoll_ctl()`/`epoll_wait()` were silently corrupting their `data` field under TCC — see the `kx_epoll_event` entry in "Locked-in technical decisions" above, and ADR-0008 for the full root-cause writeup. It surfaced as an intermittent (~50-60% of runs) segfault on the very first request, requiring a core-dump-free `gdb`+`strace` bisection since the failure wasn't reproducible on demand.

Design rationale for the API-first reordering, the OpenAPI spec choice, and the daemon's hand-rolled/no-external-libs approach: ADR-0005, ADR-0006, ADR-0007.

Verified end to end by `test/test_daemon.c` (`test/daemon_child.c` is its exec target; takes a sleep-seconds and an exit-code argument) — drives the built daemon purely over real HTTP (originally hand-written request/response handling, generalized into `client/src/httpclient.c` in Phase 4 and reused from there since):

1. `GET /v1/health` → `200`.
2. Create a container that exits quickly with a known code; poll until `status:"exited"` and confirm the exact `exit_status` came back through the API.
3. `GET /v1/containers` lists it.
4. Create a second, long-running container and `DELETE` it while still running → `204`, and confirm its PID is actually gone from `/proc` (not just marked removed).
5. Deleted container → subsequent `GET` is `404`.
6. Duplicate name → `409`; missing required field → `400`.
7. `SIGTERM` → clean daemon exit (not killed by a timeout).
8. Zero warnings under `-Wall -Werror` across every new file.
9. Phase 1 (`test_harness`) and Phase 2 (`test_overlay`) re-run and still fully pass — no regression from this phase's `linux_compat.h`/shared-code changes.

## Phase 4 — CLI, pure REST API client (done)

`kanxeoctl` (`cli/src/main.c`) — one subcommand per endpoint (`health`, `ps`, `run`, `inspect`, `rm`), zero direct runtime access, per the API-First Mandate. `run`'s request body is built with the JSON writer (`jw_*`), not `snprintf` string concatenation, since its `name`/`image`/`cmd` values come from arbitrary user-supplied argv and must be properly escaped. `--json` prints the raw response (re-serialized through the same JSON writer the daemon itself uses to build responses, so there's no second JSON-rendering implementation); otherwise output is formatted text. Exit codes: `0` for a 2xx response, `1` for a 4xx/5xx or transport failure, `2` for a usage error — scriptable (`if kanxeoctl inspect foo; then ...`).

`test_daemon.c`'s ad hoc socket code (`do_request()`/`connect_to_daemon()`/`write_all()`) was extracted into `client/src/httpclient.c` (`kx_client_request()`) — a real, reusable "talk to the Kanxeo API" library, now shared by `kanxeoctl` and the daemon's own test suite, eliminating what would otherwise have been two independent implementations of the same concern. While generalizing it, the response buffer became dynamically-growing (same doubling pattern as `daemon/src/http.c`) instead of the test's fixed 16KB cap, since a real container listing can legitimately exceed that. `test/test_image_fixture.c` similarly extracts the shared test-image staging logic so `test_cli.c` doesn't duplicate it either.

**A second real, non-obvious bug found here, via the same stress-test discipline ADR-0008 established:** `test_daemon.c` was silently taking ~30 seconds per run (matching its long-running test container's sleep duration) instead of milliseconds — no failure, just a severe latency regression that repeated/back-to-back runs eventually made impossible to ignore. Root cause: none of the daemon's own fds (listening socket, accepted client sockets, the `epoll` fd, the cgroup `O_PATH` fd) were `CLOEXEC`, so every container `clone3()`'d from inside request-handling inherited a duplicate of the triggering client connection — and the kernel won't deliver EOF on a TCP connection until *every* reference to it, across every process, closes. Fixed by making every one of those fds `CLOEXEC` from creation. See ADR-0009. Verified fixed by timing, not just pass/fail: `test_daemon.c` went from ~30s to ~0.3s per run.

Verified end to end by `test/test_cli.c`, driving the real, built `kanxeoctl` binary as a subprocess (not calling `httpclient.c` directly, so it proves the actual shipped binary) — all of:

1. `health` → exit `0`.
2. `run --name=c1 --image=test -- /bin/daemon_child 0 5` → exit `0`, output shows `running`.
3. `ps` → output lists `c1`.
4. Poll `inspect c1` until output shows `exited` and `exit_status=5`.
5. `run --name=c2 ... /bin/daemon_child 30 0`, then `rm c2` while running → exit `0`; the PID (parsed from `run`'s own output) is confirmed gone from `/proc`; `inspect c2` afterward → nonzero exit.
6. Duplicate name → nonzero exit, error message present in output.
7. Daemon unreachable (wrong port) → exit `1`, no crash.
8. Zero warnings under `-Wall -Werror` across every new/changed file; `test_harness`, `test_overlay`, and the refactored `test_daemon` re-run and still fully pass.

## Phase 5 — Web dashboard, pure REST API client (done)

`web/index.html` + `web/app.js` + `web/style.css` — vanilla HTML/CSS/JS, no framework, no build step (ADR-0010): a health indicator, an auto-refreshing (2s poll) container table, a create-container form, and a remove button per row. Mirrors `kanxeoctl`'s exact command surface — no dashboard feature without a CLI/API equivalent, and no separate "inspect" view since `GET /v1/containers` already returns every field a per-container detail view would add.

Served by `kanxeod` itself, same origin as the API (`daemon/src/staticfile.c`, new `--web-root` flag, default `web/`) — confirmed with the user directly rather than assumed: a separate static-file process would make the dashboard's `fetch()` calls cross-origin, needing CORS preflight/header handling in the daemon for no functional benefit. `dispatch()` in `daemon/src/main.c` now falls through to `static_serve()` for any GET path that doesn't start with `/v1/`, before the existing JSON-404 fallback (which still covers unrecognized `/v1/...` paths unchanged). `main.c`'s private `make_blocking()` was promoted to a public `http_set_blocking()` in `daemon/src/http.c`, since `static_serve()` needed the identical "blocking mode before this small, connection-closing write" behavior `respond_json()` already relied on.

`client/include/httpclient.h`'s `struct kx_response` gained `content_type`/`body`/`body_len` (previously it only exposed the parsed JSON tree) — needed to verify static file responses, which aren't JSON at all.

Verified end to end by `test/test_web.c` (reusing `client/src/httpclient.c`, like every test since Phase 4):

1. `GET /` → `200`, `Content-Type: text/html`, body contains the page title.
2. `GET /app.js` → `200`, `Content-Type: application/javascript`.
3. `GET /style.css` → `200`, `Content-Type: text/css`.
4. `GET /nonexistent.txt` → `404`.
5. `GET /../CLAUDE.md` (path-traversal attempt) → `400`, response body does **not** contain `CLAUDE.md`'s actual content.
6. `GET /v1/health` still `200` — the new static-fallback branch didn't regress API routing.
7. Zero warnings under `-Wall -Werror`; `test_harness`, `test_overlay`, `test_daemon`, `test_cli` re-run and still fully pass (including a repeated-run stress pass, per the ADR-0008/ADR-0009 lesson that a single passing run isn't enough).

**Explicit scope boundary (not a silent gap):** whether the dashboard actually *renders and behaves* correctly in a real browser (form submission, table updates, delete button) wasn't automated — this project has no headless-browser/Node toolchain, and adding one for a single small dashboard would repeat the exact dependency-cost trade-off ADR-0010 decided against. What was checked instead: `node --check` (a pre-installed system tool, not a new project dependency) confirms `app.js` is syntactically valid, and every DOM element ID `app.js` references was confirmed present in `index.html`. Whether it looks and behaves right needs a real browser at `http://127.0.0.1:7620/`.

## Phase 6 — Custom virtual switch / rtnetlink data plane (done)

Confirmed with the user before writing any code: "custom" means our own control-plane code driving the kernel's native bridge/veth/routing via rtnetlink directly — never `ip`/iproute2, never OVS, never eBPF — with the kernel itself still doing the actual packet forwarding. See ADR-0011.

**Part 1 (done): rtnetlink primitives, proven standalone.** `netplane/include/rtnetlink.h` + `netplane/src/rtnetlink.c` — hand-built netlink messages (a small generic message/attribute builder, including the one genuinely intricate construction here: `IFLA_LINKINFO` → `IFLA_INFO_DATA` → `VETH_INFO_PEER` nesting, which the kernel's veth driver expects to open with a raw embedded `struct ifinfomsg`) for bridge creation, veth pair creation, moving a link into another process's netns, bridge attachment, IPv4 addressing, default-route installation, and link deletion. Links are addressed by name for every existing-link operation (no separate ifindex lookup needed). Before writing any of it, per ADR-0008's lesson, confirmed via a throwaway `sizeof`/`offsetof` check that TCC lays out `nlmsghdr`/`ifinfomsg`/`ifaddrmsg`/`rtmsg`/`rtattr`/`nlmsgerr` identically to GCC (none of them rely on non-default packing, unlike `epoll_event`), and that `<linux/rtnetlink.h>`/`<linux/if_link.h>`/`<linux/veth.h>` don't conflict with glibc's own `<net/if.h>`/`<sys/socket.h>`.

A real design pitfall surfaced during this work, not just a test gap: the gateway IP must go on the **bridge device**, never on a veth port that's enslaved to it — a bridge port doesn't behave like a normal addressable interface once attached, even though assigning it an address doesn't itself return an error. See ADR-0011.

Verified end to end by `test/test_rtnetlink.c` (reuses `ns_clone3()` from `src/ns_create.c` to fork a "container-like" `CLONE_NEWNET` child — no second way to create a namespaced process invented for this):

1. Clears any leftover state from a previous interrupted run first.
2. Creates bridge `kanxeo-test0` — confirmed via `/sys/class/net/kanxeo-test0/bridge/`.
3. Creates veth pair `vt-a`/`vt-b` — both appear on the host.
4. Moves `vt-b` into the child's netns — confirmed by its disappearance from the host's `/sys/class/net`.
5. Attaches `vt-a` to the bridge — confirmed via `/sys/class/net/kanxeo-test0/brif/vt-a`.
6. Assigns the gateway IP to the bridge, addresses `vt-b` inside the child.
7. **Real TCP connectivity** through the resulting topology (host → bridge → veth → child), not just "the syscalls didn't error" — a one-byte round trip.
8. Cleanup (`rtnl_link_delete`) leaves no interfaces behind — confirmed directly.
9. Zero warnings under `-Wall -Werror`; all five prior test suites (`test_harness`, `test_overlay`, `test_daemon`, `test_cli`, `test_web`) re-run and still fully pass, plus this new test itself re-run repeatedly (no regression, and no flakiness of its own).

**Part 2 (done): wired into the real container lifecycle.** `container_spec` gained an opt-in `struct network_spec net` (`include/container.h`) — `bridge == NULL` means exactly what every container has gotten since Phase 1 (isolated netns, only `lo`), unchanged. `test_harness.c`/`test_overlay.c` needed zero source changes to prove this: their existing `memset(&spec, 0, ...)` already zeroes the new field, and re-running them (not just reasoning about it) confirmed nothing regressed.

New `src/container_net.c` (`container_net_host_setup()`/`container_net_child_configure()`, declared in `include/internal.h`, following the same one-file-per-concern pattern as `mountns.c`/`overlay.c`), and a new `rtnl_link_rename()` primitive in `netplane/` (needed to rename the container's veth end to `eth0` — the one operation here that can't identify its target via `IFLA_IFNAME`, since that attribute means "set this as the new name," so it resolves the old name to an ifindex first instead, same as `rtnl_link_set_master()` already does for a *referenced* interface).

`container_create()` gained a synchronization barrier (a `pipe()`, created before `clone3()`, inherited by both branches) for exactly one reason: the parent must move a veth into the child's netns before the child touches it, but there was no pause point for that. A real subtlety surfaced here, not just plumbing: the parent names the veth pair from the child's *real* pid, but `CLONE_NEWPID` means the child sees itself as pid 1 in its own namespace — `getpid()` inside the child can't recover that name. Fixed by sending the veth's name *through* the same barrier pipe rather than inventing a second channel. The failure path got real attention too: if the parent's host-side network setup fails, it closes the pipe's write end *without writing*, which makes the already-blocked child's `read()` see EOF and fail cleanly (`_exit(126)`) instead of hanging forever — then the parent reaps it, frees its fds, and reports the whole `container_create()` call as failed, the same contract every other early-return in that function already honors.

Verified end to end by new `test/test_container_net.c` (`test/net_child.c` is its exec target — binds `0.0.0.0:<port>`, echoes one byte, exits 0) — through the real `container_create()`, not the raw primitives:

1. Creates **two** containers concurrently (not sequentially) on the same bridge, distinct static IPs.
2. Real, simultaneous TCP connectivity to both from the host — proves the bridge correctly demultiplexes between two ports, not just that one point-to-point link works.
3. Both exit 0, reaped via `container_wait()`.
4. Confirms the host-side veth for each is gone after that container exits **with no explicit delete call** — moving a veth's peer into a dying netns makes the kernel destroy both ends automatically. One genuinely useful kernel fact learned here: that teardown runs on a workqueue, not synchronously with the process being reaped, so the interface can briefly still exist right after `waitid()` returns — the test polls for its disappearance (same pattern as every other "wait for something async" check in this project) rather than asserting immediately, after an initial run caught exactly that race.
5. Zero warnings; all six prior suites (`test_harness`, `test_overlay`, `test_daemon`, `test_cli`, `test_web`, `test_rtnetlink`) re-run and still fully pass.

`test/test_image_fixture.c` gained a third parameter (destination basename) so this test's `net_child` exec target could reuse the same staging function as every other test's `daemon_child`, rather than a second, near-duplicate one.

**Part 3 (done): exposed through the daemon/API/CLI/dashboard.** `kanxeod` now owns a real default network end to end, not just a test-owned bridge: `daemon/src/main.c`'s `ensure_default_network()` creates bridge `kanxeo0` (`172.30.0.0/24`, gateway `.1`) at startup, tolerating `EEXIST` on both the bridge create and the gateway address assignment — the same idempotent-restart pattern `ensure_dir()` already established for the storage directories, run unconditionally on every startup exactly as `ensure_dir()` is.

IP allocation is tracked in `daemon/src/registry.c`, deliberately kept topology-agnostic: `registry_alloc_ip(network_base_be, host_min, host_max, *out_ip_be)` takes the subnet as parameters and scans in-use entries for the first free host address — `main.c` remains the single owner of the actual topology (bridge name, subnet, gateway), never duplicated into the registry. `registry_create()`'s signature gained an `ip_be` parameter set atomically at construction, not poked in afterward by the caller — closes a real footgun, since the registry reuses freed slots and an unconditional reset is what stops a new non-networked container from appearing to inherit a previous occupant's stale IP.

`POST /v1/containers`'s optional `"network"` field (`docs/api/openapi.yaml`, only `"default"` supported in v1 — anything else is `400`) allocates an IP and populates `struct network_spec` from Part 2; omitting it leaves `spec.net` zeroed, exactly the pre-existing behavior, unchanged. The `Container` schema's new `"ip"` field is `null` for non-networked containers. `kanxeoctl run --network=default` and an `ip=` column in its `ps`/`inspect` output; the web dashboard gained a matching create-form field and IP column (`node --check` clean, DOM IDs cross-referenced — same scope boundary as Phase 5/ADR-0010, actual rendering not automated).

**Stated v1 scope boundary, not a silent gap:** exactly one fixed network (`"default"`), sequential IP allocation, no user-defined networks/subnets, no DHCP. No new ADR for this — it's a stated limitation, not a durable architectural decision beyond what ADR-0011 already covers (per ADR-0000's own guidance against writing one for everything).

Verified end to end by new `test/test_daemon_net.c` (`test/net_child.c` is its exec target again) over real HTTP:

1. `POST` with `"network":"default"` → `201`, non-null `ip`, real TCP connectivity through it.
2. A second such `POST` gets a **different** `ip` — proves allocation actually advances, not just returns the same address twice.
3. `GET /v1/containers` shows both containers' correct, distinct IPs.
4. `POST` **without** `network` still works exactly as before, `ip` is `null` — the explicit regression check on this endpoint's unchanged default behavior.
5. `POST` with an unsupported network name → `400`.
6. Zero warnings; `test/test_cli.c` gained a matching scenario driving the real `kanxeoctl` binary (`--network=default` shows a real `ip=` in its output); all 8 suites (`test_harness`, `test_overlay`, `test_daemon`, `test_cli`, `test_web`, `test_rtnetlink`, `test_container_net`, `test_daemon_net`) re-run repeatedly back-to-back and still fully pass, confirming no leftover interfaces between runs.

**A real test-hygiene bug found here, not a bug in the shipped daemon/library code:** `ensure_default_network()` runs unconditionally on every `kanxeod` startup (correct, intentional behavior — mirrors `ensure_dir()`), which means *every* test that starts a real `kanxeod` creates `kanxeo0` as a side effect, whether or not that specific test exercises networking. `test/test_rtnetlink.c` (Part 1) creates its own standalone bridge on the **same** `172.30.0.0/24` subnet, so a `kanxeo0` left behind by an earlier `test_daemon.c`/`test_cli.c`/`test_web.c`/`test_daemon_net.c` run collided with it and hung the test. Fixed by giving every test that transitively starts `kanxeod` the same cleanup: a shared `test_cleanup_bridge()` (`test/test_net_cleanup.c`/`.h`) that retries the delete (up to 20 times, 100ms apart) rather than a single attempt, since network namespace/veth teardown runs on a kernel workqueue and can lag briefly behind the process being reaped — the same async-teardown fact `test_container_net.c` (Part 2) already had to account for. One implementation, not four copies of the same retry loop.

## Phase 7 — Routing protocols for containerized VPNs/routers (done)

Confirmed with the user before designing any of this: we are not reimplementing routing protocols ourselves. A container just runs a real routing daemon (BIRD, FRR, ...) as a normal workload, talking to the kernel via netlink from inside its own netns — exactly like any other containerized app, and something it can already do today with zero extra plumbing, since containers have never been given a user-namespace UID remap (Phase 1's stated scope boundary), so every container already has full `CAP_NET_ADMIN` inside its own netns. Our job is the platform substrate a routing workload needs underneath it: more than one network a container can attach to, an IP-forwarding toggle, and static route installation — the "statics" the user explicitly placed in our scope, as distinct from the dynamic protocol itself. Split into three parts, each separately verified before the next starts, same cadence as Phase 6:

- **Part 1 (done): the network resource itself.** Networks are now a real, dynamic, REST-managed resource rather than one thing hardcoded at compile time — the user's explicit choice when asked directly whether to keep a small fixed table or make this a proper API. Containers still attach to exactly one network at a time in this part; multiple attachments per container are Part 2.
- **Part 2 (done): multi-homed containers** — a container attaches to more than one network at once, the actual routing prerequisite.
- **Part 3 (done): IP forwarding + static routes** — turns a multi-homed container into a real router.

**Part 1 design.** New `daemon/include/network.h` + `daemon/src/network.c` (one-concern-per-file, mirroring `registry.c`'s existing shape): a fixed-size `struct network_def` table (name, subnet, prefix length, derived gateway), `network_create()`/`network_delete()`/`network_find()`/`network_alloc_ip()` (the last delegating straight to the existing, already topology-agnostic `registry_alloc_ip()` — no changes needed there, it was deliberately built this way in Phase 6 part 3 for exactly this reuse). `daemon/src/main.c`'s old `DEFAULT_BRIDGE`/`ensure_default_network()`/single-hardcoded-subnet machinery is gone entirely, replaced by `POST/GET/DELETE /v1/networks` and a `network_find()`/`network_alloc_ip()` call inside `handle_create()`.

A consequence worth stating plainly, not a side effect discovered later: unlike containers (safe to be in-memory-only, since every one of them dies with the daemon via `PR_SET_PDEATHSIG` — Phase 3's reasoning), a bridge created via this new API is real, persistent kernel state that outlives the daemon process. Forgetting about it on restart would silently break IP allocation and API visibility for a bridge still functioning underneath. So this part introduces the project's **first durable host-state persistence file** (see ADR-0012), `/var/lib/kanxeo/networks.json` — written atomically (temp file, `fsync`, `rename()` over the real path; a crash mid-write must never corrupt the one record of which bridges this daemon owns) on every create/delete, and reloaded at startup, idempotently recreating each persisted network's bridge (`EEXIST` tolerated, same spirit as `ensure_dir()`). `registry_entry` gained a `network` field (the attached network's name, recorded directly rather than inferred from IP-range containment) so `network_delete()` can refuse removal while any container is still attached to it.

Validation in `network_create()`: name is 1–15 chars (`IFNAMSIZ`, since a network's name *is* its bridge's interface name) and unique; the given subnet's host bits must actually be zero for the given prefix (`172.31.0.5/24` is rejected, only `172.31.0.0/24` is valid); prefix length must be in `[8,30]`; the range must not overlap any existing network's. The gateway is always the subnet's first host address — never an independently-settable field, so it can never drift from the subnet it's derived from.

Verified end to end by new `test/test_networks.c`:

1. Two distinct, non-overlapping networks created (`201` each), both visible via `GET /v1/networks`, one confirmed via `GET /v1/networks/{name}`.
2. Validation: duplicate name → `409`; misaligned subnet, overlapping subnet, and out-of-range prefix length → `400` each.
3. Deleting an unused network → `204`, its bridge actually gone (`if_nametoindex`).
4. A container attached to a network blocks that network's deletion (`409`); removing the container unblocks it (`204`).
5. **Restart-survival proof, the actual point of the persistence file:** a network is created, the daemon is `SIGTERM`'d and a fresh instance started, and `GET /v1/networks/{name}` still reports it — plus its bridge is confirmed still present at the kernel level — without a second create call.
6. Zero warnings; all 8 prior suites re-run and still pass, repeated across multiple full back-to-back runs (per the ADR-0008/ADR-0009 stress-testing discipline), confirming no leftover interfaces or persisted-state residue between runs.

`test/test_daemon_net.c` and `test/test_cli.c`'s existing networking scenarios were updated to create their own network via this new API first (there is no more free-standing "default" network to assume), and `kanxeoctl` gained a matching `network create`/`ls`/`rm` subcommand family plus a Networks section on the web dashboard (table + create form + remove button, same pattern as the containers section; `node --check` clean, every DOM ID cross-referenced — same Phase 5/ADR-0010 scope boundary, real-browser rendering not automated).

**A real bug found and fixed during this part's own verification, not just a test gap:** `network.c`'s `save_state()` wrote the persisted file correctly but then compared the byte count written against `w.len` *after* already calling `jw_free(&w)` — which resets `len` to `0` — so the post-write length check always failed, `network_create()` always rolled back (deleting the bridge it had just created) and returned a `500` on what was actually a fully successful save. Fixed by capturing the length in a local variable before freeing the writer. Caught immediately by `test_networks.c`'s very first assertion, not left to surface later — exactly the value of writing the test before declaring a part done.

**Part 2 design.** `struct container_spec` (`include/container.h`) changes from a single `struct network_spec net` to `struct network_spec nets[CONTAINER_MAX_NETWORKS]` (`CONTAINER_MAX_NETWORKS` is `4` — a v1 cap, comfortably more than the 2 a router needs, consistent with this project's existing fixed-array style) plus `net_count`; `net_count == 0` is exactly today's isolated-netns behavior, unchanged. `container_net_host_setup()`/`container_net_child_configure()` (`src/container_net.c`) loop over the array with one `rtnl_open()` for the whole loop rather than per-attachment: veth names become `vh<pid>-<idx>`/`vc<pid>-<idx>` (one pair per attachment, not per container), and the child renames each to `eth<idx>` instead of a hardcoded `"eth0"`. The existing pipe-based synchronization barrier (Phase 6 part 2) needed no new IPC to support this — just *N* round trips through the same barrier instead of one, in the same order on both sides. Only `nets[0]` — the "primary" attachment — gets the default route; every other attachment already has its own subnet's connected route, installed automatically by the kernel as a side effect of the address assignment itself, so no extra syscall was needed to support multi-homing at the routing level.

`daemon/include/registry.h`'s single `ip_be`/`network` fields on `registry_entry` become `struct registry_network_attachment nets[CONTAINER_MAX_NETWORKS]` + `net_count` (a new small struct: name + `ip_be`), copied atomically into the slot by `registry_create()` just like the single fields were before. `registry_network_in_use()` and `registry_alloc_ip()`'s internal scans were generalized to walk each entry's `nets[]` array instead of reading one field — `registry_alloc_ip()`'s own signature and topology-agnostic contract are otherwise unchanged. `registry_write_json_one()` emits a `"networks"` array (`[{"name", "ip"}, ...]`) in place of the old singular `"network"`/`"ip"` fields — the second API-shape evolution networking has gone through in two phases, each one lifting a stated v1 limitation from the phase before it.

`daemon/src/main.c`'s `handle_create()` parses a `"networks"` array (1–4 entries, each validated via the existing `network_find()`) instead of a singular `"network"` string; IP allocation loops once per requested entry with no rollback needed if a later one in the list fails, since allocation was already a pure scan over `in_use` registry entries with nothing reserved out-of-band (the same invariant Phase 6 part 3 established). `kanxeoctl`'s `--network=NAME` flag became **repeatable** (same flag, appends to a request array) rather than a new flag, and the web dashboard's Network field accepts a comma-separated list, split client-side — kept the no-framework/no-build-step dashboard (ADR-0010) simple rather than building dynamic multi-input UI.

Verified end to end:

1. `test/test_container_net.c` (Phase 6 part 2's raw `container_create()` test) gained a new scenario: one container attached to **two** bridges at once, real TCP connectivity to both of its independently-addressed interfaces from the host — not just that `container_create()` didn't error out.
2. `test/net_child.c` (the exec target used across these tests) gained an optional argv count of connections to accept (default `1`, every existing single-network caller unchanged) so the same binary could prove connectivity to a multi-homed container from more than one of its networks without a second, near-duplicate exec target.
3. `test/test_daemon_net.c` gained a scenario: two networks created via `/v1/networks`, one container created with `"networks":[...]` naming both, its response's `networks` array showing two distinct real IPs, real connectivity to both.
4. `test/test_cli.c` gained a matching scenario driving the real `kanxeoctl` binary with two `--network=` flags.
5. Zero warnings; all 9 suites re-run repeatedly across multiple full back-to-back runs, confirming no leftover interfaces or persisted-state residue between runs.

**Part 3 design.** `struct container_spec` gains `int ip_forward` and `struct route_spec routes[CONTAINER_MAX_ROUTES]` (`CONTAINER_MAX_ROUTES` is `8`) + `route_count`. `netplane/`'s route primitive was generalized rather than duplicated: the existing `rtnl_route_add_default_ipv4()` (dst prefix 0, no `RTA_DST`) becomes a one-line wrapper around a new `rtnl_route_add_ipv4(fd, dest_be, dest_prefix_len, gateway_be)`, so there's still exactly one piece of code that builds an `RTM_NEWROUTE` message. Two new, independent functions in `src/container_net.c` run in the child after the existing interface-setup step, needing no pipe synchronization of their own since both only touch the child's *own* already-established netns: `container_net_install_routes()` (one `rtnl_open()` session, one `rtnl_route_add_ipv4()` call per entry) and `container_net_enable_ip_forward()` (a direct `write()` to `/proc/sys/net/ipv4/ip_forward` — a per-netns sysctl, so this only ever affects the one container, never the host or a sibling). Both failures follow the exact same `perror()` + `_exit(126)` contract every other post-barrier child-side setup step already uses (`sethostname()`, `mountns_pivot()`, ...) — no new failure-handling design was needed, since by this point the parent's side of the network barrier has already succeeded and a child-side failure here surfaces exactly like any other existing one, through the completely unchanged reap path.

`POST /v1/containers` gained `ip_forward` (boolean) and `routes` (array of `{dest, prefix_len, via}`, 0–8 entries, all required per entry) — format-validated only (well-formed IPv4, prefix in `[0,32]`); whether `via` is actually reachable is the caller's responsibility, consistent with this project's existing stance on API-supplied addresses. Deliberately **not** stored or echoed back in `GET`/list responses (only `ip_forward` is, since it's a cheap single bool worth showing) — routes are set once at creation, the operator already knows what they asked for, and modifying them on an already-running container would need a new "enter another netns from outside" primitive this project doesn't have. `kanxeoctl run` gained `--ip-forward` and a repeatable `--route=DEST/PREFIX:VIA`; the web dashboard gained a matching checkbox and comma-separated routes field.

Verified end to end with a real 3-container router topology, not just that the syscalls to configure it didn't error — this is the actual payoff of the whole phase:

- **R**: attached to two networks, `ip_forward` on.
- **H**: attached only to the first network, with a static route to the second network's subnet via R's IP on the first network.
- **T**: attached only to the second network, with a static route back to the first network's subnet via R's IP on the second network — needed for T's *reply* to route back through R, the real asymmetric-routing consideration any router setup runs into, and exactly why this is a meaningful test rather than a one-way check.
- H connects to T and gets a real one-byte echo back, crossing entirely through R's kernel routing table.

This needed a new small exec target, `test/net_connect.c` — every other connectivity check in this project connects *from the host*, but that would prove nothing about forwarding through a third container: the host isn't a router in these tests, so a host-originated connection never touches R's routing table at all. `net_connect` runs *inside* H, making the connection with H's own kernel routing table (including the static route it was given) — the thing actually under test. It passed on the first real run against `test/test_container_net.c`'s raw `container_create()` version of this topology; `test/test_daemon_net.c` gained the same topology driven entirely over real HTTP (with a bug caught immediately: the two containers' `via` gateways were swapped in the first draft — `T`'s route must go via R's IP on *T's own* subnet, not R's IP on the far one, since a gateway has to be directly reachable on one of the container's own connected subnets — fixed and re-verified before moving on). `test/test_cli.c` gained a scenario confirming `--ip-forward`/`--route=` are accepted and plumbed through by the real `kanxeoctl` binary (the full forwarding proof already lives at the daemon level, so this doesn't repeat it).

Zero warnings; all 9 suites re-run repeatedly across multiple full back-to-back runs, confirming no leftover interfaces or persisted-state residue between runs. No new ADR: the route-primitive generalization and the "set-once-at-creation" scope boundary are consistent extensions of ADR-0011's existing rtnetlink-control-plane decision, not a new durable architectural stance in their own right.

**Phase 7 is now complete.** A container can attach to multiple real, dynamically-managed networks, forward packets between them, and have other containers route through it via static configuration — the full platform substrate the user asked for. Dynamic routing protocols (BIRD, FRR, ...) are, as scoped at the very start of this phase, just a normal containerized workload on top of this substrate — no further platform work required for that.

## Phase 8 — DNS service (done)

Confirmed with the user before designing any of this, the same way Phase 7's routing scope was: DNS resolution is **not** hand-rolled. ADR-0007's "no external libraries" rule governs this project's own platform components (the daemon, the CLI, the runtime) — it never applied to workloads a container runs, which is exactly why BIRD was fine as a routing workload in Phase 7 without anyone hand-rolling a routing protocol. A real DNS server — **dnsmasq**, chosen for being the lighter of the two options discussed (PowerDNS was the other) — runs as a normal containerized workload; the daemon's own job is owning DNS **records** as a REST resource (name → IP), exactly like `/v1/networks`, and getting the current record set into that container.

**Part 1 design.** New `daemon/include/dns.h` + `daemon/src/dns.c` (mirrors `network.c`'s shape): a fixed `struct dns_record` table (`DNS_MAX_RECORDS` 256, `DNS_NAME_MAX` 254 per RFC 1035), `dns_record_create()`/`_delete()`/`_find()`, persisted to `/var/lib/kanxeo/dns_records.json` the same way networks are (ADR-0012). The atomic-rewrite-plus-reload pattern itself was pulled out of `network.c` into a new shared `daemon/include/persist.h` + `daemon/src/persist.c` (`persist_atomic_write()`, `persist_read_file()`, `persist_mkdir_p()`) rather than duplicated a second time — `network.c` was refactored to call it too, re-verified against `test_networks.c`'s existing restart-survival scenario to confirm no regression.

A second, independent piece in the same file: DNS **server bindings** (`POST/GET/DELETE /v1/dns/servers`) — registering a specific running container as a target to keep in sync. Deliberately in-memory only, unlike records: a binding references a container's pid for signaling, and containers themselves don't survive a daemon restart either (`PR_SET_PDEATHSIG`, Phase 3), so persisting a binding would just mean persisting a reference to something already gone.

**The approved design changed mid-implementation, on real evidence, not preference.** The original plan (agreed with the user before any code was written) was for the daemon to write dnsmasq's hosts file directly into the target container's upperdir — a path the daemon already owns and creates. Verified empirically before building on it (this project's standing discipline since ADR-0008/ADR-0009): a live test showed writes made directly into a running container's upperdir from the host are **not** visible in that container's mounted view, even after correctly pre-creating the parent directory — the kernel documents this as unsupported/undefined for an already-mounted overlay. The user was told, and approved building a `setns(CLONE_NEWMNT)`-based helper to fix it (a capability Phase 7 part 3 had already flagged as needed for live route updates, just for the network namespace instead). Before implementing that, a simpler alternative was tried and confirmed to work just as well: `/proc/<pid>/root/<path>` — a magic symlink the kernel already resolves through the target process's own mount namespace and root — needs no `setns()`, no forked helper, no new namespace-entry syscalls at all. Brought back to the user again, who chose it over building the heavier primitive. See ADR-0013 for the full account and why this is now the standing pattern for any future "reach into a running container's filesystem" need.

Verified end to end, with real protocol resolution as the actual payoff, not a config-file check:

1. Records CRUD + hostname/IP validation (a different charset from network/container names — hostnames allow dots) + duplicate/not-found handling.
2. **A real dnsmasq container, staged the same way every other exec target in this project is** (`test_image_fixture_build()`, extended with a new `test_image_fixture_add_lib()` for the ~20 additional shared libraries a real Debian-packaged dnsmasq needs beyond the usual ld.so+libc pair) — registered via `POST /v1/dns/servers`, then queried with the host's own real `dig` and confirmed to actually resolve a record created through the API.
3. **A live update, the actual point of the `/proc/<pid>/root/` + `SIGHUP` mechanism**: a second record `POST`ed while dnsmasq keeps running, `dig`ged again, confirmed to resolve too — not just the initial snapshot at registration.
4. Deleting the container cleans up its DNS server binding (no dangling reference).
5. `kanxeoctl dns record create/ls/rm` and `dns server register/ls/unregister`, mirroring the `network` subcommand family; the web dashboard gained matching DNS Records and DNS Servers sections (and, in passing, a latent styling gap from Phase 7 part 1 was fixed — the Networks form was never actually getting its intended CSS, since the rules were scoped to `#run-form`'s ID specifically; generalized to `.panel form` so every current and future panel's form is styled consistently, not just `run-form`).

**Real, non-obvious bugs found and fixed during this part's own verification, not left to surface later:**
- A minimal container image has no `/dev` at all, so dnsmasq's attempt to seed its RNG from `/dev/urandom` failed outright. Fixed by creating real character-special device nodes (`mknod`, major/minor `1,9` and `1,3` for `/dev/urandom`/`/dev/null`) in the test image — device access isn't gated by the mount namespace, only by the node's major:minor and (absent here) any device-cgroup restriction this project never applies, so a plain device node works without needing a devtmpfs mount this project doesn't have yet.
- dnsmasq's `-u root`/default group still perform a real NSS lookup (`getpwnam`/`getgrnam`) even to resolve the account it's already running as, which fails with no `/etc/passwd`/`/etc/group` at all. Fixed with a minimal two-line `/etc/passwd`+`/etc/group` in the test image, and an explicit `-g root` alongside `-u root`.
- A real use-after-free in `handle_dns_server_create()`: `json_free(root)` was called before reading `container_name`/`hosts_path` (pointers into the freed tree) to build the success response, producing garbled output. Caught immediately via manual smoke-testing before writing the automated test, fixed by building the response first and freeing afterward (the exact ordering `handle_create()`'s own existing comment already explains for a different field).

Zero warnings; all 10 suites re-run repeatedly across multiple full back-to-back runs, confirming no leftover interfaces or persisted-state residue between runs.

**Part 1's stated deferral, picked back up in part 2:** automatic container-name → IP registration. Requested by the user immediately after part 1 shipped, explicitly to remove the need for a second `POST /v1/dns/records` call for the common case of "give this container a resolvable name."

**Part 2 design.** `struct dns_record` (`daemon/include/dns.h`) gained `char owner_container[DNS_OWNER_NAME_MAX]` (`DNS_OWNER_NAME_MAX` 64, matching `REGISTRY_NAME_MAX` by value only — no new header dependency on `registry.h`, consistent with `DNS_SERVER_NAME_MAX`'s existing precedent). Empty string means "created directly via `POST /v1/dns/records`," unowned, exactly the part-1 behavior; non-empty means "this record belongs to that container's lifecycle." `dns_record_create()` gained an `owner_container` parameter (the existing manual-creation call site passes `NULL`); a new `dns_record_forget_owner(container_name)` looks up the record named exactly after the container and deletes it only if its `owner_container` matches — a safe no-op for every container that never had one, so it's called unconditionally from the container-delete handler, mirroring `dns_server_forget()`'s existing shape. `dns_write_json_one()` gained an `"owner"` field (`null` or the owning container's name) so an operator can tell which records are container-managed at a glance.

`POST /v1/containers` gained an optional `"dns_register"` boolean. `true` with no `networks` is a `400` (nothing to register without an IP) — validated alongside the existing networks/routes checks. On success, the daemon best-effort registers a record named after the container, pointing at its primary (first) network's IP — the same "first entry is primary" convention Phase 7 part 2 already established for the default route. Since `dns_record_create()` already calls `dns_server_sync_all()` internally, an auto-registered record reaches any already-registered dnsmasq container the exact same way a manual one does, with no new sync path.

**Stated v1 boundary, not a silent gap:** registration is attempted once, at creation time, and never force-replaces a colliding record — if a record with that name already exists (e.g. a stale one persisted from a same-named container created before a daemon restart; DNS records survive a restart, containers don't, ADR-0012), registration is skipped and logged to the daemon's own stderr, and the container is still created successfully. Silently overwriting what could be an operator's own manually-created record is worse than a container occasionally missing its auto-record until cleaned up by hand.

`kanxeoctl run` gained `--dns-register`; `dns record ls`'s output gained an owner column (`-` when unowned). The web dashboard's run form gained a "Register DNS name" checkbox and the DNS Records table gained an Owner column.

Verified end to end in `test/test_dns.c`, reusing the dnsmasq container and network already set up earlier in that same test (no new container image needed):

1. `dns_register: true` with no `networks` → `400`.
2. A container created with `dns_register: true` gets a record matching its own name and primary IP; `GET /v1/dns/records/<name>` confirms both the IP and `"owner"` == the container's own name.
3. `dig` against the already-running, already-registered dnsmasq container resolves the new name — proving the existing `dns_server_sync_all()` path picks up an auto-registered record exactly like a manual one.
4. **The ownership check specifically, not just "delete by name":** a record is created manually (unowned) under a name, then a container with that *exact same name* is created with `dns_register: true` — registration is silently skipped (`DNS_ERR_DUPLICATE`, logged) since the name collides, and container creation still succeeds. Deleting that container is then confirmed to leave the manually-created record untouched (`GET` still `200`, same IP) — proving `dns_record_forget_owner()` checks `owner_container`, not just whether a same-named record exists. A separate container's own auto-registered record is confirmed to actually disappear (`GET` → `404`) when *that* container is deleted, showing the positive case works too.

Zero warnings; all 11 suites (the 10 from part 1's count plus `test_dns` itself now counted individually — same physical set) re-run across 3 consecutive full back-to-back runs with no failures attributable to this change. `test_harness` was seen to fail once during this cycle with a `cgroup.procs has 0 entries` timing error and passed cleanly on every other run before and after — unrelated to any file this phase touched (`daemon/src/dns.c`, `daemon/src/main.c`, `cli/src/main.c`, `web/`), consistent with a pre-existing cgroup-population race under host load rather than a regression introduced here.

**Not designed or built yet, per Zen:** any record type beyond A-record-equivalent name→IPv4, live modification of DNS server bindings' `hosts_path` (re-register instead), and any retry/force-replace path for a collided auto-registration (stated v1 boundary above).

## Phase 9 — PKI / certificate management (done)

MISSION.md groups "DNS, PKI/certificate management" together as REST-controlled shared infrastructure, and CLAUDE.md's API-First Mandate names "PKI primitive" alongside host/network/DNS as something only the daemon has direct access to. Confirmed with the user before any code was written (the same question shape as DNS's "why hand-roll?"): actual cryptography (CA keypair generation, CSR signing) is done by the daemon shelling out to the system's real, unmodified `openssl` binary as a short-lived subprocess — never linked into the daemon (ADR-0007's "no third-party dependency footprint anywhere in the daemon" stays intact, since exec'ing isn't linking) and never a separate persistent CA container either (PKI operations are request/response, not continuously-served the way DNS resolution needs dnsmasq to be). The exact `openssl` CLI flow (`genpkey` → `req -x509` for the CA; `genpkey` → `req -new -addext subjectAltName=...` → `x509 -req -CAcreateserial -copy_extensions copy` per leaf) was verified live in a scratch directory before any daemon code was written, confirming `-CAcreateserial` correctly persists and increments its own serial file across repeated invocations with no collisions — openssl's own serial file is the source of truth for uniqueness, not a counter this project invents.

**Part 1 design**, a pure REST resource family exactly as independent and manual as DNS records were in Phase 8 part 1 (no auto-issuance at container creation yet — deferred to a natural part 2, per Zen, the same shape DNS was phased in): new `daemon/include/pki.h` + `daemon/src/pki.c`. `dns_name_is_valid()` was exported from `dns.h` (previously `static` in `dns.c`) and reused directly for leaf cert names/SANs rather than re-implementing hostname validation a second time — a cert's CN/SANs are conceptually hostnames just like a DNS record's name, and duplicating that label/charset/length logic would be exactly the "parallel implementation" the maxims forbid.

On-disk layout under `/var/lib/kanxeo/pki/`: `ca.key` (chmod 0600, explicit `chmod()` call after generation, never relying on umask), `ca.crt` (0644), `ca.srl` (openssl-managed); `certs/<name>.key` (0600) / `certs/<name>.crt` (0644) per leaf, CSR files deleted after a successful sign. A `pki_certs.json` metadata index (name/serial/not_after/sans) persisted via the existing `persist_atomic_write()`/`persist_read_file()` from `daemon/src/persist.c` — Phase 8 part 1's shared persistence module getting its intended second consumer. The index is a fast-listing cache, not the source of truth for correctness; the key/cert files on disk are authoritative, and `GET /v1/pki/certs/{name}` reads `cert_pem` fresh off disk rather than caching PEM content in the index.

**Two asymmetric security properties, both deliberate, both load-bearing:**
- **The CA private key is never returned over the API, in any endpoint, ever** — `GET /v1/pki/ca` reads `ca.crt` fresh off disk via `openssl x509 -noout ...` on every call (One Source of Truth, no in-memory cache to keep in sync — this is a low-frequency management call so the extra subprocess cost is a non-issue) and never touches `ca.key`.
- **A leaf certificate's private key is returned exactly once** — in the `POST /v1/pki/certs` response, at the moment of issuance. Neither `GET /v1/pki/certs` (list) nor `GET /v1/pki/certs/{name}` (single) ever includes one again, matching the "credential shown once" pattern most real ACME-shaped systems use. This is why `pki_cert_create()`/`pki_ca_get()`/`pki_cert_get_one()` write straight into a `json_writer` instead of returning a `struct dns_record *`-shaped pointer the way `dns_record_create()` does — keeping the key out of any long-lived in-memory struct a list/get handler might later accidentally also serialize is a real security property, not just a style choice.

A CA's `common_name` is a free-form display label ("Kanxeo Root CA"), not a hostname, so it isn't run through `dns_name_is_valid()` — but it *is* embedded verbatim into an `openssl -subj "/CN=<common_name>"` argument, so an unvalidated `/` would let a caller inject additional, unintended DN fields (e.g. `"Foo/O=EvilOrg"` becomes `CN=Foo, O=EvilOrg`). A small `common_name_is_valid()` in `pki.c` rejects `/` and control characters — a real, spotted-during-design correctness requirement of accepting free-form user input into a DN string, not scope creep.

`respond_pki_error()` maps `PKI_ERR_NOT_BOOTSTRAPPED` to `400` by default (correct for `POST /v1/pki/certs`, a genuine "you can't do this yet" precondition on an action) — but `handle_pki_ca_get()` special-cases that same error to `404` instead, matching every other single-resource `GET` in this API (`/v1/dns/records/{name}`, `/v1/networks/{name}`) where a missing resource is `404`, not `400`. Caught and fixed before writing the automated test, once the test's own verification section made the inconsistency obvious.

`kanxeoctl pki ca bootstrap/show` and `pki cert create/ls/rm` mirror the `dns record`/`dns server` subcommand families. Multi-line PEM output (`fmt_pki_cert_issued()`, `fmt_pki_ca()`) is a deliberately distinct formatter from the single-row `%-Ns` table shape every other `ls`/list view uses — a certificate's PEM content can't sensibly fit a table row. The web dashboard gained a "PKI: Root CA" panel (bootstrap status/button) and a "PKI: Certificates" panel (issuance form + table + a one-time "copy your key now" reveal built with `textContent`, never `innerHTML`, since PEM content is text, not markup).

Verified end to end in `test/test_pki.c`, with real cryptographic verification as the actual payoff, not a string check:

1. `GET /v1/pki/ca` before bootstrap → `404`; `POST /v1/pki/certs` before bootstrap → `400`.
2. `POST /v1/pki/ca` → `201` with subject/serial/dates populated; the returned `cert_pem` is round-tripped through the test's own `openssl x509 -noout -subject` call to confirm it's real, parseable PEM, not just non-empty text. A second bootstrap → `409`.
3. **The actual payoff**: a leaf cert issued with SANs is verified with `openssl verify -CAfile ca.crt leaf.crt` from the test itself — proving it genuinely chains to the root, not just that the API returned something cert-shaped — plus a real `openssl x509 -noout -ext subjectAltName` round-trip on the SAN list.
4. Duplicate name → `409`; invalid name → `400`.

Requested by the user immediately after part 1 shipped, the same "keep rockin'" continuation DNS part 2 got — a cert sitting only in `/var/lib/kanxeo/pki/certs/` on the host is useless to a workload that needs to actually `read()` it.

**Part 2 design.** `struct pki_cert_record` (private to `pki.c`) gained `owner_container[DNS_NAME_MAX]`, exactly mirroring `dns_record`'s field from Phase 8 part 2; `pki_cert_create()` gained an `owner_container` parameter (the manual call site passes `NULL`); `write_cert_json()` gained an `"owner"` field. Unlike `dns_register`, `pki_issue` does **not** require `networks` — the cert's CN/SAN is the container's own name, not its IP, and delivery via `/proc/<pid>/root/` works regardless of networking. It **does** require the CA to already be bootstrapped, validated upfront as a `400` — a genuine precondition, the same class `dns_register`'s networks check already is — while a *name collision*, only discoverable at issuance time, stays best-effort/skip-and-log, matching `dns_register`'s exact asymmetry between upfront-checkable preconditions and issuance-time surprises. `kanxeoctl run --pki-issue [--pki-cert-dir=PATH] [--pki-days=N]`; `fmt_pki_cert_line()` gained an owner column. ## Phase 10 — Package manager (done)

A source-based package manager: recipes are shell scripts (a proven format — Gentoo ebuilds/Arch PKGBUILDs/CRUX Pkgfiles all work this way), builds happen inside this project's own container runtime, and every installed package lands in one canonical image that every container built on `"image": "base"` shares — the thing that makes "the same 100% for host and containers" true, confirmed as the goal with the user up front. MISSION.md's "package wrappers... written in C, compiled exclusively with TCC" mandate is about this project's own tooling, not about forcing arbitrary upstream C projects through TCC — confirmed directly with the user, the same "our code hand-rolled, real software as workloads" split ADR-0007/DNS/PKI already established: each package's own build step uses whatever toolchain it actually needs.

**Two more architecture questions, confirmed with the user, then verified against real environment constraints before any code was written:**
- **Builds run inside this project's own container runtime** (reuse, not a second isolation mechanism) — but the build container gets **no network access**. This project's networking plane has no outbound NAT/masquerade (Phase 6/7 only ever built inter-container routing on private bridges; adding NAT would mean netfilter/nftables, a whole kernel subsystem never touched here, and would contradict the "no `ip`/iproute2, no OVS" custom-dataplane philosophy if shelled out to `nft`). Fetching happens on the **host** instead (a `curl` subprocess — same "real software, not hand-rolled" precedent as `openssl`/`dig`), before the container ever starts — a stronger isolation boundary for untrusted build scripts, and no NAT needed at all.
- **Installs are asynchronous.** The daemon's reactor is single-threaded, non-blocking, `epoll`+`pidfd`-driven (ADR-0009); a network fetch or a real compile can take anywhere from seconds to minutes, and blocking a request handler for that long would freeze every other API request — exactly the class of bug ADR-0009 already treats as a must-fix, not a v1 boundary. `POST /v1/pkg/install` returns immediately (`202`); both the fetch subprocess and the build container are tracked via `pidfd`+`epoll`, the same non-blocking shape containers already get.

**A real build toolchain sandbox turned out to be a substantial sub-problem on its own, verified empirically (`chroot` compile+link+`make install DESTDIR=`) before committing to a design**, the same discipline this project used for the DNS/PKI upperdir and hand-roll questions: gcc alone needs `cc1`, `as`, `ld`, `crt*.o` startup objects, its own spec/header files, and (this being a merged-`/usr` Debian host) `/bin`/`/lib`/`/lib64`/`/sbin` are themselves symlinks into `/usr/...`. A hand-curated file list (the `ldd`-closure-per-binary approach DNS/PKI's test fixtures used for `dnsmasq`) doesn't scale to "gcc plus everything `./configure`/`make` typically needs" — so `POST /v1/pkg/bootstrap` instead copies whole `/usr/{include,lib,lib64,bin,libexec}` directories from the daemon's own host with the real `cp -a` (correct symlink/permission handling a hand-rolled copier would get wrong) plus recreates the compatibility symlinks, into a dedicated `pkgbuild` image. Idempotent; not automatic at startup (an explicit, `PKI`-CA-bootstrap-shaped one-time action instead, since startup should stay fast). Measured at ~1.5s on this host — well within acceptable synchronous-request bounds for a one-time administrative action, unlike the per-package fetch/build path.

**Part 1 design.** New `daemon/include/pkg.h` + `daemon/src/pkg.c`, mirroring `dns.c`/`pki.c`'s shape. The daemon **never sources or executes a recipe on the host** — metadata (`pkg_name=`/`pkg_version=`/`pkg_source=`/`pkg_sha256=`/`pkg_depends=`) is read with a strict, non-executing line scanner; a recipe's real shell code (`pkg_build()`/`pkg_install()`) only ever runs inside the isolated, network-less build container, the only place executing a recipe's actual logic is safe. `POST /v1/pkg/install` forks+execve's `curl` on the host (tracked via a new `CONN_PKG_FETCH` reactor kind — `sys_pidfd_open()`, a raw syscall added to `linux_compat.h` alongside `sys_pidfd_send_signal()`/`sys_clone3()`/`sys_pivot_root()` per ADR-0002, since a plain `fork()`'d subprocess needs the pidfd containers already get for free from `CLONE_PIDFD`). Once fetched, the download is verified against `pkg_sha256` via the real `sha256sum` (never hand-rolled crypto, same posture PKI's CA/cert signing already established), extracted, and built inside a single, fixed, reserved container name (`__pkgbuild` — v1 serializes installs, one at a time) on the `pkgbuild` image, with **no networks attached**. The build container shows up in the normal `GET /v1/containers` listing too, deliberately — one source of truth for "what's running," not a second hidden tracking path.

`handle_container_event()` (`daemon/src/main.c`) gained an unconditional call to `pkg_build_completed()`, mirroring exactly how `dns_record_forget_owner()`/`pki_cert_forget_owner()` are already called unconditionally on every container delete — `pkg.c` decides relevance (no-op unless the exited container is `__pkgbuild`), so the hook itself stays trivial. On a successful build, the daemon merges `<build container upperdir>/build/pkg-dest/` into the base image via **plain host file I/O** — the container has already exited by this point, so there is no running mount namespace left to reach into via `/proc/<pid>/root/` the way DNS/PKI's live-container writes needed (ADR-0013); reading a stopped container's own upperdir directly is simpler and needs no magic symlink. Every copied file's path is recorded into the package's manifest, enabling exact removal later. Symlinks in a package's own `DESTDIR` output are skipped — a documented, narrow v1 boundary (regular files and directories cover this part's own test fixture and typical `make install DESTDIR=` output; a package that specifically installs symlinks needs a later part).

Verified end to end in `test/test_pkg.c`, kept hermetic (no real internet dependency — a `file://` URL against a tiny synthetic C fixture the test stages itself, so the real `curl` subprocess code path is genuinely exercised, not mocked, while the suite stays offline-safe for repeated runs):

1. `POST /v1/pkg/bootstrap` → `204`; the real toolchain proof is the full install pipeline itself (scenario 3), not a separate isolated check.
2. Install with an unknown recipe name → `400`.
3. **The actual payoff**: a real install (`202`, `state: "fetching"`) is polled via `GET /v1/pkg/{name}` until it leaves `fetching`/`building`; the resulting `installed` state is confirmed by actually executing the built binary from the base image and checking its real stdout — proof the whole fetch → verify → build → install → merge pipeline produced genuinely working content, not just files with the right names.
4. **v1's serialization boundary, checked as a real overlapping-in-time request, not a code-read assumption**: a second install for a *different* package, issued immediately (no sleep) right after the first's `202` — reliably still "fetching" at that exact point, since `fork()` for the curl subprocess has barely started — gets `409`.
5. Checksum mismatch (a recipe with a deliberately wrong `pkg_sha256`) → ends in `failed`, confirmed never installed.
6. `DELETE /v1/pkg/{name}` → `204`; the manifested file is confirmed actually gone from the base image via `stat()`, not just the registry entry; repeat `GET` → `404`.

**A real bug, caught and fixed in the test's own code before trusting any result**: `poll_pkg_state()`'s first draft called `kx_response_free(&r)` (which frees `r.json`) before `strcmp()`-ing a `state` pointer that pointed *into* that same freed tree — a genuine use-after-free, not a daemon bug, that manifested as the test hanging/misreporting state unpredictably. Fixed by comparing against `out_state` (a stable, already-copied buffer) instead of the dangling pointer, after the free — caught by the test's own first real run doing something unexpected, the same "verify with a real run, don't trust the first pass" discipline this project has applied everywhere else.

Zero warnings; all 13 suites (12 from Phase 9's count plus `test_pkg`) re-run across 3 consecutive full back-to-back runs with no failures.

**Part 1's stated deferral, picked back up in part 2:** automatic dependency installation and a package upgrade flow — the "keep things up to date" half of the user's original ask, deliberately deferred until the core fetch/build/install pipeline was proven. Confirmed with the user before writing any code: an upgrade must be **explicit** (`{"upgrade": true}`), not automatic on a bare re-`POST` — a plain re-install of an already-installed package stays a `409` even after its recipe's version changes, the same "no silent overwrites, state intent explicitly" posture DNS's/PKI's collision-skip logic already established.

**Part 2 design.** `pkg_install_start()` gained an `upgrade` parameter and, before forking anything, resolves the full install order via a recursive DFS over `pkg_depends` (post-order — a package's own dependencies queue before the package itself), entirely from local recipe files already on disk (no async need for resolution itself, only the fetch/build steps stay async). Already-installed dependencies are skipped as satisfied; a dependency reappearing on its own current resolution path is a circular dependency (`400`, nothing forked); a `pkg_depends` name with no matching recipe is the same `400` class as an unparseable recipe. The already-installed short-circuit is unchanged in shape, just gated on `upgrade`: still an immediate `409` unless `upgrade` is true **and** the recipe's current version genuinely differs from what's installed.

`pkg_build_completed()`'s contract grew to support chaining: on a successful build, if more packages remain queued, it starts the next one's fetch itself and returns `1` with the new pid/pidfd, so `main.c` (which owns `epoll`) can `register_pkg_fetch_pidfd()` exactly like a fresh top-level install already does — `handle_container_event()`'s existing unconditional `pkg_build_completed()` call just started reacting to a return value it didn't have before, no new call site. **The `202` response to `POST /v1/pkg/install` describes whichever package actually started fetching first** (documented explicitly, not left implicit) — a dependency, not necessarily the name the caller asked for, if that name needed something installed first; `pkg_install_start()` gained an `out_started_name` parameter specifically so the request handler can build an honest response instead of assuming it's always the requested name.

**Upgrade completion is deliberately conservative with a working install**: for a genuine in-place upgrade, `start_fetch_for()` does *not* reset the existing entry's `version`/`files` — they're left exactly as they are (still correctly describing the OLD, still-physically-present install) until the new build has actually succeeded, at which point the OLD manifest's files are unlinked first and *then* the new ones are merged and recorded. A fetch or build failure partway through an upgrade reverts the entry back to `PKG_STATE_INSTALLED` (the old version, which was never actually touched) rather than leaving it `FAILED` with an empty file list while the old binary is still genuinely sitting in the base image, untracked and unremovable via the API — a real correctness bug caught and fixed during this part's own manual verification, before it reached the automated test. `GET`'s responses gained `"available_version"` (`null`, or the recipe's current version) computed by re-reading the recipe fresh on every call — One Source of Truth, no cached comparison to keep in sync — the concrete, live answer to "is this out of date."

**A second real bug, also caught during manual verification before the automated test was written**: the reserved `__pkgbuild` container path is reused across every build (v1 serializes to one at a time), and nothing was clearing its upperdir between builds — a chained dependency's `pkg-dest` could silently inherit leftover files from whatever built there previously (a prior chain link, or even a completely unrelated earlier install), producing a manifest that claimed ownership of files it never actually installed. This was a latent gap in part 1 too, just never triggered by a test that only ever built one package per daemon lifetime. Fixed with `reset_build_container_dir()` (a real `rm -rf` subprocess on the whole container directory, not a hand-rolled recursive delete) called before every build's prep, guaranteeing each one starts genuinely clean regardless of what ran there before.

Verified end to end in `test/test_pkg.c`, reusing the bootstrap and fixture-staging helpers part 1 already established:

1. A `leaf` recipe (no deps) and a `top` recipe with `pkg_depends="leaf"`: a single `POST /v1/pkg/install {"name": "top"}` results in *both* reaching `installed` — the real proof dependency chaining works, not just that the top package alone succeeds.
2. A circular pair (`circ1` ↔ `circ2`) → `400` for installing either; confirmed neither was ever registered (`GET` → `404`), not just that the install call failed.
3. A recipe depending on a name with no `.recipe` file → `400`.
4. Upgrade: `leaf` installed at `1.0`; its recipe rewritten to `2.0` (a genuinely new fixture tarball + checksum, not just a version-string bump) — `GET` shows `available_version: "2.0"` *before* any upgrade call, proving the visibility field is live, not just correct after the fact; a plain re-`POST` → `409`; `{"upgrade": true}` → `202`, polls to `installed` at `2.0`, and the installed binary is actually executed and its real stdout checked against the *new* fixture's expected output — proof the rebuild used the new source, not a stale cache re-labeled with a new version string.

## Phase 11 — Bare-metal boot: kernel, bootloader, A/B root, installer

Every prior phase built and verified `kanxeod` as a guest process running on top of an already-booted Linux system — this dev environment has, since Phase 1, always been a privileged LXC container on someone else's kernel. Phase 11 is what makes Kanxeo the operating system itself: a kernel we build, a bootloader that starts it, and an installer that puts it on a real disk, with `kanxeod` as PID 1.

**Architecture confirmed with the user before any code was written, the same discipline every prior phase used for its own "how does this actually work" questions:**

- **Firmware: UEFI only.** No BIOS/legacy support in v1 — narrows the bootloader choice to something UEFI-native and genuinely thin, and avoids GRUB's hybrid-BIOS+UEFI complexity and its own scripting/config language entirely.
- **Bootloader: `systemd-boot`.** A boot *manager*, not a shell — reads loader entries from the EFI System Partition (ESP) directly, no config language of its own to maintain. Its native Automatic Boot Assessment (a `+LEFT-DONE` suffix convention on the loader entry's filename) is reused as-is for A/B rollback rather than inventing a second boot-counting mechanism — one already-correct, already-tested implementation instead of a bespoke one.
- **Root filesystem: read-only A/B, `squashfs`.** Two identical-role root slots; only one is active at a time. Read-only close the door on the entire class of "a bad write during normal operation corrupts the OS" failure — the actual "in case of corruption" property the user asked for. `squashfs` (compressed, natively read-only, one `CONFIG_SQUASHFS` kernel option, no exotic dependency) makes writing a slot a single atomic whole-image operation: the same code path serves both the installer's initial write and a later update's write to the *inactive* slot, so building the update mechanism costs almost nothing extra once the installer can write an image at all.
- **Root scope: thin, control-plane only.** Root A/B holds exactly the kernel, `kanxeod`, and the handful of real binaries it shells out to (`openssl`, `curl`, `tar`, `sha256sum`, `dnsmasq`, `cp`, `rm`, ...) — never the package manager's canonical base container image or any container's own data. This keeps the two things that actually have independent lifecycles (the OS itself, and installed packages/running containers) on independent storage: a package install never requires an A/B flip, and an OS rollback never reverts installed packages or container state. The alternative (a fatter root carrying the base image too) was explicitly rejected for conflating two lifecycles that don't change together.
- **No initramfs.** The bootloader loads the kernel directly; the kernel mounts the active root slot itself (its storage driver and `squashfs` support built in, not modular) and `exec`s `kanxeod` via `init=`. This is the thinnest possible boot chain and needs nothing built/regenerated on a kernel update beyond the kernel image itself — but it only works because of the next decision:
- **Target hardware: fixed/known, not arbitrary bare metal.** This is not a general-purpose installer meant to boot on any PC — the kernel's defconfig only needs to carry the specific storage and NIC drivers the actual target machine(s) need. This is what makes "no initramfs" safe: a genuinely arbitrary-hardware installer would need dynamic module loading before root is even reachable, which is exactly what an initramfs is for.
- **A/B failover: automatic.** `systemd-boot`'s boot-counter marks a slot "trying" on boot; `kanxeod`, once it reaches a real healthy state (detailed in part 2), renames its own loader entry to mark the boot successful — a plain `rename(2)` on the ESP, not a `bootctl` subprocess call, consistent with this project's hand-rolled-daemon posture (ADR-0007) for something this simple. An unconfirmed boot after the counter's retry budget is exhausted falls back to the other slot with no operator involved.
- **Kernel: built from mainline source**, honoring MISSION.md's literal "the host OS... compiled directly from source," with a minimal defconfig scoped to exactly what the target hardware and this design need (cgroup v2, the namespaces `container.c` already relies on, OverlayFS, `squashfs`, the target's real storage/NIC drivers, rtnetlink/netfilter-free networking — no support for anything this project doesn't use). Built with a real GCC toolchain, not TCC — the same "TCC governs our own code, not unmodified upstream software" precedent Phase 7's routing daemons, Phase 8's `dnsmasq`, Phase 9's `openssl`, and Phase 10's own build-toolchain bootstrap already established. Likely reuses Phase 10's `pkg/bootstrap` GCC-staging approach rather than inventing a second one.
- **Partition layout, 5 GPT partitions on the target disk:**

  | # | Role | Filesystem | Mutability | Contents |
  |---|---|---|---|---|
  | 1 | ESP | FAT32 | writable (bootloader-managed) | `systemd-boot`, kernel image(s), loader entries |
  | 2 | Root A | squashfs | read-only | kernel-paired control plane: `kanxeod` + its direct runtime deps |
  | 3 | Root B | squashfs | read-only | the other root slot, identical role to (2) |
  | 4 | Config | ext4 | writable | `kanxeod`'s own durable state — `networks.json`, `dns_records.json`, `pki/`, the package registry — plus NIC/hostname config from the installer. Exactly today's `/var/lib/kanxeo/` layout, minus container/image data, split onto its own partition so it survives every OS update/rollback untouched |
  | 5 | Containers | ext4 | writable | the package manager's canonical base image, every container's upper/work/merged dirs — all workload data, likewise untouched by OS updates/rollback |

  Root A/B sizing depends on the actual built image size (Part 1's own output); config and containers get generous-but-modest and "rest of disk" respectively. Not pinned further until Part 1 produces a real image to measure.
- **Networking at boot: static IP, set once during install**, applied with the `rtnetlink` primitives `netplane/` already has — no new dependency, no protocol to hand-roll or shell out for. Consistent with a fixed-hardware deployment where the address is planned in advance, not discovered by walking up with DHCP.
- **Installer partitioning: real, interactive `cfdisk`.** The operator creates and sizes partitions themselves and marks each one's role via cfdisk's own GPT partition-type/name menu; the installer then reads the resulting table back (`sfdisk -d` or `/sys/class/block`) and matches roles by type/name — no separate "which number is root A" prompt, less room for operator error than either a fully-scripted non-interactive layout or a manual number-picking step.
- **Disk selection: multi-disk aware.** The installer enumerates available block devices and the operator picks the target before `cfdisk` runs, rather than assuming a single disk is present.
- **PID 1 detection: explicit, not inferred.** `kanxeod` gains a `--init-mode` flag (set via the kernel command line / loader entry) that gates the boot-init responsibilities (mounting `/proc`/`/sys`, bringing up the NIC, reading the config partition, health-signaling the bootloader) — deliberately not a `getpid() == 1` auto-check, so this entire code path can be exercised by an automated test inside a namespace/container the same way `test_harness.c` already tests namespace logic, without needing to actually be a real machine's PID 1 to test it.
- **Update scope: included now, not deferred.** Writing a new image to the *inactive* slot and flipping the active pointer is nearly the same operation as the installer's own initial write — building it now, rather than punting to a "Phase 12," keeps the A/B mechanism genuinely exercised rather than theoretical.

See ADR-0014 for the full reasoning behind the squashfs-A/B-with-native-boot-counting decision specifically — the one call here that's both significant and hard to reverse once real installs exist on real disks.

**Verified, before any of this touched real hardware:** the build/boot-test tooling this phase needs (`qemu-system-x86`, `ovmf`, `systemd-boot-efi`, `squashfs-tools`, `mtools`, plus kernel-build prerequisites `flex`/`bison`/`libelf-dev`) is installed and confirmed working in the dev environment. ## Phase 12 and beyond — the expanded charter

`docs/MISSION.md` was given a genuinely new charter once Phase 11 proved the platform on real hardware: Kanxeo is now explicitly a hardware and workload orchestration platform, not just a container host, with a "desktop"-style web control surface, real device passthrough, non-disruptive rolling delivery for packages as well as the OS, and an eventual multi-host trajectory. Phases are numbered and written up here, in this same format, exactly as each one is actually designed and built — not before.

### Phase 12 part 1 (done): PCI/USB (character/block) device passthrough

The agreed first step of the expanded charter's hardware-passthrough goal: pass a real USB device or a driver-backed PCI device (e.g. an NVMe namespace) directly to a container. Namespace containers (not VMs) need no IOMMU/VFIO handoff — the mechanism `docs/MISSION.md` already committed to is the specific `/dev` node inside the container's own mount namespace, with the cgroup device controller granting access to it.

Two real design forks were confirmed directly with the user before building anything, matching this project's own precedent (ADR-0011) for resolving ambiguous charter wording in writing first:

- **Enforcement:** cgroup v2 has no file-based device controller — `BPF_CGROUP_DEVICE` (an eBPF program attached per-container to the cgroup leaf `cgroup_create()` already opens) is the only kernel mechanism. This is the first eBPF code anywhere in Kanxeo; ADR-0017 documents why it doesn't reopen the networking plane's own "no eBPF" rule (that rule's wording, checked against every occurrence in the repo, is scoped to the packet-forwarding data plane specifically). Hand-assembled in `src/container_dev.c` with no libbpf/clang dependency, matching `netplane/`'s existing hand-rolled-netlink posture. Namespace-only isolation was considered and rejected: this project's containers run as full root with no user namespace and no capability dropping, so `mknod()` of an ungranted device's major:minor would otherwise just work.
- **Discovery:** `daemon/src/device.c` walks `/sys/bus/usb/devices` and `/sys/bus/pci/devices` fresh on every `GET /v1/devices` call (never persisted — real host hardware, not daemon-owned state, the same distinction that already separates networks' ADR-0012 persistence from containers' own restart-non-survival). USB nodes resolve via each device's own `dev` sysfs attribute (confirmed empirically not derivable from `busnum`/`devnum`, which are reassigned on every replug anyway). PCI nodes are driver-specific and not uniform — found via a bounded-depth walk of each PCI device's own sysfs subtree (an NVMe controller owns both its controller node and a separate node per namespace, nested two levels deep; a bridge/root port's own subtree contains a real, further-walkable subdirectory for each downstream device, requiring an explicit "don't re-descend into an independently-enumerable PCI address" guard to avoid duplicate entries — found and fixed via this session's own real hardware, not synthetic test data).

`container_spec` gained `devices[]`/`device_count` (mirroring the existing `nets[]`/`route_spec` pattern exactly); `container_create()` attaches the BPF program before `ns_clone3()` (so the policy covers the child's very first instruction, including its own `mknod()` calls) and `mknod()`s each granted node right after `mountns_pivot()` (the first point the container's `/dev` is genuinely private). `POST /v1/containers` gained a `devices` array of bare ids (the same request-is-references / response-is-full-objects asymmetry `networks` already established); `GET /v1/devices` is read-only (devices aren't daemon-created, unlike networks — no `POST`/`DELETE`). `kanxeoctl device ls` and a repeatable `run --device=ID` flag are pure REST clients, per the API-First Mandate.

Explicitly out of scope for this part: GPU passthrough specifically (same mechanism, a later step); wireless/wired PCI network cards (these present as `netdev`s, not `/dev` nodes — "assigning" one means moving the interface into a container's netns via the *existing* rtnetlink-based network-attachment feature, not this one); disk quotas; live attach/detach on an already-running container (creation-time-only, matching how `networks`/`routes` already work); per-device-access-type granularity (a grant is full read/write/mknod, all-or-nothing); exclusivity (two containers can be granted the same device simultaneously — real hardware sharing at the kernel level, no lock).

Verified with real, not mocked, syscalls: `test/test_devices.c` proves the actual security property through a real `container_create()` — a container with a device granted opens it and `fstat()` confirms the correct major:minor; a second container with a *different* grant is denied `EPERM` on a device it wasn't granted, even though that device is visibly present (baked into the shared base image); a third container requesting no devices at all is byte-for-byte unaffected (No Regressions) — 3 consecutive passes. `test/test_daemon_devices.c` proves the REST/registry/CLI wiring over real HTTP against a running daemon, adapting to whatever real hardware the test host actually has rather than hardcoding a specific device. `image/kernel/qemu-part1.config` gained `CONFIG_BPF_SYSCALL`/`CONFIG_CGROUP_BPF` (confirmed absent before this change) for the shipped kernel; this dev environment's own host kernel already supported `bpf(2)`, so verification needed no kernel rebuild.

A real environment constraint surfaced and documented rather than papered over (ADR-0017's own Consequences): `BPF_CGROUP_DEVICE` checks are hierarchical, and this project's own dev/build environment (a privileged, nested LXC) runs under an ancestor cgroup that only permits a standard device set — `test_devices.c` grants real device numbers (`/dev/null`/`/dev/zero`/`/dev/full`'s own major:minor) rather than synthetic ones for exactly this reason. Real deployment targets have no such ancestor.

### Phase 12 part 2 (done): a real reboot no longer wipes every installed package, network, and image

Found while scoping the next step (installing real software — `bash`, `iproute2`, `bird` — via `pkg install`, which only matters if it survives a reboot): `boot_init()` has mounted a fresh `tmpfs` at `BASE_DIR` (`/var/lib/kanxeo`) on *every* real boot since Phase 11 part 1, and every piece of state this daemon persists lives there — `images/` (including the shared `base` image every `pkg install` build lands its files into), `networks.json`, `dns_records.json`, `pki_certs.json`, `pkg_installed.json`. A full power cycle on a real installed system silently discarded all of it. This was never the intent — the fifth partition `kanxeo-install` already creates and formats for exactly this purpose (`kanxeo-containers`) has been sitting on every installed system's disk, correctly formatted, completely unused, since Phase 11 part 3. See ADR-0018 for the full account, including a stale code comment that had promised this swap since Part 1 without it ever actually happening.

`boot_init()` now mounts the real `kanxeo-containers` partition (`/dev/vda5`, the same fixed-layout convention `ESP_DEVICE`/`CONFIG_DEVICE` already use) at `BASE_DIR`, falling back to `tmpfs` only when that device doesn't exist (Part 1/2's own throwaway test disks). `main()` also gained one `sync()` call, right after state-init and before the listening socket opens, gated on `--init-mode`: QEMU's default write-back disk cache (and, on real hardware, the same class of guest-side dirty-page caching) only guarantees a write reaches the actual disk once the guest flushes, and "listening on" is exactly the line both this project's own tests and a real operator treat as "safe to power-cycle."

Verified end to end, not just "the mount succeeded": `test/test_installer.c` gained a real cross-boot proof — after the installed system's first full boot, the real on-disk `kanxeo-containers` partition is extracted and confirmed to genuinely contain `kanxeod`'s own directories, a marker file is written directly into it (`debugfs -w`, no mount needed, this project's established no-loop-devices posture), and a *completely independent second boot* of the same disk confirms it's still there, byte-for-byte — 3 consecutive passes. Getting there surfaced two more real, non-obvious bugs, both fixed and documented rather than routed around: an earlier draft placed the new `sync()` *after* the "listening on" print, racing the test harness's own kill-on-marker behavior and defeating the fix entirely; and a partition extracted right after a QEMU session still carries a pending ext4 journal from that abrupt stop, which a raw `debugfs` write can have silently reverted by the next real mount's own journal replay unless `e2fsck -fy` forces that replay first.

**Not designed or built yet, per Zen:** a config-partition-style restore path for anything beyond what the `kanxeo-containers` partition itself now covers; real target hardware's own partition-name-based device lookup (same open item `ESP_DEVICE`/`CONFIG_DEVICE` already carry, per Part 4's own scope boundary).

### Phase 12 part 3 (done): real pkg recipes for bash, iproute2, and bird

With persistence genuinely real (part 2), the first real `.recipe` files: `pkg/recipes/{bash,iproute2,bird}.recipe`, each with a real upstream source URL and a sha256 verified against an independent authority beyond the daemon's own download (a second GNU mirror for bash; kernel.org's own published `sha256sums.asc` for iproute2; Debian's own `.dsc` `Checksums-Sha256` for bird's Debian-repackaged `.orig.tar.xz`, since `bird.network.cz`'s own download page 403s any non-browser `User-Agent`).

Verified by actually building and installing all three through a live daemon — not written from a template and assumed correct. Doing that surfaced a chain of real, generic gaps in the pkgbuild toolchain image (`pkg_bootstrap_build_image()`, `daemon/src/pkg.c`) that would have blocked *any* package's build, not just these three: no `/dev` at all (a build's own `./configure` routinely redirects probes to `/dev/null`); no `/tmp` (autoconf's `config.guess` needs one); several Debian-specific paths a real build reaches for that the existing `/usr/{include,lib,lib64,bin,libexec}` copy never covered — an `/etc/alternatives/awk` symlink target, bison's and autoconf's own runtime M4/macro libraries, and the core Perl modules `autoconf` itself is written in. Each fixed narrowly (staged from the host the same `cp -a`, idempotent way the existing toolchain copy already is — `/etc/alternatives`, `/usr/share/bison`, `/usr/share/autoconf`, `/usr/share/perl`), found and fixed one real build failure at a time rather than guessed at up front. BIRD's own tarball (Debian's repackaged upstream release) needed one more real fix specific to it: no pre-generated `./configure`, requiring `autoreconf -fi` in its own recipe's `pkg_build()`.

Going one step further than "the package installed" — actually running the freshly-built `bash` inside a real container — surfaced Phase 12 part 4's own finding (see below): nothing yet stages a C runtime into the shared `base` image, so nothing installed this way could actually execve() successfully until that part landed too.

### Phase 12 part 4 (done): a C runtime for the shared "base" image, seeded at install time

`pkg_build_completed()` only ever merges a package's own build output into `base/rootfs` — confirmed directly (part 3's own final check) that a freshly pkg-installed `bash` fails outright inside a real container: `child: execve: No such file or directory`, because `/lib64/ld-linux-x86-64.so.2` doesn't exist anywhere in the image. Not specific to bash — this blocks any dynamically-linked package from ever running.

Confirmed with the user directly which of three real options to build (a runtime REST bootstrap action mirroring `pkg bootstrap`; baking it into the boot-image-build tooling; or leaving it as a documented gap): baking it in. Investigating the actual code changed the concrete shape of that from the literal first guess (`mkbootroot.c`, which builds the OS's own control-plane squashfs — a wholly separate artifact from the containers partition where `images/base/rootfs` actually lives) to `mkinstalleriso.c`, which already had exactly the right, proven pattern (`g_lib_closure[]`, a hardcoded host-library-path array staged via `test_image_fixture_add_lib()`, already used for the installer's *own* execution environment) — extended with three more entries (`ld-linux-x86-64.so.2`, `libc.so.6`, `libtinfo.so.6`) into a new `/payload/kanxeo-runtime/` subtree. `kanxeo-install.c`'s own containers-partition block (previously format-check only, see part 2) now copies those three files into `images/base/rootfs/{lib64,lib/x86_64-linux-gnu}` at real install time. See ADR-0019.

Verified two ways: `test/test_installer.c` extracts the real containers partition right after the installer's own first boot — before any `pkg install`, before the independent second-boot persistence check — and confirms all three files are present with correct real byte sizes; separately, a throwaway `base` image manually seeded with the same three files let a real `bash -c` genuinely execve() and run inside a real container, printing its own version string. 3 consecutive `test_installer` passes; `test_boot`/`test_boot_ab` re-verified with no regression.

**Not designed or built yet, per Zen:** this seeds a fixed, minimal runtime (exactly what bash needs) — not a general dependency-resolution mechanism; a future package needing a library beyond this set is a real, known gap (extending the same set the same way is the straightforward path when that's actually needed, not attempted speculatively now).

### Phase 12 part 5 (done): `pkg install` targets an explicit image, not always "base"

With `bash`/`iproute2`/`bird` genuinely installable and runnable (parts 3-4), the user's actual use case surfaced the next real gap directly: building a `router`-flavored image carrying them without every other container on the shared `base` image getting them too. `pkg install` had exactly one destination, hardcoded (`pkg_build_completed()`'s merge step, `daemon/src/pkg.c`). See ADR-0020 for the full design.

`pkg_install_start()`/`pkg_get_one()`/`pkg_delete()` all gained an `image` parameter (`NULL`/empty defaults to `"base"` — every existing caller is unaffected). Because the same package name is now independently trackable per target image, the registry's lookup key became a **(name, image) compound key** — `struct pkg_entry` gained an `image[]` field, persisted in `pkg_installed.json` (absent on load defaults to `"base"`, so every pre-existing state file stays valid). A package's own dependency chain always installs into the same target image as the top-level request. `POST /v1/pkg/install`'s body gained an optional `"image"` field; the two single-resource endpoints gained `@`-separated compound addressing, `GET`/`DELETE /v1/pkg/{name}@{image}` (bare `{name}` still means `base`), reusing the existing path segment rather than adding query-string parsing (confirmed entirely absent from `http.h`). CLI: `pkg install --image=NAME`, `pkg rm NAME[@IMAGE]` (the latter needed no code change — it already forwards its argument straight into the URL path), `pkg ls` gained an image column.

Verified end-to-end over real HTTP against a live daemon (`test/test_pkg.c`, extended): the same recipe (`greeter`) installed into both `base` and `router` lands in two genuinely separate rootfs trees with zero cross-contamination, `GET /v1/pkg` lists both as distinct entries, `@`-addressed `GET`/`DELETE` reach the right one, and deleting `greeter@router` leaves the independently-installed `greeter@base` untouched — 3 consecutive clean runs. Full regression sweep (`test_daemon`, `test_cli`, `test_networks`, `test_dns`, `test_pki`, `test_daemon_net`, `test_daemon_devices`) re-run clean against the rebuilt daemon.

**Not designed or built yet, per Zen:** no image *creation* endpoint — a target rootfs is created on demand by the first install into it, the same way `base` itself already behaves before `pkg bootstrap` (closed in part 8's own follow-up: C-runtime seeding is now generalized to every image, see ADR-0023); v1's single-install-in-flight-at-a-time serialization is still global across every image, not per-image (a `router` install still 409s while a `base` install is mid-flight) — a documented, not-yet-relaxed boundary.

### Phase 12 part 6 (done): explicit, operator-chosen IPs for container network attachments

Also from the router use case: a router's own interfaces typically need stable, predictable addresses, not whatever `network_alloc_ip()`'s first-free-address scan happens to pick. See ADR-0021.

Each `networks[]` array entry in `POST /v1/containers` may now be an object, `{"name": "...", "ip": "..."}`, instead of only a bare name — an explicit address is validated against the target network's own subnet (correct masked base, not the reserved gateway or network address, within the usable host range) and checked for collision against every other running container's attachments, then honored exactly as given rather than auto-allocated. `daemon/src/registry.c` gained `registry_ip_available()`, a pure collision check extracted from `registry_alloc_ip()`'s own scan loop (registry.c stays deliberately topology-agnostic, per its own existing design); `daemon/src/network.c` gained `network_ip_available()`, which owns the subnet/range/gateway validation and delegates the final collision check to the registry. CLI: `--network=NAME:IP`, parsed the same way `--route=DEST/PREFIX:VIA` already is.

Verified over real HTTP against a live daemon: `test/test_networks.c` extended to confirm an explicit valid IP is honored (not auto-allocated), and that the reserved gateway address, an address outside the subnet, and an already-assigned address are each correctly rejected (400/400/409) — 3 consecutive clean runs. Full regression sweep re-run clean.

**Not designed or built yet, per Zen:** two network attachments in the *same* `POST /v1/containers` request aren't cross-checked against each other for an IP collision, only against already-registered containers — mirrors a pre-existing boundary `network_alloc_ip()` itself already had, not a new gap, and not a realistic use case (attaching to the same network twice in one request).

### Phase 12 part 7 (done): real network interface passthrough

The third and largest piece of the router use case: a real PCI/USB NIC has no `/dev` node at all, so the existing device-passthrough mechanism (BPF_CGROUP_DEVICE, ADR-0017) doesn't apply — the only real kernel primitive is moving the interface's netdev into a container's own network namespace. See ADR-0022 for the full account, including two real bugs found and fixed only while building this part's own verification: the kernel administratively downs a link as part of moving it to a new netns (the original "bring it up before moving" design was wrong, corrected to bring it up after, from inside the target netns), and a first draft of the verification test itself was fooled by `/sys/class/net`'s mount-time-captured (not dynamically netns-aware) view.

`daemon/src/device.c` gained a third bus, `net:`, walking `/sys/class/net` and excluding every kernel-created software interface (bridges, veths, kanxeo's own managed networks — anything resolving under `/sys/devices/virtual/net/`) — a more precise discriminator than a name-based heuristic. `src/container_net.c` gained `container_net_host_attach_interfaces()` (parent side, moves the interface in, then a forked helper briefly enters the container's own netns to bring it up) and `container_net_teardown_interfaces()` (a forked helper does the reverse move at container removal, addressed via an fd on `/proc/<pid>/ns/net` held open for the interface's entire attachment lifetime specifically so a self-exiting container doesn't lose it to the kernel's own unrecoverable fallback-name path). `netplane/src/rtnetlink.c` gained `rtnl_link_set_netns_fd()` (moves a link via an open netns fd instead of a pid, needed since the owning process may already be gone by teardown time). `POST /v1/containers` gained an `"interfaces": ["wlan0"]` array, validated against `GET /v1/devices`' own `net:` entries; CLI gained repeatable `run --interface=IFNAME`.

Verified two ways: `GET /v1/devices`' new discovery logic was checked directly against this dev sandbox's own real hardware (a real PCI NIC present in `/sys/bus/pci/devices` but, confirmed directly, invisible in this LXC's own `/sys/class/net` — a real, documented sandbox limitation, not a bug); the actual netns-move mechanism was proven end-to-end in `test/test_container_net.c` using a real veth pair's own two ends as a stand-in for "a named interface not yet in a container's netns" (legitimate since `rtnl_link_set_netns_pid()`/`rtnl_link_set_netns_fd()` are confirmed fully generic, not veth-specific) — 3 consecutive clean runs, full regression sweep (every other test in the suite) re-run clean.

**Not designed or built yet, per Zen:** genuine end-to-end proof with a literal physical NIC handed to a literal container has not happened and can't in this sandbox (no real, physically-backed netdev is visible in its own root netns at all) — real deployment hardware, or a future QEMU boot harness with a passed-through NIC, would be needed for that; the mechanism itself is proven, the literal hardware path is an explicit, known-open item, not silently assumed to work. Part 9's own follow-up closed the boundary precisely: `test/test_daemon_devices.c` now proves what *is* testable without real hardware (a real veth never appears under `GET /v1/devices`' `bus: "net"`, and `POST /v1/containers` correctly rejects it as an interface) — negative/validation paths only, the positive "grant a real NIC" path remains the open item above.

### Phase 12 part 8 (done): C-runtime seeding generalized to every image

ADR-0019's own Consequences section named this gap directly: runtime seeding (`ld.so`/`libc.so.6`/`libtinfo.so.6`) only ever landed in `images/base/rootfs`, at real install time — a `router` image with `bird`/`bash`/`iproute2` installed into it (part 5's own per-image `pkg install`) had no way to execve() any of them. See ADR-0023.

Investigating a runtime-level fix surfaced a real, previously unexamined risk first: the natural design (mirroring `pkg_bootstrap_build_image()`'s own "copy from wherever kanxeod is running" precedent) would have silently found nothing to copy for `libtinfo.so.6` on any real deploy, since `image/src/mkbootroot.c`'s own control-plane squashfs only staged `ld.so`/`libc.so.6` before this change — working in this dev sandbox only by coincidence (a rich `/usr` this sandbox happens to have, not something Kanxeo's own architecture guaranteed). Fixed first: `mkbootroot.c` now also stages `libtinfo.so.6`, so the *running* system's own root reliably carries all three files on any real deploy.

`daemon/src/pkg.c`/`daemon/include/pkg.h` gained `pkg_seed_image_runtime(const char *image)` — copies the three runtime files into any image's rootfs from those same fixed host paths, idempotent, tolerant of a missing source file (skip, not fatal, matching `pkg_bootstrap_build_image()`'s own precedent). Called from `pkg_build_completed()` for whatever image a job merges into, `base` included (harmlessly redundant there). A genuine addition, not a supersession of ADR-0019 — `base`'s own install-time mechanism is untouched.

Verified: `test/test_pkg.c`'s existing per-image scenario extended to confirm all three runtime files land in a freshly created `router` image's rootfs after its first install — 3 consecutive clean runs. `kanxeo-install.c`/`mkinstalleriso.c` confirmed byte-for-byte untouched (zero diff); a full QEMU-level `test_installer.c` re-run was not performed this session (no kernel image cached, and the change never touches that code path) — noted explicitly as a low-risk, known gap rather than silently skipped.

**Not designed or built yet, per Zen:** on a real deploy whose running root genuinely lacks these three files for some other reason, seeding still silently no-ops (same tolerant-of-missing-source rule); `pkg_bootstrap_build_image()`'s own toolchain sourcing has the identical "copy from wherever kanxeod is running" shape and was not fixed here — a real installed system's minimal squashfs root likely still lacks a full build toolchain for `pkg bootstrap` itself, a real, separate, pre-existing gap confirmed while investigating this one but explicitly out of scope for this change.

### Phase 12 part 9 (done): image lifecycle endpoints (`GET`/`POST`/`DELETE /v1/images`)

Before this part, an image was purely implicit — a directory that came into existence either at real install time (`base`) or as a side effect of the first `pkg install` targeting a name never seen before. No way to list what images exist, create one explicitly, or delete one. See ADR-0024.

New `daemon/src/image.c`/`daemon/include/image.h`, mirroring `/networks`' own four-endpoint shape but deliberately **not** persisted — an image genuinely is its directory, re-enumerated fresh on every list/get call, the same posture `device.c` already has for host hardware. `POST /images` creates an empty rootfs and immediately seeds its C runtime (part 8's own `pkg_seed_image_runtime()`), so it's usable right away. `DELETE /images/{name}` refuses `"base"` outright (protected, never removable), refuses if a running container still references it (`registry_image_in_use()`, `registry_entry` gaining a `char image[]` field via a new explicit parameter on `registry_create()` — `GET /v1/containers` responses gain an `"image"` field as a natural side effect), and refuses if `pkg.c` still tracks any package against it (`pkg_image_has_packages()`) — avoiding orphaned `pkg.c` state referencing a rootfs that no longer exists. Recursive removal is a hand-rolled `nftw()`-based walk, not a shell-out to `rm -rf`, consistent with this project's own "hand-rolled C for daemon-owned operations" posture. CLI: `image create --name=NAME`, `image ls`, `image rm NAME`.

Verified over real HTTP against a live daemon: `test/test_images.c`, new — create/list/get, 409 on duplicate create, runtime seeded immediately after create, 400 deleting `base`, 404 for an unknown image, 409 deleting an image a running container references (then 204 once that container is gone, directory genuinely removed), 409 deleting an image with a package still tracked against it (a deliberately-wrong-checksum install, reaching FAILED fast with no real build ever launching, but still counted as "tracked" — exactly the property under test). 3 consecutive clean runs. Full regression sweep re-run clean.

**Not designed or built yet, per Zen:** no image rename or clone — `router` still means starting empty and `pkg install`ing into it, not forking `base`'s own contents; not a v1 need identified yet.

## Phase 13: container lifecycle durability

A distinct theme from Phase 12's device/network/package work: containers themselves have been in-memory only since Phase 3 (deliberate at the time — every container dies via `PR_SET_PDEATHSIG` if the daemon exits, no restart-orphan state to reconcile). For a real deployment (routers, a NAS, a git-repo container, an ad-blocking DNS server, some depending on others), that boundary became the real blocker, raised directly by the user.

### Phase 13 part 1 (done): `restart: "always"` + `depends_on`

No new REST resource — two new optional fields on the existing `POST /v1/containers` (`restart`, default `"no"`; `depends_on`, an ordering-only list). `restart: "always"` persists the exact create request (`daemon/src/containerdef.c`/`daemon/include/containerdef.h`, new) alongside creating it live immediately, replayed verbatim at every future daemon boot and after any unprompted exit. See ADR-0025 for the full account, including a critical, confirmed-before-design constraint (`confirm_boot()`'s own "healthy means about to serve traffic, nothing more" definition, which auto-start must never disturb) and two real bugs found and fixed during verification: a double-pidfd-registration bug (crashed the daemon outright on the first real restart-across-reboot test) and a `DELETE /v1/containers/{name}` gap that made a definition permanently stuck once it failed to autostart even once (a `depends_on` cycle or unknown dependency) — surfaced by cross-test state leakage in the full regression sweep, fixed by decoupling "stop the live instance" from "remove the persisted definition."

`handle_create()` was split into a thin HTTP wrapper and a reusable `create_container_from_body()` (zero HTTP coupling), shared by the live REST path, boot-time `containerdef_autostart_all()` (runs once, right after `confirm_boot()`, unconditionally, blocking like every other startup step already is), and crash-restart replay. Crash restart is the reactor's first-ever timer: a one-shot `timerfd_create()`-based delay (2s, fixed, daemon-wide) rather than a blocking `sleep()`, which would freeze the entire single-threaded, non-blocking event loop for the whole delay. `depends_on` resolution mirrors `pkg.c`'s own `resolve_chain()` shape exactly (DFS + a `visiting[]` cycle-detection stack), applied to container names instead of package names. `DELETE /v1/containers/{name}` now also removes the persisted definition, permanently, in the same call — confirmed directly with the user as the intended v1 model (no separate "pause vs. disable").

Verified end-to-end against a live daemon, not just at the unit level: a fast-exiting `restart: "always"` container was observed crash-looping with a real, measured ~2.0s gap between each exit and the next (different) pid appearing; a daemon restart brought a persisted container back with a fresh pid; `DELETE` was confirmed to both stop it and leave it gone after a subsequent restart. The entire pre-existing REST-facing test suite was re-run unchanged after the `handle_create()` refactor, confirming zero regressions, before any new test was added.

**Not designed or built yet, per Zen (closed by Part 3 below):** no per-service restart delay or backoff policy (a single fixed daemon-wide constant for v1); no `restart: "on-failure"`/`"unless-stopped"` variants (Docker's fuller policy set) — only `"always"`/`"no"`, extendable later if actually needed.

### Phase 13 part 2 (done): TCP readiness checks for `depends_on`

Part 1 left `depends_on` as start-order only — a dependency being "started" (its `clone3()` returned) said nothing about whether it was actually ready to serve, a real gap for the user's own stated case (a router depending on DNS actually answering, not just having a pid). New optional `"readiness": {"tcp_port": N, "timeout_seconds": N}` (default 30, bounded 1–300) on the same `POST /v1/containers` request `restart`/`depends_on` already extended, following the exact same shape (out-parameters through `create_container_from_body()`, cached fields on `struct container_def`, echoed live in `GET /v1/containers` from `containerdef_find()`) — see ADR-0026 for the full design reasoning, including why TCP-only, boot-time-only, and best-effort were each the right v1 boundary.

`wait_for_tcp_ready()` (`daemon/src/main.c`) is a plain, blocking, retried `connect()` against the container's own primary network address (`entry->nets[0].ip_be`) — no non-blocking-connect-plus-`poll()` needed, since the destination is always a directly L2-adjacent bridge network the daemon itself manages (a refused/not-yet-listening port returns `ECONNREFUSED` immediately, never hangs). Called only from `containerdef_autostart_all()`, right after each definition's own successful autostart and before moving on to whatever depends on it — never from the live `POST` path (a container never waits on its own readiness at creation) and never from crash-restart (which runs inside the reactor's non-blocking event loop, where any blocking wait would violate the design ADR-0025 already established; crash-restart's own dependents are normally already running/ready anyway, since only the one container crashed). A readiness check that never succeeds logs a warning and lets boot proceed regardless — best-effort, matching the existing "one bad thing shouldn't take down the rest of boot" posture a `depends_on` cycle or unknown dependency already has.

Verified end-to-end against a live, restarted daemon (`test/test_container_restart.c`, extended, plus a new `test/tcp_listen_child.c` fixture that only starts listening after a deliberate 2s delay): a dependent's autostart was confirmed to genuinely wait — the whole daemon-restart-to-healthy window measured at least 1s, dominated by the dependency's own 2s readiness delay, not just present-in-code; a readiness check that never succeeds (1s timeout, nothing ever listening) still let its dependent autostart afterward, proving best-effort holds and boot never hangs; `readiness` without any network attachment was confirmed rejected with 400 at creation time. 3 consecutive clean runs; full regression sweep (`test_daemon`, `test_cli`, `test_networks`, `test_dns`, `test_pki`, `test_daemon_net`, `test_daemon_devices`, `test_pkg`, `test_images`) re-run clean against the rebuilt daemon.

**Not designed or built yet, per Zen:** no exec-inside-namespace or HTTP readiness probe (TCP-only for v1); readiness isn't consulted on crash-restart (a stated, deliberate boundary, not an oversight — see ADR-0026); no per-dependency override of the daemon's blocking-wait behavior (always synchronous at boot, for every definition that configures it).

### Phase 13 part 3 (done): restart policy expansion + backoff

Part 1 deliberately shipped only `restart: "always"`/`"no"` and a single fixed 2s crash-restart delay, deferring both Docker-style restart policy variants and any per-service/backoff delay. Both closed here, together. See ADR-0027 for the full design reasoning.

`restart` gains `"on-failure"` (restarts only after a nonzero-exit/signal-killed crash, not a clean `0` exit -- but this decision only ever governs the crash-restart timer, never boot-time autostart, since `exit_status` is never persisted and so can't survive a daemon restart -- a stated, permanent v1 boundary) and `"unless-stopped"` (behaves like `"always"`, except a new `POST /v1/containers/{name}/stop` -- reusing `registry_remove()`'s own existing SIGKILL+reap verbatim, no new kill primitive -- is remembered across a daemon restart; `"always"`/`"on-failure"` get a fresh chance at every boot regardless of a prior stop, matching Docker's own real `--restart=always` behavior). Since "a persisted definition exists at all" no longer implies `"always"` on its own, `struct container_def` gains an explicit, persisted `restart_policy` field -- a `container_defs.json` written by parts 1/2 has no such key, so its absence on load defaults to `"always"`, matching the old implicit semantics exactly (`No Regressions`). "Start" is still just a re-`POST /v1/containers` with the same body, same as it's always been -- `containerdef_add()` now also explicitly clears the new `stopped` flag on every call.

New optional `restart_delay_seconds` (1-300, default 2, the old fixed constant) overrides only the *base* crash-restart delay; automatic backoff on top of it (doubling per consecutive failure, capped at 30s, reset once a container's own uptime reaches 30s before it exits again) is uniform and not itself a further per-container knob. A non-persisted `consecutive_failures` counter on `struct container_def` naturally resets to 0 every daemon boot. A real, non-obvious consequence confirmed while writing this part's own test suite: a container's first-ever failure already applies one doubling (the failure counter goes 0 -> 1 on that very first fast exit), so a 5s base's real first restart delay is ~10s, not 5s -- the first draft of the test itself got this wrong (too-tight polling windows around the wrong expected value), not the daemon; fixed by correcting the test's own expectations after confirming the daemon's actual behavior directly with a temporary debug trace.

Verified end-to-end against a live, restarted daemon: `on-failure` confirmed to skip a restart after a clean exit but perform one (with a real, measured, backed-off delay) after a crash; `restart_delay_seconds` confirmed honored; a `stop` issued mid-delay-window confirmed to permanently cancel that pending restart (closing a real race `handle_restart_timer_event()` would otherwise have -- the registry entry is already gone and a timer already armed by the time a stop can race it); backoff confirmed genuinely growing across two consecutive fast-crash cycles, contrasted against a second, always-stable container landing at the un-doubled base delay instead (proving the reset branch, since a single container can't be made to alternate fast-crash vs. stable-run between restarts -- the daemon replays its exact same command verbatim every time, by design); `unless-stopped` confirmed to stay down across a real daemon restart while an identically-stopped `always` container came back. 3 consecutive clean runs; full pre-existing regression suite (all 17 binaries) re-run clean.

**Not designed or built yet, per Zen:** no `SIGTERM`-then-grace-period-then-`SIGKILL` for `POST .../stop` -- reuses DELETE's own instant-SIGKILL semantics exactly, a deliberate boundary; no exit-history persistence, so `on-failure`'s clean-exit memory never survives a daemon restart (see ADR-0027); backoff's cap/stability-reset thresholds are fixed daemon-wide constants, not configurable.
