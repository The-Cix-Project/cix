# 0168 — Every container's capability bounding set is trimmed to a default-safe list before `execve()`

## Status

Accepted

## Context

Confirmed directly (issue #29, raised by the user questioning whether user-namespace segregation was scoped from the start — it wasn't): Cix's containers run as real root with no user namespace (`CLONE_NEWUSER` is never used, `daemon/src/main.c`'s own comment on this predates this ADR) **and**, until now, with no capability restriction at all — a container's process inherited the full, untrimmed capability set every real-root process on the host has.

This is materially worse than the missing user namespace alone suggests. `CAP_SYS_MODULE` in particular is not exploit-dependent: kernel modules are not namespaced, so `init_module()`/`finit_module()` load code into the one shared host kernel regardless of which mount/pid/net namespace the calling process sits in. Any container's root process could call this directly, with zero vulnerability required anywhere — a straight line from `POST /v1/containers` with an arbitrary `cmd` to full host-kernel compromise. `CAP_SYS_ADMIN`'s own wide mount/namespace/admin grab-bag is a well-documented container-breakout vector on its own. Neither seccomp, AppArmor, nor SELinux exist anywhere in this codebase (confirmed by grep) — the BPF `BPF_CGROUP_DEVICE` gate (ADR-0017) is real and correctly restricts raw `/dev` node access, but has no bearing on either of these.

Full user namespaces (`CLONE_NEWUSER` + `uid_map`/`gid_map`) are the textbook complete fix, and remain the long-term goal (tracked separately, see Consequences below) — but are genuinely heavy: reconciling file ownership across every OverlayFS layer and staged image rootfs (id-mapped mounts or a real chown pass), `uid_map`/`gid_map` write ordering, and they still want capability trimming alongside them regardless, since a process can hold "full capabilities" relative to its own non-init user namespace too. Blocking the one fix that actually matters most (`CAP_SYS_MODULE`) on that larger design landing first was judged the wrong tradeoff — ship the small, surgical, immediately-effective fix now, keep the complete one on the backlog.

## Decision

Right before a container's `cmd` is `execve()`'d — after `mountns_pivot()`/`overlay_create()`/cgroup join are already complete, the last point still running as trusted, non-attacker-influenced setup code — permanently lower the process's capability bounding set via a real `prctl(PR_CAPBSET_DROP, cap, 0, 0, 0)` loop (`src/container_caps.c`, `container_caps_drop()`), plus `prctl(PR_SET_NO_NEW_PRIVS, 1)`.

- **Deny-list, not allow-list**: an allow-list would need an exhaustive per-service audit before shipping at all. A short, named deny-list of the capabilities that are actually dangerous (`CAP_SYS_MODULE`, `CAP_SYS_ADMIN`, `CAP_SYS_PTRACE`, `CAP_SYS_RAWIO`, `CAP_SYS_BOOT`, `CAP_SYS_TIME`, `CAP_SYS_RESOURCE`, `CAP_SYS_TTY_CONFIG`, `CAP_LINUX_IMMUTABLE`, `CAP_SYS_PACCT`, `CAP_MAC_OVERRIDE`, `CAP_MAC_ADMIN`, `CAP_SYSLOG`, `CAP_WAKE_ALARM`, `CAP_BLOCK_SUSPEND`, `CAP_AUDIT_CONTROL`, `CAP_AUDIT_READ`, `CAP_PERFMON`, `CAP_BPF`, `CAP_CHECKPOINT_RESTORE` — twenty entries, `src/container_caps.c`'s own comment gives the reasoning for each) ships today; `CAP_NET_ADMIN`/`CAP_NET_RAW`/`CAP_SETUID`/`CAP_SETGID` stay by default — confirmed, real, in-use needs on this project's own live containers (dnsmasq's `-u root` no-privdrop, sshd's own privilege-separation and per-session user drop in `jumpbox1`), verified by inspecting each live container's actual `cmd`/config on 192.168.15.95 before writing the list, not assumed.
- **No `capset()`, no `libcap`**: every container's `cmd` runs as real root executing plain, non-file-capability binaries. The kernel's own documented legacy-root-exec rule (`capabilities(7)`, "Capabilities and execution of programs by root") already recomputes each subsequent exec's effective/permitted sets from the bounding set for exactly this case — verified directly with a standalone syscall-level probe (drop two bits as real root, `execve()` an ordinary `bash`, then a further nested `sh -c`, confirm the same trimmed value survives both hops) before relying on it, not assumed from the man page alone. This is why the bounding-set drop alone is sufficient: it persists through a container's whole process tree (e.g. `jumpbox1`'s `bash` → `sshd` → a user's own login shell), not just the immediate `cmd`.
- **Opt-in exceptions**: `cap_add` (`POST /v1/containers`, `run --cap-add=CAP_NAME`, repeatable) names an explicit exception to the default list — e.g. `CAP_SYS_TIME` for chrony/NTP containers' own `clock_settime()` need. Only a capability actually on the deny-list is a meaningful entry; an unrecognized name, or one that was never dropped in the first place, is a `400` (`container_cap_name_valid()`, checked at REST-parse time, independently re-checked inside `container_caps_drop()` itself).
- **Struct/wire shape**: `CONTAINER_MAX_CAP_ADD` 8 entries, `CONTAINER_CAP_NAME_MAX` 32 bytes — same "generous fixed bound" posture every other `CONTAINER_MAX_*` constant already documents. `cap_add`/`cap_add_count` on `container_spec` (`include/container.h`) and `registry_entry` (`daemon/include/registry.h`), echoed back on `GET /containers`/`GET /containers/{name}` the same way `sysctls` already is.

## Consequences

- `include/container.h`, `include/internal.h`, `src/container_caps.c` (new file, added to `LIB_SRCS`), `src/container.c` (the one new call site, right before the final `execve()`, its own numbered exit code `120` + diag-pipe message matching every other pre-exec setup step's existing convention) — the runtime library's own change.
- `daemon/src/main.c` (REST parse + validation), `daemon/src/registry.c`/`daemon/include/registry.h` (copy-in + JSON echo), `cli/src/main.c` (`run --cap-add=CAP_NAME`, repeatable, usage string updated) — every surface offers it, per the API-First Mandate.
- `docs/api/openapi.yaml` (`ContainerCreate.cap_add`, `Container.cap_add`) and `docs/api/README.md` (new "Capability restriction (issue #29)" section) updated together, in the same change. `docs/guides/cli-reference.md`'s `run` flag listing updated too.
- Verified two ways: (1) a standalone syscall-level probe proving the underlying kernel behavior this whole design leans on is real, not assumed; (2) a real, freshly-built `cixd`, a real container (`capture_output` running a tiny helper that dumps its own `/proc/self/status`), confirming bit-for-bit via `CapBnd` that the default list is dropped, that `cap_add` correctly restores a named exception, and that an unrecognized/not-on-the-list `cap_add` name is rejected with `400` — `CAP_SYS_ADMIN` (present in this dev sandbox's own baseline) was the actual bit exercised end-to-end for both the drop and the restore path; `CAP_SYS_MODULE`/`CAP_SYS_TIME` are already absent from this dev LXC's own real-root capability set regardless of this change (a confirmed, documented sandbox limitation — see root `CLAUDE.md`'s Environment notes), so their own restore/keep paths need verification on a real installed host, not provable here. `sudo ./build/test_daemon`, `test_container_lifecycle`, `test_container_restart`, `test_container_net`, `test_container_stats`, `test_pkg`, and `test_daemon_devices` all pass unmodified, confirming no regression to existing container-creation paths.
- Every container created before this change (every one currently live on 192.168.15.95) gets the new default deny-list applied only on its *next* creation — an already-running container is unaffected until recreated. `ntp-1`/`ntp-2` (chrony) specifically need `cap_add: ["CAP_SYS_TIME"]` added on their next recreation, or their own `clock_settime()` calls will start failing where they previously succeeded — a real, tracked follow-up, not a silent gap.
- Full user-namespace support (`CLONE_NEWUSER` + `uid_map`/`gid_map`) remains open as issue #29's own original scope — this ADR closes the single most severe consequence of its absence (`CAP_SYS_MODULE`'s no-exploit-needed path chief among them), not the underlying gap itself. Root UID inside a container is still real host UID 0 after this change; a kernel bug wholly unrelated to capabilities is still a residual risk, same as any container runtime without user namespaces.
