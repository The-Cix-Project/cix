# 0042 — the installer relays interactive I/O through a PTY across both consoles at once

## Status

Accepted

## Context

The installer's own GRUB kernel command line already requests both consoles (`console=tty0 console=ttyS0`, `image/src/mkinstalleriso.c`), but Linux binds `/dev/console` to whichever `console=` is listed *last* — today, `ttyS0`. `thinc-install` (the installer's own PID1 program) inherits that single fd for everything: its own status output, and the two genuinely interactive subprocesses it runs (`fdisk`'s manual partitioning session, `mokutil --import`'s Secure Boot enrollment password prompt). An operator watching the video console — the common case on real hardware/Proxmox — sees nothing at all until the final reboot. The user confirmed this live and, offered a one-line kernel-arg reorder (flips which single console is interactive, doesn't fix "both") against real dual-console support, chose the latter.

The *post-install* system doesn't have this problem: `thincd` (`daemon/src/main.c`) forks an independent process per tty (`spawn_console_shell("/dev/tty0")`/`spawn_console_shell("/dev/ttyS0")`), each running its own persistent shell session. That mechanism doesn't transfer to the installer: `thinc-install` is a linear, single-pass sequence (partition → format → write → sign → enroll), not a daemon hosting independent sessions — running the whole installer twice, once per console, is nonsensical (you can't partition the same disk twice, and a duplicate `mokutil --import` would double-enroll the same key). The right mechanism here is different: relay *one* child process's I/O across both consoles simultaneously.

## Decision

A new PTY relay, `image/src/dual_console.c`/`.h`: `dual_console_open(path0, path1)` opens two console fds (tolerant per-path — a real machine/VM may only have one); `dual_printf()`/`dual_perror()` mirror the installer's own status/error output to both; `run_subprocess_dual_console(bin, argv)` replaces the two `run_subprocess()` calls for `fdisk` and `mokutil` (not `mkfs.vfat`/`mkfs.ext4`/`sfdisk`, which are non-interactive and keep their existing pipe-based helpers) — `posix_openpt()`/`grantpt()`/`unlockpt()`/`ptsname_r()` create a PTY, the child's controlling terminal becomes the slave (mirroring `spawn_console_shell()`'s own `setsid()`+bare-`open()` precedent), and a `poll()` loop (modeled on the existing precedent in `test/test_disk_image.c`'s own `qemu_boot_capture()` relay) copies PTY-master output to both consoles and console input from whichever one has data into the PTY master. The two real consoles are put into raw/cbreak mode (`cfmakeraw()`) only for the duration of each call, restored immediately after — the PTY slave's own line discipline (echo, canonical mode, a password prompt's own `tcsetattr()`) is entirely the child's business, untouched by the relay.

This is the first PTY usage anywhere in this codebase, extracted into its own module specifically so `test/test_dual_console.c` can link and exercise the *real* relay logic directly (No Parallel Implementations) against two throwaway PTYs standing in for the two real consoles, rather than a re-implementation of it.

**A genuinely new mount, found during design, not incidental**: `posix_openpt()`'s slave device only resolves once `devpts` is actually mounted — nothing else in this from-scratch PID1 environment ever does that. `early_mounts()` (`image/src/thinc-install.c`) now also mounts `devpts` at `/dev/pts`, same tolerance posture as its existing `proc`/`sysfs` mounts. The one kernel Kconfig option gating this (`CONFIG_UNIX98_PTYS` — no separate `CONFIG_DEVPTS_FS` exists in this kernel version) was, it turned out, already compiled into the exact kernel this project has been testing against all session, via `make olddefconfig`'s own default resolution rather than an explicit line in `image/kernel/qemu-part1.config` — added explicitly there now for honest, reproducible documentation; no kernel rebuild was needed to prove this design.

## Consequences

- Verified two ways. `test/test_dual_console.c` (no QEMU) proves the relay logic itself directly: a forked "driver" process plays `thinc-install`'s own role against two self-created PTYs; the test process plays "two operators," driving input into first one console then the other and confirming the echoed output lands on *both* each time — 3 consecutive clean runs. `test/test_installer.c`'s existing real 5-session Secure-Boot QEMU flow (which already scripts a real interactive `fdisk` session and a real `mokutil` password prompt) re-run clean through the new code, confirming no regression on the one console (`ttyS0`) this sandbox's own harness can actually automate.
- **Real video-console output stays an explicit, honest, user-owned gap** — this sandbox's QEMU harness has no video backend at all and cannot scrape text off one, the same already-accepted boundary Phase 14's own video-console driver work has. `test_dual_console.c`'s two PTYs prove the relay mechanism is correct; they cannot prove a real `/dev/tty0` device behaves identically to a PTY slave, though there's no reason to expect otherwise (both are ordinary character-device terminals from this code's own point of view). The user's own real-hardware/Proxmox confirmation is the necessary final check.
- A write failure on one real console mid-relay (e.g. an unplugged serial cable) drops just that one for the rest of the call, not the whole install — same tolerance philosophy as `dual_console_open()` itself.
- No signal handler for a mid-relay crash: this is PID1, nothing in this codebase ever signals it, and any crash here already means an imminent panic/reboot that makes a leaked termios setting moot (it doesn't survive the reboot into a fresh install session either way).
