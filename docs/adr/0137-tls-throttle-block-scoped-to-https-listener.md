# 0137 — TLS throttle blocks now only apply to the HTTPS listener

## Status

Accepted

## Context

Direct follow-up to ADR-0136, same investigation: after that fix shipped and the box rebooted, the user's own desktop appeared briefly unreachable ("I cannot connect to https? It's down?"). Live logs on 192.168.15.95 showed the desktop repeatedly failing HTTPS handshakes with a client-sent "certificate unknown" alert both before and after the reboot — genuinely still an untrusted-cert problem on the desktop's side, unrelated to the chain fix — which tripped a real ADR-0134 block. The user, once they confirmed the box itself was fine, asked directly: does an HTTPS-triggered block also throttle plain HTTP for that source, and does that make sense?

Reading `accept_loop()` confirmed it does: ADR-0134 deliberately enforces `connthrottle_should_block()` uniformly across both listeners, on the stated reasoning that "a source flooding one is a reasonable thing to also stop bothering with on the other." In practice, this meant the desktop's own untrusted-cert HTTPS failures — a real, ongoing but essentially self-inflicted condition while the user worked out their local trust store — also cut off its plain HTTP access, with no HTTPS-specific problem on the HTTP side at all. Only a failed TLS handshake can ever cause a block in the first place (`connthrottle_record_failure()` is called exclusively from the HTTPS handshake-failure path); enforcing that block against a listener that had nothing to do with causing it removes a legitimate fallback path for exactly the scenario ADR-0134's own loopback exemption already exists to prevent — locking out otherwise-legitimate access because of an unrelated failure mode.

## Decision

**`accept_loop()`'s throttle check is now gated on `is_tls`.** `connthrottle_should_block(peer_ip)` is only ever consulted when the connection came in on the HTTPS listener; a plain HTTP connection from a currently-blocked source is accepted and processed normally, regardless of how many HTTPS handshakes that same source has failed. No change to `connthrottle.c`'s own tracking table, thresholds, or the block/expiry mechanics themselves — this is purely a change to *where* an already-correct block is enforced, not how it's computed. `connthrottle_record_success()` still resets a source's failure count on a clean request from either listener (a legitimate distinction from enforcement: a clean plain-HTTP request is just as real evidence of non-malicious behavior as a clean HTTPS one, and there's no reason to make a source's HTTPS block outlive that evidence just because it arrived on the other listener).

Not implemented as two separate tracking tables — the single shared table already correctly identifies which sources have been failing HTTPS handshakes; the fix only needed to stop *enforcing* that state against a listener the failures never happened on. Matches this project's own "No Parallel Implementations" maxim: one source of truth for which sources are misbehaving, just applied more precisely.

## Consequences

- A source whose only problem is an untrusted HTTPS certificate — exactly ADR-0135's documented CA-download-and-trust scenario, and exactly what happened live here — can no longer lose its plain HTTP access as a side effect of retrying a broken HTTPS connection.
- `test/test_tls_throttle.c` rewritten to prove the new scoping directly: a real `openssl s_client -bind <attacker-ip>:0 -connect <https-port>` probe (this project's own established fork/execve `openssl` subprocess pattern, `test_pki.c`/`test_https_chain.c`) distinguishes "blocked before `SSL_accept()`" (`Cipher is (NONE)`, connection closed before any TLS record exchange) from "reached real TLS handshake processing" (a real negotiated cipher) — the raw-byte-count check the test used before this rewrite couldn't tell the two apart, since a garbage `ClientHello` gets an immediate connection reset with zero application bytes either way, blocked or not. The test now asserts a blocked attacker's HTTPS connection is refused at `accept()` while its plain HTTP is simultaneously, fully reachable — the exact behavior this ADR changes — and that block expiry, `enabled=false`, and cross-listener failure-count reset via a clean plain-HTTP request all still work as ADR-0134 originally established.
- `docs/api/README.md`'s TLS Throttle section and `docs/guides/security.md`/`web-dashboard.md` did not describe the "both listeners" enforcement detail explicitly enough to need a correction — no prose changes needed beyond this ADR itself.
- ADR-0134's own Decision/Verification text is left as-is (append-only, per `docs/adr/0000-adr-process.md`) with a short pointer annotation added at the end noting this ADR changed one specific claim within it, following the same precedent ADR-0052 established for ADR-0046 — the rest of ADR-0134 (per-source tracking, thresholds, the loopback exemption, the "record failure/success" mechanics) remains exactly as decided and accurate.
