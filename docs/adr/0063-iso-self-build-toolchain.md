# 0063 — ISO self-build: a real, from-source GRUB2/xorriso/mtools/sbsigntools toolchain

## Status

Accepted

## Context

Part 5 of the bare-metal-readiness plan, deliberately de-scoped and deferred at plan-writing time as "the largest, most uncertain part" — until now, `image/src/mkinstalleriso.c` (a dev-machine-only build tool, never shipped or run server-side) has shelled out to whatever `grub-mkrescue`/`sbsign` happen to already be installed on the machine building a release, rather than software this project's own package manager produced from real source. This ADR closes that gap: nine new real, from-source recipes, all verified end to end against the real daemon pipeline, plus a genuine architectural fix to the package manager itself that the effort surfaced.

A dedicated research pass (two parallel research agents, one on GRUB2's real build system, one on xorriso/mtools/sbsigntools/gnu-efi) preceded any implementation, per the plan's own instruction not to lock in an under-researched design. Both reports are reflected directly in the decisions below; nothing here was guessed.

## Decision

**GRUB2 builds in a single `./configure` pass, not two** — the plan's own original text speculated a second, separately-configured "target platform" build tree would be needed to produce x86_64-efi's own module set; confirmed directly against the real GRUB 2.14 source that this is wrong. `grub-mkrescue` is a real compiled C binary (`util/grub-mkrescue.c`) that statically links the same in-tree image-generation code `grub-mkimage.c` itself calls — one `./configure --prefix=/usr --sysconfdir=/etc --target=x86_64 --with-platform=efi --disable-efiemu --disable-werror && make && make install` (Linux From Scratch's own real, tested x86_64-efi flags) builds everything: the host-side utility binaries and the target platform's real `.mod` files, confirmed by a genuine hostbuild producing all 601 real module-related files under `usr/lib/grub/x86_64-efi/`. The BIOS/`i386-pc` pass real distros also build is deliberately skipped entirely — Cix is UEFI-only (ADR-0031) — which also means the `--image-base` sed-patch gotcha LFS documents for that pass doesn't apply here.

**xorriso and mtools are real, runtime-only dependencies of `grub-mkrescue`, never build dependencies of GRUB itself** — confirmed directly from `util/grub-mkrescue.c`: it invokes `xorriso`, `mformat`, and `mcopy` by literal name via fork/exec, searched on `$PATH` (with a `--xorriso=` override flag for the first, no override at all for the other two) — never linked as a library. GRUB's own upstream `INSTALL` file lists both only under "prerequisites for running make-check" (the test suite), not the build itself — confirmed by a hostbuild that never needed either package installed to succeed. `xorriso.recipe`/`mtools.recipe` exist purely so a later ISO-assembly step has real `mformat`/`mcopy`/`xorriso` on `$PATH` when `grub-mkrescue` actually runs, not for GRUB's own build.

**gnu-efi is needed by sbsigntools, not by GRUB2** — GRUB2 maintains its own self-contained EFI headers and PE32+ struct definitions in-tree (`grub-core/kern/efi/`, `include/grub/efi/`), confirmed directly; no external EFI library dependency exists for it at all. `sbsigntools`'s own `configure.ac`, by contrast, searches standard prefix-relative paths for `crt0-efi-$ARCH.o`/`efi.h` — real, confirmed via reading it directly, not assumed. `gnu-efi.recipe` (3.0.18, real upstream SourceForge tarball, a plain `make PREFIX=/usr install`, no `./configure` at all, confirmed via the real source tree) installs to `/usr/include/efi`/`/usr/lib`, matching sbsigntools' own hardcoded search paths exactly — no path-patching needed, unlike Guix's own package definition for the same software, which does need to patch those paths for its own different install layout.

**sbsigntools' real canonical upstream is James Bottomley's fork, not the original Canonical/Jeremy Kerr tree** — confirmed via multiple converging primary sources (the repo's own README stating this explicitly, `configure.ac`'s maintainer contact, and independent corroboration from GNU Guix's own package definition sourcing the identical URL/tag), at `git.kernel.org/pub/scm/linux/kernel/git/jejb/sbsigntools.git`, tag `v0.9.5` (upstream's newest real tag). Upstream ships **no release tarball at all** — only git tags — so `sbsigntools.recipe`'s `pkg_source` fetches a real git-archive snapshot from cgit's own `/snapshot/` endpoint instead, the same shape `cix.recipe`'s own self-hosted-gitea archive-download already established for the identical reason. A second `pkg_source` entry supplies CCAN (a vendored git submodule, `lib/ccan.git` → `git.ozlabs.org/~ccan/ccan`, pinned at commit `b1f28e1`, confirmed by reading the real submodule gitlink in the sbsigntools tree at tag `v0.9.5`) — fetched from `rustyrussell/ccan` on GitHub (ccan's own author's real mirror) rather than `git.ozlabs.org`'s own snapshot endpoint, whose query-string-only URL produces an unusable basename under this project's own `/build/extra/<basename-of-its-own-URL>` multi-source convention (ADR-0036) — confirmed byte-identical (matching sha256) against the git.ozlabs.org original before committing to the switch.

**`autogen.sh` is replicated directly, not patched or run verbatim** — a real, confirmed necessity: two of its steps (`AUTHORS`/`ChangeLog` generation) call `git log` against a live `.git` history a tarball-based fetch genuinely doesn't have. Every other real step (CCAN build-tree materialization via `lib/ccan.git/tools/create-ccan-tree`, then `aclocal`/`autoheader`/`autoconf`/`automake --add-missing`) is the identical sequence `autogen.sh` itself runs, confirmed by reading it directly — only the two git-log calls are replaced with minimal static files (neither is read by the build itself; `configure.ac`/`Makefile.am` reference neither). `docs/` (needs `help2man`, not staged anywhere in this project, and only regenerates man pages `pkg_install()` already discards) is excluded via a `SUBDIRS="lib/ccan src"` override on `make`/`make install` — confirmed the full unrestricted build genuinely succeeds through `lib/ccan` and `src` (all 6 real binaries: `sbsign`/`sbverify`/`sbattach`/`sbvarsign`/`sbsiglist`/`sbkeysync`) before ever reaching `docs`, so this is a real scope trim, not a workaround for a build failure in the parts that matter.

**`binutils-dev` is a new package, splitting binutils' dev files out from `binutils.recipe`'s own runtime-only install** — the same real runtime/dev split `libc.recipe`/`libc-dev.recipe` already established, needed because `sbsigntools`'s own `configure.ac` hard-fails (`AC_MSG_ERROR`) without `bfd.h`, which `binutils.recipe`'s own `pkg_install()` deliberately drops ("nothing else in this project's image set links against libbfd directly" — no longer true once sbsigntools exists). Unlike `libc-dev.recipe` (which copies pre-built files from this build sandbox's own real host toolchain, since building glibc from source is its own giant undertaking, out of scope), `binutils-dev.recipe` does a real, independent from-source build of the identical binutils-2.42 source `binutils.recipe` itself uses, keeping only the headers and static archives its own `pkg_install()` deliberately discards.

**A genuine architectural gap in `pkg.c` itself, found and fixed, not routed around**: every *ordinary* (non-hostbuild) package build runs inside one fixed, shared, persistent toolchain sandbox (`g_pkgbuild_rootfs`, staged once from this dev sandbox's own real host toolchain via `pkg_bootstrap_build_image()`) — never the target image's own rootfs, confirmed by reading `pkg_build_completed()`/`resolve_chain()` directly, not assumed from a recipe-level symptom. A successful install's own `$PKG_DESTDIR` was, before this fix, merged *only* into the target image (`merge_tree(dest_dir, target_rootfs, ...)`) — never into `g_pkgbuild_rootfs` — so a package installed via this project's own recipe mechanism was permanently invisible to any *other* recipe's own build step, even a formally-declared `pkg_depends`. Every prior recipe with a real `pkg_depends` (gcc on m4/binutils, autoconf on m4, ...) happened not to expose this, because those dependencies' own real tools already existed in this sandbox's actual host OS toolchain, masking the gap until `sbsigntools.recipe` needed `bfd.h`/`efi.h`/`uuid.h` — headers that exist nowhere on this sandbox's own bare host OS, only via this project's own from-source `binutils-dev`/`gnu-efi`/`libuuid` packages. Confirmed the hard way: `binutils-dev` was verified genuinely installed and merged into the "dev" target image (its `bfd.h` directly readable on disk there) while `sbsigntools`'s own real build, inside the real, separate `g_pkgbuild_rootfs` sandbox, still failed `configure`'s `bfd.h` check with a real, reproducible "No such file or directory" — not a flaky or environmental symptom, a structural one.

**Fix**: `pkg_build_completed()` now also merges every ordinary install's own `$PKG_DESTDIR` into `g_pkgbuild_rootfs` (best-effort, non-fatal on failure — the authoritative target-image merge already succeeded by that point) — the same `merge_tree(..., NULL)` no-manifest shape the pre-existing hostbuild-artifact harvest already uses, since `g_pkgbuild_rootfs` is a build-time-only sandbox, never itself an installed image needing file-tracking for a later uninstall. This makes the build sandbox a genuinely cumulative reflection of everything this project's own package manager has ever installed, matching the standard real-distro build-chroot posture (e.g. Gentoo's own `$ROOT` staging) rather than a narrower, per-recipe workaround — a durable fix for every future recipe with a genuine cross-recipe build-time dependency, not just `sbsigntools`.

## Consequences

- Verified real, end to end, empirically, in this exact order: all 9 new recipes (`patch`, `gettext`, `gnu-efi`, `xorriso`, `mtools`, `libuuid`, `binutils-dev`, `sbsigntools`, `grub`) installed successfully onto a real "dev" image through the real daemon pipeline, 3 real build failures found and fixed along the way (a `binutils-dev` relative-path bug from `pkg_build()`'s own `cd build` persisting into `pkg_install()`; the `g_pkgbuild_rootfs` cross-recipe visibility gap above; `sbsigntools`'s own `docs/` subdirectory needing `help2man`), each root-caused via the real build's own failure output, never guessed.
- **A real, complete, self-built ISO was produced and a real Secure Boot signature verified**, using *only* the freshly pkg-installed toolchain (explicit `$PATH` override to a scratch copy of exactly the newly-built `grub-mkrescue`/`grub-mkimage`/`xorriso`/`mformat`/`mcopy`/`sbsign`/`sbverify` binaries and the real 601-file `usr/lib/grub/x86_64-efi/` module tree, deliberately excluding this sandbox's own pre-existing system copies of the same tools to prove the self-built ones specifically): `grub-mkrescue` produced a genuine, valid, bootable ISO 9660 image (`file` confirms a DOS/MBR boot sector, "bootable" flag set); `sbsign`, using Cix's own real signing key, signed a real EFI binary (`systemd-bootx64.efi`); `sbverify` confirmed "Signature verification OK" against that same key.
- **Not verified, per Zen:** the daemon-side, REST-triggered ISO-assembly mechanism the plan's own text flags as a distinct, real follow-on ("architecturally settled... can be designed in that later pass without re-litigating it," a `CONN_BOOTROOT_ASSEMBLE`-shaped addition mirroring ADR-0057's own `mkbootroot` mechanism) has not been built in this pass — `image/src/mkinstalleriso.c` remains, as before, a dev-machine-only tool a release-builder runs by hand, now capable of using this project's own from-source toolchain instead of the host's pre-existing one, but not yet reachable via `POST`/CLI the way every other capability this platform offers already is (the API-First Mandate). A real, complete signed-ISO build using the self-built toolchain *end to end through `mkinstalleriso.c` itself* (rather than the standalone `grub-mkrescue`/`sbsign` invocations this ADR's own verification used) also remains a real, honest gap, deliberately deferred rather than rushed.
