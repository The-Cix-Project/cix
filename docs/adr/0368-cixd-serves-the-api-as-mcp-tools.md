# 0368 — cixd serves the API as MCP tools

## Status

Accepted by the owner on 2026-11-01, for #391. Their direction the same day: mark MCP exposure separately on each operation, work towards full parity with the API, generate it from the contract with no hand-written code, govern it with its own permission group, log it clearly, and give it clear exposure control. A dedicated agent user is the principal. ADR-0317's permission model, which #391 waited on, shipped in 0.2.57-396.

## Context

An LLM client (Claude Code in agent-1, ADR-0366) can drive Cix today only through `cixctl` in a shell. The Model Context Protocol lets a client call an API as typed tools instead. #391 asked for cixd to serve one with no second description of the API anywhere.

Measured on 2026-11-01:

- **The contract is not on the host.** `docs/api/openapi.yaml` (24,898 lines) is not staged into the control-plane root: neither the cix recipe nor `mkbootroot` names it. cixd has no YAML parser. Everything cixd knows of the contract arrives at build time, through `tools/apigen`: the route table (`api_routes.h`), the response shapes, and `web/api.js` for the dashboard.
- **apigen already resolves every request body**, the 82 written inline as well as the 41 named components, into schemas the dashboard's forms render from (ADR-0338).
- **An in-process call path exists.** ADR-0339's self-check runs a GET handler into memory through `events_run_get()`: the handler writes through the response sink as for a client, into a sentinel connection.
- **Per-operation authorization outside a handler exists.** The events stream asks the decision `authorize_route()` makes through `hostauth_authorize_peek()`. An app password authenticates one request as its user with `Authorization: Basic user:secret` (ADR-0317 section 8).
- **`x-cix-expose` names the surfaces an operation appears on** (`cli`, `web`), and `test_api_surfaces` holds each surface to it.

## Decision

1. **cixd serves MCP itself, at `POST /v1/mcp`**, on its existing listeners. It is not a separate process: cixd stays the only process holding host primitives (the API-First mandate), and a tool call goes through the same handler and the same authorization as the REST request it stands for, so the two cannot diverge. Transport is MCP's Streamable HTTP, stateless (no `Mcp-Session-Id`), with plain JSON responses and no server-sent events. Implemented methods: `initialize`, `notifications/initialized`, `ping`, `tools/list` and `tools/call`. Any other method answers JSON-RPC `-32601`. `initialize` names the protocol revision implemented (2025-06-18) and negotiates down to a client's older one when they differ.

2. **Exposure is a mandatory per-operation annotation: `x-cix-mcp: tool` or `x-cix-mcp: none`.** apigen refuses an operation without it, as it refuses one without `x-cix-read`, `x-cix-invalidates` or `x-cix-permission`. Neither value is a default, and exposing an operation is a visible line in a diff. It is a key of its own rather than a third word in `x-cix-expose`: `cli` and `web` say which clients must call an operation, a promise `test_api_surfaces` enforces, while `tool` offers an operation to any MCP client and promises no caller.

3. **Parity is the goal, reached by turning `none` into `tool` operation by operation**, each once it is verified over the gateway. Three classes cannot be tools as they stand, and are `none` until their mechanism exists:
   - a **WebSocket upgrade** (console, build log, event stream) is a session, not a call, and never becomes a tool;
   - a handler that **parks** (a credential check, a backup, a verification, a filtered log read, an uninstall: ADR-0340, ADR-0342) writes nothing until its helper finishes, and a sentinel connection cannot be served again. Phase 5 runs such a call on the MCP request's own connection, so an inner park parks the outer request and the re-serve runs the call again;
   - a **non-JSON body** (a raw file read) has no tool form until one is decided.

4. **The tool table is generated by apigen from the contract, at build time.** A tool's name is its `operationId`. Its description is the operation's `summary` and `description`. Its `inputSchema` is a JSON Schema built from the path parameters, the query parameters and the resolved request body. Its annotations are derived from the method: `readOnlyHint` for a GET, `destructiveHint` for a DELETE. The table is emitted under `build/` and never committed (ADR-0218). Reading the YAML at runtime was the issue's proposal; it is rejected under Alternatives.

5. **A tool call runs the operation's own handler, in-process.** `events_run_get()` is generalised to a method, a path with its parameters substituted, a query and a body. A 2xx answer is the tool's text result. Any other answer is a tool result with `isError` set, carrying the API's own error body. A 202 returns its body, and the client follows the job through another tool, as cixctl does. Responses are not trimmed, because a trimmed response would be a second description of what the API returns.

6. **Authorization is ADR-0317's, applied twice, and never in a handler.**
   - `POST /v1/mcp` carries its own `x-cix-permission: mcp:call`. A principal without it cannot reach the gateway at all.
   - A call to operation X then authorizes X's own `x-cix-permission` for the caller, through the factored decision `authorize_route()` uses, before the handler runs. A refusal is a tool error naming the permission.

   **A standard `cix-agents` group** is provisioned like ADR-0317's other standard groups. It holds `mcp:call` and the `read` permissions, and nothing else by default. Granting it more is an ordinary group edit. A saved group is never re-defaulted.

7. **The principal is a dedicated LDAP user, authenticating with an app password.** It is an ordinary directory user in `cix-agents`, so a prompt injection reaches no further than that group allows, and its actions audit under its own name. The app password is held in the MCP client's configuration, not in the conversation. In agent-1 that is a file in the operator's home on the `agent-home` volume, whose backups ADR-0366 already calls secret-bearing. In a deployment recipe it is a `{{SECRET:KEY}}` token, never a value in git.

8. **Every tool call writes one audit line:** the user, `surface=mcp`, the tool, its HTTP status and its duration. The inner request is not logged a second time.

9. **Off by default, with REST control.** `GET` and `PUT /v1/system/mcp {enabled}` (permission `system:write`) switch it, exposed to `cli` and `web`. While disabled, `POST /v1/mcp` answers 503 naming the switch. `POST /v1/mcp` declares `x-cix-invalidates: []`: the inner handler's own setters announce what it changes (ADR-0339).

10. **The order:**
    1. `x-cix-mcp` on every operation (all `none`), apigen's tool table and refusal, and the switch.
    2. `tools/list` and read-only `tools/call`, with a daemon-linked `test_mcp` speaking JSON-RPC to the endpoint, and the first read operations marked `tool`.
    3. Write operations, the audit line, and `cix-agents`.
    4. agent-1's deployment stages the MCP client configuration from a secret.
    5. Parked handlers.

## Alternatives considered

- **Read `openapi.yaml` at runtime** (#391's proposal). It would put a 24,898-line file into a root that does not carry it today, and a YAML parser into cixd, to answer at runtime what apigen already answers at build. A build-generated table is not a parallel registry: it has one source and one generated consumer, the posture `api_routes.h` and `web/api.js` already have, and the gates that hold those hold it. The drift #391 feared belongs to a committed list.
- **A third word in `x-cix-expose`.** That would bind the gateway to a rule that every `mcp` operation has a caller, and it does not.
- **Opt-in for context-window reasons.** #391 argued that exposure must stay small to fit a model's context. The client this serves loads tool definitions on demand, so the size of the set is not the constraint. Exposure is a governance decision, made per operation.
- **A separate MCP process.** A second holder of host credentials, to start, supervise and secure, against the API-First mandate.
- **Trimmed responses.** A second description of each response.
- **The operator's own account as the principal.** Every permission the operator holds would be reachable by prompt injection, and the agent's actions would audit as the operator.

## Consequences

- apigen gains one mandatory annotation and one emitted table. Every operation is edited once, mechanically, to declare `none`.
- `test_apigen`'s counts move. `docs/api/README.md` changes with the contract in the same change. A new `test_mcp` joins `DAEMON_SELFTESTS`.
- An agent's reach is its group's permissions, and every call it makes is in the audit log under its own user.

## Implementation notes

Recorded as each step lands, where the implementation is narrower than or departs from the text above.

- **Steps 1 to 4 landed in 0.2.57-646 to 0.2.57-650 and in agent-1 1.2.0**, verified on 192.168.15.95 on 2026-11-01. ROADMAP Part 352 has the measurements.
- **`test_mcp` is pure and `test_mcp_gateway` is the daemon test.** The protocol is tested over the generated table against stubs of the two callbacks the gateway reaches the daemon through: may the caller hold this permission, and run this request. What a call does once it reaches a handler, including the announcement a write must make, is tested against a real cixd and ends with `test_assert_no_drift()`.
- **The audit line is `mcp: <who> called <tool> (<METHOD> <path>) -> <status> in <N> ms`.** Decision 8 wrote `surface=mcp`; the line says it with its `mcp:` prefix. `<who>` is `audit_who()`, so an app password is named beside its user.
- **A write announces from `api_run()`.** Decision 9 says the inner handler's own setters announce what it changes. They announce only the changes a subsystem makes by itself; a change's `x-cix-invalidates` is announced by `dispatch()`, which a gateway call does not pass through, so `api_run()` makes the same `events_announce_change()` call for a successful write.
- **Adding `mcp:call` exposed a gap in ADR-0317's mapping**: a saved group gained no word that a later build added, so `cix-admins` stopped holding every permission. [ADR-0369](0369-an-admin-group-holds-every-permission-including-new-ones.md) settles it: an admin group holds every permission, including later ones. Standard groups are recorded as provisioned by name, so `cix-agents` reached a host that already had the other three.
- **agent-1's client configuration is in `/etc/claude-code/managed-settings.json`, not in the operator's home.** Decision 7 placed the app password in a file in the operator's home. A deployment cannot write there, because `/home` is the volume, so step 4 stages it where Claude Code reads managed settings: a `managedMcpServers` entry, which is additive, unlike `managed-mcp.json`. The secret therefore sits in the container's rendered definition and in a system backup, as the LDAP bind password already does. It is reached over HTTPS at `cix.internal`, the name cixd's certificate carries, because that key refuses plain HTTP.
- **Responses are not trimmed (decision 5), and `listPkg` answers 6.2 MB on .95.** That is a question for the API's own filters, not for the gateway.
- **Decision 3's "each once verified over the gateway" became verification by class** (the owner, 2026-11-02, *"Yes please"*), because the gateway adds nothing per operation. A tool runs the handler `dispatch()` calls, so what decides whether an operation can be one is a property of its contract entry and its handler's text, and both are gated mechanically:
  - `apigen` refuses a WebSocket (it answers 101), an `authenticated` operation and a non-JSON 200.
  - `test_mcp_exposure` refuses a handler that parks, reads a request header, or runs operations in-process itself.
  - `test_mcp_gateway` compares every read tool with REST against a real cixd.

  That took the tools from 17 to 327 of 356 in one release. A read whose `x-cix-read` is `stream` is a plain GET of a changing value, not a WebSocket, so the class decision 3 named as "streams" is the three operations that answer 101.
- **A request body travels in one `body` argument, not as properties beside the parameters.** Decision 4 said the `inputSchema` is built from the parameters and the resolved request body. Laying the body's properties beside the parameters, as step 3 first did, collided in three operations (a body `name` beside a path `{name}`), and could not express a free-form body (`patchContainer`'s merge, a map). `apigen` refuses a parameter named `body`.
- **`api_run()` refuses re-entry.** It has one sentinel connection, so an operation that itself runs operations in-process answers 503 from inside one rather than reusing it.
