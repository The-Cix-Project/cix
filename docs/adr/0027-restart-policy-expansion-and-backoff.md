# 0027 — restart policy expansion and backoff

## Status

Accepted

## Context

ADR-0025 (Phase 13 part 1) shipped `restart: "always"`/`"no"` and a single, fixed 2s crash-restart delay, explicitly deferring both a per-service delay/backoff and Docker-style restart policy variants beyond `always`/`no` (its own Consequences section, and `docs/ROADMAP.md`'s "Not designed or built yet" line for that part). Both gaps are real for the user's own deployment case: a service that should only come back after an actual crash (not a deliberate `0`-exit stop) needs `on-failure`; a service the operator wants to take down for maintenance without losing its definition, and without it silently reappearing on the next reboot, needs `unless-stopped`; and a genuinely crash-looping container shouldn't hammer the host at a fixed 2s cadence forever.

## Decision

**`restart` enum expands** to `["always", "on-failure", "unless-stopped", "no"]`. Before this, "a persisted definition exists at all for this name" implicitly meant `restart:"always"` — `registry_write_json_one()` read this straight off `containerdef_find(name) != NULL`, and no explicit policy field existed anywhere. With 3 non-`"no"` values that implicit equivalence breaks, so `struct container_def` gains an explicit `restart_policy[16]` field, persisted. A `container_defs.json` written by parts 1/2 has no such key at all — on load, its absence defaults to `"always"`, matching the old implicit semantics exactly (a `No Regressions` requirement, not optional polish); a *present but invalid* value is still treated as real corruption, the same posture every other field in that file already has (it's only ever written by this daemon's own validated path).

**`on-failure`** skips the crash-restart timer for a clean (`exit_status == 0`) exit only — `entry->exit_status` is read in `handle_container_event()` before `registry_remove()` destroys the entry. This decision cannot, and does not, survive a daemon restart: `exit_status` is never persisted anywhere, so `containerdef_autostart_all()` has no way to know how a definition last exited, and attempts every persisted `on-failure` definition unconditionally at boot — exactly like `always` does. This is a genuine, permanent v1 boundary, not an oversight: fixing it would mean persisting exit history nobody has asked for, real new scope.

**`unless-stopped`** needs a new REST action, since nothing before this stopped a container without deleting its definition: `POST /v1/containers/{name}/stop`. It reuses `registry_remove()` verbatim — already does `SIGKILL` + a synchronous reap (`daemon/src/registry.c`) — rather than inventing a new kill/reap primitive or a graceful-stop state machine that would sit asymmetrically next to `DELETE`'s own always-`SIGKILL` behavior. Unlike `DELETE`, it does not call `containerdef_remove()`, `dns_server_forget()`, `dns_record_forget_owner()`, or `pki_cert_forget_owner()` — the definition and this name's DNS/PKI ownership survive a stop, only a new persisted `stopped` bool is set (`containerdef_set_stopped()`, mirroring `containerdef_remove()`'s own "no-op if the definition doesn't exist" shape). It applies uniformly regardless of policy — killing a live container and (harmlessly, if no definition exists) marking it stopped — keeping `handle_stop()` itself free of policy branching; what `stopped` actually *means* going forward is entirely up to the two sites that consult it, not this handler.

The stopped-consultation split is deliberately not uniform, and that's the whole point:
- `containerdef_autostart_all()` skips a definition only when `stopped && restart_policy == "unless-stopped"` — for `always`/`on-failure`, a daemon restart is always a fresh chance, matching Docker's own real `--restart=always` behavior (a manual stop doesn't survive a daemon restart there either).
- `handle_restart_timer_event()` checks `stopped` **unconditionally**, regardless of policy — this closes a real race: `handle_container_event()` already removes the registry entry *before* arming the restart timer, so a `stop` call during that in-flight delay window must still prevent the timer from resurrecting the container a moment later, no matter what policy it was created with.

**"Start" is just a re-`POST /v1/containers`** with the same body — already how "define and start" has worked since part 1. `containerdef_add()` explicitly zeroes `stopped` (and `consecutive_failures`, below) on every call, since it doesn't `memset` the whole struct on an overwrite the way loading from disk does — a fresh create/redefine is definitionally not stopped and not backed off.

**Per-container base delay + automatic backoff.** New optional `restart_delay_seconds` (1–300, default 2 — the old fixed constant) overrides only the *base* delay; given with `restart:"no"` it's ignored, not rejected, mirroring `depends_on`'s own existing "ignored, not an error" precedent. Backoff itself — doubling per consecutive failure, capped at a fixed 30s — is automatic and uniform, not itself a further per-container knob (YAGNI: one fixed cap and stability threshold, not a second and third dial). A `consecutive_failures` counter lives on `struct container_def` but is deliberately **not persisted** — absent from `save_state()`/`parse_persisted_entry()` on purpose, so it naturally resets to 0 on every daemon boot via `containerdef_init()`'s own `memset(g_defs, 0, ...)`. A crash-loop history from before a daemon restart isn't meaningful afterward; a fresh boot is a fresh start. It increments on each restart, or resets to 0 if the container's own uptime (`time(NULL) - entry->started_at`, a new field on `registry_entry`) was at least 30s before it exited again — a container that ran fine for a while doesn't deserve the same backoff as one that's failing every second. The backoff calculation is a self-terminating loop (doubles until it would meet or exceed the cap, then clamps), safe regardless of how large `consecutive_failures` grows over a long daemon lifetime — no risk of shift/multiply overflow.

One consequence worth stating plainly, confirmed directly while writing the test suite for this: **a container's own first-ever failure already applies one doubling.** `consecutive_failures` starts at 0 and increments to 1 on that very first fast exit (uptime under the 30s stability threshold), so the first observed restart delay is `2 × base`, not `1 × base`. This isn't a bug — it falls directly out of "increment before computing delay" being the same code path for every failure, first or fortieth — but it's easy to mis-predict, and the first draft of this ADR's own end-to-end test did exactly that (see Consequences).

## Consequences

- **A real bug in the test's own expectations, not the implementation, was found during verification**: the first version of `test/test_container_restart.c`'s `delaytest`/`stopwindow` scenarios assumed a container's first-ever crash-restart delay equals its bare base delay. It doesn't — per the "first failure already doubles" point above, a 5s base produces a real ~10s first delay, not ~5s. The test's own polling windows and lower-bound assertions were too tight around the wrong expected value, timing out even though the daemon's actual behavior was correct throughout (confirmed directly with a temporary debug trace of `uptime`/`consecutive_failures`/computed `delay` before removing it). Fixed by widening the test's windows and correcting its expected values to match the real formula, not by changing the daemon's behavior.
- Verified end-to-end against a live, restarted daemon: `on-failure` was confirmed to not restart after a clean exit but to restart (with a real, measured, backed-off delay) after a crash; `restart_delay_seconds` was confirmed honored (base 5s, observed first-restart gap ≥8s, consistent with the real ~10s formula above); a `stop` issued mid-delay-window was confirmed to permanently prevent that pending restart from firing; backoff was confirmed to genuinely grow across two consecutive fast-crash cycles (~4s then ~8s, base 2s); the stability-reset branch was confirmed by contrast against a second, always-stable-before-crashing container landing at the un-doubled ~2s base instead — a single container can't be made to alternate "fast crash" then "stable run" between restarts (the daemon replays its exact same command verbatim every time, by design, ADR-0025), so reset is proven by comparison against growth rather than one container's own before/after; `unless-stopped` was confirmed to stay down across a real daemon restart while an otherwise-identical `always` container, stopped the same way, came back. 3 consecutive clean runs; full pre-existing regression suite re-run clean.
- Readiness (ADR-0026) is consulted at exactly one call site (`containerdef_autostart_all()`), unaffected by this change: `stop`/`unless-stopped` add no new readiness interaction, and a stopped `unless-stopped` dependency is simply skipped by the same `def->stopped` check autostart already gained here, same as any other skipped definition.
- No exec-inside-namespace graceful stop, no `SIGTERM`-then-`SIGKILL` grace period for `POST .../stop` — it reuses `DELETE`'s own instant-`SIGKILL` semantics exactly, a deliberate scope boundary (see Decision above), not an oversight.
