# 0030 — per-container config files and generalized sysctls

## Status

Accepted

## Context

Every container's filesystem was exactly its shared image's OverlayFS lowerdir plus its own empty upperdir, with no volume/bind-mount concept and no operator-facing way to write a file into a container at all — the only file-injection mechanism that existed, `/proc/<pid>/root/` (ADR-0013), is wired to exactly two daemon-internal side effects (DNS hosts-sync, PKI cert delivery), not a general API. And only one specific sysctl (`net.ipv4.ip_forward`) could be tuned per container, via a hardcoded single-purpose function. Raised directly by the user: several containers built from the *same* image (e.g. a `router` image with a shared `bird` binary) each needing their *own* `bird.conf` and their own bash orchestration script, plus generalized sysctls (`rp_filter` and others, relevant to policy-based routing) beyond just `ip_forward`.

## Decision

**Config files (`"files"` on `POST /v1/containers`) are a purely daemon-side, pre-`clone3()` mechanism — `struct container_spec`/the runtime library never see them at all.** Confirmed directly before designing this: the daemon (long-lived host process) already computes `upperdir` and `mkdir()`s the container's own base directory itself, before `registry_create()`/`container_create()`/`clone3()` is ever called (`daemon/src/main.c`); `overlay_create()`'s own `mkdir(upperdir, ...)` (child-side, post-`clone3()`) is already `EEXIST`-tolerant. So the daemon writes files directly into `upperdir` via plain host-side `open()`/`write()` *before* `registry_create()` runs, and the container's own overlay mount picks them up unchanged — the files are simply already there the moment `cmd` `execve()`s. This is why `files` can safely *be* `cmd` itself (e.g. `["/bin/bash", "/usr/local/bin/pbr.sh"]`) — a post-hoc mechanism like `/proc/<pid>/root/` needs an already-running pid, which doesn't exist yet at this point.

**Path validation is the one place in this feature with real security weight.** Every existing path-shaped field in this codebase (`dev_path` on `device_spec`) is daemon-sourced from sysfs, never client-supplied — `files[].path` is the first field where an attacker- or mistake-controlled string becomes a real host filesystem write target. Validated by requiring a leading `/` and rejecting any `.` or `..` path component (checked by walking the path component-by-component, which also naturally rejects empty components from a stray `//`). No existing name/path validator in the codebase was reusable as-is: `namecheck.h`'s `simple_name_is_valid()` rejects `/` and `.` outright (a pure resource-name validator, never meant to express a real path), so this is new, purpose-built validation.

**`sysctls` extends, rather than replaces, the existing `ip_forward` pattern.** `container_net_enable_ip_forward()` (`src/container_net.c`) is child-side, called after `clone3()` but before `execve()`, writing directly to a literal `/proc/sys/...` path — safe specifically because the entire `net.*` sysctl tree is per-netns, and the child is already living inside its own `CLONE_NEWNET` at that point. `ip_forward` stays exactly as-is (a simple boolean shorthand for the single most common case); `sysctls` is new, additive, general escape hatch alongside it — the same "add, don't replace" shape `restart_delay_seconds` already established alongside `restart`.

**Deliberately restricted to keys starting with `net.`** — a real, load-bearing security boundary, not incidental. Most non-`net.*` sysctls (`vm.*`, `fs.*`, ...) are **not** namespace-isolated at all in Linux; allowing arbitrary keys here would make this a real host-wide kernel-state write primitive from inside a container, not a per-container knob. Validated by requiring `net.` as the first dot-separated component and every component non-empty and `[A-Za-z0-9_]` only — this also naturally rejects `net..foo` or `net.ipv4..` (an empty component that, translated `.`-to-`/` by `container_net_apply_sysctl()`, would otherwise become a `/proc/sys/net/../..` traversal).

**`registry_create()` grows two new ways to receive this data, matching two different existing precedents on purpose.** `sysctls` is already part of `container_spec` (since the child needs it), so `registry_entry` copies it straight from `spec` inside `registry_create()` — the same shape `interfaces[]` already has (read from `spec`, no separate explicit parameter). `files` never touches `container_spec` at all, so its display-only path list needs a genuinely new explicit parameter — the same shape `ip_forward`/`devices` already have (explicit parameters, redundant with what a fuller `spec` read could technically provide, for historical/incremental-feature-addition reasons this ADR doesn't need to unwind).

## Consequences

- Verified directly against a live daemon, not just by code inspection: a real file staged via `"files"` landed at the correct host path with the correct content and mode; `../../etc/passwd` and `etc/passwd` (no leading `/`) both rejected with `400`; a `net.ipv4.conf.all.rp_filter` sysctl was confirmed, via `nsenter` into the container's own `/proc/<pid>/ns/net`, to land inside *that* netns specifically (value `0`) while the host's own value (`2`) stayed completely untouched — proving real per-netns isolation, not just that the write syscall succeeded somewhere. `vm.swappiness` and `net..foo` both correctly rejected with `400`.
- Because `restart:"always"`/`"on-failure"`/`"unless-stopped"` already persists the entire raw request body verbatim and replays it through this same code path on every boot/crash-restart (ADR-0025), `files` content and `sysctls` are automatically re-staged/re-applied correctly on every replay for free — no extra persistence work was needed for this.
- `registry_create()`'s own signature grows again (now: `name, image, spec, nets, net_count, ip_forward, devices, device_count, file_paths, file_count, out`) — a long, still-growing parameter list. Not addressed here; a future refactor bundling these into a smaller number of structs is a real, deferred cleanup, not attempted as part of this change (scope discipline: this ADR is about the two new capabilities, not a signature refactor).
- No volume/bind-mount concept still exists for anything *other* than these explicitly-declared, content-inlined files — a large binary asset or a directory tree still has no home in this model. A real, stated v1 boundary: the actual use case raised (small text configs and a shell script) doesn't need one, and inventing a general mount-in mechanism wasn't justified by it.
