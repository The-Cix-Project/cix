# 0110 — NTP: hand-rolled SNTP client for the host clock, plus container time-source registration (tasks #751-755)

## Status

Accepted

## Context

Raised directly by the user alongside a unified-logging question (the logging half was already covered by ADR-0070): *"we need a command to see the date and time, and to set them, and to point to a ntp container (or multiple) same as dns/ldap and so on... same type of configuration same capabilities add/delete/edit, and enrollment same as ldap and same as dns."*

Two genuinely independent questions, both confirmed with the user via `AskUserQuestion` before writing any code:

1. **How does the host's own clock get synced?** DNS and LDAP both delegate their actual protocol serving to a containerized workload (dnsmasq, glauth) that thinC's REST layer merely configures/registers. NTP cannot follow that pattern for the *host's own clock*: setting it needs `clock_settime(CLOCK_REALTIME, ...)`, which needs `CAP_SYS_TIME` from the **host's own namespace** — no container can be granted that without either breaking container isolation outright (handing a workload a host-level capability) or `thincd` doing the actual syscall itself anyway, which is simplest done directly. Confirmed with the user: hand-roll a small SNTP client inside `thincd` itself, the same "platform-level primitive gets hand-rolled" precedent `daemon/src/ping.c` already set (ADR-0007) for raw ICMP.
2. **Does container-to-container NTP still make sense, mirroring DNS/LDAP registration?** Yes — confirmed as a second, additive capability: `POST`/`GET`/`DELETE /v1/ntp/servers` registers a running container as an available time source, the exact same shape `dns_server_register()`/`ldap_server_register()` already have.

## Decision

### Part 1 — the host's own clock: a real hand-rolled SNTP client

`daemon/include/ntp.h`/`daemon/src/ntp.c` implement the client subset of RFC 5905 (historically RFC 4330): a 48-byte fixed wire packet (`struct ntp_wire_packet`, `#pragma pack` — not `__attribute__((packed))`, TCC ignores the latter entirely, ADR-0008), client mode (`li_vn_mode = 0x23`) request, server-mode (`mode == 4`) reply validation against both the source address and the client's own echoed-back origin timestamp (the field the client actually sent as its own *transmit* timestamp — a real, easy-to-get-backwards detail: the client puts its send time in the request's `transmit_ts`, and validates by checking that same value echoed back in the reply's `origin_ts`, not the other way around). RFC 5905's own offset formula, `theta = ((T2-T1)+(T3-T4))/2`, computes the correction; `clock_settime(CLOCK_REALTIME, ...)` applies it directly. The known NTP-epoch 2036 rollover (32-bit seconds-since-1900 wraparound) is accepted, undocumented-further — the same posture this project already takes toward Y2038 elsewhere.

`GET`/`PUT /v1/system/ntp`: the upstream server address list, persisted the same plain-text `"server A.B.C.D\n"` line format `resolv.c` already uses for its own nameserver list (not a JSON wrapper — no JSON needed for a bare address list), same `NTP_MAX_UPSTREAM = 3` cap as `RESOLV_MAX_NAMESERVERS`.

The sync mechanism itself (`ntp_sync_start()`/`ntp_sync_handle_reply()`/`ntp_sync_handle_timeout()`, wired into `main.c`'s epoll loop as `CONN_NTP_SYNC`/`CONN_NTP_SYNC_TIMER`) is a real, bounded async job matching this daemon's own established "one job of this kind in flight at a time" v1 constraint (ping/disk-format/ISO-build/pkg-fetch all already work this way) — never a blocking syscall in thincd's single-threaded epoll loop (ADR-0005/0007). One real, deliberate divergence from `ping.c`'s simpler always-one-shot-then-teardown shape: a sync attempt can have multiple **candidates** (registered server containers, then configured upstream addresses, in that order) and must retry across them on timeout — so the same UDP socket is reused across every candidate within one attempt (not recreated per-candidate), and the paired timerfd is **re-armed**, not recreated, on each retry. Documented directly in `ntp.h`'s own header comment so a future reader doesn't mistake this for an oversight against the `ping.c` pattern.

A permanent, self-re-arming timer (`start_ntp_periodic_timer()`, the same "schedule the next one-shot fire on completion" idiom the console-respawn timer already uses — this codebase has no precedent for a genuinely recurring `it_interval` timerfd, and this doesn't introduce one) fires an automatic sync attempt every `NTP_SYNC_INTERVAL_SEC` (1 hour).

**A real gap found and fixed during live testing, not left for later**: the periodic timer's first fire is a full hour after daemon startup — an operator who just configured upstream servers or registered a server container had no way to see a result without waiting up to an hour, and the sync mechanism itself had no REST surface at all beyond the passive hourly trigger. `POST /v1/system/ntp/sync` closes this: triggers one sync attempt on demand (`202` started, `409` already in flight, `400` nothing configured — the same v1 single-job/`202`-then-poll-status shape `POST /v1/system/ping` already established). `start_ntp_sync_job()` was changed from `void` to returning `enum ntp_start_error` so both the periodic timer (still best-effort, ignores the result) and this new handler (which reports it) can share the one implementation — no duplicated job-setup logic.

`GET /v1/system/ntp/status` reports the outcome of the most recent attempt: `never`/`ok`/`failed`, plus `synced_from`/`last_sync_unixtime` when `ok`. A `failed` state covers two different underlying causes the client can't always distinguish from the REST surface alone — every candidate exhausted with no valid reply, *or* a valid reply arrived but the final `clock_settime()` itself failed (e.g. no `CAP_SYS_TIME`) — both are real, reportable failures, and retrying either is handled identically (the next scheduled or on-demand attempt).

### Part 2 — container-to-container NTP: server registration

`POST`/`GET`/`DELETE /v1/ntp/servers` mirrors `dns_server_register()`/`ldap_server_register()`'s exact REST shape (`daemon/include/ntp.h`'s own header comment cross-references both). Deliberately simpler than either: NTP is itself a live query/response protocol, the same reasoning that already let LDAP registration (task #725) skip pid/pidfd entirely — no config-file push, no signal needed at registration time. `ntp_server_register()` resolves and validates the named container directly against `registry_find()` (self-contained, unlike DNS which relies on `main.c`'s own pre-check) — `NTP_ERR_CONTAINER_NOT_FOUND` (no such container) is a genuinely distinct case from `NTP_ERR_CONTAINER_NOT_RUNNING` (exists but stopped), both mapped to `404` with different messages; a bug caught during live curl testing where both cases collapsed into one ambiguous `NTP_ERR_NOT_FOUND` (shared with the *unregister* "no such registration" case) was fixed by splitting the enum before this shipped, not left as a known rough edge.

`ntp_sync_start()`'s own candidate-list builder resolves a registered container's **live** IP fresh from the registry at every sync attempt (`registry_find()`'s `nets[0].ip_be`), never cached — a registered container is just one more candidate ahead of the configured upstream addresses, tried in registration order.

### Part 3 — GET/PUT /v1/system/time: manual override

A separate, deliberately independent escape hatch: view or directly set the host's current clock (`clock_settime()`, immediate, host-wide, no reboot — the same live-apply posture every other resource here already has). Independent of NTP sync in both directions: setting it manually doesn't touch the upstream/server config, and the next scheduled or on-demand sync will overwrite it again, which is intentional (NTP staying authoritative is the whole point once it's configured).

## Consequences

- No new dependency, no new capability the daemon didn't already effectively need (root, already required for namespaces/cgroups) — `CAP_SYS_TIME` comes along with running as root.
- This sandbox denies `clock_settime()` outright with `EPERM`, even as real root (documented in `CLAUDE.md`, confirmed via a minimal standalone reproduction isolated from any of this project's own code) — the *failure*-detection path (a well-formed `400` with a clear message, not a crash or a silent no-op) is fully verifiable here; the *success* path needs a real box (192.168.15.95).
- `test/test_ntp.c` proves the full mechanism end to end over real HTTP against a real `thincd` subprocess, including a genuine SNTP wire round trip: a tiny hand-rolled UDP responder (this test's own forked child, not a container — binding the privileged port 123 needs no extra setup since the whole test already needs root for the daemon's own namespace/cgroup work) answers exactly like a real upstream server, proving `ntp_sync_start()`/`ntp_sync_handle_reply()`'s candidate-resolution and reply-matching logic actually runs, not just that the REST scaffolding compiles. Since this sandbox's `clock_settime()` denial means the very last step can't be asserted to succeed here, the test asserts the sync resolved **quickly** (well under the 1.5s per-candidate timeout, proving a valid reply was received and processed) rather than asserting `state == "ok"` outright, and separately reports which outcome it actually got — a deliberately environment-tolerant assertion for a genuinely environment-dependent last step, not a weakened test.
- Every other endpoint (config CRUD/validation, status, server registration CRUD including the not-found/not-running/duplicate/forget-on-container-delete paths, time GET, and time PUT's negative-value validation) is asserted unconditionally, regardless of environment.
