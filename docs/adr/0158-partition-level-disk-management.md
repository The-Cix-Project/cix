# 0158 — partition-level disk management

## Status

Accepted

## Context

Task #844 asks for multiple partitions per disk, with a role assignable per partition, not just per whole disk. `disk.c`'s `disk_enumerate()` (Phase A of multi-disk management) explicitly skipped every partition (anything with a `partition` sysfs attribute under `/sys/class/block/<name>/`) — only whole disks were ever independently addressable, and `diskrole.c`/`diskformat.c` (Phases B/C) both operate purely on whatever `disk_enumerate()` reports.

Direct investigation (per this project's own "Outline" discipline) before designing anything: both `diskrole.c` and `diskformat.c` key every operation off `disk_enumerate()`'s own `name`/`dev_path`/`is_os_disk` fields, with zero whole-disk-specific assumption anywhere in either module. This means the actual gap is narrow — teach `disk_enumerate()` to also report partitions, and role assignment/format-and-mount work on a partition for free, no changes needed to either module.

`sfdisk` (util-linux, `/usr/sbin/sfdisk`) is already the project's proven tool for scripted partitioning — `image/src/cix-install.c`'s own `auto_partition()` already drives it this way for the installer's fixed OS-disk layout. The same scripted-stdin mechanism, run incrementally against an operator-chosen data disk after install, is the natural fit here too — confirmed directly against a scratch disk image file in this sandbox before writing any daemon code: `printf 'label: gpt\n' | sfdisk <target>` creates a fresh table; `sfdisk --append <target>` with a `size=NMiB, type=linux, name="..."` stdin line (or no `size=` field at all for "consume all remaining space", the same convention `auto_partition()`'s own last line already relies on) adds one partition without touching the others; `sfdisk --delete <target> <partno>` removes one.

## Decision

**`disk_enumerate()` (`daemon/src/disk.c`) now reports partitions as ordinary entries**, not just whole disks. `struct discovered_disk` (`daemon/include/disk.h`) gained `is_partition`/`parent_disk` fields. Implementation is two passes over `/sys/class/block`: pass 1 populates whole disks exactly as before; pass 2 adds every partition, propagating `is_os_disk` from its already-populated parent (looked up by `parent_disk`, itself computed via the pre-existing `disk_name_from_partition()` helper). Two passes, not one, because `readdir()` order is not guaranteed to put a parent before its own partitions, and a partition's `is_os_disk` must come from its parent. `model`/`removable` stay empty/false for a partition entry — neither sysfs attribute exists per-partition, only on the parent whole disk (confirmed directly against this sandbox's own real partitions).

**A new module, `daemon/src/diskpart.c`/`daemon/include/diskpart.h`**, adds three operations, all synchronous (no pidfd/epoll job-tracking, unlike `diskformat.c`'s async mkfs — creating or modifying a partition table is metadata-only and near-instantaneous, the same "quick admin op runs inline" precedent rtnetlink bridge creation already uses):

- `diskpart_create_table()` — a fresh, empty GPT table. Destructive (wipes any existing table); rejects a disk that's a partition, the OS disk, already has a role assigned directly to it, or is mounted.
- `diskpart_add()` — appends one partition to an existing table via `--append`; same preconditions as create-table (a disk in whole-disk role/format use must never also be partitioned underneath that use).
- `diskpart_delete()` — removes one partition; rejects a target that isn't actually a partition, doesn't belong to the disk named in the request, is part of the OS disk, still has a role assigned, or is mounted.

A disk is used in exactly one of two mutually-exclusive modes going forward: role assigned directly to the whole disk (the pre-existing model), or partitioned with roles assigned to the individual partitions instead — enforced at the point of the destructive action, the same "the destructive action carries its own safety checks" convention `diskformat.c` already established, not a new state flag.

**REST surface** (`daemon/src/main.c`): `POST /v1/disks/{name}/partition-table` (body: `{"confirm_disk_name": "..."}`, the same double-confirmation `POST .../format` already requires), `POST /v1/disks/{name}/partitions` (body: `{"name": "...", "size_mib": N}`, `size_mib` omitted or `0` means "rest of the disk"), `DELETE /v1/disks/{name}/partitions/{partition_name}`. Dispatch reuses the exact same `char *slash = strchr(name, '/')` split ADR-0156's container-networks endpoints already established for a similarly-shaped `{parent}/{subresource}[/{child}]` path.

**Incidental fix found during this task's own testing**: `DISK_ENUM_MAX` (the fixed-size stack array every `disk_enumerate()` caller uses) was `64`. Direct testing in this dev sandbox — whose `/sys/class/block` is shared with its own LXC host and therefore also shows every one of that host's unrelated LVM `dm-*` volumes (72 of them, confirmed directly) — found this cap could silently truncate real disks (here, entirely losing every partition) out of the enumeration with no error, since `readdir()` order doesn't guarantee a real target disk's own entries come first. Not a new problem this task introduced (whole-disk enumeration already shared the same array), but partitions now sharing the same budget made it easier to hit, which is how it was actually found live rather than reasoned about in the abstract. Raised to `256` — comfortably covers this sandbox's own real 89-entry `/sys/class/block` plus headroom, at a still-trivial stack cost per call site.

## Verification

Full clean rebuild (`-Wall -Werror`), zero warnings, across the whole build (`make all`).

**What was verified for real, against a real spawned `cixd`** (`test/test_diskpart.c`): `GET /v1/disks` correctly reports `is_partition`/`parent_disk`/empty-`model`/`removable:false` for this sandbox's own real, pre-existing partitions (`sdb1`, `nvme0n1p1`/`p2`/`p3`), with each partition's `parent_disk` resolving to a real, non-partition entry in the same list — proving `disk_enumerate()`'s new second pass and parent-lookup against real kernel sysfs state, not code read in isolation. Every validation-only rejection path in `diskpart.c` that returns before ever invoking `sfdisk` — invalid disk name, disk/partition not found, a partition targeted where a whole disk was expected (and vice versa), wrong parent, a required field missing, wrong `confirm_disk_name` — exercised as real HTTP requests. A disk (and separately, a partition) with a role assigned directly to it correctly rejects the corresponding destructive operation with `409`; assigning a `diskrole` is pure daemon-side bookkeeping, so this was safe to exercise for real without touching any real disk content, and it also proves `diskrole.c`'s existing name-agnostic design already works for a partition name with zero changes of its own.

**What was not, and could not be, verified in this sandbox**: the real `sfdisk`-invoking success path of `diskpart_create_table()`/`diskpart_add()`/`diskpart_delete()` end to end through the daemon. This sandbox has no loop devices (`losetup -f` on a fresh scratch file fails outright with "cannot find an unused loop device," confirmed directly — the same class of gap `test_disk_quota.c` already documents), and `diskpart.c`'s own public functions only ever accept a disk name `disk_enumerate()` itself discovered from real `/sys/class/block` — there is no safe, disposable real block device here to run `sfdisk` against without risking this sandbox's own real, live disks. The exact `sfdisk` script syntax these functions use was instead confirmed by hand against a scratch disk image file (sfdisk operates identically on a plain file as on a real block device, the same property `test/test_disk_image.c`'s own sfdisk-driving tests already rely on) — table creation, `--append` with and without a `size=` field, and the resulting `sfdisk -d`/`-J` dump all behaved exactly as documented above. Real end-to-end success-path verification needs a real installed system with a genuinely spare data disk (e.g. 192.168.15.95) — not attempted here, to avoid risking that box's own live role-assigned/formatted disks without first confirming a truly spare one exists.

Full regression sweep clean afterward: `test_disk_quota`, `test_storage_placement`, `test_backup_config`, `test_container_storage_migrate`, `test_system_backup`, `test_daemon`, `test_daemon_devices`, `test_web`, `test_hostauth`.

## Consequences

- `diskrole.c`/`diskformat.c` needed zero code changes — the entire feature landed by extending what `disk_enumerate()` reports and adding one new, narrowly-scoped module, exactly the "keep it simple" shape the user asked for on the immediately preceding design task (ADR-0157) and which was applied here too.
- The `DISK_ENUM_MAX` fix benefits every existing `disk_enumerate()` caller, not just this task's own new code — a real, previously-undiscovered silent-truncation gap on any host (real or dev) with enough block devices to exceed the old `64` cap.
- Real success-path verification of the three new `sfdisk`-invoking operations remains open against a real box with a genuinely spare disk — tracked the same way this project already tracks its other sandbox-only-partially-verified features (e.g. `clock_settime()`'s success path, ADR/CLAUDE.md environment notes), not as a silent gap.
