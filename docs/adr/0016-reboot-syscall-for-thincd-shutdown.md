# 0016 — thincd calls reboot(2) as PID 1, exposed via REST, SIGTERM/SIGINT default to poweroff

## Status

Accepted

## Context

Once a real install was up and reachable, the natural next question was "how do I shut this down or restart it?" — and the honest answer, checked directly, was: there was no way to do that cleanly. `thincd` handles `SIGTERM`/`SIGINT` by breaking its event loop and returning `0` from `main()` — but as PID 1 (the `--init-mode` boot path this phase already established), a plain `return 0` is exactly "init exited," which the kernel treats as fatal and panics on unconditionally (`Attempted to kill init!`), the identical failure mode already confirmed and accepted as harmless for `thinc-install` (a one-time, operator-supervised install run) but genuinely not acceptable for a live, unattended production system that the operator might reasonably want to power off or restart.

## Decision

`thincd` now calls the real `reboot(2)` syscall (via glibc's own wrapper — a wrapper exists, so ADR-0002's "raw syscalls where glibc has none" scope doesn't apply here) after its own cleanup, but **only when running as real PID 1** (`--init-mode`, the same flag this phase's boot chain already gates on). A dev/interactive `thincd` (every `test/*.c` invocation, and any operator running `build/thincd` directly) never reaches this code path at all — it returns normally exactly as it always has, regardless of what triggered the stop.

Two new REST endpoints, `POST /v1/system/shutdown` and `POST /v1/system/reboot` (API-first per ADR-0005 — `thincctl shutdown`/`reboot` are pure clients of these, nothing more), just record which `reboot(2)` argument to use (`RB_POWER_OFF` or `RB_AUTOBOOT`) and set the existing `g_stop` flag — the actual syscall happens in the same single place the event loop already exits through, whether that exit was triggered by a REST call or a plain signal. `SIGTERM`/`SIGINT` default to `RB_POWER_OFF` (unchanged signal *handling*, but no longer silently fatal under `--init-mode`) rather than distinguishing shutdown-vs-reboot by which signal arrives — this project has no established signal convention to build on (unlike, say, sysvinit's SIGINT-means-Ctrl-Alt-Del-reboot), and a plain, single safe default beats guessing at one.

## Consequences

- **A real, honestly-documented testing boundary**: the core mechanism — `reboot(2)` called from genuine PID 1 — was verified directly and empirically (a minimal standalone init booted via this exact kernel build, confirmed `reboot(RB_POWER_OFF)` produces a clean `ACPI: PM: Preparing to enter system sleep state S5` / `reboot: Power down`, and `RB_AUTOBOOT` a clean `reboot: Restarting system`, neither panicking) — but the *full* path (a real HTTP request reaching `thincd` inside a booted guest to trigger it) could not be exercised by this project's own QEMU test harness end to end: QEMU's `-netdev user` (SLIRP) networking does not route host-to-guest traffic to a guest's own self-configured static IP (only to addresses SLIRP itself hands out via its internal DHCP), which is exactly the addressing `thincd`'s `--bind=<ip>` (and `apply_static_ip()`, Phase 11 part 3) uses. This is a test-harness limitation, not a real-world one — bridged/routed networking (this project's actual deployment target, e.g. the user's own Proxmox setup) has no equivalent restriction, and the REST dispatch/`g_stop` mechanics either side of the syscall are unchanged, already-proven code paths (every existing daemon test already exercises them). Revisit if a future session sets up real bridged networking for the test harness.
- `thincd` has no ACPI power-button event handling (no `acpid`/`systemd-logind`-equivalent) — a hypervisor's own "ACPI shutdown" action (as opposed to a direct REST call or a delivered `SIGTERM`) will not trigger this path today. Explicitly out of scope for this change; the operator-facing answer today is `thincctl shutdown`/`reboot` (or the web dashboard), not the hypervisor's own power button.
- This is now the reference pattern for any future PID-1 lifecycle action this project adds (e.g. a future "apply an OS update, then reboot into it" flow) — go through `g_stop`/the single post-loop `reboot(2)` call, gated on `init_mode`, not a second exit path.
