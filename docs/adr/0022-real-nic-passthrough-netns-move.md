# 0022 — real network interface passthrough via direct netns move, with fd-anchored teardown

## Status

Accepted

## Context

The third and largest piece of the router use case (alongside ADR-0020/0021): "do we have an API that shows what hardware we have available on the host, and are we able to use that API to connect/disconnect hardware to containers?" — confirmed `GET /v1/devices` already covered PCI/USB char/block devices (ADR-0017), but a real network interface is fundamentally different: it has no `/dev` node at all, so `BPF_CGROUP_DEVICE` (the mechanism every other device grant uses) doesn't apply. The only real kernel primitive for "give a container a physical NIC" is moving the interface's netdev into the container's own network namespace — confirmed via kernel-source research to be fully generic (`rtnl_link_set_netns_pid()`/`dev_change_net_namespace()` have nothing veth-specific in them), even though this project's only prior use of it was for veth pairs.

Two genuinely hard correctness problems, both surfaced by trying to actually build and test this, not anticipated up front:

1. **Teardown is not symmetric with attach.** A netlink socket can only address interfaces visible in its own network namespace (confirmed: this is not a documented kernel restriction stated anywhere obvious, it's implicit in how `sk_net` is bound at socket-creation time and never re-evaluated). Once an interface is inside a container's netns, the daemon's own root-netns rtnl socket can no longer see it to move it back. Worse: if nothing keeps the container's netns alive past its last process exiting, the kernel auto-returns any real (non-`rtnl_link_ops`) interface to `init_net` **under a kernel-generated fallback name** (`devN`, confirmed via kernel-source research earlier in this session) — unrecoverable from the daemon's own perspective, since it doesn't know what `N` became.
2. **The kernel downs a link as part of moving it to a new namespace.** Confirmed directly, not assumed: an interface brought `up` in the root netns and then moved into a container's netns comes up on the other side administratively **down**. The reverse (bring up only after the move, from inside the target netns) is required. This was found empirically while building the verification test for this ADR (see below), not predicted by the design — a real, load-bearing correction to the implementation, not a documentation nit.

Confirmed with the user directly (via clarifying questions, given the size and risk of this piece) on two open points: (a) build full teardown correctness (a forked `setns()` helper + a held netns fd for the interface's whole attachment lifetime) rather than deferring it as a documented gap, and (b) since this dev sandbox has no real, physically-backed NIC visible in its own root network namespace (confirmed directly: `/sys/bus/pci/devices/0000:01:00.0`, a real `r8169` card, exists in PCI sysfs but has no corresponding entry in this LXC's own `/sys/class/net` — it belongs to a namespace this sandbox's own netns cannot see), verify the underlying kernel mechanism with a real, kernel-backed substitute (one end of a veth pair) rather than skip verification or fake it.

## Decision

**Discovery** (`daemon/src/device.c`): a third enumeration pass, `enumerate_net()`, walks `/sys/class/net` and emits a `"bus": "net"` entry (`id = "net:<ifname>"`) for each interface — but only ones whose resolved sysfs path does **not** contain `/virtual/net/`, the standard kernel convention that separates every software-created netdev (bridges, veths, dummy, tun/tap, loopback — including cix's own managed networks) from real, physically-backed hardware. This is a more precise discriminator than the name-based heuristic originally sketched (`lo`/`sit*`) — it correctly excludes *any* software interface, not just two hardcoded names. `enumerate_pci_one()`'s existing "no owned /dev node found" fallback placeholder is suppressed for PCI class `02xxxx` (network controller) devices, since those are now represented via their `net:` entry instead — when one exists. When it doesn't (the interface's netdev isn't visible in this netns at all, either because another container already holds it or, as in this dev sandbox, a nested environment simply can't see it), the device becomes invisible to `GET /v1/devices` entirely, neither as `net:` nor as the old `pci:` placeholder — a deliberate simplification: this endpoint reports actionable-right-now hardware, not a three-state PCI census. Exclusivity itself needs no separate tracking: an interface already moved into a running container's netns simply isn't visible in `/sys/class/net` from the daemon's own vantage point any more, the same visibility rule that drives the suppression above.

**Attach** (`src/container_net.c`, `container_net_host_attach_interfaces()`, parent side, called right after `ns_clone3()` returns the child's pid, alongside but independent of the existing veth path — no pipe/child coordination needed since a passthrough interface gets no rename and no address): opens `*out_netns_fd` on `/proc/<child_pid>/ns/net` *first*, before moving anything (callers must keep this open for the container's entire attachment lifetime — see Teardown). Moves each interface via `rtnl_link_set_netns_pid()`. Then, since bringing a link `up` before the move doesn't survive it, forks a short-lived helper that `setns()`s into `*out_netns_fd`, opens a *fresh* rtnl socket there (scoped to the target netns at its own creation), and brings each interface up from that vantage point.

**Teardown** (`container_net_teardown_interfaces()`, called from `registry_remove()`): the fd opened at attach time is what makes this safe even after the owning process has already exited — an open fd on `/proc/<pid>/ns/net` keeps that namespace (and everything still in it) alive for as long as the fd itself stays open, the same way a live process would. Moving the interface back out requires the same "briefly enter the target netns to get a socket scoped to it" dance, done in a forked helper (`setns()` is whole-process; isolating it in a throwaway child means the long-lived daemon's own netns is never at risk) — this time moving *out*, via a new `rtnl_link_set_netns_fd()` primitive (`netplane/src/rtnetlink.c`, `IFLA_NET_NS_FD` instead of `IFLA_NET_NS_PID`, needed because the owning process may no longer exist to name by pid). No rename is needed on the way back — since the interface was never renamed on the way in, moving it back under the same real kernel name is enough. `registry_entry` gained an `interfaces[]` name mirror (`daemon/include/registry.h`) so `registry_remove()` knows which names to hand back.

**REST/CLI**: `POST /v1/containers` gains an `"interfaces": ["wlan0"]` array (bare real names, validated against `GET /v1/devices`' own `net:` entries — unknown or already-claimed is a 400, the same shape `devices` already has). `GET`/list responses gain an `"interfaces"` array. CLI: repeatable `run --interface=IFNAME`, matching `--device=ID`'s own shape.

## Consequences

- Verified two ways, deliberately not conflated: (1) `daemon/src/device.c`'s discovery logic was checked directly against this dev sandbox's own real hardware (a real PCI NIC, confirmed present in `/sys/bus/pci/devices` but absent from this netns's `/sys/class/net` — the suppression logic was confirmed to correctly hide the old placeholder without a `net:` entry appearing, rather than assumed correct). (2) The actual kernel mechanism (move in, bring up, move back) was proven end-to-end in `test/test_container_net.c` using a real, kernel-backed veth pair's own two ends as a stand-in for "some named interface not currently in a container's netns" — legitimate given `rtnl_link_set_netns_pid()`/`rtnl_link_set_netns_fd()` are confirmed fully generic, not veth-specific. The test confirms: the interface disappears from the root netns and reappears, correctly, inside the container's own netns under its real unrenamed name and administratively up; after the container exits and `container_net_teardown_interfaces()` runs, it reappears in the root netns under that same original name, not a kernel fallback. 3 consecutive clean runs; full regression sweep (every other test in the suite) re-run clean.
- Two real bugs found and fixed *during* writing that verification, not before: the test's own first attempt at "check visibility inside the target netns" used `/sys/class/net`, which is captured at sysfs mount time and does not dynamically reflect a later `setns()` — fixed by switching the check to `SIOCGIFFLAGS` via a socket created *after* `setns()` (dynamically netns-scoped, unlike sysfs). Separately, and more importantly, this same investigation is what surfaced the "kernel downs a link on netns move" finding above — the original design (bring up before moving, based on an unconfirmed assumption about `NETDEV_MOVENS` preserving admin state) was wrong and had to be corrected in the actual shipped implementation, not just the test.
- No real, physically-backed NIC is reachable from this dev sandbox's own root netns at all (confirmed, not assumed) — genuine end-to-end hardware proof (a literal wireless card handed to a literal container) has not happened in this environment and can't, without either real deployment hardware or a QEMU boot harness with a passed-through NIC neither of which exist yet for this purpose. The mechanism itself is proven (see above); the literal hardware path is not, and is left as an explicit, known gap rather than silently assumed to work.
- Follow-up (Phase 12 part 9): what *is* provable without real hardware was added to `test/test_daemon_devices.c` — a real, kernel-backed veth pair proves `GET /v1/devices` never lists a software-created interface under `bus: "net"` (the `/virtual/net/` exclusion holds at the REST layer, not just unit-level in `device.c`), and that `POST /v1/containers` correctly 400s an `interfaces` entry naming that same veth. This is the precise boundary of what's testable here: negative/validation paths, proven; the positive "grant a real NIC, watch it work" path, still open per the paragraph above.
- `interfaces_netns_fd` is held open for a container's *entire* lifetime once any interface is attached (not just at teardown) — a real, small, permanent resource cost per interface-attached container, deliberately accepted: without it, a container that exits on its own (not via explicit `DELETE`) loses its interface to the kernel's own unrecoverable fallback-name path the instant its last process exits, before the daemon even has a chance to react.
