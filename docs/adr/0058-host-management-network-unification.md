# 0058 — the host's own management address becomes a real, API-managed network

## Status

Accepted

## Context

Raised directly by the user from real-world use of the fresh Phase 11 installer ISO on their own test VM: `thincd`'s own listen address was set up by `thinc-install.c`'s `apply_static_ip()` — a one-shot, GRUB-boot-parameter-driven `rtnetlink` call straight against the physical NIC, entirely outside the `network_def`/`POST /networks` model every *container*-facing network already used. It was invisible (`GET /networks` had no idea it existed), un-inspectable, and un-repointable without a reinstall. The user pushed back on this directly: the host's own management connectivity deserved the same first-class, API-managed treatment as everything else this platform manages, not a special-cased GRUB-only footgun.

Tracing the existing mechanism confirmed the fix was smaller than it first looked. A container-facing network's gateway address is already written directly onto the bridge device itself (`network.c`'s `rtnl_addr_add_ipv4()`, called with the bridge's own ifname), with physical NICs attached as pure L2 slave ports via `network_attach_interface()` carrying no IP of their own — exactly the shape a host management address needs. Reusing it, rather than inventing a second mechanism, is direct application of No Parallel Implementations.

A design question surfaced and was settled during this same discussion: does the host bind to a *physical NIC*, or to a *network*? Settled as the network — connectivity for a given network (a direct physical NIC attachment, or a network fed entirely by a container that owns the physical hardware itself, e.g. a WiFi-AP container bridging a passed-through wireless radio) is already fully general via the existing attach/detach mechanism, and orthogonal to where the host's own address lives. No host-level WiFi/wpa_supplicant-equivalent capability was needed to make this work — keeping this decision's scope to network-address unification only, not a much larger connectivity subsystem.

## Decision

**A reserved network named `management` (renamed from the original `mgmt`, ADR-0066), created at first boot from GRUB-supplied fields, replaces `apply_static_ip()`.** `thinc-install.c` gains a new `--interface=<name>` flag (alongside the existing `--disk=`/`--ip=`/`--prefix=`/`--gateway=`), naming the physical port to attach — a one-time bootstrap value only, freely correctable afterward via the API, so it doesn't need to be more robust than a typed-by-hand GRUB edit-prompt value. `thincd`'s own `main()` (not `boot_init()`, which stays purely about mounts + loopback — `apply_static_ip()`'s removal from it was the one real call-site change this required) creates `network_create("management", ...)`, attaches the named interface via the existing `network_attach_interface()`, and derives `g_bind_addr` from the network's own gateway address — all through mechanism that already existed for every other network.

**Two distinct "gateway" concepts, kept explicitly separate**: `network_def.gateway` (an address living on the bridge, containers' default route on that network — now also reused as the host's own bind address) is unrelated to the box's own *upstream* default route (the next-hop router this box's outbound traffic egresses through). GRUB's `--gateway=` flag continues to mean only the latter, feeding the existing `rtnl_route_add_default_ipv4()` call unchanged; the management network's own `gateway` field is populated from `--ip=`/`--prefix=` instead. Conflating these would silently break either host reachability or outbound routing — kept apart deliberately, in naming and in code.

**A new safety invariant this introduces, that never existed before**: prior to this change, no network ever carried a host-owned address, so deleting or detaching one could never cut off management access. Once the management network is an ordinary `network_def`, that becomes possible for the first time — a genuine new footgun, not a hypothetical one. `struct network_def` gains `is_management` (`network_set_management()`/`network_find_management()`, at most one network at a time); `network_delete()` and `network_detach_interface()` both gain an **unconditional** guard against it, refusing with `NETWORK_ERR_IS_MANAGEMENT` (`409`) — no override/force flag on either generic endpoint, deliberately. The only legitimate way to move `is_management` is a dedicated operation.

**A new, dedicated `daemon_config` resource** (`GET`/`PUT /v1/system/daemon-config`) owns the listen port and the management-network repoint operation — deliberately distinct from generic network CRUD, since either has a real side effect (a live listen-socket rebind) plain network endpoints were never meant to trigger. `management_network` is *not* stored a second time here: it's queried live from `network_find_management()`, `network.c`'s own one source of truth. Since `thincd` runs as real PID 1 on an installed system (ADR-0011), there is no "restart the daemon" to pick up a port or repoint change — the rebind is a live, in-process listen-socket operation: create + bind + listen the new socket, add it to `epoll` *before* tearing down the old one, so a failure rolls back to the still-working previous listener rather than ever leaving a gap.

## Consequences

- Verified via a real `test_installer` QEMU boot: the management network appears in `GET /v1/networks` after a fresh install with the named `--interface=` NIC attached, and `thincd` is reachable at the network's own gateway address exactly as `apply_static_ip()` produced before.
- `docs/api/openapi.yaml`/`docs/api/README.md` gain the `Network.is_management` field, the `409` refusal on `DELETE /networks/{name}` and `DELETE /networks/{name}/interfaces/{ifname}` while it's set, and the new `/system/daemon-config` resource.
- No CLI or web dashboard surface exists yet for `daemon-config` — a real, tracked gap (not a violation of the API-First Mandate, which only requires the REST endpoint to exist before any client uses it, not the reverse), inconsistent with how every other daemon capability in this project has shipped CLI+web alongside its REST endpoint.
- HTTP/HTTPS listener toggling (`http_enabled`/`https_enabled`/`https_port`) was deliberately *not* added to `daemon_config` in this same change — seeing it through required linking OpenSSL and a real non-blocking TLS accept/read/write path, its own separate, hard-to-reverse decision; see ADR-0059.
