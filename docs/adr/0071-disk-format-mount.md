# 0071 — Disk format + mount as a separate, explicitly-confirmed action

## Status

Accepted

## Context

Multi-disk management (`docs/roadmap/ROADMAP.md`) was designed in four phases: A (read-only enumeration, `GET /disks`), B (persisted role assignment, `GET`/`POST`/`DELETE /diskroles`), C (this ADR: format + mount), D (container-storage migration, not yet built). A and B shipped first because neither touches real disk content — this is the first phase in the feature that does, and the first genuinely destructive, hard-to-reverse operation this project has added to a resource it doesn't fully own the lifecycle of (compare `pki reset`, which is destructive but entirely self-contained state this daemon itself created).

Before writing any code, the user was asked directly how formatting should be triggered, given the risk: automatically as a side effect of role assignment, as a separate explicit action, or deferred (design only, no implementation yet). The user chose **separate explicit action** — the recommended option — over folding it into `diskrole create` or stopping short of building it.

A second, purely mechanical question came up during implementation: every existing async host job in this daemon (`pkg install`'s build container, ISO assembly, `pkg bootstrap --toolchain-url=`'s curl fetch, kernel/kanxeo hostbuild) forks a child that immediately `execve()`s exactly one external binary and never returns to this project's own C code. Format + mount needs two *sequential* steps — an external `mkfs.ext4` invocation, then a raw `mount(2)` syscall — and `execve()` irreversibly replaces its caller's entire process image, so there is no way to `execve()` for step one and still run step two afterward.

## Decision

**Role assignment and formatting stay two separate REST actions**, exactly as chosen: `POST /diskroles` (Phase B) only ever writes a small JSON record — never touches disk content — and `POST /disks/{disk_name}/format` (this phase) is the only path that ever calls `mkfs.ext4`. A disk with no assigned role cannot be formatted (`400`, `"assign one via POST /v1/diskroles first"`) — format is never allowed to run against a disk nothing has expressed intent for yet, keeping Phase B's own record meaningful rather than decorative.

**A second, independent confirmation layer inside the format request itself.** The request body must carry `confirm_disk_name`, and it must match the URL's own `disk_name` exactly, or the request is rejected before anything happens. This is deliberately redundant with "the operator already had to type the disk name once, in the URL" — the point is that a script or UI that constructs the URL programmatically (e.g. from a stale cached disk list) still has to independently supply the name again, so a single wrong variable can't silently target the wrong disk.

**The OS disk is rejected here too, re-checked live**, the same as Phase B — `disk.c`'s `is_os_disk` (resolved via a fresh `/proc/mounts` walk on every call, never cached) is checked before formatting exactly as it is before role assignment. This is not inherited automatically from the role check (a disk conceivably could have a role from before a re-partition changed what backs `CONTAINERS_DIR`) — `diskformat_start()` re-derives it independently.

**No interactive CLI confirmation prompt.** `kanxeoctl disks format NAME` sends the confirmation as part of the same request, matching this CLI's own existing `pki reset` precedent (also destructive, also no "are you sure?" prompt) — the request-body confirmation *is* the safety gate, not a second, CLI-only one.

**The forked job child does not `execve()` itself.** `daemon/src/diskformat.c`'s `diskformat_start()` forks a child that internally `fork()`s again — a grandchild that *does* `execve()` `mkfs.ext4` — waits for it, and only on a clean exit calls `mount(2)` directly before `_exit()`ing with a distinguishing code (`0` success, `1` `mkfs.ext4` failed, `2` `mkfs.ext4` succeeded but `mount(2)` failed). This mirrors `pkg.c`'s own `start_fetch_for()`, which already forks a grandchild per curl invocation for its sequential multi-source fetches — not a new pattern, an extension of an existing one to a case with a final non-`execve()` step. A plain `fork()` (no `CLONE_NEWNS`) shares the parent's mount namespace, so the `mount(2)` becomes visible daemon-wide the instant it succeeds — no namespace handling needed for this case, unlike container creation's own deliberate `CLONE_NEWNS` isolation.

**Async, single-job, same shape as every other potentially-slow host operation.** `register_disk_format_pidfd()`/`handle_disk_format_event()` in `daemon/src/main.c` mirror `register_iso_assemble_pidfd()`/`handle_iso_assemble_event()` exactly — `sys_pidfd_open()`, epoll registration with a new `CONN_DISK_FORMAT` conn kind, reap via `waitpid()` on the pidfd's `EPOLLIN`. Only one format job may run daemon-wide at a time (`409` otherwise) — the same v1 constraint `pkg install`/hostbuild/ISO assembly/bootstrap fetch already have, not a new restriction invented for this feature.

**Mounted at `<data-dir>/disks/<disk_name>`, never `CONTAINERS_DIR` itself.** Phase D (container-storage migration) is the still-unbuilt mechanism that would actually move container storage onto a disk mounted this way — Phase C's job is only to make the filesystem exist and be mounted somewhere stable, not to wire it into anything yet.

**`mke2fs`/`mkfs.ext4` is staged into the control-plane squashfs** (`image/src/mkbootroot.c`'s `shelled_bins[]`/`shelled_bin_libs[]`, `DISKFORMAT_MKFS_EXT4_BIN "/usr/sbin/mkfs.ext4"`) — a real gap closed here, not present before this phase. `test_image_fixture_copy_file()`'s plain `open()`/`read()`/`write()` transparently follows the host's own `mkfs.ext4` → `mke2fs` symlink, landing the real `mke2fs` binary content at the expected path with no separate `mke2fs` copy needed. Four new shared libraries (`libext2fs.so.2`, `libblkid.so.1`, `libuuid.so.1`, `libe2p.so.2`) were added; `libcom_err.so.2` was already staged for curl's own krb5 dependency.

## Consequences

- Purely additive: a box that never calls `POST /disks/{name}/format` behaves exactly as before this phase.
- **Not locally, empirically verified the way every other feature this project has built has been.** This dev/build sandbox has no loop devices at all (`CLAUDE.md`'s own long-standing documented constraint) and every real block device visible here belongs to the shared underlying Proxmox host, not to this session — none are safe or authorized `mkfs`/`mount` targets. The code was written and reviewed carefully against this ADR's own reasoning and the exact process-tree/mount-namespace behavior described above, but real verification needs a genuinely spare disk on a real target box (e.g. 192.168.15.95) and has not yet happened as of this ADR.
- Phase D (container-storage migration onto a disk formatted this way) remains unbuilt and unscoped beyond "queued next" — this ADR does not attempt to design it.
- `GET /disks/{disk_name}/format`'s "no job has ever run for this disk" vs. "a job ran for a different disk" distinction means a status check can never accidentally report someone else's disk's outcome, but it also means job history is not retained per-disk across daemon restarts (the same "in-flight job state is simply lost on restart" posture every other async job in this daemon already has) — an operator polling across a daemon restart during a long format would see `"none"` and have to infer completion from `GET /disks/{disk_name}/format`'s absence of a `mount_path`... actually from whether the disk is genuinely mounted (not currently surfaced by any endpoint) rather than from job status. A future "is this disk currently mounted" signal (plausibly part of Phase D) would close that gap; not addressed here.
