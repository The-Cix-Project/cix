# 0172 — hostapd rebuilt on real upstream + curated OpenWrt patches (replacing task #845's plain recipe); two real perl.recipe TCC gaps found and fixed along the way

## Status

Accepted

## Context

Issue #25, raised directly by the user: build hostapd from the **original upstream w1.fi source**, never a distro-repackaged fork, with real patches layered on top for maximum AP flexibility — the OpenWrt project's own well-maintained hostapd patch series specifically called out, plus a brief survey of what else (Debian) is commonly carried. Feeds into issue #30 (a real `ar-1` wireless-AP example container on 192.168.15.95, using the `wifi_dongle` device mapping already created there, vendor:product `2357:012e`).

`recipes/package/hostapd/2.11/build.sh` already existed, committed in `c9926c3` ("Audit every recipe for the ambient-gcc-contamination risk", task #845) — a plain, unpatched-upstream build (`CONFIG_IEEE80211W`/`CONFIG_SAE` added to `defconfig`, real system `libnl-3`/`libnl-genl-3`/`libssl`/`libcrypto` copied from the build container's own toolchain), verified working at the time but never carrying any of the OpenWrt patches issue #25 explicitly asked for — that task's own scope was a mechanical audit for missing `CC=tcc` pins across every recipe, not this issue's patch-curation ask. This ADR's own investigation started from scratch without first checking that history (a real process lapse, caught only via `git log` after the fact) and replaces that file outright rather than editing around it — recorded here so the "why does this look totally different from before" question has an answer, per One Source of Truth.

## Decision

**hostapd**: real upstream 2.11 (`w1.fi/releases/hostapd-2.11.tar.gz`, checksum-verified) with 24 patches applied — 23 individually read and selected from OpenWrt's own 59-patch series (not filename/header-matched, which produces real false negatives; the other 7 candidates that applied cleanly were dropped as genuinely OpenWrt-infra-coupled: ubus/ucode/procd-ujail-specific, netifd-VLAN-bridge-delegation-specific, an OpenWrt build-variant split thinC has no equivalent of, or — one case — a revert of a real upstream DoS fix as an mt7915-driver-specific workaround thinC's own generic hardware doesn't need) plus one real CVE fix (`CVE-2024-5290`, only load OpenSSL "engine" `.so` files from a trusted path) sourced from Debian's own `wpa` package. Full patch-by-patch rationale lives in the recipe's own header comment, not repeated here.

Built against **OpenSSL**, not OpenWrt's own mbedtls port — thincd itself already links OpenSSL, confirmed TCC-compatible; mbedtls exists in OpenWrt's stack purely for embedded-router flash-size reasons that don't apply here, and adding a second crypto library for no reason would be a real parallel-implementation. **libnl-tiny** (OpenWrt's own small, dependency-free nl80211/genl library) is vendored directly into the recipe's tarball and built as a small `.so` alongside hostapd, rather than adding a new, heavier `libnl3` package dependency thinC has never needed before — one small, well-justified compat patch applied to it (`IFNAMSIZ` redefinition; TCC treats any macro redefinition as a hard error under `-Werror`, GCC only warns and only for a genuinely different value).

TCC-by-default confirmed, not assumed: hostapd itself needed exactly one toolwrap fix (`-MMD` → `-MD`, hostapd's own `src/build.rules` hardcodes the GCC/Clang-only spelling TCC doesn't support). No Tier-3 exception needed.

**Two separate, real, previously-unverified TCC gaps found in `perl.recipe`** while proving the `perl → openssl → hostapd` dependency chain through the real pkgbuild pipeline (task #845's own comment on that recipe already flagged it as "not yet rebuild-verified... flagged honestly rather than assumed" — this is that verification):
1. `perl.h`'s `PERL_DIAG_STR_(x)` macro expands to a **parenthesized** string-literal concatenation, `("" x "")`, used as a `char[]` array initializer in `dquote.c`. GCC/Clang accept a parenthesized string-literal expression there; TCC's stricter array-initializer parser doesn't ("character array initializer must be a literal, optionally enclosed in braces"). Confirmed via two minimal, isolated probes (with/without the parens). Fixed with a targeted `sed` against the extracted source, matching this project's own established convention for a single-line third-party compat fix (m4's gnulib fix, squashfs-tools' `-Dlinux=1` fix).
2. `hints/linux.sh` sets `ccdlflags` to `-E`/`-Wl,-E` (the traditional `ld` shorthand for `--export-dynamic`) — TCC's linker frontend doesn't recognize that spelling at all. This one is genuinely load-bearing, not a flag to strip: doing so let the link succeed but broke every dynamically-loaded XS module at runtime (`Cwd.so: undefined symbol: Perl_croak_nocontext`), confirmed the hard way before finding the real fix. TCC does support the underlying capability, just as `-rdynamic` (`tcc --help`) — fixed with a thin `cc` wrapper translating the flag, matching `chrony.recipe`'s own established toolwrap pattern. Verified end-to-end, not just "link succeeded": `use Cwd`/`use POSIX` both load their real `.so` and run correctly.

**A real bug found in this ADR's own hostapd recipe during verification, not shipped and discovered later**: `pkg_build()`'s `cd hostapd` (unlike the already-correctly-subshelled libnl-tiny step) leaked into `pkg_install()`, since both functions run in the same shell session (`daemon/src/pkg.c`'s own sourcing contract) — `pkg_install()`'s relative paths then resolved one directory too deep ("cp: cannot stat 'hostapd/hostapd': Not a directory", since the leaked CWD already *was* `hostapd/`, and its own built binary is a file, not a directory, so appending another `/hostapd` onto it isn't valid). Fixed by wrapping the whole hostapd build step in a subshell, matching the pattern already used correctly for libnl-tiny.

## Consequences

- `recipes/package/hostapd/2.11/build.sh` — full rewrite, real upstream + 24 curated patches + vendored libnl-tiny + OpenSSL backend; replaces the prior plain-upstream version from task #845.
- `recipes/package/perl/5.40.1/build.sh` — `pkg_build()` gains the `PERL_DIAG_STR_` sed fix and a toolwrap translating `-E`/`-Wl,-E` to `-rdynamic`; `-Dcc=tcc` becomes `-Dcc=/build/toolwrap/tcc-perl`.
- **Verified through the real `thincd` pkgbuild pipeline, not just manual reproduction**: a scratch daemon's own `pkg install --name=hostapd` (via its real `openssl`→`perl` dependency chain) genuinely built and installed all three packages; the merged image rootfs was inspected directly and confirmed to contain a real, correctly-linked, running `hostapd v2.11` binary alongside `libnl-tiny.so`/`libssl.so.3`/`libcrypto.so.3`.
- The assembled hostapd source tarball is hosted at `http://192.168.15.31:8920/hostapd-2.11.tarball` (this sandbox's own already-running scratch LAN server, the same one glauth's own tarball has used since an earlier session) — an ephemeral, session-scoped location by design (matches `glauth.recipe`'s own precedent: "neither URL was ever meant to be a permanent artifact home... whoever re-serves this next should do the same").
- Issue #25 is closed by this ADR. Issue #30 (the real `ar-1` example container) becomes actionable now that the package itself is proven; it needs real hardware access on 192.168.15.95 and is tracked separately.
