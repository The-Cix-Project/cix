# 0167 — `POST /v1/containers` gains a real `env` field, separate from `files[]`'s `{{SECRET:KEY}}` substitution

## Status

Accepted

## Context

Every container has always been created with a hardcoded empty environment (`spec.envp` was a fixed `{ NULL }` in `daemon/src/main.c`'s `create_container_from_body()`) — `envp` itself already existed on `struct container_spec` (`include/container.h`) and was already exercised internally by `pkg.c`'s own build-sandbox spec construction (e.g. `PKG_DESTDIR`, `PATH`, `HOME`), but POST /v1/containers never exposed any way for an operator to set real environment variables on an ordinary container.

This came up directly while discussing how a container's own config files get authored (`files[]`, ADR-0151's `{{SECRET:KEY}}` recipe-apply substitution). The two mechanisms are easy to conflate but operate at different layers: `{{SECRET:KEY}}` is a one-time, server-side text substitution applied when a *recipe* is rendered into a create request — it produces baked `files[]` content indistinguishable from hand-typed text, with no runtime presence at all once the container exists. A real environment variable is a live `execve()`-time value, read by the container's own running code, refreshed on every process start — the same distinction Docker itself draws: `docker run -e KEY=VALUE` only ever injects real env vars into `execve()`'s envp, and turning those into a rendered config file is always an entrypoint-script convention (`envsubst < template > /etc/app.conf`), never a platform feature. Docker has no built-in config-templating mechanism at all. thinC's own recipe substitution already fills that role at the `files[]` layer; conflating it with `env` would just be reinventing the same capability twice at two different layers — the exact "No Parallel Implementations" maxim this file's own root CLAUDE.md holds everything to.

## Decision

Add a real `env` field to `POST /v1/containers`, `struct registry_entry`, and every surface that already offers `sysctls` (the closest existing precedent: an opt-in, bounded, string-keyed map):

- **Wire shape**: a JSON object, `{"KEY": "VALUE", ...}` (not an array of `"KEY=VALUE"` strings, despite `spec.envp`'s own execve()-ready shape being exactly that) — env vars are semantically unordered key-value data, the same reasoning `sysctls` already uses an object for; an array-of-strings would mirror `cmd`'s own shape but `cmd` is genuinely ordered/positional in a way env is not.
- **Bounds**: `CONTAINER_MAX_ENV` 32 entries, `CONTAINER_ENV_KEY_MAX` 128, `CONTAINER_ENV_VALUE_MAX` 384 (`include/container.h`) — same "generous fixed bound" reasoning every other `CONTAINER_MAX_*` constant already documents.
- **Key validation**: POSIX-portable environment variable name rules (letters/digits/underscore, not starting with a digit; `400` otherwise) — real enforcement, not cosmetic, since an unsafe key (e.g. containing `=`) would corrupt the `"KEY=VALUE"` boundary both the execve()-time render and `registry_create()`'s own split-back-into-key/value (for echo) rely on.
- **No spec-level struct duplication**: `container_spec` gains no new field beyond the `envp` it already had — `create_container_from_body()` renders the validated `"env"` JSON object directly into `envp`'s existing flat, NULL-terminated `"KEY=VALUE"` shape (mirroring how `argv_buf` is built from `cmd`). `registry_create()` recovers the structured `{key, value}` form for `struct registry_entry.env[]`/`GET` echo-back by splitting each `spec->envp[i]` string on its first `=` — safe and unambiguous, since key validation already guarantees no `=` inside a key. This keeps envp as the one source of truth at create time, rather than inventing a second, redundant key/value representation that `container_create()`'s own `execve()` call would never actually read.
- **No implicit inheritance**: a container gets *only* the env vars explicitly given, never a copy of `thincd`'s own process environment — matching `docker run`'s own default and this project's existing "opt-in" posture (`ip_forward`, `sysctls`, `interfaces` are all opt-in the same way).
- **Persistence**: `env` survives exactly like `cmd`/`sysctls`/`files` already do, via the existing `restart: "always"` create-request replay mechanism (ADR-0030/ADR-0100) — no separate persistence work needed.

## Consequences

- `include/container.h`, `daemon/include/registry.h`, `daemon/src/registry.c`, `daemon/src/main.c` — new field, validation, copy-in, JSON echo. `cli/src/main.c` gains `run --env=KEY=VALUE` (repeatable), mirroring `--sysctl=KEY=VALUE`. `web/index.html`/`web/app.js` gain a semicolon-separated `env` input on the run form and an "Environment variables" table on the container-detail view, mirroring the existing sysctls treatment.
- `docs/api/openapi.yaml` and `docs/api/README.md` updated together (the latter's existing `sysctls` example was also corrected in the same change — it showed a stale array-of-`{key,value}` shape that no longer matches the real object-shaped wire format; a second, independent doc-drift instance of exactly the kind the project's own Documentation Map was written to prevent). `docs/guides/cli-reference.md`'s `run` flag listing updated too.
- Verified live against a real, freshly-started `thincd` (not just compiled): a minimal fixture image running a small env-dumping binary confirmed via `capture_output` that only the requested variables reach the container's real process environment (no daemon-environment leakage), that `GET /containers/{name}` echoes them back correctly as an object, that invalid keys/non-object bodies are rejected with `400`, and that omitting `env` entirely is a byte-for-byte no-regression (empty envp, clean exit, same as before this change). The CLI's `--env=` flag and the web dashboard's create-form field were both verified the same way (CLI via a live `inspect`; web via a real headless-Chromium session against a live daemon). `sudo ./build/test_daemon`, `test_container_files`, `test_container_recipe`, and `test_cli` all still pass unmodified, confirming no regression to existing container-creation paths.
- No config-templating engine was built, and none is planned as a consequence of this field — `{{SECRET:KEY}}` (ADR-0151) remains the one mechanism for baking secrets/values into `files[]` content at recipe-apply time; `env` is deliberately just the real runtime primitive Docker itself also stops at, not a rendering system layered on top.
