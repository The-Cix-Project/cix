# 0096 — pkg fetch failures now capture curl's own real error text

## Status

Accepted

## Context

`start_fetch_for()`'s curl child has always run with only its exit status observable by `pkg_fetch_completed()` — `e->error` on a failed fetch was a bare `"fetch failed (curl exit status %d)"`, with curl's own `-S` stderr text (the only thing that can tell "unsupported protocol" apart from a DNS failure, a TLS failure, or an HTTP error status) discarded entirely, inherited into whatever fd the daemon process itself happened to have open for its own stdout/stderr and never captured anywhere retrievable.

This surfaced as a real, live blocker while redeploying a `cix` hostbuild during this session: a fetch against this project's own self-hosted gitea instance failed with `curl exit status 1` and nothing else, with no way to determine why — the same URL fetched cleanly from an unrelated machine, ruling out the source itself. Reaching for the established LAN-serve deploy workaround (re-serving the tarball over the LAN, documented in `docs/guides/remote-development.md` for a different, real problem: a fresh minimal install having no SSH/general shell) was explicitly rejected as the wrong move here — it would have unblocked the deploy without ever explaining the fetch failure, leaving the same opaque gap for the next person (or the next fetch) to hit again. The real fix is closing the diagnostic gap itself.

The build path already solved the equivalent problem for a recipe's build script (ADR-0087's incremental, epoll-drained output pipe) — but that machinery exists specifically because a build's own output can run to megabytes over many minutes, and a plain pipe's 64KB kernel buffer will deadlock a build that isn't drained while still running. curl's own `-S` error text is always a handful of short lines, produced once, after curl has already exited by the time anything tries to read it — none of the deadlock risk the build path was built to avoid applies here, so reusing that same epoll-registration machinery (which would also mean threading a new fd out of `start_fetch_for()`/`pkg_hostbuild_start()`/`pkg_install_start()`/the `pkg update-all` path and registering it across every one of main.c's five separate call sites) would be a disproportionate, parallel-implementation-shaped solution to a much smaller problem.

## Decision

`start_fetch_for()`'s per-source curl invocation now pipes its own stderr through a `pipe2(..., O_CLOEXEC)` pair: the grandchild `dup2()`s the write end onto its own `STDERR_FILENO` before `execve()`; the outer fetch child (already blocking on `waitpid()` for each source in sequence) synchronously reads whatever curl wrote back on a nonzero exit and writes it to a small, fixed-path sidecar file (`fetch_error_sidecar_path()`, `<sources-dir>/.fetcherr-<name>`) — a single `read()` call is sufficient since curl has already exited and closed its own write-end reference by the time the parent reads, so there is no partial-data or deadlock concern to design around, unlike the build path's still-running, long-lived output. `pkg_fetch_completed()`, running later in the real daemon process once the async job's exit status arrives, reads this sidecar file back (bounded to 512 bytes, trailing newline stripped), unlinks it, and folds it into both `e->error` (`"fetch failed (curl exit status %d): <curl's own text>"`) and a new `logstore_write()` call — matching the same "real diagnostic text, not just a category" bar the build-output and container-diag-pipe paths already meet, and giving this fetch-failure path an entry in the consolidated log store (`GET /system/logs`) for the first time, where before it had none. `pipe2()`/`open()` failures anywhere in this new path fail safe: the fetch still completes exactly as it did before this change, just without an enriched message — diagnostics are never a reason to fail a fetch that otherwise succeeded, and were never a reason to fail one that otherwise failed either.

## Consequences

- Directly unblocked the `cix` v1.7.0 redeploy this session: the real curl error (see the deploy notes / CHANGELOG entry for this phase for what it actually said) was immediately visible instead of a bare, undiagnosable exit code.
- Every future pkg fetch failure (a bad recipe URL, an expired token, a real network/TLS problem, or another instance of the unresolved curl-vs-specific-redirect quirk documented in `CLAUDE.md`'s own environment notes) now reports curl's own real reason through both `pkg ls`'s `error` column and the log store, closing a genuine, previously-silent diagnostic gap rather than working around any one instance of it.
- Verified via the existing `test_pkg` fixture (unaffected — it never exercises a real network fetch, so the new capture path is exercised only on the success/no-pipe-data branch there) plus a full regression sweep (`test_daemon`, `test_cli`, `test_dns`, `test_system_update`); no new dedicated fetch-failure test was added in this pass, since reproducing a real curl stderr failure deterministically in the existing sandboxed test harness (no real network egress) would need a fake failing HTTP server fixture this pass didn't build — a real, acknowledged gap, not silently glossed over.
