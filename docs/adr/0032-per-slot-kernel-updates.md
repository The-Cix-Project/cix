# 0032 — per-slot kernel files, extending POST /system/update to cover bzImage

## Status

Accepted

## Context

`POST /system/update` (Phase 16, ADR-0031) writes a fresh root squashfs onto the inactive A/B slot but never touches the kernel — confirmed directly: both slot A's and slot B's loader entries, including the one `do_system_update()` itself generates, hardcode the identical `linux /thinc-bzImage` line. There is exactly one kernel file on a running system, shared by both slots. ADR-0014 itself already named kernel updates as a target for its own "write to the inactive slot" pattern ("the reference pattern for any future 'the OS itself needs to change' story (**kernel updates**, thincd binary updates)") — Phase 16 only delivered the second half. Raised directly by the user immediately after Phase 16 shipped, once they understood `/system/update` didn't cover the kernel: overwriting the one shared `thinc-bzImage` file in place to deliver a kernel update would corrupt whichever slot is *currently* booted too, exactly the in-place-modification risk ADR-0014 exists to prevent.

## Decision

**The kernel becomes per-slot, the same way the root already is: `thinc-bzImage-a`/`thinc-bzImage-b` on the ESP, never a shared filename.** Each loader entry's `linux` line now references its own slot's file. This is the only way a kernel update can honor ADR-0014's own rule — write only to the inactive slot, never touch what's live — the same reason root has two partitions instead of one.

**Both slots' kernel files are pre-staged identically at install time (`thinc-install.c`'s `populate_esp()`), unlike root B's own deliberate emptiness.** Root B stays genuinely empty until the first real update ever writes there, and that emptiness is meaningful — a real payload, nothing to duplicate for free, and "empty until written" is itself the honest state. A kernel is different: it's small (~9MB), and there is nothing meaningful about slot B lacking a valid kernel file before its first update — it would only produce a real, confusing gotcha (an operator's very first *root-only* update to slot B failing for a reason that has nothing to do with what they asked to change, since the loader entry `do_system_update()` writes always references `thinc-bzImage-<slot>`, and that file has to already exist for a root-only call to have anything correct to point at). Duplicating a small, already-identical file at install time to remove an entire class of edge case is the disciplined choice here, not a shortcut — the two files are expected to diverge over time as each slot gets its own future kernel updates, exactly like root A and root B already do.

**`image_path` and `kernel_path` are independent request fields, both optional, at least one required.** Three real, independent use cases: a `thincd` security fix needs no new kernel; new hardware support (a new `CONFIG_X=y`) needs no new root; occasionally both change together. Requiring both on every call would force an operator to always transfer and re-validate a file they don't actually want to change. Both are validated — each against its own real, cheap, on-disk magic check — *before* either is written, so a bad `kernel_path` can never leave a good `image_path` half-applied, or vice versa.

**`kernel_path` is validated the same way `image_path` already is: a real magic check, not a trust-the-caller assumption.** Confirmed directly against the project's own real `build/bzImage`: byte offset `0x1FE` is `55 AA` (the x86 boot-sector signature) and offset `0x202` is `"HdrS"` (`struct setup_header`'s own magic) — the exact check real bootloaders (GRUB, syslinux) use to sanity-check a kernel image before loading it, chosen for the same reason squashfs's `"hsqs"` magic was: cheap, real, and turns a wrong-path-by-mistake into a clean `400` instead of a corrupted inactive slot.

**The kernel is written as a plain file onto the already-mounted ESP, not through `write_file_to_device()`'s raw-partition shape.** The ESP is a real vfat filesystem, already mounted read-write at `/boot` for the daemon's entire runtime (the same access the existing loader-entry write and `confirm_boot()`'s rename already rely on) — writing `/boot/thinc-bzImage-<slot>` is an ordinary `open(O_CREAT|O_TRUNC|O_WRONLY)`/write/`fsync`/close, genuinely different from a raw block device (which already exists, needs no `O_CREAT`). Rather than duplicate the read/write/`fsync` loop body for two callers with different `open()` flags, `write_file_to_device()` was split into a shared `copy_bytes(src_fd, dst_fd)` core plus two thin, flag-specific callers (`write_file_to_device()` unchanged in behavior, new `write_file_to_esp()`) — One Source of Truth for the actual copy logic, including the `fsync()`-before-success durability guarantee ADR-0031 already established, without pretending a device and a regular file are opened the same way.

## Consequences

- Verified inside a real QEMU guest (`test/test_boot_update.c`, extended): a combined root+kernel update writes both correctly; the resulting `thinc-bzImage-b` on the ESP is byte-exact against the source; the fresh loader entry's own `linux` line reads `/thinc-bzImage-b`, not the old shared name; `thinc-bzImage-a` is confirmed byte-unchanged throughout; a second, independent QEMU boot actually boots successfully from `thinc-bzImage-b` specifically — proof the per-slot resolution works, not just that bytes landed somewhere. Deliberately reuses the same real kernel bytes as both the initial slot-A kernel and the "new" `kernel_path` source (the same precedent `test_boot_ab.c` already established for reusing identical squashfs content across slots to prove the *selection mechanism*) rather than requiring a second, genuinely different, real bootable kernel build (~15-20 minutes) for what the test is actually trying to prove.
- `image/src/mkinstalleriso.c`'s own, unrelated `thinc-bzImage` reference (the installer media's own separate, one-time, GRUB-booted, single-kernel boot environment, ADR-0015) is untouched by this change — confirmed by grep across the whole repo before making any change, not assumed.
- The daemon still has no way to know *which* kernel is "better" beyond boot-counter success/failure — same posture root updates already have, and the same limitation ADR-0031 already accepted for root: verification is "does it boot and reach `confirm_boot()`," not any deeper content inspection.
- Both per-slot kernel files now permanently exist on the ESP from install time onward — a small, fixed, ~18MB combined footprint (two ~9MB copies) that was previously a single ~9MB file. Not itself a meaningful cost on a multi-hundred-MB ESP already sized for two kernels' worth of headroom in principle.
