# 0035 — portable toolchain artifact for pkg bootstrap, not just a live-host copy

## Status

Accepted

## Context

While answering how to get real, non-C, network-fetched software (gitea specifically) onto a thinC host, the user proposed building packages inside a real, durable build-toolchain container rather than depending on whatever host `thincd` happens to run on. Checking that proposal surfaced two real, live-confirmed bugs, not just a design gap:

**`pki ca bootstrap` (and, by the identical root cause, `pkg install`'s own fetch/verify/build path) is completely broken on any genuinely fresh thinC install.** Booted a fresh installed image and ran `pki ca bootstrap` on the real console: `pki: CA genpkey failed:` / HTTP 500. `thincd` shells out to `/usr/bin/openssl`/`/usr/bin/curl`/`/usr/bin/tar`/`/usr/bin/sha256sum`/`/usr/bin/cp`/`/bin/rm` (the grep-confirmed, authoritative list — not `docs/roadmap/ROADMAP.md`'s own partly-stale prose, which also mentions `dnsmasq`, something `thincd` itself never shells out to; `dnsmasq` runs inside operator-created containers), but `mkbootroot.c` never actually staged any of them onto the installed root. This stayed hidden because every test in this project's history runs `thincd` directly on this rich dev sandbox, never inside the genuinely minimal squashfs root real hardware boots.

**`pkg_seed_image_runtime()` — the function seeding `ld.so`/`libc.so.6`/`libtinfo.so.6` into every newly created image (ADR-0023) so anything installed into it can `execve()` at all — read from `/usr/lib/x86_64-linux-gnu/...`, but `mkbootroot.c` only ever writes those files to `/lib64/...`/`/lib/x86_64-linux-gnu/...` (no `/usr` prefix) on the installed root.** Confirmed by direct path comparison against `mkbootroot.c`'s own literal write paths, and confirmed the fix (drop the `/usr` prefix) is correct on both environments — this dev sandbox's own merged-`/usr` layout resolves `/lib64/ld-linux-x86-64.so.2` to the identical real file via symlink (checked with `readlink -f`), while a real install only ever has the no-`/usr`-prefix form. More fundamental than the PKI/pkg bug: this silently broke *every* `image create`, not just build tooling.

Separately, `pkg_bootstrap_build_image()`'s own existing mechanism — copying `gcc`/`make`/etc. live from whatever host `thincd` happens to be running on — has the exact same class of problem: correct on this rich dev sandbox, guaranteed empty on a real minimal install (confirmed: nothing under a fresh install's own `/usr` beyond `thincd`/`thincctl` and their bare runtime libs).

## Decision

**Fixed the two silent-breakage bugs directly** (small, surgical): `pkg_seed_image_runtime()`'s three source paths corrected; `mkbootroot.c` now stages the six real binaries `thincd` shells out to, plus each one's real shared-library closure (captured via real `ldd` on this build host), the same precedent `test_dns.c`'s own `DNSMASQ_LIBS[]` already established for a real, unmodified third-party binary with more dependencies than the bare `ld.so`+`libc` pair. One binary's own dependency ran one level deeper than expected — `openssl req -x509` additionally needed its default config file (`/usr/lib/ssl/openssl.cnf`, itself a symlink into `/etc/ssl/openssl.cnf` on this build host) — found by an actual `pki ca bootstrap` failing a second time after the binary itself was staged, not guessed at up front; `test_image_fixture_copy_file()`'s plain `open()`/`read()`/`write()` already dereferences symlinks transparently, so staging it landed the real config content as one ordinary file, no `/etc/ssl` symlink chain needed on the target at all.

**A real, portable, durable toolchain artifact replaces the live-host copy as the production path** — the user's actual ask, and the correct long-term fix for the same class of bug affecting `pkg_bootstrap_build_image()` itself. `test_image_fixture_stage_toolchain()` (extracted into `test/test_image_fixture.c` — already the established shared location both tests *and* `image/src/` build tools reuse) is the *one* place "what a toolchain needs" is defined: this build host's own `/usr/{include,lib,lib64,bin,libexec}` (wholesale, real `cp -a`), the compatibility symlinks a merged-`/usr` host needs, targeted extras found by an actual build failing (`/etc/alternatives`, `/usr/share/{bison,autoconf,perl}`, and now `/usr/local/go` — this sandbox's own real Go install, staged tolerantly so a future recipe *can* build Go packages like gitea, though no such recipe is proven by this ADR), standard `/dev` nodes, and a writable/sticky `/tmp`. Two consumers share it: `pkg_bootstrap_build_image()` (kept, now a thin wrapper — the dev/test-convenience fallback, unchanged behavior for the existing bare `POST /v1/pkg/bootstrap`) and the new `image/src/mktoolchainimage.c` (a standalone build-time tool, mirroring `mkbootroot.c`/`mkinstalleriso.c`'s own shape, that stages the same content into a squashfs — one real, portable file).

**Import via `unsquashfs -f -d`, not a mount.** This sandbox's own documented "no `/dev/loop*` at all" constraint rules out mounting; `unsquashfs` extracts a squashfs into a plain directory tree entirely in userspace, no loop device involved — the same "work at raw bytes / real userspace tooling, not mount" discipline this project already applies to disk-image assembly (`test_disk_image.c`'s own header comment). `unsquashfs` itself gets staged onto the control-plane root the same way Part 2's other binaries do.

**`POST /v1/pkg/bootstrap` gains an optional `toolchain_path` field — a local path, not an HTTP upload.** A real toolchain artifact is easily hundreds of MB; streaming it through this daemon's own hand-rolled HTTP server was never in scope, the same reasoning `/system/update`'s `image_path`/`kernel_path` already established (`HTTP_MAX_REQUEST_SIZE` is deliberately tiny, and the charter has no registry to plug into). The operator `scp`s the artifact onto the box themselves; `thincd` never becomes a file-transfer service. Omitting the field keeps today's exact bare-`POST` contract and behavior — zero regression to any existing test or usage.

**The build-time artifact tool is a separate, deliberately-manual step**, run occasionally on a real toolchain-having machine — the same "explicit one-time action, not part of the fast default `make` loop" posture `build/bzImage` itself already has (documented in `CLAUDE.md`'s own environment notes).

## Consequences

- Live-verified, not just unit-tested: booted a fresh installed image after both bug fixes and confirmed `pki ca bootstrap` now succeeds, printing a real, complete self-signed X.509 certificate — the exact operation that failed with HTTP 500 before this ADR's changes.
- `mkbootroot.c`'s new binary/library staging is unconditionally fatal on failure (unlike `firmware_dir`'s own tolerant, operator-opt-in precedent) — these binaries are required for `thincd`'s own core PKI/pkg functionality, not an extra; silently tolerating their absence is exactly the bug this closes.
- Gitea itself is **not** proven end-to-end by this ADR — Go module fetching under this system's network-less build constraint, any frontend-asset build step, and CGO/`sqlite` considerations are real, separate follow-up work once a known-good C recipe has proven the new toolchain-import mechanism itself.
- The live-copy fallback (`pkg_bootstrap_build_image()`) stays, not removed — dev/test convenience where reaching into the live host genuinely works, and zero-regression to every existing test that already relies on the bare `POST /v1/pkg/bootstrap` contract.
