# 0122 — pkg/ redesign Part 3: local build-artifact cache + plain-HTTP precompiled-artifact server

## Status

Accepted. Amended by [ADR-0279](0279-an-artifact-carries-its-own-approval.md): the artifact tier gains a second, independent gate — a minisign signature published beside the artifact — because `pkg_artifact_sha256=` is earned by the daemon at publish time and never reached git, so every host except the publisher rebuilt from source (#403). The two cache tiers here, and the recipe checksum as a git-tracked pin, are unchanged. Amended again by [ADR-0289](0289-a-hostbuild-package-is-consumed-from-the-cache-like-any-other.md): the local build-artifact cache no longer excludes a hostbuild from its **read** — that exclusion was reasoning about the hostbuild's *output* (harvested to `ARTIFACTS_DIR`, never merged into an image, still true) but sat on the read, so a hostbuild re-downloaded an artifact a prior fetch had already cached.

## Context

Part 3 of the five-part `pkg/` redesign (task #739/#768; Part 1 ADR-0120 renamed recipes to `build.sh` and fixed a backup bug, Part 2 ADR-0121 added a configurable recipe-sync repo). Every `pkg install` before this part always did a real network fetch of `pkg_source=` followed by a real compile inside the build container — correct, but wasteful: installing the identical `(name, version)` into a second image, or re-installing after an image is deleted, re-downloads and re-compiles from scratch every time, even though the exact same output was already produced once.

The design was worked through directly with the user, including a real course-correction mid-implementation: the first draft had the "network fetch of precompiled artifacts" tier reuse Part 2's own git-forge repo-sync mechanism, walking a `pkg/artifacts/` tree inside the same repo tarball recipes are pulled from. The user caught this immediately: that would mean an operator has to check compiled binaries into the same git repository as their recipes to make them fetchable — the exact "source contaminated with compiled output" problem git repositories are bad at (unbounded history growth, no real diffing of binary blobs, ever-growing clone size). The user's own framing, confirmed as final: two genuinely separate URLs — one for recipes (git, Part 2, text), one for a plain web server serving compiled binaries (never git) — with the recipe's own git-tracked checksum as the trust anchor, "a three-way validation": the recipe (git, versioned) declares the artifact's expected hash, the artifact server just serves bytes, and the daemon verifies the fetched bytes against the recipe's own checksum before ever trusting them.

## Decision

**Tier 1 — local build-artifact cache** (`daemon/src/pkg.c`'s `pkg_cache_*` functions, `<data-dir>/pkg/cache/<name>-<version>.tar.gz`): after every successful real build, `pkg_build_completed()` tars the build container's own `dest_dir` (`/build/pkg-dest`) into the cache, evicting least-recently-used entries first (`cache_evict_lru_until_fits()`, ordered by file mtime) if needed to stay under a single, real, always-enforced size cap (`PKG_CACHE_DEFAULT_MAX_BYTES` = 2 GiB, operator-configurable, `GET`/`PUT /v1/pkg/cache-config`) — "one combined cap," the user's own explicit choice over separate per-tier caps. A single artifact bigger than the whole configured cap is simply never cached rather than evicting everything else to fit it. `start_fetch_for()` checks `pkg_cache_has()` before ever forking a fetch subprocess; on a hit, `g_current_job_cache_hit` is set and the fetch child does nothing (`_exit(0)` immediately) instead of curling the recipe's real sources.

**Cache-hit install mechanism (the key implementation decision)**: rather than threading a new "already resolved, skip the container" code path through the existing async fetch→build→merge state machine (a real, tempting shortcut that would have meant either a signature change to `pkg_fetch_completed()` to expose a second kind of async chaining, or duplicating the dependency-queue-advance logic pkg_build_completed() already owns — both real risks to a heavily-relied-on pipeline, rejected under this project's own "No Regressions" maxim), a cache hit still spawns a real, unmodified build container. The one difference: `pkg_fetch_completed()` populates `dest_dir` directly from the cache (`pkg_cache_extract()`) instead of extracting a real source tarball, and the container's own command becomes a pure no-op (`:`) instead of `. /build/recipe.sh; ...` — by the time the container starts, its own upperdir already IS the finished package. Every downstream step (`pkg_build_completed()`'s `image_produce_new_version()` merge, dependency-queue chaining, upgrade tracking, `save_state()`) runs completely unchanged, for both a cache hit and a real build, with zero new control-flow branches in the dependency-queue logic itself. `pkg_cache_touch()` bumps a hit entry's own mtime so LRU eviction reflects genuine recency of use, not just insertion order.

**Tier 2 — plain-HTTP precompiled-artifact server** (`pkg_artifact_*` functions, `<data-dir>/pkg/artifact_config.json`, `GET`/`PUT /v1/pkg/artifact-config`): deliberately **not** git-forge-aware like Part 2's repo config — just a `base_url` + optional bearer `auth_token`, since this is a plain file server (a generic HTTP host, a forge's own release-assets/package-registry feature reached over plain HTTP, a peer cixd), never a git API. The computed fetch URL is `<base_url>/<name>-<version>.tar.gz` — the identical naming convention the local cache already uses. A recipe opts in explicitly via a new, optional `pkg_artifact_sha256=` field (`struct pkg_recipe`, `parse_recipe()`) — absent means "never try the artifact tier, always build from source," so none of the 67 existing recipes change behavior. When present, `start_fetch_for()`'s child (still the SAME forked child, still governed entirely by the single flag set before `fork()`) makes one best-effort curl attempt at the artifact URL *before* its own normal per-source loop, verifies the fetched file's sha256 against `recipe.artifact_sha256` (`pkg_run_capture_sha256()`, the exact same verify-before-trust primitive `pkg_source`/`pkg_sha256` already use), and only on success leaves a sentinel file behind and skips the real fetch entirely; on any failure (no server configured, 404, checksum mismatch) it silently falls through to the real per-source loop, unmodified. `pkg_fetch_completed()` checks for that sentinel file, promotes it into the real local cache (`pkg_cache_save_from_file()`) if present, and folds the job into the exact same cache-hit path described above — a verified artifact and a local cache hit are, from that point on, indistinguishable code paths.

**Two independently-configured URLs, confirmed with the user**: Part 2's `pkg_repo` (recipes, git-forge-aware, three explicit per-forge branches) and this part's `pkg_artifact` (binaries, one plain HTTP shape) are separate REST resources, separate CLI subcommand groups, separate persisted config files — never conflated into one "repo" concept, since they solve genuinely different problems with genuinely different trust models.

## Verification

Full clean rebuild (`-Wall -Werror`), zero warnings. New `test/test_pkg_cache.c`, a real end-to-end suite (real gcc compiles, real `curl` fetches, a real `python3 http.server` standing in for the artifact server): a fresh cache starts empty; a real install (real source fetch + real compile) populates it; a **second** install of the identical `(name, version)` into a different image succeeds via a genuine cache hit — proven by deleting the real source tarball first, so a real re-fetch would be physically impossible; `cache-config` get/set; LRU eviction under an artificially tiny cap, confirmed by checking the older entry's cache file is actually gone from disk afterward; `cache-clear`; and the full artifact-tier round trip — a recipe with a real `pkg_artifact_sha256` and a deliberately-broken `pkg_source` succeeds anyway (proving the artifact tier, not source, satisfied it), with the verified artifact then found promoted into the local cache. Full regression sweep (27 tests) all pass, including the pre-existing `test_pkg.c` (multi-source recipes, dependency chains, hostbuild, upgrades — all still exercising the unmodified real-build path with zero cache interference) and `test_system_backup.c`.

## Consequences

- Installing the same package into a second image, or reinstalling after deletion, is now instant and network-free once it's been built or fetched once anywhere on the host.
- An operator who wants precompiled distribution has to run two things: something serving recipes (any of Part 2's three forges) and a plain file server for artifacts — never the same one, by design.
- Sets up Part 4 (image recipes + image-artifact fetch), which is expected to reuse this same plain-HTTP-server-plus-checksum pattern for whole image rootfs artifacts, and Part 5 (rolling containers), which will trigger cache-populated reinstalls as its own update mechanism.
- `pkg_artifact_sha256=` is a new, purely optional recipe field — every recipe in this repository today is unaffected; adopting the artifact tier for any of them is a future, separate decision, not implied by this part.
