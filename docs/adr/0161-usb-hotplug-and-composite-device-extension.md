# 0161 — USB hotplug reaction + composite-device metadata (extends device.c/devicemap.c)

## Status

Proposed — a design for discussion, deliberately not implemented until explicitly requested. Requirements were gathered directly from the user via clarifying questions before this document was written; the user was explicit that the existing `device.c`/`devicemap.c` model is the right foundation ("our awesome device and device mapping") and should be extended, not replaced — the actual frustration is with standard distro (Debian/Ubuntu/Fedora) `udev`/`usbfs`-style handling, not this project's own code.

## Context

`device.c`'s `enumerate_usb()` already discovers every USB device fresh from `/sys/bus/usb/devices` on every call (`bus:device` numbers deliberately never used in the stable id — `usb:<vendor>:<product>:<serial-or-port>` — since they're reassigned on every replug; whole devices only, `usb_name_is_device()` already filters out per-interface sysfs subdirs like `"2-1:1.0"`). `devicemap.c` already persists named aliases (`exact` — one specific device's own `id`; `vendor_model` — matches any currently-present device with that vendor:product, tolerant of the mapped device being temporarily absent, `"present": false"` on `GET`). Passthrough is a real `BPF_CGROUP_DEVICE` program (`src/container_dev.c`), attached to the container's cgroup once at `clone3()` time (`CLONE_INTO_CGROUP`), with `/dev` nodes `mknod()`'d once, post-pivot, inside the child.

**Two real gaps, both confirmed by direct code reading, not assumption:**

1. **No hotplug reaction at all** — confirmed by a repo-wide grep (`uevent`/`hotplug`/`NETLINK_KOBJECT_UEVENT`: zero hits anywhere). A device that appears after a container was created simply isn't visible to that container, ever, until the container is recreated — `GET /devices` would show it on the next poll, but nothing *acts* on that.
2. **Container creation hard-fails on an unresolved device reference** — `create_container_from_body()` (`daemon/src/main.c:7623-7639`) treats a `devicemap_resolve()` call that finds the mapping but can't currently resolve it to a present device as `400 Bad Request` ("unknown, unassignable, or not-currently-present device"), explicitly by design (the comment at `main.c:7623-7629` states this is deliberate — "a real error here, not silently retried as a raw id"). **This means there is no way, today, to even define a container that wants a USB device before that device is physically plugged in** — a real prerequisite gap this ADR's own "live attach on hotplug" ask depends on closing, found only by reading the actual creation-time validation code, not visible from the ADR's own original framing.
3. **No live device attach/detach primitive exists at all**, manual or automatic — unlike networks (`POST`/`DELETE /v1/containers/{name}/networks[/...]`, ADR-0156), there is no `POST .../devices` for an already-running container. Automatic hotplug-driven attach needs this as its own foundation, the same two-layer shape ADR-0156 already established (a manual primitive first, automation calls it) — not a special hotplug-only code path.
4. **No per-interface (composite device) metadata** — confirmed by grep, `bInterfaceClass` appears nowhere in `device.c`. A device exposing multiple USB interfaces (e.g. combo HID+storage) is reported as one opaque whole-device entry today.

## Requirements (from the user directly)

- Extend `device.c`/`devicemap.c`, don't replace them — the two-layer discovery/alias model is the right foundation.
- Real hotplug reaction: when a device matching an already-configured devicemap appears, **live-attach it to an already-running container** that wants it (not just an event notification/webhook).
- Symmetric unplug reaction: **actively revoke** the grant and notify, not leave an inert grant in place.
- Composite devices: whole-device passthrough stays the model (no per-interface assignment to different containers), but `GET /devices` should clearly report every interface a composite device exposes (class/subclass/protocol) instead of staying opaque.
- Out of scope for now (explicitly not selected when offered): raw usbfs-style protocol access, USB storage auto-mount.

## Decision

This is the most novel of the three ADRs from this pass, genuinely spanning four separate new mechanisms — worth naming plainly rather than presenting as one flat decision. Ordered here from lowest-risk/most-certain to highest-risk/least-certain, deliberately (each phase should be able to ship and prove itself real before the next depends on it), and the single genuinely uncertain piece (phase D's live BPF program update) is called out explicitly as needing a real, empirical kernel-behavior check before any implementation commitment — not something to trust from documentation alone, matching this project's own repeated, hard-won lesson that a raw syscall-ABI mechanism (`struct epoll_event` packing, `clone3`'s own struct layout, and now potentially this) needs to be proven against the real kernel, not assumed correct from reading its man page.

### Phase A — composite-device interface metadata (additive, no passthrough change, no new mechanism at all)

`struct discovered_device` gains a small, fixed-size nested array — `struct usb_interface_info { int number; char class_hex[8]; char subclass_hex[8]; char protocol_hex[8]; } interfaces[USB_MAX_INTERFACES_REPORTED]` + `interface_count` — populated by `enumerate_usb_one()` reading `<devpath>/<devpath>:1.<N>/b{Interface,}{Class,SubClass,Protocol}` for each real interface subdirectory already being *skipped* by `usb_name_is_device()`'s own top-level walk (reused as the enumeration source, not a second directory walk). Purely descriptive — `GET /devices`'s existing whole-device entry now also shows what it's made of; `container_dev.c`'s own grant/mknod mechanism is completely unchanged, since the passthrough unit stays the whole device, exactly as the user confirmed. Real value on its own, independent of everything below — worth shipping first and separately.

### Phase B — a device grant a container wants but doesn't currently have (narrow, opt-in, the one behavior change here)

`POST /containers`' own `devices` array gains a per-entry optional shape — `{"id": "printer-map", "optional": true}` alongside the existing bare-string form (`"id"` shorthand, `optional` defaults `false`, preserving every existing caller's exact current behavior with zero opt-in required) — an `optional: true` entry that currently resolves to nothing is **not** a creation-time error; the container is created without that grant, and the reference itself (the raw id/devicemap name, not a resolved device) is persisted in the container's own definition (`containerdef.c`) for later. This is the one real, deliberate behavior change here, scoped as narrowly as possible (opt-in per entry, not a default-behavior flip) to respect "No Regressions" — real, useful on its own too (an operator can now at least define the intent and see it reflected on `GET`, even with phases C/D unimplemented, manually attaching later some other way).

### Phase C — real-time hotplug detection: a `NETLINK_KOBJECT_UEVENT` listener

A genuinely new pattern for this codebase, but a conceptually simple one — not `rtnetlink.c`'s synchronous open/request/close shape (never registered with epoll), but modeled on `start_kmsg_watch()`/`CONN_KMSG` (`daemon/src/main.c`): a persistent, async socket registered with the daemon's own epoll reactor once at startup, reading plain text datagrams — the same shape as the kmsg watcher this project already has and already trusts, not a new class of mechanism.

- `socket(AF_NETLINK, SOCK_RAW | SOCK_CLOEXEC, NETLINK_KOBJECT_UEVENT)`, bound to multicast group 1 (kernel uevents) — a new `start_uevent_watch()`, mirroring `start_kmsg_watch()`'s own init-time registration.
- A new `CONN_UEVENT` conn kind; `handle_uevent_event()` reads one datagram (a NUL-separated `KEY=VALUE` list — `ACTION=add|remove`, `SUBSYSTEM=usb`, `DEVPATH=...`), filters to `SUBSYSTEM=usb` and whole-device paths only (reusing `usb_name_is_device()`'s own existing filter logic against the trailing path component — an interface-level uevent for the same physical device is deliberately ignored, matching the whole-device passthrough model).
- On its own, before phase D exists, this phase can ship as pure logging/diagnostic visibility (`logstore_write()` on every relevant add/remove) — real, verifiable, zero interaction with any container's own live state yet, a genuine incremental proof point before phase D is ever attempted.

### Phase D — the live attach/detach primitive, and wiring phase C to it (the genuinely uncertain piece — needs empirical verification before commitment)

The same two-layer shape ADR-0156 already established for networks (a real, callable-by-hand REST primitive first; hotplug automation is just another caller of it, not a separate code path):

- **`POST /v1/containers/{name}/devices`** — `{"id": "..."}` (a real device id or devicemap name, resolved exactly like creation-time `devices` entries are). Updates the container's live cgroup `BPF_CGROUP_DEVICE` program and `mknod()`s the new `/dev` node directly into the running container's own view via `/proc/<pid>/root/dev/<name>` — the identical "reach into an already-running container's filesystem from the host side" mechanism ADR-0153's live file write already established and proved correct, reused rather than re-invented for the mknod half.
- **`DELETE /v1/containers/{name}/devices/{id}`** — reverse: updates the live BPF program to no longer allow this device, `unlink()`s the `/dev` node via the same `/proc/<pid>/root` path. Refuses (`409`) a device that was granted at creation time and is `optional: false` (mirrors ADR-0156's own "detach only ever removes a live attachment, never a create-time one" rule).
- Phase C's listener then calls this same in-process logic directly (not a real HTTP round-trip) on `add`/`remove` events, matching persisted `optional: true` references to running containers — the "live attach on hotplug" and "actively revoke on unplug" behaviors the user asked for.

**The one piece genuinely not safe to commit to from documentation alone**: updating a *live*, already-attached `BPF_CGROUP_DEVICE` program without a window where an already-granted, unrelated device becomes briefly ungranted. `bpf(BPF_PROG_ATTACH, ..., BPF_F_REPLACE, ...)` is the documented kernel mechanism for this, but `container_dev.c`'s own eBPF program is hand-assembled raw bytecode (not compiled via a verified toolchain), and this project has been burned before by trusting a raw kernel-ABI mechanism's documented behavior without a direct, empirical check (`struct epoll_event` packing under TCC, ADR-0008) — the same discipline applies here. **Before phase D is implemented, not as part of writing this ADR**: a small, standalone probe program should attach a `BPF_CGROUP_DEVICE` program to a real (test) cgroup, confirm a device is grantable, replace the program via `BPF_F_REPLACE` with a superset, and confirm the original device is *still* grantable throughout — proving the "no window" property directly rather than trusting the man page. If that probe finds a real gap, the fallback (build the new full device set as a fresh program and attach it, accepting a real, if brief, all-devices-off window during the swap) is a fully viable, simpler alternative already available — just a real, live tradeoff worth deciding with actual evidence, not guessing now.

## Open questions for discussion (deliberately not resolved unilaterally)

1. Phase B's behavior change (tolerating an unresolved `optional: true` device at creation time) is the one place this design touches existing, already-shipped container-creation validation — confirm the opt-in shape (`optional: true` per entry, bare-string entries unaffected) is the right way to introduce it, not some other mechanism (e.g. a container-wide flag instead of per-device).
2. Phase D's `BPF_F_REPLACE` question above — resolved by direct empirical testing before implementation, not by discussion alone, but flagging here so it's a known, tracked precondition rather than discovered mid-implementation.
3. Multiple containers referencing the same `optional: true` devicemap, with only one physical device available when it plugs in — first-match-wins? Explicit priority? Reject as ambiguous and grant neither? Not decided here.
4. Should a hotplug-driven live attach/detach be visible anywhere beyond the container's own `GET` (e.g. a log line, matching this project's own `logstore_write()` convention for other automatic/background actions) — almost certainly yes (phase C's own diagnostic logging already covers the detection side), but the exact message shape for phase D's own grant/revoke actions isn't designed yet.
5. Given the real span of this ADR (four phases, one with a genuine open technical risk), should phases A/B ship as their own, smaller, sooner deliverable independent of whether C/D are ever pursued — both are real, standalone value (composite-device visibility; the ability to at least declare optional device intent) even if hotplug automation itself turns out not to be worth pursuing once phase D's empirical check comes back.
