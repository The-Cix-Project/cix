# 0161 — USB hotplug reaction + composite-device metadata (extends device.c/devicemap.c)

## Status

Accepted — every open question resolved directly with the user (see "Resolved open questions" below), including Phase D's own empirical BPF verification. Phases A-D implemented together as one deliverable (task #884), not incrementally, per explicit user decision. The user was explicit that the existing `device.c`/`devicemap.c` model is the right foundation ("our awesome device and device mapping") and should be extended, not replaced — the actual frustration is with standard distro (Debian/Ubuntu/Fedora) `udev`/`usbfs`-style handling, not this project's own code.

## Context

`device.c`'s `enumerate_usb()` already discovers every USB device fresh from `/sys/bus/usb/devices` on every call (`bus:device` numbers deliberately never used in the stable id — `usb:<vendor>:<product>:<serial-or-port>` — since they're reassigned on every replug; whole devices only, `usb_name_is_device()` already filters out per-interface sysfs subdirs like `"2-1:1.0"`). `devicemap.c` already persists named aliases (`exact` — one specific device's own `id`; `vendor_model` — matches any currently-present device with that vendor:product, tolerant of the mapped device being temporarily absent, `"present": false"` on `GET`). Passthrough is a real `BPF_CGROUP_DEVICE` program (`src/container_dev.c`), attached to the container's cgroup once at `clone3()` time (`CLONE_INTO_CGROUP`), with `/dev` nodes `mknod()`'d once, post-pivot, inside the child.

**Two real gaps, both confirmed by direct code reading, not assumption:**

1. **No hotplug reaction at all** — confirmed by a repo-wide grep (`uevent`/`hotplug`/`NETLINK_KOBJECT_UEVENT`: zero hits anywhere). A device that appears after a container was created simply isn't visible to that container, ever, until the container is recreated — `GET /devices` would show it on the next poll, but nothing *acts* on that.
2. **Container creation hard-fails on an unresolved device reference** — `create_container_from_body()` (`daemon/src/main.c:7623-7639`) treats a `devicemap_resolve()` call that finds the mapping but can't currently resolve it to a present device as `400 Bad Request` ("unknown, unassignable, or not-currently-present device"), explicitly by design (the comment at `main.c:7623-7629` states this is deliberate — "a real error here, not silently retried as a raw id"). **This means there is no way, today, to even define a container that wants a USB device before that device is physically plugged in** — a real prerequisite gap this ADR's own "live attach on hotplug" ask depends on closing, found only by reading the actual creation-time validation code, not visible from the ADR's own original framing.
3. **No live device attach/detach primitive exists at all**, manual or automatic — unlike networks (`POST`/`DELETE /v1/containers/{name}/networks[/...]`, ADR-0156), there is no `POST .../devices` for an already-running container. Automatic hotplug-driven attach needs this as its own foundation, the same two-layer shape ADR-0156 already established (a manual primitive first, automation calls it) — not a special hotplug-only code path.
4. **No per-interface (composite device) metadata** — confirmed by grep, `bInterfaceClass` appears nowhere in `device.c`. A device exposing multiple USB interfaces (e.g. combo HID+storage) is reported as one opaque whole-device entry today.

## Requirements (from the user directly)

- Extend `device.c`/`devicemap.c`, don't replace them — the two-layer discovery/alias model is the right foundation.
- Real hotplug reaction: when a device matching an already-configured devicemap appears, **live-attach it to an already-running container** that wants it (not just an event notification/webhook).
- Symmetric unplug reaction: **actively revoke** the grant and notify, not leave an inert grant in place.
- Composite devices: whole-device passthrough stays the model (no per-interface assignment to different containers), but `GET /devices` should clearly report every interface a composite device exposes (class/subclass/protocol) instead of staying opaque.
- Out of scope for now (explicitly not selected when offered): raw usbfs-style protocol access, USB storage auto-mount.

## Decision

This is the most novel of the three ADRs from this pass, genuinely spanning four separate new mechanisms — worth naming plainly rather than presenting as one flat decision. Ordered here from lowest-risk/most-certain to highest-risk/least-certain, deliberately (each phase should be able to ship and prove itself real before the next depends on it). Phase D's live BPF program update was the one genuinely uncertain piece — rather than trusting documentation alone (this project's own repeated, hard-won lesson: `struct epoll_event` packing, `clone3`'s own struct layout, and now this, all needed proving against the real kernel, not just reading the man page), it was empirically tested directly (see "Phase D verification" below) *before* this document was finalized, not left as a deferred precondition — and the real result simplified the design below rather than just de-risking it.

### Phase A — composite-device interface metadata (additive, no passthrough change, no new mechanism at all)

`struct discovered_device` gains a small, fixed-size nested array — `struct usb_interface_info { int number; char class_hex[8]; char subclass_hex[8]; char protocol_hex[8]; } interfaces[USB_MAX_INTERFACES_REPORTED]` + `interface_count` — populated by `enumerate_usb_one()` reading `<devpath>/<devpath>:1.<N>/b{Interface,}{Class,SubClass,Protocol}` for each real interface subdirectory already being *skipped* by `usb_name_is_device()`'s own top-level walk (reused as the enumeration source, not a second directory walk). Purely descriptive — `GET /devices`'s existing whole-device entry now also shows what it's made of; `container_dev.c`'s own grant/mknod mechanism is completely unchanged, since the passthrough unit stays the whole device, exactly as the user confirmed. Real value in its own right, though shipped together with phases B-D below, not staged ahead of them (resolved — see "Resolved open questions").

### Phase B — a device grant a container wants but doesn't currently have (narrow, opt-in, the one behavior change here)

`POST /containers`' own `devices` array gains a per-entry optional shape — `{"id": "printer-map", "optional": true}` alongside the existing bare-string form (`"id"` shorthand, `optional` defaults `false`, preserving every existing caller's exact current behavior with zero opt-in required) — an `optional: true` entry that currently resolves to nothing is **not** a creation-time error; the container is created without that grant, and the reference itself (the raw id/devicemap name, not a resolved device) is persisted in the container's own definition (`containerdef.c`) for later. This is the one real, deliberate behavior change here, scoped as narrowly as possible (opt-in per entry, not a default-behavior flip) to respect "No Regressions."

### Phase C — real-time hotplug detection: a `NETLINK_KOBJECT_UEVENT` listener

A genuinely new pattern for this codebase, but a conceptually simple one — not `rtnetlink.c`'s synchronous open/request/close shape (never registered with epoll), but modeled on `start_kmsg_watch()`/`CONN_KMSG` (`daemon/src/main.c`): a persistent, async socket registered with the daemon's own epoll reactor once at startup, reading plain text datagrams — the same shape as the kmsg watcher this project already has and already trusts, not a new class of mechanism.

- `socket(AF_NETLINK, SOCK_RAW | SOCK_CLOEXEC, NETLINK_KOBJECT_UEVENT)`, bound to multicast group 1 (kernel uevents) — a new `start_uevent_watch()`, mirroring `start_kmsg_watch()`'s own init-time registration.
- A new `CONN_UEVENT` conn kind; `handle_uevent_event()` reads one datagram (a NUL-separated `KEY=VALUE` list — `ACTION=add|remove`, `SUBSYSTEM=usb`, `DEVPATH=...`), filters to `SUBSYSTEM=usb` and whole-device paths only (reusing `usb_name_is_device()`'s own existing filter logic against the trailing path component — an interface-level uevent for the same physical device is deliberately ignored, matching the whole-device passthrough model).
- Every relevant `add`/`remove` this listener acts on is logged via `logstore_write()` (resolved: yes, matching this project's own convention for other automatic/background actions — e.g. restart-timer firings, rolling-restart triggers), independent of phases A-D shipping together rather than incrementally — this is about live operational visibility, not staged rollout.

### Phase D — the live attach/detach primitive, and wiring phase C to it

**Empirically verified before writing this section, not designed from documentation alone** — see "Phase D verification" below for the real test and its results. The mechanism turned out simpler than the first draft of this document proposed: no `BPF_F_REPLACE`, no `BPF_F_ALLOW_MULTI`, no `replace_bpf_fd`, no change to `container_dev_bpf_attach()`'s own existing behavior at all. On a `NONE`-flag cgroup (exactly what `container_dev_bpf_attach()` already uses, `attach_flags=0`), attaching a *second* program is itself already an atomic replace of the first, confirmed with a real concurrent-access test, not just read from the kernel header's own comment. Live attach/detach is therefore: rebuild the full device list (existing live grants plus/minus the one being added/removed) and call `container_dev_bpf_attach()` again, completely unmodified, against the same cgroup fd already kept for that container.

The same two-layer shape ADR-0156 already established for networks (a real, callable-by-hand REST primitive first; hotplug automation is just another caller of it, not a separate code path):

- **`POST /v1/containers/{name}/devices`** — `{"id": "..."}` (a real device id or devicemap name, resolved exactly like creation-time `devices` entries are). Appends to the container's own in-memory live device list and calls `container_dev_bpf_attach()` again with the full updated list against the already-open cgroup fd — proven above to atomically replace what's currently attached, no window where a different, already-granted device becomes briefly ungranted (or, the real risk direction, briefly unrestricted). Then `mknod()`s the new `/dev` node directly into the running container's own view via `/proc/<pid>/root/dev/<name>` — the identical "reach into an already-running container's filesystem from the host side" mechanism ADR-0153's live file write already established and proved correct, reused rather than re-invented for the mknod half.
- **`DELETE /v1/containers/{name}/devices/{id}`** — reverse: rebuilds the device list without this entry, calls `container_dev_bpf_attach()` again (same proven atomic-replace property), `unlink()`s the `/dev` node via the same `/proc/<pid>/root` path. Refuses (`409`) a device that was granted at creation time and is `optional: false` (mirrors ADR-0156's own "detach only ever removes a live attachment, never a create-time one" rule).
- Phase C's listener then calls this same in-process logic directly (not a real HTTP round-trip) on `add`/`remove` events, matching persisted `optional: true` references to running containers — the "live attach on hotplug" and "actively revoke on unplug" behaviors the user asked for. **Contention, resolved**: if more than one running container's own persisted `optional: true` reference resolves to the same newly-appeared device, the daemon grants it to **neither** and logs the ambiguity (`logstore_write()`) — safer than an implicit, silently-arbitrary "first found in registry order" pick, and no new priority/ranking field to design or maintain for what should be a rare edge case.
- One real implementation detail this simplification surfaces: the daemon needs to keep the *previous* `prog_fd` `container_dev_bpf_attach()` returned (already true today, just not currently reused after creation) and `close()` it once the new one is confirmed attached — the kernel drops the old program's own cgroup attachment as part of the replace, and closing the daemon's last reference lets it actually be freed, not a new risk, just an ordinary fd-lifecycle detail to get right.

### Phase D verification (done, not deferred)

A standalone probe (`bpf_replace_probe.c`, built with this project's own real `include/linux_compat.h` structs/`sys_bpf()` wrapper, run against a throwaway `/sys/fs/cgroup/thinc-bpf-probe` leaf — never a real container) tested three things directly, each with a concurrent background process hammering `open("/dev/full")` (a device never granted in any test) at high frequency across the swap under test, to catch a real race rather than just checking before/after state:

1. **A cgroup with no `BPF_CGROUP_DEVICE` program attached at all has fully unrestricted device access** — confirmed directly (all three of `/dev/null`/`/dev/zero`/`/dev/full` openable). This corrects the risk direction from this document's own first draft: a naive detach-then-reattach would create a brief *wide-open* window, not a brief *over-restrictive* one.
2. **`BPF_F_REPLACE` alone (without also setting `BPF_F_ALLOW_MULTI`) fails with `EINVAL`** — confirmed directly; the real kernel header's own comment (not obvious without hitting the error first) states the two flags must be set together. Real evidence the "trust documentation alone" instinct this whole exercise was built to avoid was right to avoid.
3. **A plain re-`ATTACH` with `attach_flags=0`** (`container_dev_bpf_attach()`'s own existing, unmodified call shape) **on a cgroup that already has a `NONE`-mode program attached correctly and atomically replaces it** — confirmed directly: 2,000,000 concurrent `open("/dev/full")` attempts spanning the swap, zero succeeded, and the post-swap grant set was exactly right (old grant preserved, new grant active, never-granted device still denied). `BPF_F_ALLOW_MULTI | BPF_F_REPLACE` was also confirmed to work once both flags are set together (run for direct comparison on a separate cgroup), but is unnecessary — the plain re-attach this project's own code already does is sufficient on its own.

Net result: Phase D's design above is simpler than originally drafted, not just de-risked — a real example of empirical verification finding a *better* answer, not only a safer path to the original one.

## Resolved open questions

Decided directly with the user before implementation:

1. Phase B's opt-in shape: **confirmed as designed** — `{"id": ..., "optional": true}` per device entry, not a container-wide flag. Some devices on a container can be mandatory while others are opportunistic, in the same container.
2. Hotplug contention (multiple containers referencing the same devicemap): **reject as ambiguous, grant neither** — resolved and folded into Phase D above.
3. Hotplug-driven grant/revoke visibility: **yes, `logstore_write()`** on every relevant action — resolved and folded into Phase C above.
4. Phases A-D ship as **one combined deliverable**, not staged incrementally — resolved; do not ship A/B alone ahead of C/D.
