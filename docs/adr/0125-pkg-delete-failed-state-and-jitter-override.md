# 0125 — pkg_delete() failed-state removal + per-container follow_rolling jitter override

## Status

Accepted

## Context

Two follow-up gaps in Part 5 of the `pkg/` redesign (ADR-0124, task #739/#770), both surfaced directly by the user after that part's own live verification closed out:

1. **`pkg_delete()` could not remove a package stuck in `PKG_STATE_FAILED`.** `pkg_delete()`'s own guard only ever accepted `e->state == PKG_STATE_INSTALLED` — a permanently-failed fetch or build (a bad checksum, a broken recipe, a network hiccup with no retry) left its tracking entry stuck forever, `DELETE /v1/pkg/{name}` returning 404 for it exactly like it does for a name that was never installed at all, indistinguishable from the outside. Confirmed directly by reading every `PKG_STATE_FAILED` transition in `daemon/src/pkg.c`: every one of them (`pkg_build_spawn_failed()`, the fetch/checksum/build failure paths in `pkg_fetch_completed()`/`pkg_build_completed()`) either fires before the entry's own file-merge step ever ran (`e->files` still empty), or — the one path that runs `image_produce_new_version()` before deciding FAILED — fires only after that function has already discarded its own scratch staging directory on any failure (confirmed reading `image_produce_new_version()`'s own implementation: every failure branch calls `persist_remove_tree(staging)` before returning, never renaming the staging copy into a real, persisted version). So a FAILED entry's `e->files`, even when non-empty, only ever describes content that lived in an already-deleted scratch directory — never anything actually present in a real image version. There is nothing to unlink and no new image version to produce for removing one.
2. **Part 5's jitter window (ADR-0124) was daemon-wide only.** A single knob (`GET`/`PUT /v1/system/rolling-config`) controlled every `follow_rolling` container's restart spread with no way for one particularly latency-sensitive (or particularly tolerant) container to use a different window without changing the default for every other container following the same or a different rolling image.

## Decision

**`pkg_delete()`**: the state guard now accepts `PKG_STATE_INSTALLED` *or* `PKG_STATE_FAILED`. A FAILED entry takes a new, separate branch — `pkg_entry_free_files()` (releases any phantom, staging-only filenames) followed by clearing the slot directly, never through `image_produce_new_version()`/`delete_mutate()` (the INSTALLED path's own uninstall mechanism, unchanged). No new image version is produced, because none of the failed attempt's content was ever really part of one. `save_state()` is still called for consistency with the INSTALLED branch, though it's not load-bearing here — `save_state()` only ever persists `PKG_STATE_INSTALLED` entries (a documented v1 boundary, ADR pre-dating this one), so a FAILED entry was already purely in-memory.

**Per-container jitter override**: `struct container_def` gains `has_follow_rolling_jitter`/`follow_rolling_jitter_seconds`, set only by an explicit `"follow_rolling_jitter_seconds"` (0-3600, same range `PUT /system/rolling-config` already enforces) on the original `POST /v1/containers` body — mirrors `has_readiness`'s own "optional int, has-flag plus value" shape already established in this same struct, and `follow_rolling` itself's own "ignored, not an error" precedent when given without `follow_rolling:true` or with `restart:"no"`. `apply_rolling_container_restarts()` (`daemon/src/main.c`) now resolves the jitter window per-container: `def->has_follow_rolling_jitter ? def->follow_rolling_jitter_seconds : containerdef_jitter_window_get()` — a container-level override over a daemon-level default, one level up from `restart_delay_seconds`'s own override-over-hardcoded-constant shape but the same idea. Persisted (`save_state()`/`parse_persisted_entry()` in `containerdef.c`, `follow_rolling_jitter_seconds` as a nullable JSON field — `null` covers both "field absent" and "an older `container_defs.json` predating this field," the same backward-compat posture `follow_rolling` itself established one part earlier) and surfaced in `GET /v1/containers[/{name}]` (`registry.c`, nullable — `null` means "using the daemon-wide default").

## Verification

Full clean rebuild (`-Wall -Werror`), zero warnings. `test/test_pkg.c` gained a new scenario: a checksum-mismatch install (`badsum`, already an existing fixture reaching `PKG_STATE_FAILED`) is now also `DELETE`d, confirmed `204`, confirmed `404` on a subsequent `GET`, and — the real proof this doesn't silently reuse the INSTALLED uninstall path — confirmed the base image's own `current_version` is bit-for-bit unchanged by the deletion (read before and after, compared). `test/test_rolling_restart.c` gained: a round-trip proof (`follow_rolling_jitter_seconds:0` on create is echoed back by both the create response and a subsequent `GET`, never silently dropped), and a real behavioral proof that the override actually takes precedence over the daemon-wide default rather than just being stored inertly — the daemon-wide default is cranked to its own maximum (3600s), a new container is given an explicit `0` override, a second rolling rebuild is triggered, and the container is confirmed to restart within a short (~10s) poll window; since `rolling_jitter_seconds()` draws uniformly from `[0, 3600]`, a daemon-default-only container has under a 0.3% chance of coincidentally restarting that fast, so this is a real, not just plausible, proof the override was actually consulted. Full regression sweep (every daemon-linked and standalone test) confirms zero regressions; `test_rolling_restart` specifically re-run 3x consecutively given its one timing-sensitive assertion.

## Consequences

- An operator can now actually clear a permanently-failed package install/upgrade attempt without waiting for a daemon restart (which never even helped, since `save_state()` never persisted it — the entry would reappear identically on the very next attempt to install that same `(name, image)` after a restart too, since `pkg_find()` would find nothing and a fresh attempt would just fail again the same way; the real problem was purely that nothing could clear the stuck in-memory tracking entry between attempts).
- `PUT /v1/pkg/{name}` (i.e., a delete followed by a fresh install of the same name/image) now works for a package whose first attempt failed, without needing a workaround (e.g. picking a different name).
- A single container can now tune its own rolling-restart spread independently of every other container on the fleet — useful for e.g. a single stateful service that should never restart faster than some minimum spread, sitting alongside many stateless services happy with the daemon-wide default.
- Neither change is a breaking change to `openapi.yaml`'s existing contract: `pkg_delete`'s 404/409/500 responses are unchanged in shape (only newly reachable for a case that previously also 404'd, indistinguishably); `follow_rolling_jitter_seconds` is a purely additive, optional field on both the create request and every container response shape.
