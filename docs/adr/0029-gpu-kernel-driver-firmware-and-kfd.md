# 0029 — GPU kernel driver, firmware staging, and KFD discovery

## Status

Accepted

## Context

Phase 14 part 1 (ADR-0028) built GPU discovery and grouped device grants but explicitly deferred two things: the kernel driver itself (`CONFIG_DRM_AMDGPU` was absent from `image/kernel/qemu-part1.config`, the one kernel config file used for both QEMU testing and the real installed system) and firmware staging (`amdgpu` loads firmware blobs via `request_firmware()` at driver-probe time, before any container exists, so they have to live on the host root itself). Without both, GPU passthrough was discoverable and grantable but wouldn't actually work — there'd be no driver to bind to the hardware at all.

A third, real gap surfaced while scoping this part, not deferrable alongside the others: ROCm compute needs `/dev/kfd`, which lives under `/sys/class/kfd` — entirely separate from `/sys/class/drm`, which is all `enumerate_gpu()` looked at in part 1. A `gpu:0` grant without it would hand over `card0`/`renderD128` but not the one node ROCm's own runtime actually needs to submit compute work at all — for the user's actual goal (an LLM container), that's not a partial feature, it's a non-functional one.

## Decision

**Kernel config**: `CONFIG_FW_LOADER`, `CONFIG_DRM`, `CONFIG_DRM_KMS_HELPER`, `CONFIG_DRM_AMDGPU`, `CONFIG_HSA_AMD` (the KFD/ROCm driver — without it, no `/dev/kfd`, display-only wouldn't serve the actual goal) added to `image/kernel/qemu-part1.config`. No `CONFIG_DRM_AMDGPU_SI`/`CIK` (pre-GCN3 chip support the target hardware doesn't need) and no framebuffer-console options (this project's boot chain already uses serial+tty0, never a GPU framebuffer console) — no speculative extras beyond what's actually needed, same discipline every prior addition to this file has followed.

**Verified the way this project's own established discipline requires**, not just written down and trusted: `scripts/config --enable` alone doesn't check Kconfig's real dependency graph, and this exact file's own history has two real incidents where that produced silently-dropped options (`docs/ROADMAP.md`'s Phase 11 part 1 narrative). This addition was verified by fetching real kernel 6.18.40 source, `make allnoconfig`, `merge_config.sh` with the updated fragment, `make olddefconfig`, then confirming — programmatically, not by eye — that *every* `CONFIG_X=y` line in the entire fragment (not just the 5 new ones) landed as `=y` in the resulting `.config`, none silently reverted. A full `make bzImage` was then run to prove the config compiles, not just configures.

**Firmware source**: confirmed directly that this dev sandbox has no `amdgpu` firmware anywhere and the distro package (`firmware-amd-graphics`) isn't even available in its configured apt sources — the existing "copy from wherever the build host already has it" precedent (`pkg_seed_image_runtime()`, `test_image_fixture_add_lib()`) has no source to copy from here. Confirmed directly with the user: firmware is fetched fresh from upstream `linux-firmware` at build time (not vendored into the repo — binary-blob bloat and redistribution-license correctness are real costs a fetch avoids), scoped to the full `amdgpu/` set (not a specific chip's own subset — robust across any AMD GPU generation, and the user doesn't want to track a per-model file list). The fetch itself (`git clone --filter=blob:none --sparse` + `git sparse-checkout set amdgpu`, documented in `README.md`) is deliberately *not* automated into any build step — same posture the existing kernel-source-fetch recipe already has, a documented one-time/per-machine operation, not something `make` does implicitly.

**`mkbootroot.c`** gains a new required 5th argv, `firmware_dir` (empty string means "skip" — every existing call site, all 3 test binaries, updated explicitly rather than left to silent argc-based optionality, matching this project's own established practice the last time this tool's argv shape changed). When non-empty, it's staged into `<image_root>/lib/firmware/amdgpu` via the existing `copy_dir_files()` — already generic, already proven staging `web/`, reused verbatim rather than writing a second directory-copy implementation. This relies on `linux-firmware`'s own `amdgpu/` directory being flat (no subdirectories), confirmed directly against the real upstream repo (a `git ls-tree` pull of just that path's own tree listing, not the blob content — 675 files, zero nested under a subdirectory), not merely assumed. Unlike `pkg_seed_image_runtime()`'s tolerant-if-missing precedent (fine for opportunistic staging of something not explicitly asked for), a non-empty `firmware_dir` that can't be staged is a real misconfiguration the operator explicitly requested — `copy_dir_files()` already fails loud on an unreadable source, so this falls out for free rather than needing new tolerance logic. A new `test/test_mkbootroot_firmware.c` proves the mechanism directly (a synthetic scratch directory, not a real multi-hundred-MB fetch — mirroring `test_devices.c`'s own stand-in precedent): `firmware_dir=""` stages nothing under `lib/firmware`, a real directory's files land verbatim under `lib/firmware/amdgpu`, and an explicitly-requested-but-unreadable path fails the whole build rather than silently succeeding.

**`/dev/kfd` discovery** (`daemon/src/device.c`, extending `enumerate_gpu()`): after the existing DRM-node walk, if `/sys/class/kfd/kfd` exists with its own `dev` file, one `gpu:<idx>:kfd` member is emitted for *every* currently-discovered `gpu:<idx>` group. `/dev/kfd` is one shared, system-wide node — not per-card, since KFD's own topology sysfs multiplexes across however many GPUs a host has — so this reflects that real architecture rather than inventing isolation semantics Kanxeo doesn't have the primitives to provide. Correct and sufficient for the user's actual single-GPU case; on a hypothetical multi-GPU host, granting `/dev/kfd` via any one `gpu:<idx>` group exposes KFD's queue-submission path host-wide, a real, known ROCm/KFD architectural property, not a Kanxeo-specific gap — stated here plainly rather than glossed over.

## Consequences

- The kernel-config verification found zero surprises this time (unlike the two real past incidents in this same file) — every fragment symbol, old and new, landed as intended on the first `merge_config.sh` + `olddefconfig` pass. `make bzImage` completed successfully, producing a real `bzImage` with `amdgpu`/`HSA_AMD` built in, and the resulting kernel was booted for real: `test_boot`/`test_boot_ab`/`test_installer` (this project's own existing QEMU-based boot suite) all re-run clean against it.
- Real disk-space pressure on this shared dev host (down to ~1.3GB free at one point, mid-fetch) was worked around with a standard, safe `apt-get clean` (~900MB reclaimed) rather than touching anything project- or user-owned; the host's own available space then grew independently mid-session (infrastructure-level, outside this project's control) — noted here in case a future session on this same host hits tight disk again during a similarly heavy fetch+build step.
- Unverifiable in this sandbox regardless of how carefully the config/firmware/discovery pieces are built: no real GPU is bound to anything here (confirmed directly, `/sys/class/drm` and `/sys/class/kfd` both empty), so the actual "boots with a real AMD GPU, ROCm sees `/dev/kfd`, a container can compute on it" path needs real hardware — the same documented boundary ADR-0022 (real NIC passthrough) and ADR-0028 (GPU discovery) already have, for the identical reason.
- The KFD/multi-GPU host-wide-exposure property above is a real, permanent architectural limitation of ROCm/KFD itself, not something a future Kanxeo change can fix at the `BPF_CGROUP_DEVICE` grant level — stated as a known boundary, not a bug to revisit.
