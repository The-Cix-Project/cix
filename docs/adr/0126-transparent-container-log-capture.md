# 0126 — Transparent container log capture into the consolidated log store

## Status

Accepted

## Context

Kicks off a broader logging/web-UI epic (user-requested: transparent container log aggregation with regex/level/container-name filtering; redundant `syslog-1`/`syslog-2` containers; several other web dashboard changes tracked separately). Part 1 here is the foundational piece everything else depends on.

Before this part, a container's own stdout/stderr was invisible by default — inherited straight from `cixd`'s own stdio (console-only on a real install, discarded on a dev box) unless the client explicitly opted in via `"capture_output":true` at creation, which only ever populated a 4KB tail on that one container's own `GET /v1/containers/{name}` response (task #652/#761, ADR-0112) — not searchable, not filterable, not visible in the one already-existing consolidated log store (`logstore.c`, ADR-0070, covering kernel dmesg / cixd diagnostics / a per-request audit trail).

Two real design questions, both resolved with the user directly before writing code:

1. **Where should container logs live: the existing `logstore.c`, or a new mechanism?** `logstore.c` is already this project's One Source of Truth for "a consolidated, API-accessible, size-bounded log." A second, parallel store for container output would violate that outright. Confirmed: extend `logstore.c` with a new `container`-tagged source rather than inventing a second store.
2. **How does a real syslog daemon (no REST API) fit "100% API driven"?** It doesn't, as the *primary* store — a real syslog receiver (planned as an optional `syslog-1`/`syslog-2` container pair, a later part of this epic) has no queryable API of its own; making it the primary aggregation point would mean `cixd` tailing and re-parsing its log files, a second, harder-to-keep-consistent store. Confirmed: `logstore.c` stays authoritative and always API-queryable; a redundant `syslog-1`/`syslog-2` pair becomes an *optional forward target* for operators who want standard external tooling on top (a later part of this epic), never the thing the API/web UI itself reads from.

## Decision

**Capture is now unconditional, not opt-in.** Every container created via `POST /v1/containers` always gets a `pipe2()`-backed stdout/stderr pipe (`daemon/src/main.c`'s `create_container_from_body()`), dup2'd onto the child before exec, and always drained incrementally via the same `CONN_CONTAINER_OUTPUT` epoll idiom `capture_output` already established (ADR-0087's own "never let the pipe's 64KB kernel buffer block the child" discipline, unchanged). The client's own `"capture_output":true` boolean is **not removed** — it now controls only whether the *same* bytes are *additionally* mirrored into that one container's own `registry_entry.captured_output` tail (`entry->capture_requested`, previously conflated with "does the pipe exist at all," now cleanly separated). No client-visible behavior changes for anyone who already used `capture_output` — `GET /v1/containers/{name}`'s own `captured_output` field (null vs. populated) is bit-for-bit unchanged.

**Line-oriented forwarding, not raw bytes.** `handle_container_output_event()` (`main.c`) gained a second, independent consumer of the same read loop: `forward_container_output_to_logstore()`, which splits on `\n` (accumulating a partial line across reads in a new small per-`struct conn` buffer, `output_line_buf`/`output_line_len` — the same "add a field for this one conn kind" shape every other `conn` field here already uses) and calls the new `logstore_write_container(container_name, "info", "%s", line)` per complete line, plus a final flush at EOF so a container's last, unterminated line isn't dropped. stdout and stderr remain merged onto one pipe (the same simplification `capture_output` already had) — every container-sourced log line is written at a fixed `"info"` level, since there is no real signal to derive a genuine per-line severity from without a second pipe. Documented as a stated v1 boundary, not silently assumed.

**Schema**: `logstore.c` entries gain a `container` field (always present, empty string when not applicable — this store's own established "empty string means N/A, never `jw_null`" convention, unchanged). `logstore_write()` (existing callers: kernel/cixd/audit, all unaffected) and the new `logstore_write_container()` both funnel through one shared `write_entry()` helper — one source of truth for the on-disk JSON-lines shape, not two independent writers.

**New filters**: `GET /v1/system/logs` gains `container=` (exact match against the new field) and `regex=` (POSIX extended, case-insensitive, `REG_ICASE` — matches `grep -i`'s own default, the "least surprise for an operator eyeballing log text" posture) query parameters. A malformed regex is a `400` at the REST layer (validated via a throwaway `regcomp()`/`regfree()` before ever reaching `logstore_tail_ex()`), not a silently-empty result. `logstore_tail()` (the pre-existing, simpler entry point) is preserved unchanged, calling the new `logstore_tail_ex()` with both new filters `NULL` — no existing caller needed to change.

**A real TCC/glibc friction point, found and fixed along the way**: `<regex.h>`'s own `regexec()` prototype uses a C99 VLA-in-prototype size expression (`regmatch_t __pmatch[_Restrict_arr_ _REGEX_NELTS(__nmatch)]`) TCC's parser rejects outright. Not a struct-packing issue (the `struct epoll_event`/`clone_args` class of bug, ADR-0008) — the header already has an `#ifndef __STDC_NO_VLA__` branch for exactly this situation; defining that standard C11 feature-test macro ourselves (accurately — TCC really doesn't support this construct) before including the header steers it onto the plain-array branch, which TCC parses fine, with zero hand-redeclaration of `regex_t`/`regcomp`/`regexec`/`regfree` needed. See `CLAUDE.md`'s own new environment note and `daemon/src/logstore.c`'s include-block comment.

**A real, unrelated live bug found and fixed in the same session**: `client_conn_advance_handshake()` (the non-blocking TLS handshake driver) dumped the *entire* raw OpenSSL error queue to `stderr` — the physical/serial console on a real installed box — on every single failed HTTPS handshake, including the entirely ordinary case of a client not yet trusting this box's own self-signed PKI CA. Confirmed live: this floods the console non-stop whenever anything repeatedly probes the HTTPS port without a trusted cert. Fixed: routed through a new `log_tls_error()` helper that logs one summary line via `logstore_write()` (source `cixd`, level `warning`) instead, still fully draining the OpenSSL error queue (so it can't silently accumulate) but never spamming the console. Unrelated to the container-logging mechanism itself, bundled here because it was found investigating the same console-noise complaint that motivated this whole epic.

## Verification

Full clean rebuild (`-Wall -Werror`), zero warnings. `test/test_container_lifecycle.c` extended: a container created *without* `capture_output` (its own `captured_output` already confirmed `null`) is polled against `GET /v1/system/logs?source=container&container=<name>` and its real stdout line is confirmed present and correctly tagged — proving capture is genuinely unconditional, not just that the opt-in path still works. Also confirms a `container=` filter for an unrelated name returns zero entries, and a malformed `regex=` is a `400`. Manual live round-trip against a scratch daemon additionally confirmed: `capture_output:true` still populates `captured_output` exactly as before (regression check); the `container`/`regex` filters both work correctly including a self-referential match against the store's own audit-log entry for the query itself. Full regression sweep (every daemon-linked and standalone test) confirms zero regressions.

## Consequences

- Every container's real stdout/stderr is now discoverable via the API without any per-container setup — closes the exact gap the user described ("all the logs for the containers to go to a common logging backend transparently").
- One more always-open pipe + epoll registration per running container (previously only for `capture_output:true` ones) — a small, bounded per-container resource cost, consistent with every other per-container fd this daemon already holds (pidfd, cgroup fd, network fds).
- stdout/stderr staying merged onto one pipe (inherited from `capture_output`'s own original design) means every container-sourced log line is `"info"` regardless of whether the program itself considered it an error — a real, documented limitation; splitting into two pipes to recover per-stream severity is a plausible future refinement, not pursued here (scope discipline — this part's job was capture, not per-stream classification).
- Sets up the next part of this epic (optional `syslog-1`/`syslog-2` forward targets, real syslog wire protocol) to build directly on this store as its one source of truth, rather than needing its own separate capture path.
