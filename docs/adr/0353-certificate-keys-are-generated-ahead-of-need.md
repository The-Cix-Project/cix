# 0353 — Certificate keys are generated ahead of need

## Status

Accepted, 2026-10-23, for #637. The design was proposed in #637 with its measurements, and the owner then asked for #637 to be done.

## Context

Every private key the PKI makes is RSA-2048, generated by `pkicrypto_rsa_key_create()` on the event loop. That covers the root CA, the intermediate, and each leaf: a container's certificate, the host's, and every one an operator issues. Key generation takes a variable time by nature.

- **Measured on 192.168.15.95**, 2026-10-23: three `POST /v1/pki/certs` round trips for a throwaway leaf took 0.135 s, 0.125 s and 0.391 s.
- **Measured under qemu TCG** in the console boot test: `POST /v1/pki/ca` held the loop 16,142 ms in one run and 31,847 ms in another.

A container's first create issues its leaf, so it pays this on the loop. A CA bootstrap pays it three times, and a CA reset once per leaf it reissues, an estimated 1.5-5 s for .95's twelve containers.

A park (ADR-0342) cannot fix the create path. A request served again restarts from the beginning, and a container create has already written files, attached networks and placed its rootfs before it reaches the certificate.

## Decision

1. **Keys come from a pool when one is ready.** `pki.c` asks a key source the daemon installs (`pki_set_key_source()`) for each of its three keys. If the source hands over a PEM key, it is written to the key path, mode 0600, by `pkicrypto_key_file_write()`, then cleared and freed. If not, the key is generated in place exactly as before. A program with no source, such as every test binary, generates in place.
2. **The pool holds four keys and fills in a helper child.** The child generates one key with `pkicrypto_rsa_key_pem()` and returns it through a memfd. The parent keeps it, then starts the next fill until the pool is full. One fill runs at a time.
3. **It fills only while a CA exists.** It fills after autostart, after every take, and when a take first finds a CA bootstrapped. A host with no CA spends nothing on keys it may never use. That includes every boot test until it bootstraps a CA, under emulation where a key costs seconds.
4. **The keys exist only in the daemon's memory.** They are never written anywhere before they are issued, are cleared when taken, and are lost on restart, after which the pool fills again.

## What it fixes and what it does not

- **Fixed:** a container's first create, and any other single leaf issue, once the pool has filled. The cost becomes a file write.
- **Not fixed:**
  - **A CA bootstrap.** Its root key is made before a CA exists, so the pool is empty. The intermediate and the host leaf follow in the same pass, before a fill can finish. Once per install, about 1 s on .95's hardware.
  - **A reset reissuing more leaves than the pool holds.** The first four come from the pool and the rest are generated in place.

## Alternatives

- **Generate every key in a helper child, parking the request.** That works for `POST /v1/pki/certs` and `POST /v1/pki/ca`, but not for a container create, which cannot be resumed from its PKI step. It would have been two mechanisms for one cost.
- **Fill at daemon start whatever the state.** That would cover the CA bootstrap. It would also make every boot that never uses a CA generate four keys. Under emulation that is tens of seconds of CPU in a guest the release gate boots five times.
- **A larger pool.** A reset is the only burst, and it is destructive and manual. Four covers a CA bootstrap's three keys once a CA exists.

## Consequences

- An unissued private key sits in cixd's memory until it is taken. cixd already holds the CA's key on disk and in memory when it signs, and every helper child it forks inherits its memory until that child exits or execs. So this adds keys of lower value to a process that already holds the highest.
- OpenSSL 3 reseeds its DRBG when the process id changes, so a key a fill child generates is not shared with any other process.
- `GET /v1/system/stalls` shows any key still generated in place under its request, as it did before.
