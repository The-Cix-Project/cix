# 0064 — REST-driven ISO assembly: closing the API-First Mandate gap ADR-0063 left open

## Status

Accepted

## Context

ADR-0063 built a real, from-source `grub-mkrescue`/`sbsign`/`xorriso`/`mtools` toolchain, but explicitly, honestly left one piece unfinished: `image/src/mkinstalleriso.c` remained "a dev-machine-only tool a release-builder runs by hand... not yet reachable via POST/CLI the way every other capability this platform offers already is (the API-First Mandate)." The user asked directly to close that gap, with an explicit instruction that this project's capabilities be "100% API driven... with no exceptions unless explicitly called out for valid reasons." This ADR is that closure.

Three real, separate design questions had to be answered before writing any code — none of them assumed, all confirmed against real code or real host state.

## Decision

**`isotools.recipe`: a hostbuild aggregator, not a fifth from-source build.** ADR-0063's four ISO-toolchain recipes (`grub`, `sbsigntools`, `xorriso`, `mtools`) already build from source, but only ever land inside a *container image's* rootfs via ordinary `pkg install` — useless to `kanxeod` itself, which runs unsandboxed on the host and needs real, `execve()`-able binaries at a known host filesystem path. Rebuilding all four a second time as hostbuild jobs would be a real Parallel Implementation; instead, `isotools.recipe` is a thin aggregator (`pkg_depends=""`, precondition-checked in `pkg_build()` rather than declared — hostbuild jobs never honor `pkg_depends`, confirmed directly: `kernel.recipe`/`kanxeo.recipe` document their own build-image preconditions in comments for the identical reason) whose `pkg_install()` copies the already-installed `grub-mkrescue`/`sbsign`/`sbverify`/`xorriso`/`mformat`/`mcopy` binaries, grub's own real 601-file `x86_64-efi` module tree, and their confirmed real shared-library closure (`liblzma.so.5`, `libcrypto.so.3`, `libbz2.so.1.0`, `libz.so.1`, `ld-linux-x86-64.so.2` — checked directly via `ldd` against each binary, not guessed) into `$PKG_DESTDIR`. `pkg hostbuild isotools --build-image=dev` (any image that already has the four ADR-0063 recipes installed) harvests a genuinely self-contained artifact — verified directly: every harvested binary runs correctly via an explicit `ld.so --library-path` invocation with `env -i` (a completely empty environment, no inherited `$PATH`/`$LD_LIBRARY_PATH` from this dev sandbox's own system), producing real `--version` output for all four.

**`kanxeo.recipe` also builds `kanxeo-install` and `mkinstalleriso` now** — the same hostbuild round that already produces `kanxeod`/`kanxeoctl`/`mkbootroot` (ADR-0057) gains two more `make` targets, since both binaries already exist in this repo's own `image/src/`, built by the exact same `$(CC)`/`$(CFLAGS)` as everything else. Re-running this hostbuild for real (not just locally) surfaced a genuine, previously-undiscovered gap: `kanxeod` has linked `-lssl -lcrypto` since the HTTPS listener landed (ADR-0059), but no recipe had ever staged the two dev symlinks (`libssl.so`/`libcrypto.so`) a build needs to resolve those two `-l` flags — the self-hosted round-trip has been silently broken since HTTPS was added, undetected because nobody had re-run it since. Fixed with a new `openssl-dev.recipe`, the same "stage the real pre-built host copy, real genuine tarball for provenance" shape `libc-dev.recipe` already established for the analogous glibc gap.

**`mkinstalleriso.c`'s `grub-mkrescue`/`sbsign` paths are no longer hardcoded `/usr/bin/...` `#define`s** — a new required argv (`isotools-root`) replaces them, computing `<root>/bin/grub-mkrescue`, `<root>/bin/sbsign`, `<root>/lib/grub/x86_64-efi` (passed to `grub-mkrescue` via its own real `--directory=` flag, confirmed via `--help` — default is `/usr/lib/grub/<platform>`, wrong once binaries live at an arbitrary artifact path) and `<root>/bin/xorriso` (via `--xorriso=`, the one override flag `grub-mkrescue` documents). `grub-mkrescue`'s own child fork/execs of `mformat`/`mcopy` have no override flag at all (confirmed directly against GRUB's own source, ADR-0063) — resolved via `PATH`, set with `setenv()` before the fork, alongside `LD_LIBRARY_PATH` for the confirmed shared-library closure. A bare `/usr` still reproduces the tool's original host-borrowed behavior for manual/dev use — nothing about the existing dev-machine workflow breaks. Verified for real: a complete, genuine, bootable ISO 9660 image, built using *only* the harvested `isotools` artifact (no system `/usr/bin/grub-mkrescue` involved at all).

**Where the daemon looks for its own inputs, and why the signing key never lives there automatically.** `kanxeod` needs four things to assemble an ISO: the `kanxeo`/`kernel` hostbuild artifacts (already at fixed `ARTIFACTS_DIR/<name>/...` paths, ADR-0056), the new `isotools` hostbuild artifact, and a Secure Boot signing key pair. The first three are found automatically; the fourth is not, and this is deliberate, not an oversight. `image/src/kanxeo-install.c`'s own `SIGNING_CERT_SRC` comment already establishes that only the *public* DER cert is ever staged onto a real deployed target (for MOK enrollment) — the private key and PEM cert have never propagated onto a deployed box, matching this repo's own `image/keys/` posture (gitignored, must exist locally, never reproduced by a build step). Making `kanxeod` itself generate, fetch, or auto-copy a release-signing private key onto every box that happens to run it would be a genuine security regression — any single deployed box's compromise would leak the fleet's own Secure Boot key. Instead, a new `SIGNING_KEYS_DIR` (`<data-dir>/keys/`) is a real, operator-populated-out-of-band precondition, exactly like `pkg hostbuild kanxeo` already requires a real git token nobody but the operator can supply, or `pkg bootstrap --toolchain=` requires a real pre-built artifact already `scp`'d onto the box. A box with nothing there simply can't serve `POST /system/iso` — a real, environment-specific limitation, not a design gap, and precisely the kind of "no exceptions unless explicitly called out for valid reasons" case the user's own instruction anticipated.

**The mechanism itself mirrors ADR-0057's `spawn_kanxeo_bootroot_assembly()` exactly, with one deliberate difference.** A new `CONN_ISO_ASSEMBLE` conn kind, `register_iso_assemble_pidfd()`/`handle_iso_assemble_event()` — fork, `pidfd_open()`, add to `epoll`, non-blocking, reaped the same way. The deliberate difference: bootroot assembly auto-triggers the instant a "kanxeo" hostbuild completes (it needs no operator input at all); ISO assembly is a distinct, explicitly-triggered `POST /system/iso` instead, because it has real inputs of its own (`disk`/`ip`/`prefix`/`gateway`/`interface`) a hostbuild completion has no way to supply, and reuses whichever hostbuild artifacts already exist rather than forcing a fresh rebuild of any of them. State (`none`/`building`/`ready`/`failed`) lives in a small, unpersisted `g_iso_build_state` — the same "an in-progress job the daemon restarts through is simply lost" posture every other async job in this daemon already has. Every precondition (four artifact paths + the signing key trio) is checked synchronously inside the POST handler itself, before any fork — a missing one fails the request immediately with a specific, actionable message (400) naming exactly what's absent, never a background failure the caller has to poll for to discover; "already building" is checked separately and gets 409, mirroring `respond_pkg_error()`'s own `PKG_ERR_BUSY` (409) vs. `PKG_ERR_INVALID_TOOLCHAIN` (400) split.

**CLI**: `kanxeoctl iso build [--disk=... --ip=... --prefix=... --gateway=... --interface=...] [--wait]` / `kanxeoctl iso status` — a new top-level command (matching `backup`/`update`/`restore` already being top-level, not nested under a `system` group that doesn't otherwise exist in this CLI), mirroring `pkg hostbuild`'s own `--wait` polling shape (`poll_iso()` alongside the existing `poll_hostbuild()`).

## Consequences

- Verified real, end to end, in this exact order: `isotools` hostbuilt from a real `dev` image's own already-installed grub/sbsigntools/xorriso/mtools, all four binaries confirmed executing in complete isolation (`env -i`, explicit `ld.so --library-path`); `kanxeo.recipe`'s hostbuild re-run for real (through a genuine fetch+extract+build+harvest round, not a shortcut), surfacing and fixing the `openssl-dev` gap along the way; the parameterized `mkinstalleriso` producing a real bootable ISO standalone; then the full `POST /system/iso` → poll → `GET /system/iso` round-trip against a live daemon, with custom `--disk=`/`--ip=`/`--prefix=`/`--gateway=`/`--interface=` values confirmed present verbatim in the resulting ISO's own `boot/grub/grub.cfg` kernel command line; and the `kanxeoctl iso build --wait` / `iso status` CLI surface against that same live daemon.
- **Not verified, per Zen, and deliberately out of scope for this pass**: a real hardware/QEMU *boot* of a REST-produced ISO (Part 5's own ADR-0063 already established that grub-mkrescue's own output boots correctly; this pass's own new work is entirely in how the ISO gets *produced*, not what it boots into, and re-running the full `test_installer` QEMU harness against this exact artifact is a natural next verification pass, not a gap in this mechanism's own correctness). Downloading the finished ISO over REST was deliberately not built — `iso_path` is a host filesystem path, the same "artifact remains a host path, never a REST download" shape `GET /pkg/hostbuild/{name}`'s own `artifact_path` already established for hostbuild artifacts generally, kept for One Source of Truth rather than inventing a second convention for one endpoint.
