# 0018 — the real cix-containers partition backs BASE_DIR, not a fresh tmpfs every boot

## Status

Accepted

## Context

`cixd --init-mode`'s `boot_init()` (Phase 11 part 1) has mounted a fresh `tmpfs` at `BASE_DIR` (`/var/lib/cix`) on every real boot since that phase landed — and every piece of state this daemon persists lives under that one path: `images/` (including the shared `base` image every `pkg install` build lands its files into), `containers/`, `networks.json`, `dns_records.json`, `pki_certs.json`, `pkg_installed.json`. A `tmpfs` is wiped on every reboot. Concretely, on a real installed system, a full power cycle silently discarded every installed package, every created network, every DNS record and PKI certificate, and every container image — not just running containers (which are correctly never expected to survive a reboot, per `daemon/include/registry.h`'s own documented reasoning: they die via `PR_SET_PDEATHSIG` the moment `cixd` itself stops, restart or otherwise).

This was never a deliberate boundary. `boot_init()`'s own comment (present since Phase 11 part 1, before this change) said the `tmpfs` was "Phase 11 part 1's explicit stand-in for the real config/container partitions part 3's installer mounts there instead — same mount point, so nothing below this function changes when that lands." Phase 11 part 3 did add a real `cix-config` partition — but mounted it at a *different* path (`/config`, for `net.conf` only) and never made the swap this comment promised for `BASE_DIR` itself. The fifth partition `cix-install` already creates and formats for exactly this purpose (`cix-containers`, named and sized as the "rest of the disk" in every partitioning path this project has) has been sitting on every installed system's disk, correctly formatted, completely unused, since Phase 11 part 3 shipped. Found while scoping a follow-on request (installing real software — `bash`, `iproute2`, `bird` — via `pkg install`, which only makes sense if it survives a reboot) rather than by a report against the fix's own stated intent.

## Decision

`boot_init()` now tries `mount(CONTAINERS_DEVICE, BASE_DIR, "ext4", MS_NOSUID|MS_NODEV, NULL)` first (`CONTAINERS_DEVICE` = `/dev/vda5`, the same fixed QEMU virtio-blk layout convention `ESP_DEVICE`/`CONFIG_DEVICE` already use), falling back to the original `tmpfs` mount only if that device doesn't exist — the same non-fatal-fallback shape `CONFIG_DEVICE`'s own mount already has, needed for Part 1/2's throwaway 2/3-partition test disks, which have no partition 5 either. No other code changes: `ensure_dir()`'s own `EEXIST`-tolerant `mkdir()` calls, and every module's `persist_read_file()`/`persist_atomic_write()` pair, already handle "this directory/file may or may not already exist" correctly regardless of what's actually mounted at `BASE_DIR` — the entire fix is the one mount call in `boot_init()`.

A second, related durability gap surfaced while verifying this end to end: QEMU's default `-drive` cache mode (`writeback`) only guarantees a write reaches the actual disk image file once the *guest* issues a flush — and `cixd` printing "listening on" (the signal both this project's own test harness and a real operator treat as "boot finished, safe to power-cycle") happened *before* anything guaranteed that. `main()` now calls `sync()` once, right after `registry_init()` and before the listening socket is even opened — covering `ensure_dir()`'s scaffolding and every module's own state-init — gated on `init_mode` (a dev/test `cixd` invocation has no such durability concern). This mirrors the shutdown path's own `sync()` before `reboot(2)` (ADR-0016), applied to the symmetric boot-time case. Placement matters: an earlier draft placed this `sync()` *after* the "listening on" print, which raced the test harness's own kill-on-marker behavior and defeated the whole point — confirmed by first getting it wrong.

## Consequences

- `pkg install`ed packages, created networks, DNS records, PKI certificates, and container images now genuinely survive a real reboot on an installed system — the property the whole point of persisting them (ADR-0012, DNS/PKI's own state-init) already assumed but, until now, a full power cycle silently defeated.
- Verified end to end, not just "the mount succeeded": `test/test_installer.c` gained a real cross-boot proof — after the installed system's first full boot (session 3), the real on-disk `cix-containers` partition is extracted and confirmed to actually contain `cixd`'s own directories (`images/`, `containers/`, `pki/`, `pkg/`), a marker file is written directly into it (`debugfs -w`, no mount needed, this project's established no-loop-devices posture), and a *completely independent second boot* of the same disk (session 4) is confirmed to still have it, byte-for-byte — 3 consecutive passes.
- A second, genuinely new failure mode surfaced and fixed while building that test, worth recording since any future test writing similarly low-level, direct partition content after a QEMU session will hit it: a partition extracted right after `qemu_boot_capture()` SIGTERMs the QEMU process still carries a pending ext4 journal from that abrupt stop (confirmed directly: `EXT4-fs: recovery complete` on the next real mount). Writing into that extracted image with `debugfs` — which touches on-disk blocks/inodes directly, bypassing the journal entirely — before that pending journal is replayed is unsafe: the next real mount's own journal replay can silently revert exactly the blocks `debugfs` just wrote, since the journal still records the pre-write state. `test_installer.c` now runs `e2fsck -fy` (0 = clean, 1 = errors corrected — the expected case here, not real corruption; only ≥ 4 is treated as a genuine failure) on any partition extracted this way before writing to it with `debugfs`.
- `image/kernel/qemu-part1.config` needs no changes — `CONFIG_EXT4_FS` was already present (for the config partition).
- `CONTAINERS_DEVICE`'s fixed `/dev/vda5` path inherits the same "Part 1's stated fixed/known-hardware scope" boundary `ESP_DEVICE`/`CONFIG_DEVICE` already carry — real target hardware (Part 4, not yet designed) will need a GPT-partition-name-based lookup instead of a hardcoded device path, same open item already noted for the other two.
