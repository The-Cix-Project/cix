# 0115 — `DELETE`'s task #738 disk cleanup never ran for a crashed-but-defined container, causing permanent, un-fixable crash loops

## Status

Accepted

## Context

Found live on 192.168.15.95 while closing out task #759 (after ADR-0114's kernel fix made real SSH login possible): a `restart:"always"` jump box container, recreated several times under the same name (`jumpbox1`) across this session, kept crash-looping forever with `sshd`'s own `Unable to load host key: bad permissions` — even immediately after a fresh `DELETE` + `POST /v1/containers` with the correct `mode: "0600"` in its `files[]`. A brand-new, never-before-used container name (`jbnew1`) with the byte-identical creation body ran perfectly stably. This isolated the cause to something specific to the *name*, not the request body.

`main.c`'s file-staging code (`create_container_from_body()`) opens each `files[]` entry with `open(target, O_CREAT | O_TRUNC | O_WRONLY, mode)` — `O_TRUNC` truncates an *existing* file's content but never `chmod()`s it; the `mode` argument to `open()` only ever applies at the moment `O_CREAT` actually creates a new inode. So a stale upperdir file left over from an earlier, differently-permissioned run of the same container name keeps its old mode forever, regardless of what a later `files[]` request asks for.

Task #738 (ADR-0106) already fixed `DELETE` leaking on-disk `upper`/`work`/`merged` directories for exactly this reason — but its own cleanup block was gated on `e != NULL` (a live `registry_find()` hit), reasoning that "`e == NULL` means this definition never once managed to autostart, so there's nothing on disk to clean up." That reasoning is only true for a definition that genuinely never created successfully. It's false for a `restart:"always"` container that crashed: `handle_container_event()` (the crash/exit path) calls `registry_remove()` unconditionally on every exit, live or crashed, well before `handle_restart_timer_event()`'s 2-second-later retry — so `e` is `NULL` at the exact moments a container is most likely to be `DELETE`d by an operator chasing a crash loop, and the overlay mount + its upperdir are still sitting there, untouched, exactly as task #738 describes for the case it did handle. Every `DELETE jumpbox1` this session landed in that gap, silently no-opping the one cleanup that would have fixed it, and every recreate under the same name reused the same corrupted upperdir — an unbreakable loop with no way out except picking a new name.

## Decision

`handle_delete()` (`daemon/src/main.c`) no longer skips disk cleanup when `e == NULL`. `container_root_for()`'s signature changed from taking a `const struct registry_entry *e` to taking a plain `const char *disk_name`, so it can be called with either `e->disk_name` (a live entry) or a `disk_name` re-parsed from the persisted `container_def`'s own stored `body` (the same `"disk"` field `create_container_from_body()` itself reads) when no live entry exists. The `umount2(merged, MNT_DETACH)` + `persist_remove_tree(container_base)` best-effort cleanup now runs unconditionally, using whichever `disk_name` was resolved. This is exactly as safe in the `e == NULL` case as the `e != NULL` case: nothing in this codebase ever explicitly unmounts a container's overlay on a plain crash/exit either (the same fact task #738's own reasoning already established for the live case), so the mount is equally still live and equally safe to tear down here, with no risk of a still-running process being disrupted (there is none).

The ownership-forgetting calls (`dns_server_forget()`, `dns_record_forget_owner()`, `ldap_server_forget()`, `ldap_user_forget_owner()`, `pki_cert_forget_owner()`, `ntp_server_forget()`, `ldap_ssh_target_forget()`) were also moved out of the `e != NULL` block to run unconditionally, for the same reason: a crashed-but-still-defined container being permanently `DELETE`d should release its DNS/LDAP/PKI/NTP/SSH-target ownership exactly like a live one does — there is no principled reason a still-registered DNS record should outlive a definition that's being removed for good, just because the container happened to be mid-crash at the moment of the call. `handle_delete()`'s own existing comment already states the intended contract ("DELETE always means gone for good") — this fix makes every part of the function actually honor it, not just `containerdef_remove()`.

## Verification

Full clean rebuild (`-Wall -Werror`), zero warnings. Full regression sweep under `sudo`/`dangerouslyDisableSandbox` (the only way to exercise real `clone3`/`mount`/`pivot_root` in this dev sandbox — see `CLAUDE.md`): `test_container_restart` (the test that specifically exercises `DELETE` on a definition that never autostarted, i.e. the original task #738 scenario this change must not regress) plus `test_daemon`, `test_images`, `test_dns`, `test_ldap`, `test_ntp`, `test_container_lifecycle`, `test_container_files`, `test_container_stats`, `test_disk_quota`, `test_routes`, `test_daemon_bind_ip`, `test_pkg_build_log`, `test_system_update`, `test_system_backup`, `test_pki`, `test_pkg`, `test_networks`, `test_network_interfaces`, `test_daemon_net`, and `test_daemon_devices` — all pass.

Live verification on 192.168.15.95 deferred to the same deploy round-trip as ADR-0114 (hostbuild + `system/update` + reboot); the corrupted `jumpbox1` on-disk state itself was worked around operationally for task #759's own immediate deliverable by using a fresh name (`jbnew1`) rather than waiting on this fix, since the two are independent — `jbnew1` is unaffected by `jumpbox1`'s specific stale upperdir regardless of when this fix lands.

## Consequences

- Every future `DELETE` of a crash-looped `restart:"always"` container now genuinely clears its on-disk state, closing the exact "no way out except renaming" trap this session hit live. `jumpbox1`'s own already-corrupted upperdir will be cleaned the first time it's next `DELETE`d under this fixed binary.
- `container_root_for()`'s signature change is internal-only (three call sites in `main.c`, none in any header consumed elsewhere) — no API/CLI-visible change, no test fixture change needed beyond the regression sweep above.
- This closes a real gap in task #738's own original fix (ADR-0106), not a regression introduced by this session's other work (ADR-0113/ADR-0114) — the bug has existed since task #738 shipped; this session is simply the first time a container name was reused across enough crash-then-delete cycles to make it visible.
