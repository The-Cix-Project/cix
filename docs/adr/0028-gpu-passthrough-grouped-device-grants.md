# 0028 — GPU passthrough: grouped multi-node device grants

## Status

Accepted

## Context

ADR-0017 (Phase 12 part 1) built PCI/USB device passthrough — `mknod` + one shared `BPF_CGROUP_DEVICE` program per container — and explicitly named GPU passthrough as the next intended consumer of that same mechanism. The user's own stated end goal includes GPU passthrough to an LLM container, on AMD hardware (`amdgpu`/ROCm) specifically — mainline, in-kernel, no proprietary-driver conflict with this project's own TCC-exclusive stance (which governs this project's own userspace code, not the kernel itself; the kernel is already built with its own normal toolchain via a real `make bzImage`, so this was never actually a TCC question, just worth confirming explicitly before assuming otherwise).

A real GPU needs several `/dev` nodes granted together, not one — for AMD, `/dev/dri/cardN` (the display/modeset node) and `/dev/dri/renderDN` (the render/compute node, the one ROCm/compute workloads actually open). Today's device model (`daemon/src/device.c`) is strictly one-id-to-one-`/dev`-node: `struct discovered_device` has no concept of "this id is actually a set." Confirmed directly with the user: a grouped logical id (`--device=gpu:0` grants everything one physical GPU needs, atomically) was chosen over requiring an operator to list each node by hand.

## Decision

**New `"gpu"` bus**, mirroring `usb`/`pci`/`net`'s existing shape exactly: `enumerate_gpu()` walks `/sys/class/drm/*`, treats any entry with its own `dev` file as a real node (connector subdirs like `card0-DP-1` have none, filtered out by that same check with no separate exclusion list needed), and resolves each node's `device` symlink to its parent PCI device's BDF address to group multiple nodes belonging to the same physical GPU under one stable `gpu:<idx>` index (first-seen order among distinct PCI addresses). Each real node gets its own `discovered_device` with id `gpu:<idx>:<node>` (e.g. `gpu:0:card0`, `gpu:0:renderD128`) — the *individual* member nodes are what `GET /v1/devices` lists, exactly like every other bus; the bare `gpu:<idx>` logical id is never itself emitted as a listed entry. `enumerate_pci_one()`'s existing placeholder-suppression (already skips re-listing a network controller generically, since `net:` represents it) gains PCI class `03` (display controller) alongside the existing `02` (network controller), for the same reason — one physical GPU should surface once, under `gpu:`, not twice.

**New `device_find_group()`, additive — `device_find()` itself is untouched.** Every existing `usb:`/`pci:`/`net:` id, and a `gpu:<idx>:<node>` id naming one specific GPU node directly, resolves via an exact match, identical to `device_find()`'s own existing behavior (in fact identical logic, duplicated at the same small scale `device_find()`'s own "re-walk sysfs every call, simple and correct rather than cached" shape already accepts — not worth unifying into one shared helper for two ~10-line linear scans). Only a bare `gpu:<idx>` id that has *no* exact match falls through to a prefix-expansion fallback (`"<id>:"`), returning every currently assignable `gpu:<idx>:*` member at once. This fallback is provably inert for every other bus: no existing id scheme ever has one full id as a strict prefix of another (USB ids end at `:serial` or `:port...`, PCI node ids end at `:node_name`, net ids have no third segment at all) — so this is a pure addition, not a behavior change for anything granted before this ADR.

**`create_container_from_body()`'s device-grant loop** (`daemon/src/main.c`) changes from a strict 1:1 `device_specs[i]` write (request-array index == grant-slot index) to a decoupled read/write-index loop: each requested id is resolved via `device_find_group()`, and every returned member is appended to the next `device_specs`/`device_attachments` slot, bounds-checked against `CONTAINER_MAX_DEVICES` incrementally rather than against the raw request array's own length (which no longer bounds the real grant count once one id can expand into several). `GET /v1/containers` reflects what was *actually* granted — the real expanded member ids/paths — not an echo of what was requested; a single `"gpu:0"` in a create request can and will show up as two separate entries in the response. This is the honest choice (the registry's own job is to report ground truth) but is a real, deliberately-documented behavior difference from every other field's usual "echoes what you sent" shape, called out explicitly in `docs/api/openapi.yaml` so it isn't a surprise.

## Consequences

- Verified in this dev sandbox to the extent actually possible: `GET /v1/devices` returns cleanly with zero `gpu:` entries here (confirmed directly — `/sys/class/drm` exists but is empty, no driver bound to the one PCI display-class device present), and `POST /v1/containers` with `"devices":["gpu:0"]` correctly 400s ("unknown or unassignable device") via `device_find_group()`'s genuine empty-expansion path — a real exercise of the new code, not a mock. Every pre-existing `usb:`/`pci:`/`net:` grant scenario re-verified unchanged (`device_find()` itself untouched).
- The positive path — a grouped id atomically expanding into multiple real grants, `mknod`'d and BPF-allowed together — is **not** verifiable in this sandbox and can't be until real GPU hardware (or a passthrough-capable QEMU target) is available. This is the same documented boundary ADR-0022 (real NIC passthrough) already has, for the identical reason: the mechanism is proven by construction and by its provable negative paths, the literal hardware proof is a real, known-open item, not silently assumed to work.
- **Kernel driver enablement (`CONFIG_DRM`/`CONFIG_DRM_AMDGPU`, currently absent from `image/kernel/qemu-part1.config`) and firmware-blob staging (`amdgpu` needs files from `linux-firmware` present under `/lib/firmware/amdgpu/` on the host root at driver-probe time, before any container exists — a new concern for `image/src/mkbootroot.c`, which has never staged firmware) are deliberately out of scope for this change.** Real, non-trivial work of their own, proposed as a focused follow-up once this mechanism itself has landed — not bundled in here.
- `CONTAINER_MAX_DEVICES` (16) is untouched — AMD's own real need (2 nodes per GPU: card + render) leaves enormous headroom; the incremental bounds-check exists for correctness in the general case (a hypothetical vendor needing many more nodes per group), not because 16 is remotely threatened today.
