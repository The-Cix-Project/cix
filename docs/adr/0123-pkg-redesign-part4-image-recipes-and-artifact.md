# 0123 — pkg/ redesign Part 4: image recipes + image-artifact fetch

## Status

Accepted

## Context

Part 4 of the five-part `pkg/` redesign (task #739/#769; Part 1 ADR-0120 renamed recipes to `build.sh`, Part 2 ADR-0121 added a configurable recipe-sync repo, Part 3 ADR-0122 added a local build-artifact cache plus a plain-HTTP precompiled-artifact server for individual packages). Part 3's own Consequences section flagged this explicitly: an "image recipe" concept mirroring package recipes, and a whole-rootfs artifact tier reusing the same plain-HTTP-server-plus-checksum pattern.

Two real design questions had to be resolved before writing any code, surfaced by reading the existing image machinery directly (`daemon/src/image.c`) rather than assumed:

1. **Editing an image's manifest today never triggers a build.** `PUT /v1/images/{name}/manifest` (task #721) only writes operator intent into `manifest.json` — realizing it into an actual rootfs still requires a separate `pkg install --image=X --name=Y` call per package, and the daemon enforces exactly one such job in flight at a time (`g_current_job_name`). A naive "apply this recipe" feature that tried to auto-sequence N real installs would be genuinely new orchestration logic with no existing precedent in this codebase, and a real correctness question (what happens to the manifest in the N-1 packages' worth of a partially-applied recipe if job N-of-N fails?). Asked the user directly rather than guess: confirmed v1 scope is a pure bulk-declare (the recipe's whole package list gets written via `image_manifest_set()` in one call, same effect as N manual `PUT`s, but not a build trigger) — an image recipe with any `rolling` entries has no single deterministic content anyway (ADR-0107's own accepted non-determinism), so a build-on-apply guarantee couldn't have been made for it regardless.
2. **Where the async whole-rootfs artifact fetch job should live.** `pkg.c` already has three instances of the identical fork+curl+pidfd+`cix_epoll_ctl`-registration idiom (hostbuild fetch, package-install fetch, Part 2's repo-sync fetch) — none of them share a single function, each is its own small, purpose-built job. Retrofitting an image-artifact fetch into the package-install job's own `pkg_fetch_completed()`/`pkg_build_completed()` state machine (built entirely around spawning a build container and running a recipe's `pkg_build()`/`pkg_install()` shell functions) would have been a real, structural misfit — an image-rootfs-tarball fetch has no build container, no shell script, nothing in common with that state machine except "curl a file, verify it." Confirmed with the user: extend `pkg.c`'s existing job-engine *pattern* (a fourth instance of the same fork+curl+pidfd idiom, its own small completion function, still gated by the same `g_current_job_name` single-job guard so it can never race a real package install over the same shared `g_packages[]`/image-rootfs state) rather than force it through package-install's own container-spawning machinery.

## Decision

**Image recipe** (`daemon/src/pkg.c`'s new `image_recipe_*` functions, `<data-dir>/pkg/image-recipes/<name>.recipe` — name-keyed, no version-keying of its own since the image's own content-addressed versioning, ADR-0108, already tracks distinct resolved states): a plain text file, recipe name == target image name (a 1:1 relationship, not a decoupled mapping):

```
image_packages="bird:pinned:2.19.1 keepalived:rolling:2.3.4"
image_artifact_sha256="<optional>"
```

`image_packages=` is a whitespace-separated list of `package:mode:version` tokens (`mode` is `pinned` or `rolling`, matching `enum image_pkg_mode` exactly). `CRUD` via `GET`/`POST /v1/images/recipes`, `GET`/`DELETE /v1/images/recipes/{name}` — deliberately the same shape as Part 2's package-recipe endpoints (`cixctl image recipe add|show|rm|ls`), including the same reserved-path-before-generic-fallback dispatch ordering `PKG_RECIPES_PREFIX` already established (an image literally named "recipes" would otherwise be unreachable via `GET`/`DELETE /v1/images/{name}`).

**Applying a recipe** (`POST /v1/images/{name}/apply-recipe`, `pkg_image_recipe_apply_start()`): resolves per the two decisions above —

- **Common case (bulk-declare, synchronous, 204)**: for every entry, `image_manifest_set(image, package, mode, version)` — exactly what N manual `PUT /v1/images/{name}/manifest` calls already do today, just in one request. No rootfs is touched; `current_version` is unchanged. An operator (or automation) still runs real `pkg install` calls afterward to actually realize the declared intent, unchanged from today's manifest-editing workflow.
- **Fast path (async, 202)**: only when the recipe is entirely `pinned` **and** declares `image_artifact_sha256` **and** a plain-HTTP artifact server is configured (Part 3's `pkg_artifact_*` config, reused as-is — same `base_url`/token, under a distinct `images/` URL prefix, `<base_url>/images/<name>-<hash>.tar.gz`, so package and image artifacts never collide in one server namespace despite sharing one config surface — a second, near-identical config resource would have violated One Source of Truth for what is genuinely the same "plain HTTP + bearer token" server). The target hash is computed identically to how a real build would compute it — `image_hash_manifest_string()` over the canonical, sorted `"name@version,..."` string built from the recipe's own declared entries — so the fetched artifact's URL is fully predictable ahead of time from the recipe text alone. On successful fetch + checksum verification (`pkg_run_capture_sha256()`, the same verify-before-trust primitive Parts 2 and 3 already use — the artifact server itself is never a trust boundary), the tarball is extracted directly as the new version's *entire* rootfs (`image_version_rootfs_path()` + a plain `tar -xzf`, no copy-forward staging needed since this content isn't built on top of a prior version — it fully replaces it), `image_record_version()` commits it, `image_manifest_set()` declares every entry, and — critically — `pkg.c`'s own `g_packages[]` table is mirrored (each entry marked `PKG_STATE_INSTALLED` against the image) so `GET /v1/pkg` and the web dashboard's own "what's installed" view match the rootfs that was just written, not just `manifest.json`'s intent. Per-package file lists are left empty: a whole-rootfs tarball carries no per-package attribution, the same accepted, documented gap hostbuild packages already have (task #670). Any miss (fetch failure, checksum mismatch, extraction failure) leaves the image completely untouched — never half-applied — and is recorded for `GET /v1/images/recipe-apply-status` to report.

**Job engine**: a fourth small instance of `pkg.c`'s existing fork+curl+pidfd idiom (`pkg_image_recipe_apply_start()`/`pkg_image_recipe_apply_completed()`, `CONN_IMAGE_RECIPE_FETCH` in `main.c`, `register_image_recipe_fetch_pidfd()`/`handle_image_recipe_fetch_event()` mirroring Part 2's `pkg_sync`'s own registration functions almost verbatim) — not a new pattern, not entangled with package-install's own state machine. Mutual exclusion with real package installs/hostbuilds is achieved for free: the async path checks and sets the exact same `g_current_job_name` guard `pkg_install_start()`/`pkg_hostbuild_start()` already check, so an image-recipe artifact apply and a real package install can never run concurrently and race over the same shared `g_packages[]`/image-rootfs state.

## Verification

Full clean rebuild (`-Wall -Werror`), zero warnings. New `test/test_image_recipe.c`: a fresh recipe list is empty; a bulk-declare recipe (mixed pinned/rolling) applies synchronously (204), the manifest gains both entries, and `current_version` is confirmed unchanged (the empty-manifest hash) — proving no rootfs was touched; applying a recipe for an image with none stored is 404; a malformed `image_packages=` entry is rejected (400) before ever being written; a fully-pinned recipe with a real declared checksum and a real `python3 http.server` standing in for the artifact server applies asynchronously (202), reaches `state=success`, and `current_version` matches the independently-precomputed manifest hash — the test computes its own expected hash and artifact URL ahead of time, from the recipe text alone, and confirms the daemon requested exactly that URL; the manifest and `g_packages[]` are both confirmed updated; the actual extracted file is confirmed present in the new rootfs on disk at its expected path; recipe deletion round-trips (404 after). Full regression sweep (28 tests) all pass, including the pre-existing `test_images.c` and `test_pkg.c` (manifest editing, dependency chains, hostbuild, upgrades — all still exercising the completely unmodified real-install path).

## Consequences

- An image's whole package-list intent can now be declared in one git-syncable text file instead of N individual `PUT /v1/images/{name}/manifest` calls — and, git-tracked, is naturally sync-able via Part 2's existing repo mechanism in a future extension (not wired in this part; Part 2's sync currently only walks `pkg/recipes/`, not `pkg/image-recipes/` — a deliberate, separate future decision, not assumed here). **Implemented in ADR-0149**, which also moved both trees to a unified `recipes/package/` + `recipes/image/` git layout — this ADR's own `<data-dir>/pkg/image-recipes/<name>.recipe` daemon-side storage path and its unversioned API are otherwise unchanged by that later decision.
- A fully-pinned image recipe with a precompiled artifact available skips every per-package build entirely — a whole-image install becomes as fast as Part 3's package-level cache hit, at the image granularity.
- A recipe with any `rolling` entries, or with no matching/configured artifact, still requires real follow-up `pkg install` calls per package to realize its declared intent — this is not a regression from today's manifest-editing workflow, it's the same workflow with a bulk-declare convenience layered on top.
- Same "recipes in git, binaries never in git" discipline Part 3 established for packages, now applied at the image layer: only the recipe text (a package list) is ever git-tracked; the compiled whole-rootfs tarball only ever lives on the plain-HTTP artifact server or gets assembled locally via real `pkg install` calls.
- Sets up Part 5 (rolling containers + restart jitter), which is expected to use the same artifact-tier fast path as part of its own update mechanism for images with rolling package entries.
