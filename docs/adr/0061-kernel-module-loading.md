# 0061 — kernel module loading: root-critical drivers stay built-in, only network/USB become modules

## Status

Accepted

## Context

Part 3 of the bare-metal-readiness plan — the largest, most novel part, by the plan's own admission: real target hardware this project has never seen before needs broader driver coverage than the fixed, hardwired QEMU/VirtIO set every prior phase has tested against, but hardcoding every possible NIC/storage/USB chipset combination as always-resident `=y` would bloat the kernel and still never cover everything. Loadable modules are the real answer real distros already use — but this project's own architecture has a genuine constraint distros don't: no initramfs (ADR-0014). The kernel mounts root directly, with no earlier stage able to `modprobe` anything first.

This surfaced a real design question the plan's own original text didn't fully resolve: which drivers are safe to make loadable at all? Working through it directly: whichever controller a real target machine's root partition happens to live on **must** already be present the moment the kernel tries to mount root — it cannot be a module, because there is no mechanism in this project's boot sequence to load one before root is reachable. Confirmed against `CONFIG_SATA_AHCI`, already `=y` in `image/kernel/qemu-part1.config` for exactly this reason (the installer ISO's own ATAPI CD-ROM, mounted directly, no initramfs there either).

## Decision

**Storage controllers that could plausibly hold root stay built directly into the kernel (`=y`), never modules.** `image/kernel/qemu-part1.config` gains `CONFIG_BLK_DEV_NVME=y` and `CONFIG_BLK_DEV_MD=y` (+ `MD_RAID0`/`MD_RAID1`/`MD_RAID10`/`MD_RAID456`) alongside the already-`=y` `CONFIG_SATA_AHCI` — generalizing the exact reasoning that option already established to a real target machine whose root controller isn't known in advance, rather than guessing at "the QEMU-only common case is good enough."

**Network and USB drivers, never needed to reach root or console input in this project's model, become real loadable modules (`=m`).** `CONFIG_E1000E`, `CONFIG_IGB`, `CONFIG_IXGBE` (Intel), `CONFIG_R8169` (Realtek), `CONFIG_TIGON3` (Broadcom, module name `tg3` — differs from its own Kconfig symbol, confirmed against the real kernel source `Makefile`, not guessed), `CONFIG_USB_EHCI_HCD`, `CONFIG_SCSI` + `CONFIG_USB_STORAGE`. `CONFIG_USB`/`CONFIG_USB_XHCI_HCD`/`CONFIG_USB_HID` stay `=y`, unaffected — already built-in for the installer's own console keyboard input (an earlier, unrelated decision, confirmed still correct: XHCI already covers USB 3.0 and its own backward-compat mode for USB 2.0/1.1 devices on any remotely modern board, so EHCI only ever matters for genuinely old hardware with no XHCI controller at all).

**Broadcom NetXtreme II (`bnx2`) deliberately excluded from the curated module list**, unlike every other driver here: it is a fully firmware-driven NIC that cannot function *at all* without a real firmware blob loaded into the card first, unlike e.g. `R8169`, which degrades gracefully (works on many chip revisions with no firmware, only newer revisions strictly need it). Staging real `linux-firmware` blobs for `bnx2` is real, separate scope, not done in this pass — a known, honest gap, not silently dropped from the list without a reason on record.

**`kmod` (modprobe/depmod/insmod/lsmod/modinfo/rmmod) is real, unmodified upstream software** (`pkg/recipes/kmod.recipe`, kernel.org's own release tarball) — this project's own established "reuse real software, never hand-roll dependency resolution" posture (bird, keepalived, coreutils, ...), not a raw-C reimplementation of modprobe's own dependency graph. All four optional compressed-module/PKCS7-signature backends (zstd/xz/zlib/openssl) are left at their real upstream default (disabled) — this project's kernel config never enables `CONFIG_MODULE_COMPRESS`, so plain `.ko` files are all `modprobe` ever needs to find, and adding those libraries as build dependencies for a capability nothing here uses would be unjustified scope. `--sbindir=/usr/bin` at configure time: this project's images have no `/sbin` or `/usr/sbin` at all (usr/bin-only FHS convention) — `kmod`'s own `install-exec-hook` symlinks its six tool names into `$(sbindir)` by default, which would otherwise land somewhere nothing on this project's own `PATH` (`/usr/bin:/bin`) ever looks.

**`pkg/recipes/kernel.recipe` (the existing hostbuild recipe, ADR-0056/ADR-0057) is extended, not duplicated**, to also `make modules` + `make INSTALL_MOD_PATH=$PKG_DESTDIR modules_install` + a real `depmod -b $PKG_DESTDIR "$(make -s kernelrelease)"` — the version argument is the freshly-built kernel's own `kernelrelease` output, never the build container's own running `uname -r` (a bare `depmod` with no version argument silently defaults to that instead, which would never match). This requires `kmod` already installed on `--build-image=` — a real, hard precondition, the same shape `gcc.recipe`/`libc-dev.recipe`/etc. already have among each other.

**`mkbootroot.c` gains two new, optional (`""` = skip) trailing arguments**, `modules-dir` and `kmod-bin-dir` — the same tolerant-default shape `firmware-dir` (ADR-0029) already established, extended rather than given a second, parallel mechanism. `modules-dir` (a kernel hostbuild's own harvested `lib/modules/` tree) is staged via a new `test_image_fixture_copy_dir_recursive()` (real `cp -a`, correct symlink/permission handling — `copy_dir_files()` is flat-only and cannot walk `kernel/drivers/...`'s own nesting). `kmod-bin-dir` (kmod's own `usr/bin`, six tool names all symlinked to one real `kmod` binary) is staged via the *existing* flat `copy_dir_files()` — its `stat()` (not `lstat()`) already dereferences each symlink into a real, independently-readable copy of the same binary at every tool name, which works identically to a preserved symlink from `modprobe`'s own argv[0]-dispatch perspective, at the cost of a few hundred KB of harmless duplication, not a new symlink-aware copy primitive.

**`thincd`'s own boot sequence gains `load_boot_modules()`**, a curated, best-effort `modprobe` of the network/USB list above via the real, freshly-staged `/usr/bin/modprobe` — called from `main()` (not from inside `boot_init()`, which stays purely about mounts per Part 0.5's own already-established boundary), gated on `init_mode`, and **before** `bootstrap_management_network()`, not after: that function attaches a *named* physical interface, which the kernel must have already detected as a real netdev by then — on real hardware, that detection only happens once the matching driver is loaded. Best-effort per module, mirroring `cgroup_enable_io_accounting()`'s own "a real machine this project has never seen before might simply not have this exact capability" posture — a missing driver for hardware a given box doesn't have is the overwhelmingly common, expected case here (the list spans several vendors' chipsets; no single real machine has all of them), never a reason to fail boot.

## Consequences

- A real, complete kernel-with-modules hostbuild only succeeded on the 11th end-to-end attempt against this project's own long-lived "dev" build image — every one of the ten prior failures was a genuine, distinct gap on that specific image or a genuine bug in `kernel.recipe` itself, found and fixed one at a time via the real build's own error output, never guessed at:
  - `sed` was never installed on the image at all (`sed.recipe` already existed in the repo, just never applied here).
  - `bison` had been installed *before* the m4sugar/skeleton staging fix (ADR/ROADMAP history, "Phase 40 part 2") landed, so its own `usr/share/bison/` runtime data was still missing despite the recipe itself already being correct — fixed by removing and reinstalling fresh (`pkg install --upgrade` alone doesn't force a reinstall when a recipe's own `pkg_version` string hasn't changed, only its content; `pkg rm` + a fresh `pkg install` does).
  - `grep` was never installed at all (`merge_config.sh` needs it).
  - `bash` needed reinstalling to pick up its own `/bin/sh` symlink — this specific image predated that fix; without it, every `popen()`-based Kconfig `$(shell ...)` macro fails with a misleading "Cannot allocate memory" (the same ADR-0056 symptom class), not the expected "No such file or directory".
  - `libc-dev` needed reinstalling to pick up its own pthread compat archives (ADR-0057) — `objtool`/`scripts/sorttable`, both new host-tool builds `CONFIG_MODULES=y` pulls in, need `-lpthread`.
  - `zlib` and `elfutils` (libelf) were never installed — also new dependencies of `objtool` once `CONFIG_MODULES=y` is set.
  - `bc` was never installed — `include/generated/timeconst.h`'s Kbuild rule needs it, unconditionally, for any kernel build, module-enabled or not.
  - `diffutils` was never installed — surfaced only as non-fatal `sync-check.sh` warnings, not a real blocker, but installed alongside `bc` while already fixing that gap.
  - `findutils` (`xargs`) was never installed — `kernel/locking`/`kernel/printk`/`kernel/sched`'s own `built-in.a` archiving rule needs it once building `modules` as part of the same invocation as `vmlinux` (see below).
  - `gzip` was never installed — the final `bzImage` compression step needs it.
  - A genuine bug in `kernel.recipe` itself, not a missing dependency: `pkg_build()` originally ran `make bzImage` and `make modules` as two **separate** `make` invocations. Every individual module compiled cleanly under that shape, but the final `modpost` link step failed with "vmlinux.o is missing" and hundreds of "undefined!" errors for ordinary exported kernel symbols (`kfree`, `dev_set_name`, ...) — a second, independent `make modules` invocation does not reliably see the `Module.symvers`/`vmlinux.o` context the first invocation's `vmlinux` link step produced. Fixed by combining both targets into one invocation, `make bzImage modules`, the standard, documented way to build both together.
- Verified: `test/test_mkbootroot_firmware.c` extended with a new scenario proving `modules_dir`/`kmod_bin_dir` staging directly (a real recursive nested-directory copy landing at `lib/modules/<version>/kernel/drivers/...`, and a real symlink-dereferencing copy landing a working `modprobe` at `usr/bin/modprobe`) — full clean rebuild, 3 consecutive passing runs. `kmod.recipe` verified installed end-to-end onto a real "dev" image through the real thinC pipeline (`modprobe --version` runs correctly from the installed image). `kernel.recipe`'s modules-build extension verified via a real, successful hostbuild run against the "dev" image producing a genuine `bzImage` + 18 real `.ko` files (all curated Part 3 drivers plus their real dependency modules, e.g. `mdio-bus`/`libphy`) with correct `depmod` metadata (`modules.dep`, `modules.alias`, ...). The resulting artifact's own `lib/modules/6.18.40/` tree and a dedicated real `kmod`-tools directory were then fed directly through a real `mkbootroot` invocation (not just the synthetic-fixture test above) — confirmed the assembled staging root contains the identical 18-module nested tree and 7 real, independent, correctly-dereferenced kmod tool binaries (`modprobe` confirmed as a real, dynamically-linked ELF executable), end to end from a genuine kernel hostbuild through to a real assembled control-plane root.
- **Not verified, per Zen:** a real, complete QEMU boot with `load_boot_modules()` actually running against a real assembled control-plane squashfs has not happened in this pass — deliberately deferred and batched with Part 2's own `CONFIG_CPUSETS=y` and Part 4's own quota-related kernel config additions into one combined rebuild+boot cycle, per this plan's own kernel-config-consolidation decision, rather than three-plus separate multi-hour cycles. `bnx2` firmware staging (see above) remains unstarted. Part 3 is explicitly the part of this whole plan most likely to need real further iteration once tested against actual bare-metal hardware this project has never seen before — a genuine QEMU-only test, even once it passes, cannot fully stand in for that.
