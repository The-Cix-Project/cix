# 0068 — A dedicated daemon bind IP, decoupled from the management network's own address

## Status

Accepted

## Context

Raised directly by the user during the same discussion that produced ADR-0067's `gateway`→`address` rename: once it was established that `is_management` just designates *some* network as the one whose own address cixd happens to bind to (Part 0.5, ADR-0058), a natural follow-on question was whether that coupling should be mandatory. A bridge carrying the management network's own address might also carry other real traffic — containers, a routing daemon, a shared VRRP address — and an operator might reasonably want cixd itself pinned to a specific, separate address on that same bridge rather than sharing the network's own one.

Confirmed directly, not assumed, that nothing in the kernel or this codebase's own `rtnetlink.c` stood in the way: `rtnl_addr_add_ipv4()`'s own flags are `NLM_F_CREATE | NLM_F_EXCL` — `NLM_F_EXCL` only rejects an exact duplicate of an address already present, not a second, different address on the same link. A Linux bridge (like any Linux interface) can carry an arbitrary number of IPv4 addresses simultaneously; this was never a real constraint, only an unexamined assumption carried over from Part 0.5's original design, which reused a network's own address for cixd's bind purely because it was already there and already true of every network (see ADR-0067's own "always host-bound" finding).

`daemon_config.c` had no notion of a second address at all — `bind` was always derived live from `g_bind_addr`, itself always set from whichever network's own `address_be` was current management. Adding a second, independent address meant three things had none of yet: a new persisted field to remember it, a new rtnetlink primitive to remove one (nothing in this codebase had ever needed to *remove* an address from a link, only add one), and a real design decision about how it interacts with `management_network` repointing — since a dedicated bind IP, once added to a specific bridge, doesn't automatically mean anything on a *different* bridge if management moves elsewhere.

## Decision

**`daemon_config.c` gains an optional persisted `bind_ip` field** (`daemon_config_bind_ip()`/`daemon_config_set_bind_ip()`), `NULL` by default — unset means exactly today's Part 0.5 behavior (bind to the management network's own address), so this is purely additive, no behavior change for anyone who never sets it.

**A real, existing validation rule is reused, not duplicated**: `network_address_str_is_valid()` is `address_str_is_valid()` (already used by `network_create()`'s own `address_str` argument) exposed as a new public `network.h` function, so `bind_ip`'s subnet-membership check (real address, within the target network's subnet, not the network/broadcast address) is the *identical* rule every other address on this codebase's networks already has to pass — not a hand-rolled second implementation of the same logic.

**A new `rtnl_addr_del_ipv4()` primitive** (`netplane/`), the mirror-image of the existing `rtnl_addr_add_ipv4()` — `RTM_DELADDR`, same argument shape, no `NLM_F_CREATE`/`NLM_F_EXCL` (nothing to create). The first address-removal primitive this codebase has ever needed.

**Ordering matches every other live-reconfiguration path this handler already has**: the new address is added to the bridge and the listener rebound to it *before* anything is persisted; the previous `bind_ip` (if any) is only removed from its own bridge, and only after everything else has already succeeded — "create the new thing, prove it works, then tear down the old one," the same discipline `handle_daemon_config_put()`'s own listener-rebind logic already established for `management_network` repoints. A `PUT` that only partially succeeds never leaves a stale persisted claim about what's actually bound.

**Repointing `management_network` without a fresh `bind_ip` in the same request implicitly clears any previously-set one.** A dedicated `bind_ip` is inherently *relative to whichever network is currently management* — it was validated against that network's subnet and lives on that network's specific bridge. Silently carrying an old custom address over onto an unrelated new bridge would either be meaningless (wrong subnet) or, worse, coincidentally valid on the new bridge while pointing at an address the operator never actually chose for it. Per this project's standing "clean cut-over" instruction, this is not treated as a case needing a compatibility exception — the invariant is enforced outright.

**Idempotent re-submission of the same `bind_ip` is a deliberate no-op**, not a `400`: since `rtnl_addr_add_ipv4()` uses `NLM_F_EXCL`, re-adding an address the bridge already carries would otherwise spuriously fail every time an operator's automation re-asserted the same desired state.

**The old `bind_ip`'s removal is deferred by a short, fixed timer, not done synchronously in the same request that triggers it — a real hazard found empirically, not by inspection.** The first implementation deleted the stale address immediately after writing the response, reordered so the write happened first. Live testing against a real daemon still hung indefinitely: when the very connection carrying the `PUT` that clears/replaces `bind_ip` has that address as its own *local* endpoint — the natural way an operator reaches the daemon, since they're necessarily talking to whatever it's currently bound to — the response `write()` succeeds at the socket-buffer level, but the kernel's actual transmission of those bytes is asynchronous relative to that syscall returning; deleting the local address moments later can leave the segment permanently undeliverable, and the client hangs forever waiting for bytes that were "successfully" written but never left the box. Reordering C statements doesn't fix an asynchronous kernel-level race. The fix reuses this codebase's own existing `arm_restart_timer()` pattern (container restart backoff) — a new `CONN_BIND_IP_CLEANUP` one-shot `timerfd`, firing 2 seconds later, comfortably longer than any real same-host TCP round trip and irrelevant to the caller (the response has already gone out; nothing waits on this cleanup). `network_find_management()`'s value at request-received time is captured before any repoint this same request might apply, so the *old* bridge is always the one actually cleaned.

## Consequences

- Verified live against a real daemon: adding a route through a network's own address confirmed `network.name` really is reachable as a bridge ifname for `rtnl_addr_add_ipv4()`/`rtnl_addr_del_ipv4()` to target directly (the same finding ADR-0067's own Part 4 routes-UI work already relied on for its per-network filter).
- `GET /v1/system/daemon-config`'s `bind` field now means "wherever cixd is actually bound" (the dedicated `bind_ip` when set, the management network's own address otherwise) — `bind_ip` is reported separately so a client can distinguish the two cases rather than inferring it.
- A `bind_ip` left orphaned on a bridge by a failure between "add new" and "persist", or by the daemon exiting inside the 2-second cleanup-timer window, is treated as a harmless leak, consistent with this codebase's existing risk tolerance elsewhere (e.g. `network_create()` doesn't roll back a partially-created bridge on a later JSON-persist failure either) — reported plainly via a `500` where a request-time failure is involved, not silently swallowed, and never claims a persisted state that isn't real.
- CLI (`cixctl daemon-config set --bind-ip=A.B.C.D` / `--clear-bind-ip`) and web dashboard (a "Bind IP (optional)" field + "Clear bind IP" checkbox on the Daemon page) both gained the same capability the REST endpoint offers, per the API-First Mandate — neither surface has any capability the API doesn't.
