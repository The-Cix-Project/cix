# 0127 — Optional syslog forward targets (syslog-1/syslog-2)

## Status

Accepted

## Context

Part 2 of the logging/web-UI epic ([ADR-0126](0126-transparent-container-log-capture.md) was Part 1). The user's own request: "I want to be able to create syslog-1 and syslog-2, redundant, and run a syslog daemon, on them" — external, standard syslog tooling on top of this platform's own container logs, for operators who already have such tooling.

Resolved with the user directly (via `AskUserQuestion`, before any code was written): the consolidated log store (`logstore.c`, ADR-0070/ADR-0126) stays the one source of truth the REST API and web UI ever read from — `syslog-1`/`syslog-2` are an **optional, redundant forward target**, never a second store the platform itself depends on. This follows directly from the API-First Mandate: a real syslog receiver has no REST API of its own, so it can never be the thing `thincd`'s own API/UI reads from without introducing a second, harder-to-keep-consistent copy of the same data (a "No Parallel Implementations" violation). It also matches the DNS/NTP precedent already established in this codebase: the actual protocol server is always a real, unmodified upstream binary running as an ordinary containerized workload (`dnsmasq.recipe`, `chrony.recipe`) — this platform's own daemon code is a client/registrar, never a hand-rolled reimplementation of the protocol (ADR-0007).

## Decision

**Registration mirrors `ntp_server_register()`/`_unregister()`/`_forget()` almost exactly** (`daemon/include/syslogfwd.h`/`daemon/src/syslogfwd.c`, new module): `POST`/`GET`/`DELETE /v1/syslog/targets` registers a running container by name as a forward target. Pure bookkeeping — no pid/pidfd, a target's live IP is resolved fresh from the registry at every send, never cached. `syslogfwd_target_forget()` is wired into the same container-delete cleanup path as `ntp_server_forget()`/`dns_server_forget()`, so a deleted target's registration can't outlive it.

**The one real design difference from NTP's own registration**: NTP's is an inbound query thincd itself initiates and waits on a reply for (a real async job with epoll/timerfd machinery). Syslog forwarding is outbound, unacknowledged, fire-and-forget UDP triggered by unrelated container-output activity — no job state, no epoll registration, just a single persistent non-blocking UDP socket opened once at `syslogfwd_init()` and reused for every send via `syslogfwd_send()`. A send failure (target unreachable, EAGAIN, container stopped) is silently dropped — UDP syslog has never had delivery guarantees, and `logstore.c` already holds the durable, replayable copy of everything this module ever sends. This asymmetry is a direct, honest consequence of the two protocols' own real shapes, not an inconsistency.

**Scope: container-sourced entries only.** `forward_container_output_to_logstore()` (`main.c`, ADR-0126) calls `syslogfwd_send()` right alongside its existing `logstore_write_container()` call, for every complete captured line. `kernel`/`thincd`/`audit` entries are **not** forwarded — matching the user's own scoping ("all the logs for the containers"), and keeping the wire format simple (one severity per container line, `"info"`, same accepted v1 boundary ADR-0126 already documented for capture itself).

**Wire format: real RFC 3164** (`<PRI>Mmm dd hh:mm:ss HOSTNAME TAG: MSG`). `PRI` = `local0` facility (16) × 8 + severity, where severity comes from a new public `logstore_level_severity()` — a thin wrapper over `logstore.c`'s own existing internal `level_rank()` (RFC 5424 numeric scale), so that mapping is computed in exactly one place rather than duplicated. `HOSTNAME` is the *originating container's own name* (the container is the real source of the message, not this daemon) — `TAG` is always `thincd`, identifying this daemon as the relay. A target never receives its own captured stdout forwarded back to itself (`syslogfwd_send()` skips a target whose name matches the originating container), preventing a trivial self-forward loop if an operator ever registers a receiver container as its own target by mistake.

**`sysklogd` (troglobit/sysklogd fork, real GitHub release tarball) is the reference receiver recipe** (`pkg/recipes/sysklogd/2.7.0/build.sh`), for the same reason `dnsmasq.recipe`/`chrony.recipe` exist: proves the design against a real, unmodified upstream binary, not just this daemon's own sender code. Confirmed via a real local build in this sandbox: sysklogd's own real autotools `./configure` builds clean under TCC, with the exact same `<regex.h>` VLA-in-prototype parse failure ADR-0126/`CLAUDE.md` already documented for `logstore.c` (`syslogd.c`/`socket.c` both include `<regex.h>` for `syslog.conf`'s own selector matching) — fixed identically, via `CFLAGS=-D__STDC_NO_VLA__=1` at build time rather than a source patch, since this is unmodified upstream source. `/etc/syslog.conf` (staged into the image at `pkg_install()` time, one catch-all rule) writes to `/var/log/messages`, which lives in the container's own persistent overlay upperdir — not reset on restart, unlike `/run` (ADR-0119) — so an operator's external tooling has something durable to read across restarts.

## Verification

Full clean rebuild (`-Wall -Werror`), zero warnings. Local manual smoke test of the real `sysklogd` binary (this sandbox, before touching the real recipe or the box) confirmed it binds UDP `:514`, receives a hand-crafted RFC 3164 datagram, and writes it to the configured log file correctly. New `test/test_syslogfwd.c`: the registration bookkeeping half mirrors `test_ntp.c`'s own coverage exactly (404 for a nonexistent/not-running container, 201/409/204 for real CRUD, forget-on-delete) — then a genuine wire-level proof, real network + a real receiver container (`test/syslog_recv_child.c`, a small fixture binding real UDP `:514` inside its own container netns) + a real sender container (`output_child`, reused from ADR-0126's own fixture) — confirmed via the receiver's own transparently-captured stdout (Part 1's own mechanism, no new plumbing needed) that it genuinely received a well-formed datagram naming the real sender container as `HOSTNAME`, `thincd` as `TAG`, and the sender's own known message verbatim. Full regression sweep (37 test binaries) confirms zero regressions.

## Consequences

- Operators who want standard external syslog tooling on top of this platform's own container logs now have a real, supported path to it, without the platform's own API/UI ever depending on that tooling being present or correct.
- One more UDP socket held open per daemon lifetime (opened once, reused forever) — negligible resource cost, consistent with every other long-lived fd this daemon already holds.
- Container-sourced entries are the only thing forwarded; a future part could extend this to `kernel`/`thincd`/`audit` if a real operator need for that surfaces, but it wasn't asked for here and forwarding this daemon's own diagnostic chatter about the forwarding mechanism itself would need careful loop-avoidance thought first — deliberately out of scope for now.
- `sysklogd` is one reference recipe, not a hard platform dependency — any real syslogd an operator prefers to build and run as a registered target works identically, since the wire format is standard RFC 3164 UDP, not anything sysklogd-specific.
