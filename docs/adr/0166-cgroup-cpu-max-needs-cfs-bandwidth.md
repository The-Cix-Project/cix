# 0166 — `cpu.max` needs `CONFIG_CFS_BANDWIDTH`, not just `CONFIG_CGROUP_SCHED`/`CONFIG_FAIR_GROUP_SCHED`

## Status

Accepted (kernel config fix committed; the actual kernel rebuild + redeploy is deferred — see Consequences)

## Context

ADR-0165 gave the pkgbuild sandbox real `memory_max`/`cpu_max` cgroup limits, deployed to 192.168.15.95 as part of the Phase 5 rebrand migration (ROADMAP Part 168). The very first ordinary `pkg install` under those limits failed 100% of the time with a bare `could not start the build container` — a real, fully reproducible regression. Disabling the limits (`memory_max: 0, cpu_max: null`) immediately restored success, confirming the limits themselves were the trigger, not something else changing at the same time.

The box has no shell, so diagnosing this needed real, queryable log output — which took three redeploy cycles to actually get right (ROADMAP Part 165 has the full blow-by-blow): a first round of `perror()` calls in `cgroup_create()`/`container_create()` produced nothing, because `perror()` writes to real stderr and nothing mirrors stderr back into the log store (the reverse is true — `logstore_write()` also prints to stderr for boot visibility, not the other way around). Once the actual logging was moved to `handle_pkg_fetch_event()` in `main.c` (the real call site with log-store access), the first genuine diagnostic appeared: `container_create failed: No such file or directory`. A further round adding `container_create_last_error_step()` (a precise parent-side equivalent of the existing child-side diag_pipe mechanism) pinpointed the exact failing call: `cgroup_create: write cpu.max: No such file or directory`.

`memory.max`/`pids.max` writes both succeeded (no earlier error) — only `cpu.max` was missing entirely from the freshly-created cgroup leaf's own directory. Checked directly against the real kernel source (`kernel/sched/Kconfig` via `init/Kconfig`, `torvalds/linux`, both the `v6.18` tag and current `master`): `CONFIG_CFS_BANDWIDTH` is a distinct Kconfig symbol, `depends on FAIR_GROUP_SCHED` (already satisfied in `image/kernel/qemu-part1.config`), `default n`. `CONFIG_CGROUP_SCHED`/`CONFIG_FAIR_GROUP_SCHED` alone only provide `cpu.weight`/`cpu.weight.nice` (proportional scheduling) — the cgroup v2 "cpu" controller only exposes `cpu.max`'s quota/period bandwidth-limiting file when `CFS_BANDWIDTH` is separately enabled. This project's kernel config had an existing comment claiming otherwise ("`CONFIG_CGROUP_SCHED` above ... covers cpu.max's bandwidth limiting") — wrong, now corrected in the same commit as the fix.

The exact same class of gap as `CONFIG_INOTIFY_USER`'s own history (ADR-0113): a real, previously-undiscovered kernel Kconfig omission, default-off, never exercised because nothing had a real reason to request a genuine `cpu.max` value on this exact box until ADR-0165 shipped.

## Decision

Add `CONFIG_CFS_BANDWIDTH=y` to `image/kernel/qemu-part1.config`, immediately below `CONFIG_FAIR_GROUP_SCHED=y`, with a comment correcting the prior wrong claim and explaining the real dependency.

## Consequences

- **The kernel config fix is committed; the actual rebuilt kernel is not yet deployed to 192.168.15.95.** `pkg-build-config`'s `memory_max`/`cpu_max` limits stay disabled (`0`/`null`) on that box until a kernel carrying this fix is built, deployed, and rebooted onto — re-enabling them blind again would just reopen the exact regression this ADR documents.
- Building that kernel needs a real gcc-equipped build image (`kernel.recipe`'s own documented `--build-image=` requirement; TCC alone cannot build a Linux kernel — its own `scripts/kconfig`/module build tooling assumes GCC), which this box does not currently have. A first attempt to build one (a fresh `dev` image, `gcc` → `binutils` via `pkg_depends`) hit a genuine, separate TCC parser failure compiling real `binutils` 2.42 source (`bfd/bfd.c:733`, a `TLS bfd_error_type` declaration TCC's parser doesn't accept) — a real, previously-undiscovered TCC compatibility gap in its own right, deliberately **not** chased further this session: it's a distinct problem from this ADR's own root cause, and this project's own Iterative Workflow mandate (outline → execute → verify, one system at a time, never rushed) argues against layering a second unsolved compiler issue onto an already-long investigation. Needs its own dedicated session.
- `kernel/6.18.40-2` (the new recipe revision carrying the fix) also fixes a smaller, unrelated gap found along the way: its `pkg_source` used to reference a stale `http://127.0.0.1:8901/qemu-part1.config` placeholder from an earlier scratch LAN session; now fetches the real config directly from this repo's own git remote via gitea's raw-file API, pinned to the exact commit that landed this fix — the same "get it from git, not a hand-served placeholder" discipline ROADMAP Part 167 established for `thinc`/`glauth`.
- Once a kernel with this fix is actually running: re-verify `cpu.max` end to end (a real pkgbuild sandbox spawn under real limits, not just the config existing) before considering ADR-0165 fully closed. Until then, ADR-0165's own "Consequences" section's "the actual blocking mechanism... remains an open, unconfirmed question" language is now **partially** resolved (this ADR closes the *mechanism* — a missing cgroup file, not a deadlock or resource exhaustion — but the kernel carrying the fix still isn't live).
