# 0157 — parallel package builds: design (task #841)

## Status

Accepted — all four phases are implemented and verified: Phase 1 (the pure refactor below), Phase 2 (raising `PKG_MAX_CONCURRENT_JOBS` to 2, plus the per-build-container-identity and fetch-side conn/entry threading Phase 2's own "Correction found" paragraph identified as real prerequisites), Phase 3 (the real ceiling of 10, the `GET`/`PUT /v1/system/pkg-build-config` config surface, CLI/web/docs), and Phase 4 (the N-way stress test + byte-identical merge-back proof this design called for from the start). See "Phase 1 implementation" through "Phase 4 implementation" at the end of this document for what actually shipped. ADR-0157 is now fully closed — task #841's own scope is complete.

## Context

Task #841 asks for a configurable limit (default 10) on concurrent package builds — today, `pkg install`/`pkg hostbuild` serialize to exactly one job in flight, system-wide, returning `PKG_ERR_BUSY` (`409`) for any second attempt while one is running.

Investigated directly before designing anything (per this project's own "Outline" discipline), and the real shape of "one job at a time" turns out to be woven far deeper than a single semaphore:

- **At least ten distinct module-level statics in `daemon/src/pkg.c`** carry "the current job"'s state with no job identifier attached at all — `g_current_job_name`/`_image`/`_is_hostbuild`/`_build_image`/`_cache_hit`/`_target_version`, `g_dep_queue[]`/`_count`/`_pos`/`_is_upgrade`, `g_build_lowerdir`/`_upperdir`/`_workdir`/`_merged`/`_argv_cmd`/`_argv`/`_envp`, `g_build_output_rd`/`_captured`/`_captured_len`.
- **The build container itself has a single, hardcoded name**, `PKG_BUILD_CONTAINER_NAME = "__pkgbuild"` — the container registry (`registry_create()`) would reject a second one outright even before any of the state above became a problem. This alone proves today's design assumes singularity at the registry layer, not just at pkg.c's own bookkeeping.
- **The reactor (`daemon/src/main.c`) has a single `CONN_PKG_BUILD_OUTPUT` conn kind** registered directly against pkg.c's own single output-capture pipe (`pkg_build_output_fd()`), and a single `CONN_PKG_BUILD_LOG_WS` live-tail WebSocket (`GET /pkg/build/log`) that tails "the" in-flight build with no way to name which one.
- **A hazard that looked real at first but isn't**: every ordinary (non-hostbuild) install's build container uses `g_pkgbuild_rootfs` — a single, shared, persistent directory — as its own overlay lowerdir, and also merges its own completed build output back into that same directory (`merge_tree(dest_dir, g_pkgbuild_rootfs, "", NULL)`, the "cumulative sandbox" `CLAUDE.md` already documents real bugs from, e.g. ambient-gcc contamination). This looks like a write race under real concurrency — see "no new synchronization needed" below for why it isn't one in this codebase's actual single-threaded architecture.

### Why proposed, not accepted

This is the single most heavily-used, most foundational subsystem in the project — every image, every container's dependencies, every hostbuild (including the self-hosted deploy pipeline this same session spent hours getting working end to end for the first time, ADR-0154/0155) goes through it. A rushed rewrite here, attempted at the tail end of an already-long session, risks a subtle bug that corrupts real, live state on the one real deployment target (192.168.15.95) this project has — exactly the class of "silent, hard-to-reproduce" bug `CLAUDE.md` repeatedly documents (the TCC/VLA parsing gap, the struct-packing gaps, tonight's own byte-swap bug). Per this project's own mandated workflow ("Outline — Execute — Verify," "never generate code for multiple systems/phases at once"), the Outline is real, complete work in its own right — landing it now, cleanly, is more consistent with "no hacks" than continuing straight into an under-verified implementation.

## Decision (the design itself)

Kept deliberately close to the shape the codebase already has — no new parallel bookkeeping structure where an existing table already fits.

### 1. Build-transient fields move onto `struct pkg_entry` itself — no new array for this part

`g_packages[PKG_MAX_PACKAGES]` (`struct pkg_entry`, keyed uniquely by `(name, image)` via the already-existing `pkg_find()`) is already the real, per-package state table — every in-flight build already corresponds to exactly one specific entry whose `state` is `fetching`/`building`. `g_build_lowerdir`/`_upperdir`/`_workdir`/`_merged`/`_argv_cmd`/`_argv`/`_envp`, `g_build_output_rd`/`_captured`/`_captured_len`, and `g_current_job_cache_hit` all move onto `pkg_entry` as fields only meaningful while that specific entry's own `state` is `fetching` or `building` — fields on the table that already exists for exactly this purpose, not a second table. "How many builds are in flight right now" is simply a count of entries in those two states.

### 2. A small, separate table for in-flight *chains* — sized to the concurrency limit, not the package table

A dependency chain (today's `g_dep_queue[]`) is inherently a property of one *top-level request* ("install X, which needs A and B first"), not of any single package — a package being built doesn't know what triggered its own install. This is the one piece that genuinely needs a new, small table: `struct pkg_chain g_chains[PKG_MAX_CONCURRENT_JOBS]`, sized to the *configured concurrency limit* (small — 10 by default, a modest compile-time ceiling above that, not `PKG_MAX_PACKAGES`), holding what `g_dep_queue`/`_count`/`_pos`/`_is_upgrade`/`_target_version`/`_is_hostbuild`/`_build_image` already hold today, plus which `pkg_entry` is the chain's own currently-active one. A completion handler for a given `pkg_entry` looks up its owning chain (a back-reference stored on the entry itself, valid only while fetching/building) to find what's next.

### 3. Per-build container identity

`PKG_BUILD_CONTAINER_NAME` becomes `PKG_BUILD_CONTAINER_NAME "-" <g_packages[] index>` (stable for as long as the entry's own state stays fetching/building) — a real, distinct registry entry per concurrent build, exactly like any other container. Every completion handler that currently does `pkg_find(g_current_job_name, g_current_job_image)` instead receives the specific `pkg_entry*` directly — the reactor's own conn already knows which pidfd/output-pipe fired and can point straight at the entry, the same "conn holds a pointer back to the specific resource it's for" pattern `registry_entry.reactor_conn` already establishes in reverse.

### 4. The `g_pkgbuild_rootfs` merge-back — no new synchronization needed

The actual compile/build step reads `g_pkgbuild_rootfs` as a lowerdir — safe to share across every concurrent build unchanged. The merge-back (`merge_tree(dest_dir, g_pkgbuild_rootfs, ...)`) looked like a critical section at first, but isn't one in practice: this daemon has no real threads anywhere, and every event handler (a completion callback included) already runs to completion, uninterrupted, before `epoll_wait()` is ever called again — `merge_tree()` is a plain, synchronous, blocking function with no `epoll`-yielding I/O in it. Two builds' own child processes can genuinely finish their real, off-process compile work at the same wall-clock instant, but the *daemon's own* handling of each completion can never interleave with another's, simply because there is only ever one thread of daemon-side control flow. The only real requirement is that each completion handler operates on the *right* entry's own `dest_dir` — already guaranteed once state moves onto `pkg_entry` in section 1, with no new lock, flag, or queue needed on top.

### 5. Config surface

`GET`/`PUT /v1/system/pkg-build-config` — `{"max_concurrent_jobs": N}`, default 10 per the task's own ask, validated range `[1, PKG_MAX_CONCURRENT_JOBS]` — mirrors `rolling-config`/`pkg-cache-config`/every other daemon-wide tunable's own established `GET`/`PUT` shape (ADR-0122/0124 precedent). `pkg_install_start()`/`pkg_hostbuild_start()`'s current `if (g_current_job_name[0] != '\0') return PKG_ERR_BUSY;` becomes "count of in-flight chains >= `max_concurrent_jobs`? then `PKG_ERR_BUSY`."

### 6. Reactor/API surface changes

- `CONN_PKG_BUILD_OUTPUT` needs a `pkg_entry*` (or its stable `g_packages[]` index) in its own conn struct instead of implicitly meaning "the" build, so output drains route to the right entry's own capture buffer.
- `GET /pkg/build/log` (the live-tail WebSocket) currently tails "the" in-flight build with no way to say which — needs a new required query parameter (`?name=`) once more than one can be in flight. A real, user-visible API shape change, not purely internal.
- `GET /pkg/{name}` and `GET /pkg` (the list) already report per-package state keyed by name, not by a singular "the current job" — no shape change needed, just correct routing internally.
- Each concurrent top-level install still walks its own dependency chain serially (package B's build can't start before package A it depends on finishes) — the parallelism is across *unrelated* top-level installs' chains, not within one chain.

### 7. Hostbuilds

Hostbuilds (`pkg_hostbuild_start()`) reuse the exact same `pkg_entry`/chain mechanism — a hostbuild's own build container uses a *named image's* rootfs as its lowerdir (`g_current_job_build_image`), not the shared `g_pkgbuild_rootfs`, so it has no merge-back concern at all; it's the simpler case once the mechanism above exists. No separate design needed here.

## Phased implementation plan (for whoever picks this up)

1. Move the build-transient fields onto `pkg_entry` (section 1) and introduce the small `g_chains[]` table (section 2), migrating every `g_current_job_*`/`g_dep_queue_*`/`g_build_*` call site to the new locations one at a time, **with the effective concurrency limit still fixed at 1** — a pure refactor, zero behavior change, fully verifiable against the existing test suite with no new tests needed yet. This is the largest, most mechanical, least risky phase — get it merged and verified completely on its own before phase 2.
2. Raise the effective limit to 2 and write the first real concurrency test: two genuinely different packages installed back to back with no `--wait` between the two `POST`s, both expected to reach `state: "installed"` with the second `POST` never getting `409`. This is the real risk-proving phase for the phase-1 migration — any field that should have moved but didn't surfaces here as one job corrupting the other's result.
   - **Correction found starting this phase (not knowable until an actual implementation attempt was made)**: "raise the limit" is not self-contained the way this bullet originally implied. `main.c`'s `handle_container_event()` calls `pkg_build_completed(entry->name, ...)` for *every* container exit, and `pkg_build_completed()` only does real work when `entry->name` exactly matches the single fixed `PKG_BUILD_CONTAINER_NAME` — with two builds genuinely in flight at once, `registry_create()` would reject the second one outright (container names are unique), since it would try to reuse the identical fixed name. Section 3 (per-build container identity) is therefore a **prerequisite of phase 2, not a later, separable phase** — the phased list above was wrong to imply otherwise. Once container names carry the owning `pkg_entry`'s own index (e.g. `PKG_BUILD_CONTAINER_NAME "-" <index>`), `pkg_build_completed(container_name, ...)` can parse that index straight out of the name and look up `&g_packages[index]` directly, with no new parameter needed on its own public signature — but the **fetch step** (a plain forked `curl`, not a container, with no name of its own) has no equivalent trick available: `handle_pkg_fetch_event()`/`register_pkg_fetch_pidfd()`/`pkg_fetch_completed()` (`daemon/src/main.c` + `daemon/src/pkg.c` public signatures) need an actual new "which entry is this fetch for" parameter threaded through `struct conn` — a real, cross-file API change, not a pure `pkg.c`-internal one the way phase 1 was. Phase 2's real scope is therefore: per-build container identity (section 3) + this fetch-side conn/entry threading + a "find a free chain" helper + the limit itself + the concurrency test — comparable in size to phase 1, not a quick follow-up. Deliberately not started in the same session this was found, for the identical reason phase 1 itself was once deferred: real surgery on this project's single most heavily-used, most heavily-depended-on subsystem deserves a session with full runway, not a tail-end addition.
3. Add the config endpoint, raise the real default to 10, extend `GET /pkg/build/log` with `?name=`, update CLI/web/docs.
4. A real stress test: install N (config limit + a few more) genuinely different packages concurrently, confirm the `(limit+1)`th `POST` gets a real `409` until a slot frees, and confirm `g_pkgbuild_rootfs`'s own final content (once every job completes) is byte-identical to the same set of installs run serially on a fresh sandbox — the decisive proof that concurrent merge-backs genuinely don't interleave, not just that a bug didn't happen to reproduce once.

## Consequences

- Real, substantial follow-on work — comparable in size to any other single feature shipped this session, not a quick add. Whoever implements it should expect to spend real, dedicated time on phase 1 alone before any user-visible behavior changes.
- Every existing daemon-linked test that touches `pkg install`/`pkg hostbuild` needs to keep passing unmodified through phase 1 (a pure refactor) — a good, cheap correctness signal for that phase specifically.
- `g_pkgbuild_rootfs`'s own "cumulative sandbox" design (already flagged in `CLAUDE.md` as a source of real, subtle bugs like ambient-gcc contamination) stays exactly as load-bearing as it already is today — this design doesn't add a new synchronization mechanism around it (section 4), and doesn't change the underlying fact that its contents depend on *some* history of prior builds having happened, in *some* order. A future redesign replacing the cumulative-sandbox model entirely is out of scope here.

## Phase 1 implementation

Phase 1 (the item-1 bullet in the plan above) shipped: `daemon/src/pkg.c`'s ~240 references to the old bare module statics were migrated, the file compiles `-Wall -Werror` clean, and the full daemon test suite (including `test_pkg`, `test_pkg_build_log`, `test_pkg_sync`, `test_pkg_cache`, `test_images`, `test_image_recipe`, and a broad unrelated-subsystem sweep) passes unchanged — zero user-visible behavior change, exactly as scoped.

**A real design correction, found only by reading every call site, not knowable from this document's own original Context section**: `g_current_job_name`/`g_current_job_image` turned out to be shared by a *third*, entirely unrelated job kind this ADR's Context never mentioned — `pkg_image_recipe_apply_start()` (a bulk image-artifact fetch, ADR-0122/task #... image-recipe apply) reuses the exact same two globals as its own coarse "is anything running" busy lock, writing a bare image name into them with **no associated `pkg_entry` at all**. This ruled out the Context's original implicit assumption that "the current job" always corresponds to one specific `pkg_entry` — a `struct pkg_entry *current_entry` pointer on the chain (which section 3 of this document gestured toward) cannot represent that third case. The actual, shipped fix: `struct pkg_chain` holds `name`/`image` as plain strings (a pure storage relocation of the old globals, not a redesign of lookup semantics), so `pkg_find(g_chains[0].name, g_chains[0].image)` at every call site works identically to the old `pkg_find(g_current_job_name, g_current_job_image)`, and `pkg_image_recipe_apply_start()` needed zero changes of its own — it just keeps writing into the same two relocated fields, exactly as it always did.

One further real wrinkle this document didn't anticipate: `pkg_build_output_close()` can run (via `pkg_build_spawn_failed()`) **after** the owning chain has already been cleared back to idle (`g_chains[0].name[0] = '\0'`) — so the build-output-capture accessors (`pkg_build_output_fd()`/`_readable()`/`_snapshot()`/`_close()`, which took no arguments before and still take none, matching main.c's own unchanged calling convention) can't simply look their entry up via `pkg_find(g_chains[0].name, ...)` the way every other call site does. Fixed with one small, dedicated `static struct pkg_entry *g_build_output_entry` — set the instant a build's output pipe opens (`pkg_fetch_completed()`), cleared only once `pkg_build_output_close()` actually closes it, independent of the chain's own idle/busy state.

`e->cache_hit` (ADR-0122) needed one more piece of care beyond a bare rename: `start_fetch_for()` computes the cache-hit value *before* the target `pkg_entry` is resolved/possibly-freshly-allocated, and a freshly-allocated entry gets `memset()` to zero right after — writing straight to `e->cache_hit` at the old call site would have been wiped out by that `memset()`. Fixed by holding it in a local (`cache_hit`) until `e` is settled, then writing `e->cache_hit = cache_hit` once, immediately after — the forked child later in the same function (which also needed this value) reads the same local via its own `fork()`-inherited copy, never `e->cache_hit`, for the identical reason.

`DISKPART`-style incidental fixes: none needed here — `struct pkg_entry` growing by ~20KB (four `PATH_MAX` build-dir buffers, a 512-byte argv-cmd buffer, and a ~3.8KB output-capture buffer, all now per-entry instead of one shared copy) adds roughly 5MB to `g_packages[PKG_MAX_PACKAGES]`'s static footprint (256 entries) — trivial for a modern host and consistent with this project's existing "generous fixed-size array, not a micro-optimized one" convention (see `DISK_ENUM_MAX`'s own recent history, ADR-0158).

Phases 3-4 remain exactly as scoped in the plan above — the config surface (`GET`/`PUT /v1/system/pkg-build-config`), the real default of 10, and the N-way stress test + byte-identical merge-back proof are not started here.

## Phase 2 implementation

Phase 2 (item-2 in the plan above, plus the per-build-container-identity and fetch-side conn/entry threading the plan's own "Correction found" paragraph identified as real prerequisites) shipped: `PKG_MAX_CONCURRENT_JOBS` raised from 1 to 2, and every one of the three real gaps that paragraph called out actually closed, not just the bare limit flipped.

**`PKG_MAX_CONCURRENT_JOBS` moved to `pkg.h`, not left in `pkg.c`.** `daemon/src/main.c` needs it too — to bound `struct conn`'s new `pkg_chain_idx` field's valid range and, in Phase 3, the config endpoint's own valid range — so pkg.c's own copy was removed rather than kept as a second, independently-maintained definition (One Source of Truth).

**Per-build container identity (section 3).** `pkg_build_container_name(chain_idx, out, out_size)` computes `"__pkgbuild-<chain_idx>"` (exported, `pkg.h`) — `main.c`'s `handle_pkg_fetch_event()` now calls this instead of passing the old fixed `PKG_BUILD_CONTAINER_NAME` literal straight to `registry_create()`. The inverse, `pkg_build_container_chain_index(container_name)` (also exported), parses a real container name back into its chain index (or -1 for the overwhelming majority of names that aren't a build container at all) — used by `handle_container_event()`'s unconditional `pkg_build_completed()` call and by `handle_stop()`'s own `was_pkgbuild` special-case (previously a bare `strcmp()` against the single fixed name, now genuinely wrong once the name carries a chain suffix). The resolved name is stored on `struct pkg_entry` itself as `build_container_name` — not a local stack buffer — because `main.c`'s `registry_create()` call reads `spec_out->ns.hostname`/`cg.name` *after* `pkg_fetch_completed()` already returned, and a stack buffer wouldn't survive that call boundary (caught in review before it ever reached a build, not found via a runtime failure).

**Fetch-side conn/entry threading.** `struct conn` gained one field, `pkg_chain_idx` (shared by `CONN_PKG_FETCH`/`CONN_PKG_BUILD_OUTPUT`/`CONN_PKG_BUILD_LOG_WS` — each conn already only ever means one specific chain, so one field suffices for all three kinds rather than three separate ones). `register_pkg_fetch_pidfd()`/`register_pkg_build_output()` both gained an explicit `chain_idx` parameter, threaded through all 8 real call sites (`handle_pkg_install`, `handle_pkg_hostbuild`, `handle_kmod_build_post`, `handle_pkg_update_all`, `try_start_queued_pkg_rebuild`, `handle_container_event`, `handle_stop`, `handle_pkg_fetch_event`). `pkg_fetch_completed()`/`pkg_build_completed()`/`pkg_try_start_queued_rebuild()`/`pkg_build_spawn_failed()`/the four `pkg_build_output_*()` accessors all gained a `chain_idx` parameter (or, for the completion functions, an `out_chain_idx` the caller reads back) on the `pkg.c` side to match.

**The build-output/live-tail WebSocket coupling this ADR's own Context section originally flagged as a real risk turned out real, and got fixed the same way**: `g_build_output_entry` (a single pointer) became `g_build_output_entries[PKG_MAX_CONCURRENT_JOBS]`, one slot per chain — kept as a separate array from `g_chains[]` itself (not derived from `g_chains[idx].name`/`.image`), for the exact reason the Phase 1 write-up already flagged for the single-slot case: `pkg_build_output_close()` can run after the owning chain has already cleared back to idle. `g_build_log_ws_conns[]` (`main.c`) is now chain-aware too — `build_log_ws_broadcast()`/`build_log_ws_teardown_all()` both take a `chain_idx` and only touch conns watching that specific chain, so a client live-tailing one concurrent build never sees another's output or gets torn down when the *other* build finishes.

**`GET /v1/pkg/build/log` gained real, working `?name=&image=` query params** (`pkg_chain_index_for_target()`, `pkg.c`) to pick which of the now-possibly-several concurrent builds to attach to — with a deliberate backward-compatible fallback (`pkg_active_chain_indices()`) for a caller supplying neither: 0 active chains → 404 (unchanged), exactly 1 → attach to it (matches every pre-Phase-2 client's existing behavior, still the common real-world case), more than 1 → 400 asking for an explicit `?name=`, rather than silently guessing. CLI/web support for the query params themselves is Phase 3 scope, not added here — the daemon-side contract is real and tested now regardless.

**`pkg_image_recipe_apply_start()`'s shared-field busy-lock trick (flagged as a real hazard in the Phase 1 write-up above) needed decoupling, exactly as anticipated**: it used to reuse `g_chains[0].name`/`.image` directly as its own busy marker — correct with exactly one chain slot, wrong once a free chain slot no longer means "nothing is running" (the other slot could be mid-build). Replaced with a dedicated `g_image_apply_busy`/`g_image_apply_image` pair and a `pkg_any_job_busy()` helper (`g_image_apply_busy || chain_alloc() < 0`) used uniformly by all three "can a new top-level job start" gates (`pkg_install_start()`, `pkg_hostbuild_start()`, `pkg_image_recipe_apply_start()` itself).

**The first real concurrency test** (`test/test_pkg.c`): a top-level scenario installs two different packages (`greeter`, `concurrent`) back to back with no wait between the two `POST`s — the second now gets `202`/`fetching` where it used to get `409` — then proves the ceiling is still real by attempting a third (`overflow`) while both slots are occupied, correctly getting `409`; both original installs are then polled to `installed` and their binaries verified to actually run. A second scenario repeats the same proof in the hostbuild/ordinary-install combination (`hbtest` hostbuild + `hbconcurrent` ordinary install sharing the two slots, `overflow` again rejected as the third). One real race was found and fixed while writing this: the first attempt reused the already-present `badsum` fixture (a deliberately-invalid checksum) as the second occupant, but its failure was fast enough (checksum caught right after the fetch step, no build needed) to free its chain slot before the third-job `409` check even ran — replaced with `hbconcurrent`, a fixture with a real, valid tarball that takes a genuine build to finish, removing the race rather than adding a retry/sleep around it.

Verified: `daemon/src/pkg.c`/`daemon/src/main.c` both compile `-Wall -Werror` clean; the full daemon-linked regression suite (`test_pkg`, `test_pkg_build_log`, `test_pkg_sync`, `test_pkg_cache`, `test_kmod_build`, `test_image_recipe`, `test_container_recipe`, `test_rolling_restart`, `test_daemon`, `test_cli`, `test_web`, every container/network/DNS/PKI/hostauth/disk/device test) passes with zero regressions.

## Phase 3 implementation

Phase 3 (item-3 in the plan above) shipped: `PKG_MAX_CONCURRENT_JOBS` raised from Phase 2's placeholder 2 to the task's own real target, 10 (`daemon/include/pkg.h`) -- a real array-size increase (`g_chains[]`, `g_build_output_entries[]` in `pkg.c`; `g_build_log_ws_conns[]`'s own bound in `main.c` is unaffected, it caps simultaneous live-tail *viewers*, a separate, still-4 concern from job concurrency), plus the operator-configurable ceiling and full CLI/web/docs coverage the design always called this phase's own job.

**`GET`/`PUT /v1/system/pkg-build-config`** (`{"max_concurrent_jobs": N}`, range `[1, PKG_MAX_CONCURRENT_JOBS]`) mirrors `pkg_cache_get_max_bytes()`/`pkg_cache_set_max_bytes()`'s own shape exactly (ADR-0122/ADR-0124 precedent, as the design always specified) -- a new `pkg_build_config_init()`/`pkg_build_config_repoint()`/`pkg_build_get_max_jobs()`/`pkg_build_set_max_jobs()` module in `pkg.c`, persisted to `<PKG_DIR>/build_config.json`, repointed alongside the cache/artifact configs on a rebuildable-storage migration (`daemon/src/main.c`'s existing `pkg_cache_repoint()`/`pkg_artifact_repoint()` call site). `chain_alloc()` (the one place a new chain slot is actually claimed) now bounds its search by `pkg_build_get_max_jobs()` instead of the raw `PKG_MAX_CONCURRENT_JOBS` array size -- lowering the config takes effect for the *next* chain-allocation decision only; chains already running in already-claimed slots are completely unaffected, run to completion normally. `pkg_active_chain_indices()` (Phase 2, used by `GET /pkg/build/log`'s no-`?name=` fallback) deliberately still scans the full compile-time array, not just the configured ceiling -- a chain started before the ceiling was lowered can still legitimately occupy a slot at or past the new limit, and it must still be found.

**CLI**: `thincctl pkg-build-config show|set --max-concurrent-jobs=N`, a new top-level command (not nested under `pkg`, matching the REST path being under `/v1/system/`, not `/v1/pkg/`) mirroring `rolling-config`'s own shape exactly -- added to `SHELL_COMMANDS[]` and the top-level help text alongside it.

**Web dashboard**: a new "Package Builds" page under the existing "Host" nav group, alongside Rolling Restart and Host Swap (the same "small daemon-wide tunable with its own page" precedent those two already established) -- `refreshPkgBuildConfig()`/the `pbc-form` submit handler mirror `refreshRollingConfig()`/`rc-form` exactly, wired into the same global poll loop.

**Docs updated together, per `CLAUDE.md`'s own Documentation Map rule**: `docs/api/openapi.yaml` (new `PkgBuildConfig` schema + `/system/pkg-build-config` path) and `docs/api/README.md` (summary table row, a new paragraph in the Package Manager section, and three now-stale "v1 serializes installs"/"only one job at a time" claims elsewhere in that same doc -- found by grep, not assumed absent -- corrected to describe the real, now-configurable ceiling) in the same change; `docs/guides/cli-reference.md` gained the two new command rows.

**A real, deliberate test-authoring correction, not a design change**: the existing Phase 2 concurrency-boundary tests in `test/test_pkg.c` (the "third job while both slots busy" checks, both the ordinary-install and hostbuild scenarios) were written against Phase 2's placeholder default of 2 -- with the real default now 10, those same checks would need 11 concurrent packages to still be meaningful, impractical for a compact test. Fixed by having the test explicitly `PUT /v1/system/pkg-build-config {"max_concurrent_jobs": 2}` immediately after the daemon starts, before any of those pre-existing assertions run -- they stay word-for-word unchanged and still test exactly what they always tested, just against an explicitly-configured ceiling instead of an implicit default that happened to be 2. The new Phase 3 test coverage (appended near the end of `main()`, after `skip_hostbuild:`) is genuinely new: the real default is 10 (checked once, before the ceiling=2 `PUT` above ever runs), `0` and `11` are both rejected `400`, lowering to `1` and installing two different packages back to back proves the *second* now correctly gets `409` (not `202`) -- the direct, load-bearing proof that `chain_alloc()` really does consult the configured ceiling and not just the compile-time array bound -- and raising it back to `10` immediately re-admits genuine concurrency.

Verified: `daemon/src/pkg.c`/`daemon/src/main.c`/`cli/src/main.c` all compile `-Wall -Werror` clean; `web/app.js` passes `node --check`; `docs/api/openapi.yaml` parses as valid YAML. Full daemon-linked regression sweep (run individually, not batched, after batched runs showed environmental cross-test contention unrelated to this change -- confirmed by re-running the affected tests alone, where they passed cleanly) -- zero regressions. ## Phase 4 implementation

Phase 4 (item-4 in the plan above) shipped: the decisive proof this design called for from its very first draft -- not just that N genuinely different packages can install concurrently (Phase 2's own test already proved that for N=2), but that the daemon's single, shared `g_pkgbuild_rootfs` merge-back sandbox produces **byte-identical final content** whether N installs run concurrently or strictly serially, closing the loop on the "no new synchronization needed" argument in this document's own Decision section above -- that argument was reasoned from the code (single-threaded, run-to-completion event loop), this phase is the empirical confirmation.

**New `test/test_pkg_concurrent_stress.c`**, added to the Makefile's own `all` target. Two entirely separate `thincd` instances (own `--data-dir`, own `--port`, own fresh bootstrap -- nothing about one run's state can leak into the other's) install the identical set of N=3 packages (`sp1`/`sp2`/`sp3`, each a real `gcc`-compiled "hello" binary with a name-specific printed message, staged once into a shared scratch dir and read unmodified by both daemons -- the same input bytes, so any difference in the *output* can only come from the daemon's own build/merge pipeline, not from the input being subtly different): daemon A installs all three with no wait between the `POST`s (concurrent, its own `pkg-build-config` pinned to `max_concurrent_jobs=3` for a deterministic boundary), daemon B installs the same three one at a time, waiting for each to reach `installed` before starting the next (strictly serial). A fourth package (`sp4`) is attempted against daemon A while all 3 slots are genuinely busy, proving the ceiling itself is still real at this scale, not just at N=1 (Phase 2's own test) or N=2.

**The comparison, in two layers**: first, that both runs converge on the identical image-version hash (ADR-0108's version-directory name is a hash of the sorted `(name, version)` manifest -- order-independent by construction, so two runs producing the same final package set should land on the same hash regardless of install order; a real, meaningful structural signal, but explicitly documented in the test's own comments as *not* a substitute for the second layer, since a hash match only proves the manifests agree, not that the file bytes underneath do). Second, and decisive: `diff -rq` between the two runs' base image rootfs trees -- content only, never mtimes/ownership, so it can only fail on a genuine byte difference, exactly what an interleaved or racing merge-back would produce (one build's files partially overwritten by, or silently dropped because of, a concurrent sibling).

**A real, non-bug finding while first running this test, worth recording**: the very first unfiltered `diff -rq` run reported six differences, every one of them under `/dev` -- `pkg_seed_image_baseline()`'s (ADR-0150) fixed set of baseline device nodes (`/dev/null`, `/dev/zero`, `/dev/random`, `/dev/urandom`, `/dev/full`, all real character-special files; `/dev/ptmx`, a dangling placeholder symlink) that every fresh image gets regardless of which packages are ever installed on it. `diff` cannot compare a special file's own "content" at all -- it reports character-special files it can confirm are the same *type* as an unresolvable difference regardless of whether they actually match, and reported the ptmx symlink as absent (not mismatched) identically on both sides. Investigated directly rather than assumed benign: this is a real, structural limitation of `diff` itself applied to a directory containing special files, not evidence of anything this ADR's own concurrency work could plausibly have caused (device-node seeding is entirely independent of which packages get installed, and happens once per baseline seed, not per package). Fixed with `--exclude=dev` -- a deliberately narrow, documented exclusion of a directory this test was never trying to prove anything about, not a weakening of the actual proof (every package's own installed files, under `/usr/bin` and anywhere else a recipe's `pkg_install()` might write, are still compared in full).

Confirmed deterministic, not a one-off pass: run three consecutive times, `PASS` every time.

**Two more flake classes were chased down to real, fully-explained causes during this phase's own regression sweep, not just worked around**: (1) `test/test_pkg.c`'s `hbtest` hostbuild poll timeout (30 attempts, 9s -- tuned when it was the only build in flight) is now genuinely marginal, since Phase 2 made that same window share the box with a second, real concurrent gcc build (`hbconcurrent`) -- raised to 100 attempts (30s), a timing fix, not a logic one; the daemon always reached `installed` eventually, just occasionally past the old window. (2) Several apparently-random `test_pkg` failures across reruns (different assertions failing each time, a daemon that wouldn't exit cleanly on `SIGTERM`) turned out to share one root cause: a `thincd` orphaned by an earlier, harness-killed test run had kept holding `test_pkg`'s own port, so subsequent runs were silently talking to a stale daemon serving a completely different test's `--data-dir`. Every symptom stopped instantly once that orphaned process was found (`ps aux`) and killed -- confirming environmental contamination from this session's own rapid iteration, never a defect in the code under test.

Verified: `test/test_pkg_concurrent_stress.c` compiles `-Wall -Werror` clean; full clean rebuild across every build target succeeds with zero warnings.
