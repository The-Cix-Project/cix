# 0078 — From-source host tools bootstrap (mkbootroot.c's shelled-out binaries)

## Status

Accepted

## Context

Raised directly by the user, reviewing `image/src/mkbootroot.c`'s own `shelled_bins[]` table: every binary `cixd` shells out to at runtime -- `openssl` (PKI), `curl` (`pkg_source` fetches, `pkg bootstrap --toolchain-url=`), `tar`/`gzip`/`bzip2`/`xz` (source extraction), `cp`/`rm`/`sha256sum` (build-container bookkeeping), `unsquashfs` (toolchain import), `mkfs.ext4` (disk format, Phase C) -- was a raw copy of whatever the *dev sandbox running `mkbootroot`* happened to have installed at `/usr/bin`, permanently baked into every produced control-plane squashfs. The user's objection, verbatim: *"why is curl pulled not compiled? ... we've deviated from everything from source, and completely atomic OS distribution."*

Historical root cause: ADR-0035 fixed a real "PKI/pkg completely broken on fresh install" bug by staging these binaries as the immediately-available fix, reasonable at the time, but never revisited against ADR-0057's own later self-hosting precedent (bootstrap once from a host-provided starting point, then build for real from source going forward). `coreutils.recipe`/`gzip.recipe` already existed and build `cp`/`rm`/`sha256sum`/`gzip` from real source (confirmed via direct inspection) -- `mkbootroot.c` had simply never been pointed at them, a pure wiring gap, not missing infrastructure, for those four specifically.

## Decision

**`mkbootroot.c` gains a new, optional `host_tools_dir` argument** (argv[9], the tolerant-default shape `firmware_dir`/`modules_dir`/`kmod_bin_dir` already established: `""` keeps today's dev-host-sourced behavior). When given a real directory (the rootfs of a `pkg install`-populated image), `cp`/`rm`/`sha256sum`/`gzip` are copied from there instead of the dev host -- the four tools this project already has real from-source recipes for (`coreutils.recipe`, `gzip.recipe`).

**Seven new recipes**, each a real, empirically-verified from-source build (local build + functional smoke test performed for every one before being trusted): `openssl.recipe` (retires `openssl-dev.recipe`'s own dev-host-copy stopgap -- see below), `curl.recipe` (deliberately narrow: OpenSSL+zlib only, no HTTP/2/IDN/SSH/RTMP/LDAP/GSSAPI/Brotli/Zstd -- none of that is real, confirmed need for `pkg.c`'s own plain `-fsSL --retry ... -o <path> <URL>` usage), `tar.recipe`, `bzip2.recipe` (bzip2's own hand-written Makefile has no DESTDIR support; a real `make clean` between the static and shared-lib build targets is required, confirmed the hard way), `xz.recipe`, `squashfs-tools.recipe` (built with only `XZ_SUPPORT=1` -- a direct grep of this project's own `-comp` flags confirms `xz` is the only format ever produced, so LZO/LZ4/ZSTD/XATTR support is deliberately left off rather than pulling in three more from-source recipes for backends nothing here uses), and `e2fsprogs.recipe` (scoped to `mke2fs`/`mkfs.ext4` only -- the confirmed real need, `DISKFORMAT_MKFS_EXT4_BIN` -- not the full ~25-tool suite).

**`openssl-dev.recipe` is retired (deleted, not kept alongside `openssl.recipe`)** -- One Source of Truth: that recipe's own header comment explicitly punted on a real build ("substantial work of its own... a bespoke Configure script, not autoconf") and copied this dev sandbox's own pre-built `libssl.so.3`/`libcrypto.so.3` directly. That call made sense before a real gcc-based "dev" toolchain image existed to build OpenSSL in (`gcc.recipe`); now that one does, `openssl.recipe` does the real build instead -- `install_sw` + `install_ssldirs` (confirmed via a real local build+install+`openssl req -x509` round trip) produces every file the old recipe used to copy, from real source.

**A new well-known image name, `cix-hosttools`** (`HOST_TOOLS_IMAGE` in `daemon/src/main.c`) -- built exactly like `cix-builder`/`dev` (`docs/guides/building-cix.md`), no special-cased creation path. `spawn_cix_bootroot_assembly()` (the server-side handler behind a `cix` hostbuild's automatic bootroot assembly, ADR-0057) checks for this image's rootfs (`stat()`, the same "images are pure filesystem state, no registry" convention already used elsewhere in `main.c`) and passes it as `host_tools_dir` when present -- purely additive, `""` (today's behavior) on any box that never builds it.

## Consequences

- Closes the real gap the user raised: `cp`/`rm`/`sha256sum`/`gzip` (the four tools this project already had real recipes for) are now genuinely from-source when `cix-hosttools` exists, not copied off the build machine.
- `openssl`/`curl`/`tar`/`bzip2`/`xz`/`squashfs-tools`/`mkfs.ext4` (e2fsprogs) have real, verified from-source recipes and belong on the same `cix-hosttools` image, but `mkbootroot.c`'s own `shelled_bins[]` table for these seven is **not yet repointed** at `host_tools_dir` -- a real, deliberately scoped, tracked follow-on (this same argument threads through cleanly for all of them; wiring each one is mechanical once done for the first four, not a design question), not a silently-dropped gap. `mkbootroot.c`'s own doc comments name this explicitly.
- `curl.recipe`'s deliberate narrowness (no HTTP/2/IDN/SSH/RTMP/LDAP/GSSAPI) means this project's own `curl` cannot fetch from a server that hard-requires one of those (extremely rare for a plain HTTPS file download); a real, accepted trade-off against building seven more from-source recipes for backends with zero confirmed use.
- Every recipe's checksum was cross-verified against a second, independent source before being trusted (a second mirror, a Debian orig tarball, or -- where only GitHub hosts the project (`squashfs-tools`) -- content-identical via a real `diff -r` of both extracted trees, since GitHub's own auto-generated tag archives aren't byte-reproducible against a maintainer's own release tarball or a downstream repackaging even for identical source).
