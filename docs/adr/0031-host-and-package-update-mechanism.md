# 0031 — host OS update mechanism, and automatic package updates

## Status

Accepted

## Context

The A/B rollback *machinery* — read-only squashfs root, systemd-boot's native Automatic Boot Assessment counting, `confirm_boot()` renaming a healthy boot's loader entry once it's actually serving traffic (ADR-0014) — has existed since Phase 11 part 2. But no operator-facing tool has ever existed to actually *write* a new OS image into the inactive slot on an already-running system: `thinc-install` only ever performs the very first install, and root B's own device is resolved once by the installer, then explicitly discarded (`(void)root_b_dev;`, "root B stays genuinely empty until the first real update ever writes there"). For packages, most of the mechanism already existed before this ADR: `pkg install --upgrade` rebuilds from source when a recipe's version differs from what's installed, and `GET /pkg` already reports `available_version` drift. What was missing there was purely the "automagic" trigger — an operator still had to already know which package's recipe changed. Raised directly by the user ("I want a mechanism to update my running box, and containers... what about for the host? and our a/b configuration"), confirmed to build both, host first as the reference implementation the package piece then reuses the shape of — matching MISSION.md's own framing that host and package delivery should share one pattern: "write the new version to an inactive slot, verify it, cut over, never touch what's live in place."

## Decision

**`POST /system/update` fits the existing `/system/shutdown`/`/system/reboot` sibling pattern exactly — a new action endpoint, not a new resource, and deliberately does not itself reboot.** A single handler that both responds and reboots is awkward (the response may not even flush before `reboot(2)` tears the process down) and less composable than keeping "stage a new image" and "cut over to it" as two separate calls the operator (or a script) sequences themselves. The existing `confirm_boot()`/boot-counter machinery, entirely unchanged, still decides whether the fresh slot sticks once a reboot does happen — this ADR adds nothing to that half of the pattern, only to the "write the new version to an inactive slot" half that never existed.

**`image_path` is a local filesystem path, not an HTTP upload.** `HTTP_MAX_REQUEST_SIZE` is 1MiB, far too small for a real OS image, and this project's own charter has no remote-fetch/registry concept to plug into (`pkg install` fetches source via a host-side `curl`, not the daemon's own HTTP server, for the same reason). Building real streaming/chunked upload support on a hand-rolled non-blocking HTTP server would be a substantial new capability for a need this project doesn't actually have yet. The operator builds the new image the same way they always have (`make` + `mkbootroot`) and transfers it onto the box out-of-band (`scp`) — the exact same manual step already required to get the installer's own payload onto its ISO in the first place.

**Root A/B device paths are fixed macros (`ROOT_A_DEVICE "/dev/vda2"`, `ROOT_B_DEVICE "/dev/vda3"`), not GPT-name resolution.** `thinc-install.c` already has working GPT-name-to-device-path resolution (`find_partition_device()`, parsing `sfdisk -d`'s dump output) — but it lives in installer-only code, never linked into the daemon, and every existing daemon-side device macro (`ESP_DEVICE`, `CONFIG_DEVICE`, `CONTAINERS_DEVICE`) has already, twice, explicitly deferred that same lookup to "part 4's real hardware, if it turns out to be needed" (ADR-0018's own Consequences section restates it). Building new GPT-resolution machinery into the daemon now, for one more device, would contradict that stated deferral rather than extend it — the consistent, disciplined choice is to follow the exact same fixed-path precedent already established for the fixed-QEMU-layout scope this project is still deliberately targeting, not to reintroduce a different resolution strategy for this one case.

**The image is written raw, with no filesystem/offset math — the destination is a real partition block device, not a byte range inside a larger disk-image file.** `write_file_to_device()` (`daemon/src/main.c`) mirrors `thinc-install.c`'s own `copy_file()`/`write_whole_file_to_device()` shape (plain `open`/`read`/`write` loop) rather than `test/test_disk_image.c`'s `write_at_offset()`, which exists only because that test harness assembles a disk-image *file* for QEMU on a dev sandbox with zero loop devices — a fundamentally different, test-only situation. Kept as its own small private static rather than shared across the daemon/installer binaries: genuinely trivial (a ~10-line loop), and the two binaries share no common library today (the daemon can't link `test/test_image_fixture.c`, which is test-scoped).

**A cheap, real safety check runs before anything is written: the first 4 bytes of `image_path` must be squashfs's own on-disk magic ("hsqs").** This turns "wrong path by mistake" into a clean `400` instead of silently overwriting the inactive slot with garbage — cheap enough to always perform, and a real, not hypothetical, mistake an operator typing a path by hand can make.

**The fresh loader entry's `version` is the current UNIX timestamp, not a value parsed back out of the existing entry.** It only needs to be *higher* than whatever's already on disk so systemd-boot sorts it first (confirmed necessary: ROADMAP's own note that a bare `default thinc-*` glob alone isn't sufficient for prioritization) — a timestamp trivially satisfies that without needing to open and parse the current entry first. The entry itself otherwise matches `thinc-install.c`'s own `populate_esp()` shape exactly (`sort-key thinc`, `linux /thinc-bzImage`, the same `init=/bin/thincd -- --init-mode --slot=<slot> --bind=<ip>` options line), filename `thinc-<slot>+3.conf` reusing the same tries-left value (`ROOT_A_TRIES` = 3) the very first install already uses — a fresh update-written slot goes through the identical Automatic Boot Assessment gate a first install already does, not a separate, weaker one.

**`POST /pkg/update-all` reuses `pkg_install_start(..., upgrade=1, ...)` entirely — the only new code is `pkg_find_update_candidate()`, which finds what needs it.** It walks every installed package and runs the exact same fresh-recipe-parse-and-compare `write_pkg_json()` already performs per-entry for `GET /pkg`'s own `available_version` field (extracted so both call sites share one comparison, not two copies of it), returning the first one that's drifted. **It starts at most one upgrade, honestly respecting the existing v1 single-install-in-flight constraint rather than working around it** — `pkg_install_start()` already returns `PKG_ERR_BUSY` if a job is running, and this endpoint doesn't attempt to parallelize past that real, already-load-bearing serialization. An operator or cron entry drains a whole backlog of drifted packages by calling `update-all` again once each job finishes — "automagic" in the sense actually asked for (no need to already know which package changed), without pretending the underlying build pipeline can do more than one thing at once when it genuinely can't yet.

## Consequences

- Verified end-to-end against a real QEMU boot, not just HTTP-response inspection: a real `thincd` (`--init-mode --slot=a`) receiving `POST /system/update` with a real, distinguishable second squashfs correctly writes it to `thinc-root-b`'s real device with a correctly-formed, correctly-countered loader entry; a subsequent real reboot lands on slot B, confirmed via the marker; a bad-magic image is rejected with `400` without touching the inactive partition at all; a `thincd` with no `--slot=` is rejected `400` rather than guessing.
- `POST /pkg/update-all` against a real installed package with a bumped `pkg_version=` on disk starts exactly one real upgrade job, confirmed via `GET /pkg`'s own `state`/`version` transitioning; called again with nothing drifted, it reports "nothing to update" rather than erroring.
- The daemon still has no general GPT-partition-name resolution of its own — `ROOT_A_DEVICE`/`ROOT_B_DEVICE` join `ESP_DEVICE`/`CONFIG_DEVICE`/`CONTAINERS_DEVICE` as fixed paths scoped to the same known QEMU virtio-blk layout. A real GPT-name-based lookup, if part 4's real hardware ever needs one, would replace all five of these macros' resolution strategy at once, not just add a sixth one-off case — this ADR deliberately does not start that migration.
- `POST /pkg/update-all` only ever advances one package per call. A fully "hands-off" scheduled/periodic trigger (something calling this on a timer rather than an operator or cron entry calling it) is a real, deliberately deferred next step — this ADR builds the on-demand trigger MISSION.md's "automagic" language calls for, not a scheduling subsystem this project has no other need for yet.
- `POST /system/update` still requires an operator to decide *when* to call `POST /system/reboot` to actually cut over — no automatic "update then reboot" chaining exists, on purpose (see Decision above); a real deployment's own maintenance-window policy, not this daemon, should own that timing decision.
