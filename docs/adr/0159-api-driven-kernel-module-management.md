# 0159 — API-driven kernel module management (load/unload/list/build, with options)

## Status

Accepted — every open question resolved directly with the user (see "Resolved open questions" below). Phase A implemented (task #882); Phase B/C not yet started.

## Context

ADR-0061 already did real, substantial work in this space, and this document extends it rather than duplicating it:

- The kernel's own `.config` (`image/kernel/qemu-part1.config`) already marks a curated set of network/USB drivers `=m` (`e1000e`/`igb`/`ixgbe`/`r8169`/`tg3`, `ehci-hcd`/`usb-storage`) — everything that could plausibly hold root stays `=y`, never a module, since this project has no initramfs (ADR-0014) to load one before root is reachable.
- `pkg/recipes/kernel.recipe` (a hostbuild recipe, ADR-0056) already builds `bzImage` and every `=m` module in one `make bzImage modules` invocation, runs `make INSTALL_MOD_PATH=$PKG_DESTDIR modules_install`, and a real `depmod -b $PKG_DESTDIR "$(make kernelrelease)"` — the harvested artifact already has a correct `lib/modules/<version>/` tree with `modules.dep`/`modules.alias`, not just bare `.ko` files.
- `kmod` (`pkg/recipes/kmod.recipe`) is real, unmodified upstream software, already staged onto every real image via `mkbootroot.c`'s `kmod-bin-dir` argument — `modprobe`/`depmod`/`insmod`/`lsmod`/`modinfo`/`rmmod` are all real binaries already present on a running box, not something to reimplement.
- `main.c`'s `load_boot_modules()` already `modprobe`s the curated network/USB list at boot, best-effort, before `bootstrap_management_network()` — but it is a **hardcoded, compile-time `static const char *const[]`, with zero REST surface**, no per-module options, and no way for an operator to add a module to it without a new kanxeod build.

**What's genuinely missing, and what this ADR is actually about**: everything past "the fixed boot-time list runs once." No REST endpoint can load/unload/list a module on a running system, no way to pass module parameters (`modprobe foo bar=1` — real, standard `modprobe` syntax, not something to invent), no persisted "always use these options for this module" default, no operator-managed autoload list distinct from ADR-0061's own hardware-detection-critical one, and no way to make a driver loadable that wasn't already in the curated `=m` set baked into the kernel at its own build time — let alone a genuinely third-party, out-of-tree module.

The kernel source tree itself is never kept around after a hostbuild: `kernel.recipe`'s `pkg_source` is fetched fresh into the hostbuild container's own ephemeral overlay on every single run and discarded when the container exits — only `bzImage` + `lib/modules/` survive, into `ARTIFACTS_DIR`. Building any *additional* module later (in-tree or out-of-tree) needs a real kernel build tree (`Module.symvers`, generated headers, matching `Module.symvers`/`vermagic`) still present and matching the exact currently-running kernel version — which does not exist as a persistent thing anywhere in this project today. This is the one genuinely novel piece of infrastructure this ADR needs to design, not just wire up.

## Requirements (from the user directly)

- Full pipeline: REST-triggered **build** (a hostbuild-shaped job, like `pkg hostbuild`) in addition to load/unload/list — not just management of modules that happened to already exist.
- Both in-tree (drivers in the kernel source this project already builds, just outside today's curated `=m` set) and out-of-tree (genuinely third-party) modules.
- Dependency resolution: real `depmod`/`modprobe`, not a hand-rolled dependency graph (matches ADR-0061's own already-stated "reuse real software" posture).
- Module options ("configure on the fly" at insert time): both a per-load API value, **and** a persisted default per module that a bare load-with-no-body falls back to.
- A persisted autoload list — modules that load automatically on every boot, REST-managed, distinct from ADR-0061's own hardcoded hardware-detection list (which has a real timing constraint — before `bootstrap_management_network()` — this new list doesn't share and shouldn't be forced into).
- Access control: host-auth write-gating only, same posture as every other host-level endpoint in this project (no separate allowlist/blacklist concept requested).

## Decision (phased — Phase A is the well-scoped, low-risk part; Phase B/C are real, separate, larger pieces of work)

### Phase A — module *management*: load/unload/list/options/autoload for whatever the kernel already knows how to load

Wraps real `modprobe`/`rmmod` exactly the way this project already wraps `sfdisk`/`mkfs.ext4`/`tar`/`curl` elsewhere — fork+exec, never a raw `init_module(2)`/`finit_module(2)` reimplementation, since `modprobe` already does real dependency resolution (via the harvested `modules.dep`) and real module-parameter passing (`modprobe <name> key=value ...`, standard, existing `modprobe` syntax) — there is nothing to reinvent here, only to expose over REST.

- **`POST /v1/system/kmod/{name}`** — `{"options": {"key": "value", ...}}` (optional). Forks `/usr/bin/modprobe <name> [key=value ...]`. Options given in the body are used; if the body omits `options` (or is empty), falls back to this module's own persisted default options (see below) if one exists, otherwise loads with none. Synchronous — a single `modprobe` invocation for an already-built module is fast (no compilation), matching `diskpart`'s own "quick admin op runs inline" precedent (ADR-0158) rather than `diskformat`'s async job machinery.
- **`DELETE /v1/system/kmod/{name}`** — `/usr/bin/modprobe -r <name>` (real `modprobe`'s own reverse-dependency-aware removal, not a bare `rmmod` that would leave now-unused dependencies loaded).
- **`GET /v1/system/kmod`** — reads `/proc/modules` directly (a plain, always-available kernel text interface — no need to fork `lsmod` at all, which is itself just a thin wrapper around this same file) and reports name/size/refcount/dependents/state for every currently-loaded module, live, never cached — matching `disk.c`'s own "re-enumerate fresh on every call" convention.
- **`GET /v1/system/kmod/{name}`** — `modinfo <name>` (real tool, real parsed output: description, real available parameters and their types, version, license, in-tree vs. out-of-tree) for a module that's built and available, whether currently loaded or not — the one place `modinfo`'s own output genuinely can't be replaced by reading `/proc/modules` (which only shows what's *loaded*, not what's *available to load*).

**Persisted per-module option defaults + autoload list** — one small new module, `daemon/src/kmodconfig.c`, matching `devicemap.c`'s own established shape (a small, atomic-JSON-persisted table, `GET`/`POST`/`DELETE`, loaded once at `kmodconfig_init()`):

- **`PUT /v1/system/kmod-config/{name}`** — `{"default_options": {"key": "value", ...}, "autoload": true|false}`. Either field alone updates just that field (read-modify-write, matching `daemon-config`'s own established PUT shape) — `default_options` is what a bare `POST /kmod/{name}` with no body falls back to; `autoload` marks this module for the new boot-time list below.
- **`GET /v1/system/kmod-config`** — every module with a persisted config (default options and/or `autoload: true`).
- **`DELETE /v1/system/kmod-config/{name}`** — clears this module's persisted config entirely (both fields).
- **A new, separate boot-time step, `load_configured_modules()`**. Resolved boot ordering (coordinated with ADR-0160's own `apply_configured_sysctls()`): `load_boot_modules()` (ADR-0061, unmodified, hardware detection) → `apply_configured_sysctls()` (ADR-0160 — a `net.*` sysctl can affect how the management network itself comes up) → `bootstrap_management_network()` → `load_configured_modules()` (this step, last — operator autoload is the least boot-critical of the four, and a container-usable driver loaded slightly later than the management network is fine, unlike ADR-0061's own hardware-detection list which genuinely must precede it). Walks the persisted `kmod-config` table, `modprobe`s every entry with `autoload: true` using its own persisted `default_options`, best-effort per module (a module that fails to load — e.g. hardware not present, or a module an operator configured for autoload but never actually got built — logs and continues, never fails boot), matching ADR-0061's own established "missing driver for hardware this box doesn't have is the expected case" posture.

### Phase B — on-demand build of an *additional in-tree* module: reuse the whole-kernel hostbuild, don't invent new persistent state

**Simpler than the first draft of this document proposed, on purpose, per direct "keep the mechanics simple" feedback.** The first draft designed a new, permanently-kept, version-pinned kernel build tree (`KDIR`) as a second, parallel piece of long-lived host state alongside every other artifact this project already tracks — a real, ongoing source of exactly the "too many moving parts" risk to avoid: it would need its own "is this still the tree matching the currently-running kernel" freshness tracking (nothing else in this project works this way), gigabytes of kept-forever disk for something most installs would never touch, and a real, new class of bug (a stale `KDIR` silently producing a `vermagic`-mismatched `.ko` that fails to load, or force-loads incorrectly) that only exists because of the new mechanism itself.

The proven, already-working alternative: `kernel.recipe` (ADR-0061) already builds the *whole* kernel and *every* `=m` module together, in one `make bzImage modules` invocation, which is precisely what guarantees perfect version/ABI match today — by construction, not by careful bookkeeping. Adding one more module the same way needs no new mechanism at all:

- **`POST /v1/system/kmod-build`** — `{"config_symbols": ["CONFIG_FOO"]}` — starts an ordinary hostbuild (the exact existing `pkg hostbuild` mechanism, unmodified) against `kernel.recipe` itself, gaining an optional REST-supplied extra-symbols parameter (resolved: the *same* recipe, not a second, parallel `kernel-with-extra-modules.recipe` — avoids a second file that would need to be kept in sync by hand every time the base kernel version is upgraded) passed through to its own `pkg_build()`, merged via `merge_config.sh` on top of the base `qemu-part1.config`, same `make bzImage modules` + `modules_install` + `depmod` sequence already proven correct. The result is a complete new `bzImage` + full `lib/modules/` tree — cut over the same way any kernel update already happens in this project (the existing A/B kernel-update mechanism, `docs/guides/kernel-build-and-ab-updates.md`), not a live, same-boot addition. This also directly answers the "does `kmod-build` need kernel-version-awareness" question: a rebuilt kernel's own `lib/modules/<new-version>/` is only ever used once that kernel is actually booted (the existing A/B cutover), so there is no window where a mismatched module tree could be loaded against the wrong running kernel — the direct payoff of not inventing a separate, independently-updatable `KDIR`.
- Real, honestly-stated tradeoff: this needs a reboot to take effect, and rebuilds the whole kernel (a genuinely heavier operation than compiling one small driver) rather than compiling just the one new module — accepted deliberately, in exchange for zero new persistent state, zero new ABI-tracking mechanism, and zero new failure mode beyond what `kernel.recipe`'s own hostbuild path already has proven, working error handling for.

### Phase C — genuinely out-of-tree (third-party) modules: real added complexity, evaluate whether it's actually needed before designing it further

Phase B's "just rebuild the whole kernel" trick only works because the module's source already lives inside the kernel tree `kernel.recipe` already fetches. A genuinely third-party module (source from outside the kernel tree entirely) has no equivalent free lunch — it does need a real, persistent, version-matched kernel build tree (the `KDIR`/`make M=<path> modules` mechanism the first draft proposed for Phase B) with all the same freshness-tracking and staleness risk just avoided above, plus a *new* risk Phase A/B don't have at all: `vermagic`/ABI compatibility between the third-party source and this exact kernel build becomes the operator's own responsibility, not something this project's own build can guarantee by construction the way Phase B still does.

**Recommendation, not a decision made unilaterally**: don't design Phase C in detail until Phase A + B are real and in use — the user's original ask ("configure on the fly," "load and unload and list") is fully satisfied by Phase A, and "both in-tree and out-of-tree" is satisfied for the overwhelmingly common case (a driver that exists in mainline Linux, just not in this project's own curated `=m` set yet) by Phase B's much simpler mechanism. True third-party, closed-source-vendor-driver support is a real, separate, higher-risk piece of work worth its own dedicated ADR once (and if) an actual concrete need for it shows up, rather than committing to its added complexity speculatively now.

## Resolved open questions

Decided directly with the user before implementation:

1. Phase B's `kernel.recipe` variant: **the same recipe**, gaining an optional, REST-supplied extra-symbols parameter, not a second, parallel recipe file — avoids a second file needing to be kept in sync by hand as the base kernel version is upgraded over time. Folded into "Decision" above.
2. `kmod-config`'s persisted `default_options`: **does not** distinguish "deliberately empty" from "not configured" — both collapse to "load with no extra options," matching the design as already drafted. No schema change needed.
3. Phase C (genuine out-of-tree/third-party modules) stays deliberately undesigned, per the recommendation above, until a real, concrete need for it exists — confirmed, not revisited.
