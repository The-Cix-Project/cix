# 0038 — VLAN via 802.1q sub-interfaces, physical NIC attachment via the existing rtnl_link_set_master

## Status

Accepted

## Context

Raised in the same conversation as ADR-0037, as the other half of "what does the host's own switching fabric actually look like": how does real physical ethernet get onto a Kanxeo-managed bridge at all, and how do VLANs fit in? Before this, neither existed. `network create` only ever created a bridge for veth/container attachment; the only physical-NIC mechanism in the codebase (ADR-0022, `--interface=`) moves a whole NIC into *one* container's own netns — real and useful, but a wholly different thing from "attach a physical link to a host-managed bridge so multiple containers, or multiple VLANs, can share it."

Two Linux VLAN models exist: 802.1q sub-interfaces (a distinct netdev per VLAN, e.g. `eth1.100`) versus bridge VLAN filtering (one bridge, many VLANs multiplexed over shared ports via per-port tag/untag state). Checked directly against this project's own existing model (`daemon/src/network.c`, `src/container_net.c`) before choosing: it's strictly one-bridge-per-network, a network's own name *is* its bridge's ifname, with no existing concept of "one bridge carrying several VLANs' worth of segments." Bridge VLAN filtering would need inventing a new per-port-tag concept this codebase has nowhere today. 802.1q sub-interfaces need none of that — a VLAN sub-interface is just another netdev, created the same way `rtnl_bridge_create()`/`rtnl_veth_create()` already create netdevs, and it slots into the existing one-bridge-per-network model unchanged: it just plays the same role a physical NIC would, something to enslave to a network's own bridge.

Checked directly, not assumed: `rtnl_link_set_master()` (`netplane/src/rtnetlink.c`), which enslaves a link to a bridge, is fully generic — nothing veth-specific in it, confirmed by reading the function itself and by ADR-0022's own prior, independent finding that the adjacent netns-move primitives have no veth-specific assumptions either. Enslaving a real physical NIC needed no new rtnetlink primitive at all for that half of the work.

## Decision

**One mechanism covers both physical-NIC attachment and VLANs**: `network_attach_interface(net_name, ifname, vlan_id)` (`daemon/src/network.c`). `vlan_id` 0 enslaves `ifname` directly to the network's bridge via the existing, unchanged `rtnl_link_set_master()` — untagged/access mode, the whole link belongs to this one network. A nonzero `vlan_id` instead creates a new `<ifname>.<vlan_id>` 802.1q sub-interface (`rtnl_vlan_create()`, new — `IFLA_LINK` to the parent's ifindex, nested `IFLA_LINKINFO{IFLA_INFO_KIND="vlan", IFLA_INFO_DATA{IFLA_VLAN_ID}}`, reusing the existing generic `nl_msg_nest_start`/`nl_msg_nest_end` helpers, no new low-level nesting plumbing needed) and enslaves *that* — the parent NIC itself is left untouched, free to be attached (with a different `vlan_id`) to other networks, so one physical trunk can genuinely serve several Kanxeo networks at once.

**Validation reuses `--interface=`'s own existing single source of truth**: `ifname` must resolve via `device_find("net:<ifname>")` (`daemon/src/device.c`) and be `assignable`. `enumerate_net_one()` gained one addition to make that check correct for bridge enslavement, not just netns moves: an interface with a `/sys/class/net/<ifname>/master` symlink present (already enslaved to *any* master) is now reported `assignable=0` — the same "sysfs visibility is exclusivity, no separate claimed table" pattern ADR-0022 already established for netns-moved interfaces, extended here rather than inventing a second bookkeeping mechanism.

**Persistence and restart-safety mirror the bridge/gateway themselves**: attached interfaces are stored as part of a network's own persisted entry (`interfaces: [{ifname, vlan_id}]`) and re-applied by `network_init()` on every daemon restart — but, unlike the bridge (pure software, always reconstructible), a physical interface's re-attachment is deliberately best-effort at startup, not a hard failure: the same "not present on this host, skip, not fatal" posture `test_image_fixture_stage_toolchain()`'s own extras loop already established for hardware that may or may not exist on a given boot.

**Detach is simpler than ADR-0022's own container-passthrough teardown.** `network_detach_interface()` either clears `IFLA_MASTER` (new `rtnl_link_clear_master()`, the direct reverse of `rtnl_link_set_master()`) or deletes the VLAN sub-interface outright (`rtnl_link_delete()`, already existed). Neither needs ADR-0022's netns-fd-anchored lifetime or kernel-fallback-name handling — a bridge-enslaved interface never leaves the root netns at all, so none of those hazards apply.

## Consequences

- Verified two ways, split by what this sandbox can and can't actually prove — it has no real, physically-backed NIC visible in its own root netns at all (confirmed directly, the identical gap ADR-0022 already documents), and *every* software-creatable interface (veth included) lives under `/sys/devices/virtual/net/`, so it's excluded by `enumerate_net_one()`'s own exclusion by construction, not just by bad luck. (1) The actual kernel mechanism -- `rtnl_vlan_create()`/`rtnl_link_clear_master()` -- needs no `device_find()` gate at all, so it's proven directly and fully (`test/test_rtnetlink.c`, extended): a VLAN sub-interface created over a real veth-pair stand-in, confirmed as the thing that actually becomes the bridge port while its parent link never does, then released via the new clear-master primitive. (2) `network_attach_interface()`'s own validation layer is proven end-to-end over real HTTP (`test/test_network_interfaces.c`, new): an unknown ifname and a real-but-virtual veth end are both correctly rejected (the latter proving `enumerate_net_one()`'s existing exclusion is genuinely reused, not reimplemented, for this new endpoint), attaching to an unknown network 404s, an out-of-range `vlan_id` 400s, and a network's own `interfaces` list stays empty throughout since nothing above ever legitimately attaches. The remaining positive path -- a real assignable interface actually attaching, `GET /v1/devices` flipping it to `assignable: false`, detach flipping it back -- needs real hardware this environment doesn't have, and is left as an explicit, known gap rather than faked with a stand-in that can't actually exercise it, the same honesty ADR-0022 already established for its own equivalent boundary.
- `daemon/src/network.c` now depends on `device.h` (previously networking and device discovery were independent modules) — a real, new coupling, justified by reusing the exact validation `--interface=` already established rather than inventing a second one.
- `NETWORK_MAX_INTERFACES` (8 per network) is a generous fixed bound, the same "host hardware, no natural daemon-side ceiling" reasoning `CONTAINER_MAX_INTERFACES` (`include/container.h`) already set for the container-passthrough case.
- Bridge VLAN filtering itself was never built, and isn't a documented gap so much as a considered non-choice: nothing in this project's own topology needs one bridge to carry several distinct VLANs' worth of *segments* sharing the same set of ports — every VLAN here is its own Kanxeo network, with its own bridge, same as every other network.
