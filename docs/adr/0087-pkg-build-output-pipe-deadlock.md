# 0087 — build-output capture pipes were drained once, after exit, deadlocking any sufficiently verbose build

## Status

Accepted

## Context

Found live while bootstrapping `cix-hosttools` on 192.168.15.95 (ADR-0084/0085's own follow-on work, self-hosted from-source `perl` build): `pkg install perl --image=cix-hosttools` reproducibly stalled partway through `make`, with `__pkgbuild`'s own `cpu.usage_usec` frozen for 90+ seconds and the host's `load1`/`load5`/`load15` correspondingly near zero. Several hypotheses were investigated and ruled out with direct evidence before the real cause was found: an interactive-prompt hang (ruled out -- no prompt in the recipe), a DNS-resolution hang (ruled out -- the stall was deep in `make`'s own CPAN-module phase, long past `Configure`'s network probing, and outlasted this box's own documented 150s DNS-timeout precedent), and a parallel-`make` race under real SMP (partially disproven -- a `-j1` diagnostic build progressed much further than `-j2` but eventually stalled too, at a different point each time). PSI (`cpu.pressure`/`memory.pressure`/`io.pressure`, ADR-0073/0074) reading exactly zero across all three, combined with zero disk I/O and a frozen `cpu.usage_usec`, was the decisive signal: this is the specific signature of an in-memory synchronization block (pipe-full backpressure), not any kernel-tracked resource contention.

Reading `daemon/src/pkg.c` confirmed it directly: the build container's own stdout/stderr are captured via a plain `pipe()` (`struct container_spec`'s `capture_output`/`stdout_fd`/`stderr_fd`, added by the original build-output-capture feature -- CHANGELOG's own "Part 12: real build-container stdout/stderr capture") whose read end, `g_build_output_rd`, was **never registered with epoll anywhere** -- it was read exactly once, in a blocking drain-to-EOF loop inside `pkg_build_completed()`, called only *after* the build container had already exited. A plain `pipe()`'s kernel buffer is 64KB by default. Once a build's cumulative stdout+stderr exceeded that, its next `write()` blocked forever, since nothing was reading from the pipe while the container was still running -- an unconditional deadlock, not a timing-sensitive one, for any recipe verbose enough to cross that threshold. `perl`'s own `Configure`+`make` output comfortably exceeds 64KB.

`daemon/src/main.c`'s `handle_bootroot_assemble_event()` (the reaper for `spawn_cix_bootroot_assembly()`, ADR-0057/0080) turned out to have the identical architectural gap: mkbootroot's own captured stdout/stderr were likewise read exactly once, in `cc->output_fd`'s single `read()` call, only after `waitpid()` confirmed the child had already exited -- just never yet observed live, since a control-plane-only rebuild's own output volume had never crossed 64KB. Left as-is, this would have deadlocked the *assembly* step itself (not a package build) the first time it did.

This directly threatens the user's own stated hard requirement that the self-hosted build path (`mkbootroot` + `pkg hostbuild`, both running entirely on the real installed box) work "flawlessly, atomically, without builds or support from any external system" -- any sufficiently verbose from-source recipe, not just `perl`, was one `pipe()`-buffer-full away from wedging the daemon's single in-flight build slot indefinitely.

## Decision

Both capture pipes are now drained **incrementally**, as data arrives, via the daemon's own `epoll` event loop -- never read in one shot after the fact:

- `pkg.c`'s `g_build_output_rd` (opened `O_NONBLOCK` on the read end only, via `pipe2()`) is registered directly with `main.c`'s epoll instance the moment the build container is successfully spawned (`handle_pkg_fetch_event()`, new `CONN_PKG_BUILD_OUTPUT` conn kind) -- watching the pipe's own fd for `EPOLLIN`, not a pidfd. `pkg_build_output_readable()` drains everything currently available into a persistent, bounded sliding-window buffer (`g_build_output_captured`, same tail-keeping semantics the old single-shot drain already had) each time it fires. `pkg_build_completed()` (the container-exit reaper) now just reads from that already-filled buffer, plus one final non-blocking top-off call to catch anything written in the brief window between the build's last `write()` and its own exit.
- The exact same pattern is applied to `main.c`'s own `spawn_cix_bootroot_assembly()`/`handle_bootroot_assemble_event()`: a new `CONN_BOOTROOT_OUTPUT` conn kind registers mkbootroot's own output pipe directly, `bootroot_output_readable()` drains it into `g_bootroot_output_captured` as the assembly runs, and the exit reaper reads from that buffer instead of `cc->output_fd` directly.

This is the same `enum conn_kind`/`struct conn` mechanism every other long-lived daemon-owned fd already uses (`CONN_PKG_FETCH`, `CONN_BOOTSTRAP_FETCH`, `CONN_DISK_FORMAT`, etc.), specifically modeled on `CONN_KMSG`'s own shape (`start_kmsg_watch()`/`handle_kmsg_event()`/`logstore_kmsg_readable()`) -- a bare fd registered and drained live via `EPOLLIN`, not a pidfd-then-single-read. No new pipe-size tuning (`F_SETPIPE_SZ`) was considered: a larger buffer only raises the threshold, it doesn't remove the deadlock for an arbitrarily verbose build, which the "No Stop-Gaps" maxim rules out as a real fix.

Both fd's own close/cleanup is now owned exclusively by their own EPOLLIN-driven handler (`handle_pkg_build_output_event()`/`handle_bootroot_output_event()`), triggered when a read reports EOF/error -- the exit-status reaper functions (`pkg_build_completed()`, `handle_bootroot_assemble_event()`) no longer close these fds themselves, since doing so could otherwise race a still-live epoll registration for the same fd (the container's own process-tree exit and the pipe reaching EOF are two independently-delivered epoll events, dispatched in no guaranteed order within the same batch).

## Consequences

- Any `pkg install`/`pkg hostbuild` recipe, regardless of how verbose its build output is, can no longer deadlock on this mechanism -- confirmed by design (nothing lets the pipe's kernel buffer fill while a reader exists) and **verified live**: the real `perl.recipe` (upstream CPAN URL, real `make -j"$(nproc)"`), which had reproducibly stalled every prior attempt at the same point, completed to `state: "installed"` on 192.168.15.95 with `cpu.usage_usec` climbing continuously the entire time (no freeze at the ~90s mark the old code always hit).
- `spawn_cix_bootroot_assembly()`'s own captured-output mechanism gets the identical fix pre-emptively, before it was ever observed to fail live -- consistent with this project's own practice of fixing every instance of a confirmed bug class found in one pass (see ADR-0085's own two same-class follow-ons), not just the one that happened to trigger first.
- `struct conn`'s `output_fd` field (previously `CONN_BOOTROOT_ASSEMBLE`-only) is now unused and removed -- `CONN_BOOTROOT_OUTPUT` uses the conn's own `fd` field directly, the same convention `CONN_PKG_BUILD_OUTPUT` and `CONN_KMSG` both already use.
- General lesson, matching ADR-0086's own closing note: any future "capture a subprocess's own stdout/stderr for later diagnostics" mechanism in this codebase must drain its pipe live via epoll from the moment the subprocess is spawned, never in a single post-exit read -- a plain `pipe()`'s 64KB kernel buffer is a real, silent ceiling on how much output a single-shot read pattern can ever safely support.
