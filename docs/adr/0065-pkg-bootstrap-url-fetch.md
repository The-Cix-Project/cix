# 0065 — pkg bootstrap URL-fetch: closing a real gap in ADR-0031's own "operator scp's it" assumption

## Status

Accepted

## Context

Raised directly by the user while getting a hands-on, real-world install running for the first time: `POST /v1/pkg/bootstrap`'s `toolchain_path` mode (ADR-0035) and `POST /system/update`'s `image_path`/`kernel_path` (ADR-0031) both rest on the same explicit assumption — "the operator transfers it onto the box out-of-band (`scp`)." Tested for real, against a genuinely separate, freshly-installed box (`192.168.15.95`, installed earlier this session via `POST /system/iso`, ADR-0064) rather than this dev sandbox's own filesystem, that assumption turned out to be false: a real Kanxeo install has **no SSH server and no general shell at all**, deliberately (ADR-0034, console login is a supervised `kanxeoctl` shell, not a shell an operator could `scp` through). There was never actually a way to get a multi-hundred-MB toolchain artifact onto a fresh box over the network — confirmed directly (`nc -z <box> 22` closed) rather than assumed, before treating this as a real, fixable gap rather than routing around it with something out-of-band and untracked.

## Decision

**Reuse the daemon's own existing host-side curl-fetch primitive, don't invent a second one.** `pkg.c`'s own recipe `pkg_source` fetch (`curl -fsSL --retry 8`, host-side, checksum-verified, no container, no HTTP-upload streaming through the daemon's own hand-rolled server) is exactly the shape this problem needs — it was just never wired up anywhere except recipe sources. `POST /v1/pkg/bootstrap` gains a third mode: `{"toolchain_url": "...", "toolchain_sha256": "..."}`, fetched by the daemon itself into a fixed scratch path (`<data-dir>/pkg/bootstrap_toolchain.squashfs`), checksum-verified via `pkg_run_capture_sha256()` (exported from `pkg.c`, the identical real check every recipe source already gets — not a second implementation), then handed to the existing `pkg_bootstrap_from_toolchain()` for staging, completely unchanged. The two existing modes (no body / `toolchain_path`) are untouched — this is a strict addition, not a revision of ADR-0031's or ADR-0035's own decisions; both keep exactly their previous synchronous, 204-on-success behavior.

**Async, not synchronous — a real network fetch of a real, large artifact cannot block the daemon's single-threaded event loop.** The unsquashfs staging step (already synchronous, already fast, unchanged) is fine to run inline once the fetch completes; the fetch itself is not. Mirrors `POST /system/iso`'s own shape (ADR-0064) exactly: a new `CONN_BOOTSTRAP_FETCH` conn kind, fork+`pidfd_open()`+`epoll`, `202` on start, `GET /v1/pkg/bootstrap` polls `{state, error}` (`none`/`fetching`/`ready`/`failed`). A precondition check (both `toolchain_url` and `toolchain_sha256` required — unlike a recipe's own `pkg_source`, there is no "trust whatever shows up" mode for something that gets unsquashfs'd wholesale into the shared build sandbox) fails the request itself with `400`, before any fork; "already fetching" is a separate `409`, mirroring `respond_pkg_error()`'s own `PKG_ERR_BUSY` vs. `PKG_ERR_INVALID_TOOLCHAIN` split every other async job in this daemon already uses.

**`PKG_CURL_BIN` moves from `pkg.c`'s own private `#define` into `pkg.h`, shared, not duplicated.** The only genuinely new shared surface this needs — every other bin-path constant (`PKG_TAR_BIN`, `PKG_SHA256SUM_BIN`, `PKG_UNSQUASHFS_BIN`) stays private to `pkg.c`, since only the curl invocation itself is needed from `main.c`.

**CLI**: `kanxeoctl pkg bootstrap --toolchain-url=URL --toolchain-sha256=SHA256 [--wait]` / `kanxeoctl pkg bootstrap-status` — the existing `pkg bootstrap` verb gains the new flags rather than becoming a new subcommand (it is still fundamentally "stage a toolchain," just a third way to point at one), while status polling gets its own verb, the same split `iso build`/`iso status` already established.

## Consequences

- Verified real, end to end, twice: a real ~1.25GB toolchain artifact served over plain HTTP (this dev sandbox's own existing squashfs, `python3 -m http.server`) and fetched by a real, separately-running `kanxeod` via `POST /v1/pkg/bootstrap` with `toolchain_url`/`toolchain_sha256` — real `202`, real polling to `state: "ready"`, and `gcc` confirmed present at the expected path in the resulting pkgbuild sandbox afterward. A second run with a deliberately wrong checksum correctly reached `state: "failed"`, `error: "checksum mismatch"`, without ever touching the build sandbox. The existing no-body and `toolchain_path` modes were re-tested unchanged (`204`, unmodified behavior).
- **The real box this gap was found on (`192.168.15.95`) cannot retroactively receive this fix** — pushing a fix onto a box has the exact same "no transfer path" problem the fix itself solves, a genuine chicken-and-egg this ADR does not attempt to route around. The clean resolution is what this project already does for every other update: rebuild the ISO with the fix included (self-hosted, via the now-REST-driven `POST /v1/system/iso`, ADR-0064) and reinstall — the same "write once, verify, cut over" posture as every other update in this system, just at reinstall granularity for this one box, this one time.
- `/system/update`'s own `image_path`/`kernel_path` still only accept local paths — not extended by this ADR. Unlike the toolchain bootstrap case, a fresh install never needs `/system/update` to reach a working state (the fix, once built into a new `kanxeod`, ships inside the ISO itself); `/system/update`'s own real gap, if it turns out to matter in practice, is a separate, later decision, not assumed here.
