# 0170 — TCC cannot build cgo-based Go packages: glauth/gitea join the Tier-3 TCC exception list

## Status

Accepted

## Context

Issue #31 asked a narrow, well-scoped question: glauth and gitea (both CGO+sqlite Go builds) currently build in production via cgo's own ambient `cc` lookup, with no explicit `CC=` pin at all — the exact same implicit-pickup risk class already confirmed once on `openssh.recipe` (a real GCC silently picked up over TCC, flags/libraries reported as linked by `configure` but never actually present in the output binary). The issue asked whether `CC` could be pinned explicitly to TCC instead, matching this project's own "TCC by default, with real effort" policy (`gcc.recipe`'s own comment states the full 3-tier policy: Cix's own code is always TCC; third-party recipes are TCC by default with real effort; a small, explicit, documented exception list exists for genuinely infeasible cases).

A real, multi-stage investigation (not guessed, not abandoned after the first obstacle) found four separate TCC/cgo gaps, three of which were genuinely fixable at the recipe/wrapper level:

1. **`-Qunused-arguments`** — cgo unconditionally passes this Clang-only flag when compiling `runtime/cgo`'s own bridging code. Fixed with the same thin "toolwrap" pattern `chrony.recipe` already established (strip the one unsupported flag, pass the rest through unchanged). Confirmed via `go build -x` that no other flag cgo passes is a problem.
2. **C99 `_Complex`** — cgo unconditionally emits `GoComplex64`/`GoComplex128` (`_Complex`-typed) typedefs into every package's generated `_cgo_export.h` whenever any exported Go function exists anywhere in the build graph, regardless of whether complex numbers are ever actually used. TCC 0.9.27 cannot parse `_Complex` in any spelling tested (`float _Complex`, `_Complex float`, nor via `<complex.h>`'s own `complex` macro, which itself fails inside glibc's `bits/cmathcalls.h`). Fixed by neutralizing the two dead typedefs to a plain struct before compiling, since neither glauth nor gitea (nor go-sqlite3's own real `//export` user, `callback.go`) ever does complex arithmetic.
3. **No `__atomic_*`/`__sync_*` builtin support at all** — confirmed directly: both families compile only as bare implicit-declaration external calls, then fail to link. Go's own `runtime/cgo/gcc_libinit.c` (part of every cgo build, not package-specific) uses `__atomic_load_n`/`__atomic_store_n` with `CONSUME`/`RELEASE` ordering on two native-word-sized operands (a plain `int`, a function pointer) — a full grep of `runtime/cgo/*.c` confirmed no other builtin or ordering is used anywhere in the tree. Fixed with a real, provably-correct macro shim: x86-64's own TSO memory model already gives `CONSUME`/`RELEASE` ordering for free on an aligned load/store of a native-word-sized object, needing only a compiler barrier (`asm volatile("" ::: "memory")`), not a hardware fence — this is standard C/C++ memory-model theory for a strongly-ordered architecture, not a hand-wave, and Cix has no non-amd64 target to worry about.
4. **THE ACTUAL WALL — TCC aborts the entire compilation unit after the first error.** Confirmed directly with a minimal, isolated probe: three independent top-level functions, each containing one guaranteed real error; only the first function's error is ever reported, compilation halts there, the second and third are never reached. GCC/Clang, by contrast, continue past most errors (up to a configurable limit). `cmd/cgo`'s own type-probing (`gcc.go`'s `typeCheck`) depends structurally on this continue-past-errors behavior — its own source comment states the mechanism plainly: it batches every C symbol's five probe functions (`not-declared`/`not-type`/`not-int-const`/`not-num-const`/`not-str-lit`) into one combined source file, compiles it once, and classifies every symbol from the full resulting error list in a single pass ("we can infer what we need from only the presence or absence of an error on a specific line"). TCC stopping at the first error breaks this for every name after the first, in every probed package. Confirmed reproducing this exact failure against the Go standard library's own `os/user` package (pulled in transitively) — not glauth- or go-sqlite3-specific code — so this is a systemic TCC-vs-cgo incompatibility, not anything this project's own recipes could plausibly work around by patching their own third-party source.

   (A related, separately-confirmed bug was found and fixed along the way: TCC's `#line`-directive diagnostic handling prepends the compiled file's own directory onto a `#line`-supplied filename in error messages — e.g. `#line 1 "not-type"` prints as `/some/dir/not-type:1: error: ...` instead of the C-standard-correct `not-type:1: error: ...` — which independently breaks `cmd/cgo`'s exact-string pseudo-filename matching. This was fixed at the wrapper level by rewriting TCC's stderr before cgo ever sees it. It is gap #4 above, not this one, that is the real, unfixable wall.)

No wrapper-level trick closes gap #4 without literally reimplementing `cmd/cgo`'s own batch-probe compiler-driver semantics — splitting every probe into its own individual `tcc` invocation and synthesizing GCC-shaped combined output to fake continue-past-errors behavior. That is exactly the kind of brittle, bespoke reimplementation this project's own **No Hacks** maxim rules out, and it would need to be re-verified against every future glauth/gitea/Go-toolchain update rather than being a one-time fix.

## Decision

TCC cannot build any cgo-based Go package end-to-end — this is a categorical, structural incompatibility (gap #4), not something specific to glauth or gitea's own code. Both recipes join the existing Tier-3 TCC exception list (`gcc.recipe`, `kernel.recipe`, `openssl.recipe` already there for their own reasons) for this reason.

`CC` is pinned to the real, already-staged ambient gcc **explicitly, by absolute path** (`/usr/bin/gcc` — never a bare `gcc`/`cc`, per this project's own confirmed gotcha that a bare-name invocation computes a wrong relative install prefix and breaks `cc1` lookup) in both `glauth.recipe` and `gitea.recipe`. This closes the actual risk issue #31 raised — implicit, accidental ambient-compiler pickup — without pretending TCC can do a job it categorically cannot. Both recipes previously had no `CC=` at all; both keep building the identical binary they already build in production today, now via a deliberate, documented, and safe choice rather than accidental luck.

## Consequences

- `recipes/package/glauth/2.4.0/build.sh`, `recipes/package/gitea/1.24.7/build.sh` — `pkg_build()` now sets `CC=/usr/bin/gcc` explicitly; both comment blocks rewritten with the full investigation trail (this ADR is the canonical "why," referenced rather than repeated in full a third time).
- Live `ldap-1`/`ldap-2` were never touched during this investigation — all testing used a throwaway scratch image on 192.168.15.95, per this project's own standing safety discipline for real-hardware testing. Production glauth/gitea behavior is unchanged (same ambient gcc it already silently used, now pinned deliberately).
- Any future Cix package that uses cgo (a large fraction of the Go ecosystem needing C interop — sqlite drivers, some crypto packages) should expect gap #4 by default and reach for this ADR first, rather than re-deriving the same investigation from scratch. TCC-by-default remains correct policy for everything else; cgo specifically is now a known, documented exception, not an open question.
- The gcc-dependency this creates for glauth/gitea's own build step is the same class of "genuinely necessary ambient toolchain, not a violation of the cleanup effort" carve-out `gcc.recipe`'s own bootstrap-compiler build already established for itself (task #845's ambient-toolchain-contamination cleanup should treat both as documented exceptions, not gaps to silently close).
