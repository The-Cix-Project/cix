# 0017 — BPF_CGROUP_DEVICE for device passthrough enforcement, not a blanket eBPF ban

## Status

Accepted

## Context

`docs/mission/MISSION.md`'s expanded charter (this session's own rewrite) commits, in its Technology Stack section, to a specific mechanism for hardware passthrough: "Hardware assigned to a container — PCI devices, USB devices, GPUs, block devices — is exposed the same way: the specific `/dev` node inside the container's own mount namespace, with the cgroup device controller granting access to it." That sentence was written before establishing what "the cgroup device controller" actually means on cgroup v2 — this project's only cgroup version (`src/cgroup.c` writes `memory.max`/`pids.max`/`cpu.max` under `/sys/fs/cgroup/<name>`, cgroup v1 is never used anywhere).

Cgroup v2 removed cgroup v1's file-based `devices.allow`/`devices.deny` interface entirely. Confirmed directly against the kernel source (`security/device_cgroup.c`): the only mechanism cgroup v2 offers for device access control is a `BPF_PROG_TYPE_CGROUP_DEVICE` program attached via `BPF_CGROUP_DEVICE`. There is no other kernel-native way to fulfill MISSION.md's own sentence.

This raises a real question: this project's stated "no eBPF" rule (`docs/mission/MISSION.md`, `CLAUDE.md`, `docs/roadmap/ROADMAP.md`, `README.md`, `netplane/include/rtnetlink.h`) appears once in each of those files, and in every single occurrence the wording is identical and specific — "*A 100% custom virtual switching and routing data plane written in C (no Open vSwitch or eBPF)*" — inside the **Networking Plane** bullet, describing the packet-forwarding data plane specifically. ADR-0011 already resolved a closely related ambiguity for that same sentence (whether "custom" meant hand-rolled rtnetlink control of the kernel's own forwarding, or reimplementing switching in userspace) with the same rigor this ADR now applies to a second question the same sentence raises: does "no eBPF" mean *nowhere in thinC, ever*, or specifically *not in the networking data plane*? A full-repo grep of every occurrence of the phrase found it stated only in the networking-plane context, never as a project-wide maxim (the Immutable Maxims list itself, in both `docs/mission/MISSION.md` and `CLAUDE.md`, contains no eBPF mention at all). Textually, the rule is scoped to networking.

This also isn't cosmetic: containers in this project run as full root with the complete Linux capability set and no user namespace (`CLONE_NEWUSER` is never set in `spec.ns.clone_flags`, confirmed via `daemon/src/main.c`'s `handle_create()` and every test harness). Device-node access is not gated by the mount namespace at all — a fact already documented in `test/test_dns.c`'s own `ensure_dev_node()` comment before this feature existed: "device access isn't gated by the mount namespace, only by the node's major:minor and (absent here) any device cgroup restriction, which this project's cgroup setup never applies." Without *some* enforcement mechanism, any container could simply `mknod()` its own node for another container's assigned device and read it directly — mount-namespace-only isolation would be a no-op given this project's existing no-capability-dropping container model.

## Decision

Use `BPF_CGROUP_DEVICE` — the kernel-standard, and only, cgroup v2 device access control mechanism — implemented with no external dependency (no libbpf, no clang/LLVM BPF backend, no `bpftool`), matching this project's existing zero-external-dependency posture (`netplane/src/rtnetlink.c`'s own hand-built netlink messages, ADR-0007's hand-rolled daemon). `include/linux_compat.h` gains a raw `bpf(2)` syscall wrapper (`sys_bpf()`) and self-declared `struct thinc_bpf_prog_load_attr`/`struct thinc_bpf_prog_attach_attr`/`struct thinc_bpf_insn` types, following the exact same pattern `struct clone_args` already established for `clone3(2)`: declare only the fields this project's one use case needs, relying on `bpf(2)`'s documented "shorter attr = trailing fields implicitly zero" contract, rather than pulling in `<linux/bpf.h>` (which would clash with glibc headers the same way `<linux/sched.h>` does). `src/container_dev.c` hand-assembles a `BPF_PROG_TYPE_CGROUP_DEVICE` program at container-creation time: an unrolled comparison block per granted `(type, major, minor)`, default-deny, no loops, no maps, no helper calls — a plain C loop emitting instruction bytes directly, the same posture as rtnetlink's hand-built messages. One program per container, attached to that container's own existing `cgroup_create()` leaf, loaded and attached *before* `ns_clone3()` (parent side) so the policy is in effect from the child's very first instruction — `CLONE_INTO_CGROUP` places the child into the cgroup atomically as part of `clone3()` itself, leaving no race window, and the child's own `mknod()` calls (`container_dev_mknod()`, called after `mountns_pivot()`) are themselves subject to a `BPF_DEVCG_ACC_MKNOD` check under this same program.

This is the first eBPF code anywhere in thinC. This decision authorizes `BPF_CGROUP_DEVICE` for device-cgroup access control specifically — it does not reopen or relax the networking-plane's own "no eBPF" rule, and any future proposal to use eBPF for anything networking-adjacent still needs its own explicit sign-off, not an inference from this ADR.

`device_count == 0` is a deliberate no-op: `container_dev_bpf_attach()` returns immediately without loading or attaching anything, so a container that doesn't request any devices is byte-for-byte unaffected by this feature (No Regressions) — verified directly in `test/test_devices.c`.

## Consequences

- A genuinely new class of syscall-ABI risk alongside the ones ADR-0002 (`clone3`/`pivot_root`) and ADR-0008 (`epoll_event`'s TCC packing bug) already catalog: hand-encoded eBPF instruction bytes, not just a struct's field layout. The same "confirmed empirically, not from first principles" discipline applies — the register-nibble packing (`dst_reg` low nibble, `src_reg` high nibble, matching the x86_64 kernel/GCC bitfield layout `struct bpf_insn` itself uses) and the full comparison-chain/jump-offset arithmetic were verified by loading and running real programs against a live kernel (a minimal `mov r0,1; exit` sanity check, then multi-device grant/deny scenarios through a real cgroup) before being trusted, not derived and assumed correct.
- `image/kernel/qemu-part1.config` needs `CONFIG_BPF_SYSCALL`/`CONFIG_CGROUP_BPF` (confirmed absent before this change) — a real, new prerequisite for the *shipped* thinC kernel. This dev environment's own host kernel already supports `bpf(2)`, so feature development and `test/test_devices.c` itself needed no kernel rebuild; only the boot-tested/installed kernel does, the next time `build/bzImage` is rebuilt per its own documented one-time recipe.
- A real, encountered environment constraint worth recording for future test-writing: `BPF_CGROUP_DEVICE` checks are hierarchical — every cgroup level from the true root down to a process's own leaf is consulted, and any single ancestor level denying fails the whole chain regardless of what a more specific descendant program allows. This project's own dev/build environment (a privileged, nested LXC container) turned out to already run under an ancestor-level device policy permitting only a standard device set (`/dev/null`, `/dev/zero`, `/dev/full`, etc.) — confirmed by hand (a fabricated device number was denied even for a plain root shell on the bare host, entirely outside any container this project creates). `test/test_devices.c` therefore grants real, standard device numbers rather than synthetic ones. Real deployment targets (bare metal, or this project's own QEMU boot tests) have no such ancestor and are unaffected.
- This is now the reference pattern GPU passthrough (the next agreed step after disk quotas) will reuse: the same `mknod` + same per-container `BPF_CGROUP_DEVICE` grant, only the discovered `/dev` node source differs.
- `struct container_handle` gains a `bpf_prog_fd`; `registry_remove()` closes it alongside the existing `pidfd`/`cgroup_fd`. This project never `rmdir()`s a cgroup leaf on container removal (a pre-existing gap, orthogonal to this feature, not touched here) — the attached BPF program stays pinned to that still-existing leaf for exactly as long as its other limits (`memory.max`, `pids.max`) already do.
