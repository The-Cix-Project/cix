# 0025 — persisted, auto-restarting containers (`restart: "always"`, `depends_on`)

## Status

Accepted

## Context

Containers have been deliberately in-memory only since Phase 3 — every container dies automatically via `PR_SET_PDEATHSIG` if the daemon exits, so there was never any restart-orphan state to reconcile. Networks, images, DNS records, PKI certs, and pkg state all already survive a daemon restart; containers were the one resource that didn't. For a real deployment (routers, a NAS, a git-repo container, an ad-blocking DNS server — all expected to keep running across a reboot, some depending on others being up first), that's a hard blocker, raised directly by the user.

Two constraints were confirmed before designing anything:

1. `confirm_boot()` (the A/B boot-health mechanism, `daemon/src/main.c`) fires immediately after the listening socket opens, and its own comment defines "healthy" as *"about to serve traffic"* — deliberately uncoupled from anything else succeeding. Auto-starting containers must never be able to affect that signal, so it has to run strictly after it, never before.
2. Confirmed directly with the user: a real, non-blocking restart delay is required for a crash-looping container (not immediate infinite retry), and `DELETE /v1/containers/{name}` is the single action that removes both the live instance and its persisted definition — no separate "pause vs. disable" split.

## Decision

**No new REST resource.** `restart`/`depends_on` are two new optional fields directly on the existing `POST /v1/containers` request (default `restart: "no"`, empty `depends_on` — byte-identical behavior to every existing caller, confirmed by re-running the full existing test suite unchanged after the refactor below). When `restart: "always"` is set and the container is created successfully, the daemon *also* persists that exact request body — the same "define and start in one call" shape `POST /v1/networks` already has for its own bridge.

**Persistence (`daemon/src/containerdef.c`/`daemon/include/containerdef.h`)** stores the original, already-validated JSON request body verbatim, plus a parsed `depends_on` list cached alongside it for the dependency resolver — not a second schema for "what a container looks like." `containerdef_resolve_order()` mirrors `pkg.c`'s own `resolve_chain()` shape exactly: DFS with a `visiting[]` cycle-detection stack, applied to `depends_on` instead of `pkg_depends`. A `depends_on` naming an unknown or non-`"always"` definition, or a cycle, disables just that one definition (and anything transitively depending on it) — logged, never aborting the rest of boot.

**`handle_create()` was split** into a thin HTTP-response wrapper and a new `create_container_from_body()` with zero HTTP coupling, doing the exact same parsing/validation/spec-building/`registry_create()` work (plus the `dns_register`/`pki_issue` side effects) — reused by three callers: the live REST handler, boot-time auto-start, and crash-restart replay. Verified byte-for-byte behavior-preserving by re-running every existing REST-facing test (`test_daemon`, `test_cli`, `test_networks`, `test_images`, `test_dns`, `test_pki`, `test_pkg`, `test_daemon_devices`) unchanged, all passing before adding a single new test.

**Boot-time auto-start** (`containerdef_autostart_all()`) runs once, right after `confirm_boot()`, unconditionally (not just under `--init-mode` — this is "whenever this daemon process starts fresh" behavior, not installed-boot-specific), as a blocking sequence before the event loop starts, consistent with every other startup step already blocking. The kernel's own listen backlog queues any incoming connection during this window; none are dropped.

**Crash restart + delay is the reactor's first-ever timer.** In `handle_container_event()`, an unprompted exit (never reached by an explicit `DELETE`, which removes the pidfd from epoll before this event could ever fire) of a `restart: "always"` container arms a one-shot `timerfd_create(CLOCK_MONOTONIC, TFD_NONBLOCK)`, registered under a new `CONN_RESTART_TIMER` conn kind, for a fixed `CONTAINER_RESTART_DELAY_SECONDS` (2s, daemon-wide, not per-service — YAGNI for v1). A blocking `sleep()` was rejected outright: this daemon's entire event loop is single-threaded and non-blocking by design, and a blocking sleep would freeze every other in-flight request or event for the whole delay. Matches Docker's own `--restart=always` semantics precisely: restarts regardless of exit code, including a clean `0` exit.

**`DELETE /v1/containers/{name}`** now also calls `containerdef_remove()` unconditionally (a no-op if no definition exists) — the container never comes back, not via a pending crash-restart timer (none exists, since this path never touches `handle_container_event()`) and not on a future daemon restart.

## Consequences

- A real, load-bearing bug was found and fixed *during* verification, not before: my first working version called `register_container_pidfd()` a second time in both the boot-autostart and crash-restart call sites, on top of the call already inside `create_container_from_body()` itself (unchanged from the original `handle_create()`, just easy to miss having *not* removed it while adding new call sites around it). Registering the same pidfd with epoll twice returns `EEXIST`, which the existing `register_container_pidfd()` treats as fatal (`abort()`) — confirmed directly: a real daemon restart with a persisted `restart: "always"` container crashed the whole process immediately after printing "listening on." Fixed by leaving the one call where it already was and documenting it explicitly in `create_container_from_body()`'s own comment so the next call site added there doesn't repeat the mistake.
- A second real bug surfaced by the full regression sweep, not the new test's own assertions: `handle_delete()` required a container to be currently *live* (`registry_find() != NULL`) before it would even look at whether a persisted definition existed, so a definition that had never once successfully autostarted (a cycle, an unknown `depends_on`, ...) had no live registry entry to satisfy that check and could never be `DELETE`d at all — permanently stranded, with no fix short of hand-editing `container_defs.json` on disk. Found concretely: `test/test_container_restart.c`'s own cleanup of exactly this case silently 404'd, leaking `cycleA`/`cycleB`/`needsghost`'s definitions into `/var/lib/thinc/container_defs.json` on the real dev host, which then printed a `containerdef: 'ghost' depends_on an unknown definition` warning on *every other, unrelated test's* daemon startup afterward — the sweep's own cross-test log noise was the tell. Fixed by having `handle_delete()` treat "live, or has a persisted definition, or both" as "exists," running the live-instance teardown and `containerdef_remove()` as two independent steps rather than gating the second on the first.
- Verified end-to-end, not just at the unit level: a fast-exiting `restart: "always"` container was observed crash-looping with a real, measured ~2.0s gap between each exit and the next (different) pid appearing — proving the timer genuinely delays, not just that the code path is reachable. A daemon restart with a persisted container brought it back with a fresh pid. `DELETE` was confirmed to both stop it and leave `container_defs.json` empty, with no restart on a subsequent daemon restart.
- `depends_on` controls **start order only** — no readiness-probe or health-check concept exists anywhere in this project yet, so a dependency being "started" (its `clone3()` has returned) is not the same as it being ready to serve. A real, stated v1 boundary, not solved here — an operator's own services still need to handle a dependency not yet being ready, the same well-known boundary every container orchestrator has before real health checks exist.
- `registry_write_json_one()` (`daemon/src/registry.c`) now queries `containerdef_find()` directly to source the `restart`/`depends_on` response fields, rather than mirroring them onto `registry_entry` itself — a small, deliberate layering choice: `containerdef.c` stays the one source of truth for "should this persist and auto-restart," and a `registry_entry` only ever exists for as long as the process itself is alive or recently exited anyway.
