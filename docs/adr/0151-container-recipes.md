# 0151 — container recipes: a git-syncable template for a running container's own definition

## Status

Accepted

## Context

User-requested, directly: "let's make the container recipes so it will make things easier in the future." Concrete motivation, visible across this same session: `jumpbox1`, `dns-1`/`dns-2`, `ldap-1`/`ldap-2`, and `syslog-1`/`syslog-2` have each been recreated multiple times (config fixes, tooling additions, the LDAP privsep chroot fix) — every single time, their full `cmd`/`files`/network/restart-policy definition was hand-retyped from memory and prior session notes, never sourced from a single, reviewable, git-tracked artifact.

`recipes/package/` (ADR-0107/0120/0149) and `recipes/image/` (ADR-0123/0149) already establish the shape: git-tracked, versioned, synced into a running daemon's own catalog via `pkg sync`. Both are deliberately narrow — a package recipe describes how to build one piece of software; an image recipe describes only a package manifest. Neither covers what a *container* actually is: `cmd`, staged `files`, network attachment, restart policy, sysctls. That's a real, distinct concern, and asking image recipes to grow into covering it would conflate two things ADR-0123 was careful to keep separate (shared image content vs. per-instance container configuration, mirroring the platform's own OverlayFS split of lowerdir vs. upperdir/cmd).

One real design question, surfaced by reading the existing `create_container_from_body()` (`daemon/src/main.c`) before designing anything: a container's persisted create-request body is *already* a complete, self-contained JSON representation of everything needed to recreate it (ADR-0124's own rolling-restart mechanism already relies on this — it does raw string surgery on that exact persisted body). Rather than inventing a third recipe format, a container recipe's content **is** that same JSON shape verbatim — the one already accepted by `POST /v1/containers`.

A second real question, raised directly rather than assumed: several of this session's real container recipes (an LDAP client's `nslcd.conf`/`ldap-authkeys.conf`) would need a live bind password embedded in staged file content. Committing that to git bakes a real secret into permanent history. Asked the user directly (`AskUserQuestion`): generalize `kanxeo.recipe`'s own existing `REPLACE_WITH_REAL_TOKEN` placeholder convention into a real, mechanical substitution step, rather than leave secrets out of recipes entirely (which would leave the exact containers that most need reproducibility — the LDAP-backed ones — only partially covered). Confirmed: build the substitution mechanism.

## Decision

**Format**: `recipes/container/<name>/<version>/container.json` (ADR-0149's layout convention, extended to a third kind) — content is a real `POST /v1/containers` body, including its own `"name"` field. `<version>` tracks the recipe's own revision history, the same meaning ADR-0149 established for image recipes (a distinct axis from anything about the *container's* own running state, which has no version concept of its own at all).

**Daemon storage** (`daemon/src/pkg.c`, mirroring `image_recipe_*` almost exactly): `container_recipe_init()`/`_repoint()`/`_add()`/`_get()`/`_rm()`/`_write_json_list()`, `<data-dir>/pkg/container-recipes/<name>.recipe`, one current, unversioned recipe per name (no version-keying at the daemon layer — the same split ADR-0149 already draws between git history and daemon-side "current" state). `container_recipe_add()` validates content parses as real JSON and that its own `"name"` matches the name it's published under (mirroring `pkg_recipe_add()`'s `pkg_name=` contract) — but does **not** otherwise validate it as a real container body; that's checked only when actually applied, by the same code a direct create already runs through.

**Secret substitution**: `{{SECRET:KEY}}` tokens, matched anywhere inside the recipe's raw text (in practice, inside a `files[].content` string value) and substituted from the apply request's own `"secrets"` object. Implemented as a byte-level scan (`container_recipe_substitute_secrets()`) rather than a JSON-tree walk — a token lives *inside* an already-encoded JSON string, so substitution has to happen at the text level, splicing in the replacement value's own correctly-escaped form (two new small, reusable primitives added to `json.c`: `jw_raw_text()` for verbatim passthrough, `jw_raw_escaped_content()` for escaped-content-only splicing, both extracted from the existing `jw_escaped_string()` so there's still exactly one escaping ruleset, not two). An unmatched token (no key in `secrets`) is left completely untouched — a missing secret surfaces as whatever error the resulting malformed value causes downstream, never silently swallowed, and `GET .../recipes/{name}` always shows the real, unsubstituted content, never a guess.

**Apply** (`POST /v1/containers/recipes/{name}/apply`): renders the recipe, then calls `handle_create()` — the exact same handler `POST /v1/containers` itself uses — with the rendered body. No new container-creation logic at all; a recipe apply *is* a create, just body-sourced from a stored template instead of an inline request. Always synchronous (containers create synchronously already; there is no async artifact-fetch fast path the way image recipes have, since there's no equivalent "whole container as one downloadable blob" concept).

**`pkg sync`** (`daemon/src/pkg.c`'s `pkg_sync_completed()`) extended a third time: walks `recipes/container/<name>/<version>/container.json`, publishing the highest version per name via `container_recipe_add()` — identical selection/always-overwrite semantics to the image-recipe walk ADR-0149 already added.

**CLI**: `kanxeoctl container recipe add|show|rm|ls`, `kanxeoctl container apply-recipe NAME [--secret=KEY=VALUE ...]` — mirrors `image recipe`/`image apply-recipe` exactly, added to the existing (previously `ls`-only) `container` noun-based command group.

## Verification

Full clean rebuild (`-Wall -Werror`), zero warnings. Manual end-to-end smoke test against a real local daemon confirmed the full pipeline before writing permanent coverage: add → apply with a secret containing a literal `"` character → the staged file's real content correctly shows the unescaped value, proving both substitution and JSON-round-trip-safety. New `test/test_container_recipe.c`: empty list; a name/content mismatch and non-JSON content both rejected (400); add + list + get (raw content shows the unsubstituted token); apply with the secret supplied (real container created, real file content correctly shows the substituted, correctly-escaped value); apply with no secret supplied (token left completely untouched, not blanked); apply on an unknown name (404); recipe rm + 404 after. Full regression sweep (container/pkg/image/network/backup-related tests) confirmed clean, including a second pass after the byte-level substitution scanner was added.

## Consequences

- Every container this session recreated by hand (`jumpbox1`, `dns-1`/`dns-2`, `ldap-1`/`ldap-2`, `syslog-1`/`syslog-2`) can now be captured as a real, git-tracked recipe — closing the exact "hand-retyped from memory every time" gap that motivated this ADR. Capturing those 7 as the first real recipes is tracked as direct follow-up work, not part of this ADR's own code change.
- The `{{SECRET:KEY}}` mechanism is generic, not LDAP-specific — any future recipe needing a credential in staged file content uses the identical convention, one substitution primitive for the whole platform rather than a per-recipe ad hoc one.
- A container recipe's content already being a real `POST /containers` body means no new schema was invented, no new thing to keep in sync with `create_container_from_body()`'s own accepted fields as they evolve — the recipe format inherits every future container-create capability automatically.
- Recipe content is stored and applied byte-for-byte as authored; the daemon never edits it (no analogue to `ldap_write_config_file()`'s managed-tail rewriting) — a recipe author is fully responsible for its own correctness, discovered only at apply time.
