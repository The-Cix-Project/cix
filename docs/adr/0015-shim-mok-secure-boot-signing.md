# 0015 — shim + MOK enrollment for Secure Boot on the installed system, installer media stays unsigned

## Status

Accepted

## Context

The user reported the real, shipped installer ISO (`v1.1.0`, Phase 11 part 4) failed to boot on their own VM: UEFI's `BdsDxe` boot manager rejected it with `Access Denied`. Reproduced exactly, locally, by booting the actual `build/cix-install.iso` under Secure-Boot-enabled OVMF (`OVMF_CODE_4M.ms.fd` + `OVMF_VARS_4M.ms.fd`, `-global driver=cfi.pflash01,property=secure,value=on`): `grub-mkrescue`'s own self-built `BOOTX64.EFI` is unsigned, and Secure Boot firmware refuses to execute an unsigned/untrusted binary. This is not a one-off environment quirk — Secure Boot ships on by default on most Windows-certified hardware, and on Proxmox VMs using the `.ms` OVMF firmware variant (a common default), which the user's VM evidently was.

Two paths exist for making a boot chain trusted under Secure Boot: get every binary signed by a CA the firmware already trusts (Microsoft's UEFI CA, in practice), or enroll a project-owned key into the firmware's own additional trust store — the **MOK (Machine Owner Key) list**, checked by Microsoft's own pre-signed `shim` loader. Getting a from-scratch, mainline-source kernel signed by Microsoft's CA is not realistic for this project (no CA relationship, no code-signing program membership). MOK enrollment is the standard, well-precedented mechanism for exactly this situation — the same one VirtualBox, ZFS, and NVIDIA's out-of-tree kernel modules use.

**The chain-loading mechanics, confirmed empirically this session** (not assumed from documentation):
- Debian ships `shim` (`/usr/lib/shim/shimx64.efi.signed`, Microsoft-signed) and `MokManager` (`/usr/lib/shim/mmx64.efi.signed`, Debian-signed) as complete, pre-built binaries. Both load under Secure Boot with **zero enrollment** — confirmed by booting `shimx64.efi.signed` directly under `.ms.fd` OVMF and observing no `Access Denied`.
- `shim` has a **hardcoded second-stage lookup filename**: `\\grubx64.efi`, in its own directory — confirmed via `strings` on the real binary (`\\grubx64.efi`, `\mmx64.efi`, `\fbx64.efi` all appear as literal wide strings). This is purely a filename convention; `shim` validates by signature, not by inspecting what the file actually is. This project's own bootloader for the *installed* system, `systemd-boot`, is therefore staged under that name (`cix-grubx64.efi`) when chain-loaded through `shim` — a deliberately non-obvious rename, commented at both places it's staged/consumed (`image/src/mkinstalleriso.c`, `image/src/cix-install.c`).
- Once `shim` is trusted, it also validates whatever it subsequently loads — confirmed by reproducing a *second*, different failure (`bad shim signature`) when a signed `shim`+`grub` chain tried to load this project's own **unsigned** kernel. Secure Boot requires a signed kernel, not just a signed bootloader.

**The bootstrap problem this creates, and why it shapes the design:** enrolling a brand-new key into the MOK list is itself gated by Secure Boot — a not-yet-trusted key can't validate the code that would enroll it (classic chicken/egg). There is no way to make a *brand-new, self-signed kernel* boot under Secure Boot on a machine that has never trusted this project's key before, without one of: (a) a CA relationship (not available), or (b) one unavoidable, one-time step where either Secure Boot is off, or an already-trusted piece of pre-boot code (not our kernel) performs the enrollment.

`mmx64.efi` (MokManager) *is* that already-trusted piece of pre-boot code — Debian-signed, needs no enrollment of its own, and is `shim`'s automatic destination whenever a pending MOK enrollment request exists (staged via `mokutil --import`, which is a plain EFI-variable write, not itself gated by Secure Boot state).

## Decision

The **installer media's own boot stays exactly as it was** (`grub-mkrescue`, unsigned, Secure Boot must be off for that one boot) — this is not a regression, it's the standard, unavoidable bootstrap step every non-Microsoft-signed OS with a from-scratch kernel has, and it only has to happen once per machine, not once per boot.

What's new is entirely in what `cix-install` writes onto the **target disk's ESP**, and one new install-time step:

1. A single, project-owned Cix signing key (`image/keys/cix-signing.{key,crt,cer}`, generated once, persisted deliberately — see `README.md`'s generation recipe) signs `systemd-boot` and the kernel via `sbsign` at ISO-build time (`image/src/mkinstalleriso.c`).
2. The target ESP's `EFI/BOOT/` gets the full chain: `BOOTX64.EFI` = Microsoft-signed `shim`, `grubx64.efi` = Cix-signed `systemd-boot`, `mmx64.efi` = Debian-signed `MokManager`.
3. `cix-install`'s new `enroll_signing_key()` mounts `efivarfs` and runs `mokutil --import` against the Cix public cert, prompting once for a password — staging a pending enrollment request in the firmware's own persistent NVRAM. This runs during the (unsigned, Secure-Boot-off) installer boot, so it isn't gated by the chicken/egg problem at all.
4. At the **installed system's very next boot** (which can already have Secure Boot on), `shim` loads (Microsoft-signed, always trusted), sees the pending request, and auto-invokes `MokManager` — which prompts once more, with the same password, to confirm. After that single confirmation, the key is in the persistent MOK list and every subsequent boot on that machine validates cleanly with zero further exceptions.

One key, no rotation/revocation story built yet — if the key is ever compromised or needs replacing, every already-enrolled machine needs a fresh manual MOK enrollment; not designed for here, and not needed until this project actually ships more than one signing key's worth of history.

## Consequences

- Operators see exactly one Secure-Boot-related interactive step, ever, per machine: confirm the MOK enrollment at the newly-installed system's first reboot (a standard blue-screen `MokManager` UI, not anything this project built). Every install/boot after that is exception-free.
- The installer ISO itself remains permanently unable to boot with Secure Boot on — a documented, permanent boundary (`README.md`), not a partial fix. A future decision to also sign the installer's own boot chain would hit the exact same bootstrap problem this ADR describes and would need its own new answer (e.g. a CA relationship), not an extension of this mechanism.
- `image/src/cix-install.c` now depends on `mokutil` and `efivarfs` (`CONFIG_EFIVAR_FS`, added to `image/kernel/qemu-part1.config`) being present in the installer's own boot environment — a real, new runtime dependency, staged the same way `cfdisk`/`sfdisk`/`mkfs.*` already are.
- `test/test_disk_image.c`'s `qemu_boot_capture()` gained a `secure_boot` option (switches OVMF firmware variant, enables the pflash `secure` property) and scripted, event-driven stdin input (`struct qemu_scripted_input`) to drive both `mokutil`'s password prompt and `MokManager`'s own confirmation screen without guessing at boot timing — a reusable capability for any future test that needs to script an interactive pre-boot UI, not just this one.
- The `v1.1.0`-tagged ISO shipped with the defect this ADR fixes; raised with the user as a real, user-facing regression worth a follow-up tag, not silently absorbed into the next release.
- **A real operator-facing landmine, found live during the user's own install, confirmed empirically (booted it twice to check): selecting "Continue boot" at `MokManager`'s main menu doesn't defer the pending enrollment request to a later boot — it permanently discards it.** `MokManager`'s design is apparently one-shot: whatever choice is made at that menu (even the "do nothing special" option) consumes the pending `MokNew` request; there is no code of ours involved, this is `shim`/`MokManager`'s own firmware behavior. Recovery without a full reinstall exists (hash-enrolling `\EFI\BOOT\grubx64.efi` and `\cix-bzImage` individually via the same menu's "Enroll hash from disk," confirmed working) but is strictly weaker than the cert-based path — it trusts those exact file hashes, not the signing key, so it doesn't survive a kernel rebuild. `README.md`'s Secure Boot section now warns about this explicitly and documents the recovery. Not something this project can fix in its own code; worth knowing if a future session revisits this flow.
