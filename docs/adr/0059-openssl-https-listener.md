# 0059 — OpenSSL-backed HTTPS listener, reusing the PKI host cert, via a small TLS side-table

## Status

Accepted

## Context

ADR-0058's `daemon_config` resource was deliberately shipped without `http_enabled`/`https_enabled`/`https_port` — turning either on would have been exactly the "persisted but doesn't really work yet" shape the Immutable Maxims' No-Stop-Gaps rule forbids, since no HTTPS listener existed at all. This ADR is that follow-on: a real, working second listener.

Two design questions needed real answers, not assumptions:

**Which TLS library.** OpenSSL is already load-bearing in this system via the PKI subsystem (`pki.c` shells out to the `openssl` binary as a subprocess for CA/cert operations) — introducing a second crypto library for the HTTPS listener itself would be a real, unjustified violation of One Source of Truth. Linking `libssl`/`libcrypto` directly (rather than continuing to shell out) was confirmed empirically to work cleanly under TCC: a real `SSL_CTX`, a real non-blocking handshake, no ABI incompatibility found. (An early debugging session initially looked like a TCC/OpenSSL interop problem — raw, undecrypted TLS wire bytes appearing where HTTP plaintext was expected — but traced to a bug in this project's own new code, not OpenSSL or TCC; see Consequences.)

**How to retrofit non-blocking TLS into the existing reactor.** `kanxeod`'s core is a single-threaded `epoll` loop with roughly 100 request handler functions, every one of which only ever sees a raw `int fd` — never a richer connection type. Threading TLS-awareness through all of them to make a `struct conn*` (or equivalent) reachable everywhere would have been a large, high-risk refactor for a change whose actual low-level I/O surface is tiny: exactly two writers (`http_write_response()`, the WebSocket frame sender) and the read loop in `main.c` itself.

**Certificate source.** The already-issued PKI `"host"` leaf certificate (ADR-0050, keyed off `siteconfig_host_fqdn()`) is reused rather than inventing a second issuance path — One Source of Truth again, and it means enabling HTTPS needs no new operator action beyond having already bootstrapped a root CA.

## Decision

**`tlsconn.c`/`tlsconn.h`: a small, additive fd → `SSL*` side table** (`TLS_CONN_MAX` entries, linear scan), not a signature-threading refactor. `main.c` registers/unregisters an fd's `SSL*` exactly when it creates/tears down a TLS-wrapped connection; every plain-HTTP fd — the overwhelming majority — is simply absent from the table, and a lookup miss costs one small linear scan. `tls_write_all()`/`tls_read()` are the only two functions that need to know whether a given fd is TLS-wrapped at all; `http_write_response()` and the WebSocket frame sender each get exactly one call-site change (`kx_write_all()` → `tls_write_all()`), and the `main.c` read loop's `read()` becomes `tls_read()`. No other handler changes.

**A dedicated, second listener** (`CONN_LISTENER_TLS`, `g_https_listener_conn`), started/stopped/rebound independently of the plain-HTTP one via `start_https_listener()`/`stop_https_listener()`/`rebind_https_listener()` — the same live-rebind shape ADR-0058's HTTP listener already established (new socket bound and added to `epoll` before the old one is torn down). `create_tls_ctx()` builds a real `SSL_CTX` from the PKI host cert/key, refusing (not falling back to a broken listener) if PKI isn't bootstrapped yet.

**Non-blocking handshake driven from the existing `epoll` loop, not a blocking call.** `client_conn_advance_handshake()` drives one `SSL_accept()` step per event, widening the fd's epoll interest to `EPOLLIN|EPOLLOUT` on `SSL_ERROR_WANT_WRITE` and narrowing it back to `EPOLLIN`-only once `SSL_is_init_finished()`. After a completed read, `SSL_pending()` is explicitly re-checked and looped on in both `handle_client_event()` and `handle_console_ws_event()` — a well-known non-blocking-TLS gotcha: OpenSSL can buffer more decrypted application data internally than fit in one `SSL_read()` call (e.g. a single TCP segment carrying both the final handshake message and the start of application data), and since the kernel socket buffer is already empty at that point, level-triggered `epoll` will not re-fire on its own — a caller that reads once per event and waits for the next `epoll_wait()` would stall until the peer sent more data than it ever intended to for this round-trip.

**`daemon_config` gains `http_enabled`/`https_enabled`/`https_port`** now that both listeners really work — refusing (`DAEMON_CONFIG_ERR_WOULD_HAVE_NO_LISTENER`) to persist a state leaving both off, and refusing `https_enabled=1` (`DAEMON_CONFIG_ERR_HTTPS_NOT_AVAILABLE`) with no PKI cert to serve. A single request disabling HTTP while enabling HTTPS persists the HTTPS-enable first — `daemon_config_set_http_enabled(0)` itself refuses unless `https_enabled` is *already* true, so the ordering isn't optional.

## Consequences

- Two real bugs were found and fixed via live, empirical testing against a running daemon with real `curl`/`openssl s_client` (this project's own established discipline — confirm via a real failure, fix precisely, never guess):
  - `g_tls_conns[]` is a `static` array, zero-initialized by the C runtime like any other — meaning every slot's `.fd` started at `0`, not the intended `-1` "free" sentinel. `tls_register()`'s "find a free slot" scan (`if (fd == -1)`) never matched, so every TLS connection silently registered nothing; `tls_lookup()` always missed, and `tls_read()`/`tls_write_all()` silently fell back to plain `read()`/`kx_write_all()` — reading/writing raw, undecrypted TLS wire bytes. This is what initially looked like a TCC/OpenSSL ABI problem; it wasn't. Fixed by adding a real `tls_init()` that explicitly sets every slot's `.fd = -1`, called once early in `main()` — documented directly in `tlsconn.h`'s own doc comment as a standing warning against assuming BSS zero-init is a safe "unused" sentinel for anything other than `0`/`NULL`/`false`.
  - `rebind_https_listener()` was initially missing the no-op short-circuit its HTTP counterpart (`rebind_listener()`) already had. `SO_REUSEADDR` only helps across a TIME_WAIT teardown, not for two simultaneously-open sockets on the identical address:port — so any `PUT /system/daemon-config` touching an unrelated field (e.g. only `http_enabled`) still unconditionally re-bound HTTPS to its own already-bound address, failing with a real `EADDRINUSE`. Fixed with the identical no-op check `rebind_listener()` already used.
- Verified: full regression suite (24 daemon-linked test binaries) green; a real manual end-to-end HTTPS check (`curl`/`openssl s_client` against the PKI host cert, live HTTP/HTTPS independent toggling); the definitive `test_installer` QEMU run, including its own second independent reboot, confirming `daemon_config`/TLS-listener state persists correctly across a real reboot.
- `docs/api/openapi.yaml`/`docs/api/README.md` gain `http_enabled`/`https_enabled`/`https_port` on the `DaemonConfig` schema/resource introduced by ADR-0058.
- CLI/web dashboard parity for `daemon_config` remains an open, tracked gap — same note as ADR-0058's Consequences, not repeated here.
