# 0019 — the shared "base" image's C runtime is seeded at install time, not by pkg or at boot

## Status

Accepted

## Context

With real `.recipe` files for `bash`/`iproute2`/`bird` (this session) and `BASE_DIR` persistence genuinely working (ADR-0018), the natural next check was whether any of it was actually *usable*: create a container against the `base` image and run the freshly-installed `bash`. It failed outright — `child: execve: No such file or directory` — because the container's own private `/dev`-less, near-empty rootfs had no `/lib64/ld-linux-x86-64.so.2`, the ELF interpreter every dynamically-linked binary's `PT_INTERP` segment names. `pkg_build_completed()` (`daemon/src/pkg.c`) only ever merges a package's own `DESTDIR` output into `base/rootfs` — real distro package managers work the same way, treating libc as a *separate*, already-present dependency, never bundled per-package. Nothing in this project currently provides that separate dependency at all. This isn't specific to bash, or to these three recipes — it would block *any* dynamically-linked package from ever running.

Confirmed by direct `ldd`: a real, non-trivial dynamically-linked program needs three files beyond the binary itself — `ld-linux-x86-64.so.2`, `libc.so.6`, and (for anything using readline, like bash) `libtinfo.so.6`.

Three genuinely different places this could be seeded were weighed with the user directly: a one-time REST bootstrap action mirroring `pkg bootstrap` (runtime, on an already-installed system); baking it into the OS's own boot image; or leaving it as a documented gap. The user chose baking it into the boot-image-build tooling. Investigating the actual code changed the concrete shape of that from the literal first guess ("mkbootroot.c"): `mkbootroot.c` builds the OS's own control-plane squashfs (root A/B) — a wholly separate artifact from the *containers partition*, where `images/base/rootfs` actually lives (a partition `cix-install` formats but, until ADR-0018, never wrote content onto). `mkbootroot.c` itself needed no changes. `mkinstalleriso.c` already had exactly the right, proven pattern: a hardcoded array of host library paths (`g_lib_closure[]`) staged via `test_image_fixture_add_lib()`, used today to give the *installer's own* execution environment (fdisk, mokutil, etc.) the shared libraries it needs — extending that file with three more entries, into a new `/payload/cix-runtime/` subtree, was the natural, minimal-new-code fit.

## Decision

`image/src/mkinstalleriso.c` stages `ld-linux-x86-64.so.2` and `libc.so.6` into `/payload/cix-runtime/` at their fixed, interpreter-expected/glibc-default-search-path destinations — the exact same source-path-to-fixed-destination convention `test_image_fixture_build()` already uses for `cixd`'s own two — plus `libtinfo.so.6` via `test_image_fixture_add_lib()`'s host-path-preserving copy, already used for this installer's own closure. `image/src/cix-install.c` gains a new `CIX_RUNTIME_DIR_SRC` payload-path constant (matching `SHIM_EFI_SRC`/`ROOT_SQUASHFS_SRC`'s own fixed-payload-path style) and, inside its existing containers-partition mount/write/unmount block (previously format-check only), creates `images/base/rootfs/{lib64,lib/x86_64-linux-gnu}` and copies the three files in — using the file's own existing `copy_file()` helper, no new dependency, no new argv/flag on either tool.

## Consequences

- A package installed via `pkg install` can now actually run inside a container — verified two ways: `test/test_installer.c` extracts the real containers partition right after the installer's own first boot (before any `pkg install` and before session 4's independent reboot) and confirms all three files are present with real, correct byte sizes; separately, a throwaway `base` image manually seeded with the same three files was confirmed to let a real `bash -c` execve() and run successfully inside a real container (`daemon/src/pkg.c`/`src/container.c`'s own existing machinery, untouched).
- This is a fixed, minimal runtime (exactly what `bash` needs) — not a general dependency-resolution mechanism. A future package needing a library beyond this set is a real, known gap: nothing currently discovers or stages a package's own additional runtime dependencies (as opposed to build-time ones, which `pkg_depends` already covers via other *packages*). Extending `CIX_RUNTIME_DIR_SRC`'s own set the same way libtinfo.so.6 was added here is the straightforward path when that's needed for real, not attempted speculatively now.
- Consistent with ADR-0018: this now genuinely persists too, since it's written directly onto the real `cix-containers` partition at install time, not somewhere `boot_init()`'s tmpfs fallback (or, before that fix, its unconditional tmpfs) could ever have wiped.
- `mkbootroot.c` is unchanged — the OS's own control-plane image and the containers-partition-backed `base` container image remain two genuinely separate artifacts, each populated by the tool that actually owns writing to their respective destination (`mkbootroot`/root-A vs. `cix-install`/the containers partition).
