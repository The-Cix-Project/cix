# 0124 — pkg/ redesign Part 5: rolling containers + restart jitter

## Status

Accepted

## Context

Part 5 of the five-part `pkg/` redesign (task #739/#770; Part 1 ADR-0120 renamed recipes to `build.sh` and fixed a backup/restore bug, Part 2 ADR-0121 added a configurable recipe-sync repo, Part 3 ADR-0122 added a package-artifact cache and server, Part 4 ADR-0123 added image recipes and a whole-rootfs artifact fast path). ADR-0107 already gave rolling images an auto-rebuild trigger (`queue_rolling_rebuilds_for()`, run from the tail of every completed pkg job) — a rolling image's `current_version` keeps advancing on its own whenever one of its `rolling`-mode packages gets a new version installed. What ADR-0107 deliberately left open: nothing ever consumes that drift. A container created with `POST /v1/containers` pins a specific `image_version` at creation time (`create_container_from_body()`) and — until this part — that pin never moves again on its own, no matter how many times the underlying image rebuilds. An operator following a rolling image today has to notice the drift and manually re-`POST` the container to pick up the new pin.

Two real design questions, both surfaced by reading the existing container-create and reconciliation code rather than assumed, and both resolved with the user via `AskUserQuestion` before writing anything:

1. **Which running containers should auto-restart onto a newer rolling-image version?** Every container pinned to a rolling image, always, was rejected outright — a rolling image's own non-determinism (ADR-0107) means an unconditional auto-restart could silently change a container's running content at a time the operator never chose, for containers that may be mid-task or intentionally pinned to "whatever it happened to get at creation time." Confirmed with the user: **opt-in per container**, a new `follow_rolling` boolean set only by an explicit `"follow_rolling":true` on the original `POST /v1/containers` body — mirrors `restart_policy`/`depends_on`'s own "parsed once by the caller, cached in `struct container_def`" shape, and gives every existing container (which never set this field) exactly today's behavior, unchanged.
2. **How should simultaneous restarts be spread out?** A rolling image with N containers following it would otherwise all restart in the same instant the moment `current_version` changes — a real thundering-herd risk for anything the containers themselves front (a shared backend, a shared network path). Confirmed with the user: a new configurable jitter window (`GET`/`PUT /v1/system/rolling-config`, `jitter_window_seconds`, default 60, range 0-3600, mirrors Part 3's own `pkg-artifact-config`/`pkg-cache-config` resource shape exactly) — each container that needs restarting on a given reconciliation pass gets an independent uniformly-random delay in `[0, jitter_window_seconds]` before its own restart fires, so a rebuild affecting many containers spreads their restarts out instead of firing them all at once. `0` means no jitter — restart immediately.

`follow_rolling` is meaningless without a persisted definition to replay it against, so it is silently ignored (never reaches `containerdef_add()` at all) when the create request's `restart_policy` is `"no"` — the same "ignored, not an error" precedent `restart_delay_seconds` already established for that exact combination (no persisted def exists to patch or replay for a container that was never meant to be automatically brought back up).

## Decision

**Reconciliation hook**: `apply_rolling_container_restarts()` (`daemon/src/main.c`) runs from the tail of `try_start_queued_pkg_rebuild()` — the same "runs after every pkg job completion" trigger point ADR-0107's own `queue_rolling_rebuilds_for()` already uses. Deliberately generic over *why* an image's `current_version` moved (a rolling auto-rebuild, a manual `pkg install`, or Part 4's own artifact-tier apply) rather than threading a bespoke signal from `pkg.c` into `main.c` — any of those three completions can legitimately advance a rolling image's version, and all three should be reconciled the same way. For every currently-defined container (enumerated via `containerdef_resolve_order()`, reused purely as a name-enumerator here — its real purpose, dependency-ordered topological sort, is irrelevant to this loop, but writing a second enumeration function purely to avoid reusing an oddly-named one would have been a One Source of Truth violation) with `follow_rolling` set: parse its persisted body for `image`/`image_version`, compare against `image_current_version()`, and if they differ, patch the pin and (if the container is currently running) arm a jittered restart.

**Body-patch-then-jittered-timer mechanism**: `containerdef_patch_image_version()` (`daemon/src/containerdef.c`) does a raw string find/replace of the already-spliced `"image_version":"..."` value inside the persisted create-request body — mirroring `handle_create()`'s own splice-time string-surgery posture rather than re-serializing the whole JSON tree. This runs *before* the restart timer is armed, so the eventual replay via `create_container_from_body(def->body, ...)` automatically picks up the new pin with no separate "apply the new version" step.

**New timer idiom**: `CONN_ROLLING_RESTART_TIMER` / `arm_rolling_restart_timer()` / `handle_rolling_restart_timer_event()` — a deliberately new, parallel instance of the existing `CONN_RESTART_TIMER` idiom, not a reuse. `CONN_RESTART_TIMER`'s handler assumes the container has already exited (crash respawn); the rolling case must actively tear down a still-live container first — deregister its `reactor_conn`, `registry_remove()` it, explicitly *without* `containerdef_set_stopped()` since this is a version-following restart, not an operator-initiated stop — before replaying `create_container_from_body()` against the freshly-patched body.

**Jitter**: `rolling_jitter_seconds(window)` mirrors `ldap_generate_secret()`'s own `/dev/urandom` read idiom exactly (4 bytes → `uint32_t` → modulo `window+1`) — the only other randomness-for-any-purpose precedent in this codebase, reused rather than inventing a second one.

**The timerfd zero-value bug** (found by the new test, described in Verification below): `timerfd_settime(2)`'s documented semantics are that an all-zero `it_value` **disarms** the timer, not "fire immediately." `arm_restart_timer()`'s own `restart_delay_seconds` never hits this because it's always validated to 1-300 by its own caller — but `jitter_window_seconds=0` is an intentional, user-facing "no jitter, restart now" setting, and `rolling_jitter_seconds(0)` correctly returns `0`. Fixed in `arm_rolling_restart_timer()` with `if (delay_seconds <= 0) its.it_value.tv_nsec = 1;` — a 1-nanosecond floor that is indistinguishable from "immediately" to any caller but keeps `it_value` non-zero so the kernel actually arms the timer.

**Config resource**: `containerdef_rolling_config_init()`/`containerdef_jitter_window_get()`/`containerdef_jitter_window_set()` (`daemon/src/containerdef.c`) persist `jitter_window_seconds` to `<data-dir>/rolling_config.json`, mirroring `pkg_cache_init()`'s own shape exactly. `GET`/`PUT /v1/system/rolling-config` (`daemon/src/main.c`) mirror `handle_pkg_cache_config_get/put()` exactly, including the same validation-before-persist discipline.

## Verification

Full clean rebuild (`-Wall -Werror`), zero warnings. New `test/test_rolling_restart.c`: stages a real dynamically-linked test binary (`build/daemon_child`, already relies on `pkg_seed_image_baseline()`'s existing shared-library staging) as a synthetic package's install payload — avoids needing a working compiler inside the test's own build sandbox for a test that isn't about compilation. Bootstraps the shared toolchain sandbox, marks the package `rolling` in the image manifest, creates two containers pinned to the same image version — one with `follow_rolling:true`, one without — records both containers' initial PID and pinned version, then publishes a new package version purely through the real `POST /v1/pkg/recipes` API (never pre-written to disk — the daemon correctly 409s a version whose file already exists, so a test recipe meant to be published via the API has to be built entirely in memory). Polls for the image's `current_version` to advance and confirms: the `follow_rolling` container's PID changes and its own `image_version` field updates to match; the plain container's PID and pin are completely untouched. Also exercises `GET`/`PUT /v1/system/rolling-config`, including range rejection outside 0-3600. This test is what caught the timerfd zero-value bug above — every step through `arm_rolling_restart_timer(name, 0)` traced clean, but the timer never fired, which is what led to re-reading `timerfd_settime(2)`'s actual documented semantics rather than assuming a logic bug elsewhere. Full regression sweep (all daemon-linked and standalone tests) confirms zero regressions from this part's changes.

## Consequences

- A running container can now opt in to automatically tracking a rolling image's own drift, closing the gap ADR-0107 deliberately left open — an operator no longer has to notice a rolling rebuild happened and manually re-create the container to pick it up.
- The opt-in default (unset `follow_rolling`) means this is purely additive: every container defined before this part, and every container that never sets the flag, behaves exactly as before.
- The jitter window is a single daemon-wide knob, not per-container — matches the "spread out a herd" problem this solves (many containers on the same rolling image), and mirrors the daemon-wide granularity Part 3's own cache/artifact config already established for comparable settings. A future per-container override remains possible without disrupting this default if a real need for it surfaces.
- `follow_rolling` containers can lose local runtime state (anything not persisted outside the container's own overlay upper dir) on every rolling-image drift they follow — this is the same tradeoff any "auto-update onto latest" mechanism accepts, made explicit and opt-in rather than silently forced onto every container of a rolling image.
- Closes out the five-part `pkg/` redesign (task #739): Part 1 fixed the on-disk recipe format and a real backup/restore bug, Part 2 made the recipe repo configurable and syncable, Part 3 added package-level artifact caching, Part 4 extended that to whole images, and this part makes running containers able to actually consume a rolling image's own version drift automatically. Task #771 (an extensive package-management test pass across sandbox and 192.168.15.95) is the last remaining item.
