# 0033 — platform state backup/restore, not workload data, never PKI

## Status

Accepted

## Context

Cix had zero backup, export, or restore mechanism of any kind. Raised directly by the user while preparing a one-shot, no-rollback migration of a real production home lab (six router containers, an LLM with GPU passthrough, git hosting, DNS infrastructure, metrics) from Proxmox — for an irreversible cutover, "no backup story" is a structural risk, not a missing nicety. Confirmed directly with the user: this has to follow the exact same API-first methodology every other subsystem (DNS, PKI, pkg) already does — the daemon owns the real mechanism and exposes it via REST; a container, `cixctl`, or a host cron job is a pure client that triggers it, never a second privileged path reaching into the daemon's own state some other way.

## Decision

**Scope is platform *configuration* state — what containers/networks/DNS records/packages should exist — not workload data and not PKI, confirmed explicitly with the user before writing any code.** Three separate, real questions came up while scoping this, each resolved before implementation:

**Workload data (a container's own persistent data — repos, zone files, a metrics database) is each container's own concern, not this endpoint's.** Cix has no volume-sharing or exec-into-a-running-container capability today, and building either just to generically reach into arbitrary containers' own data would be a much larger, differently-scoped feature than "back up the platform" — most real services already have their own native export/dump tooling anyway, and duplicating that inside the platform would be exactly the kind of parallel implementation this project's own principles reject.

**Image rootfs content is deliberately not captured.** Every package is compiled from source (the project's own charter), so an image's actual content is reproducible by re-running `pkg install` for whatever `pkg_installed` already records — capturing the "shopping list" (what's installed, where) is both far smaller and more honest than trying to snapshot built bytes that are already reproducible from data this bundle *does* include. A full byte-for-byte image restore is a real, separate, out-of-band step (re-run the installs), not something this mechanism automates — stated plainly in both the OpenAPI spec and `docs/api/README.md`, not silently glossed over.

**PKI is not referenced by this endpoint at all, confirmed explicitly with the user rather than assumed.** The CA private key (and every issued leaf certificate's own key) has never been returned over the API anywhere in this system, by existing, deliberate design (`docs/api/README.md`'s own PKI section: "the CA private key is never returned over the API, in any endpoint, ever"). Three options were considered directly with the user: exclude PKI entirely from this mechanism (chosen), add an explicit opt-in flag that deliberately breaks that rule when asked, or accept re-bootstrapping the CA on every restore. Excluding it entirely keeps the existing "never leaves via API" guarantee absolute, with zero exceptions carved out for this feature — PKI backup is a genuinely separate, host-level concern (`/var/lib/cix/pki/`, backed up directly, outside the API), not partially folded in here.

> **Superseded in part by [ADR-0281](0281-the-ca-leaves-the-box-encrypted-or-it-is-lost.md) (#415).** The decision to keep the PKI out of *this* bundle stands. The alternative it rested on does not: `/var/lib/cix/pki/` became `/config/state/pki` (#250), and the host is shell-less and API-only, so "backed up directly, outside the API" names an operation an operator cannot perform here. A dedicated `POST /v1/pki/export` now carries the store, passphrase-encrypted — recognisably the second of the three options weighed above, reconsidered because the first one's premise was removed rather than because the reasoning was wrong. Note also that the parenthetical above is inaccurate on one point: an individual *leaf's* private key has always been returned, exactly once, by the call that issues it; only the CA's and the intermediate's were ever withheld.

**The bundle embeds each state file's raw content as an escaped JSON string, not nested raw JSON.** This reuses `ConfigFile.content`'s own existing "raw content as a JSON string" shape (Phase 15, ADR-0030) rather than inventing a second raw-embedding convention — every field is already valid JSON text on disk, so embedding it as a string and letting the outer JSON writer's existing escaping handle it is both simpler and one less code path to get subtly wrong than trying to splice pre-formatted JSON directly into a larger structure.

**`container_defs` alone is already a complete reconstruction source, confirmed against ADR-0025 rather than assumed.** Since a container's entire raw create request is persisted verbatim and replayed as-is (including every field Phase 12/15 later added — `devices`, `interfaces`, `files`, `sysctls`), this one file needs no separate per-feature export logic of its own; whatever `container_defs.json` already contains is definitionally everything needed to recreate a persisted container exactly.

**Restore needs no new daemon-initialization code at all — it reuses the exact boot-time replay path that already exists and is already tested.** `network_init()`/`dns_init()`/`pkg_init()`/`containerdef_init()` all run once at daemon startup; restored files only take effect on the *next* boot, through `containerdef_autostart_all()` and its siblings, unchanged. `POST /system/restore`'s entire job is "the files are now correct" — it deliberately does not reboot or hot-reload, the same "write, don't reboot, caller decides when to cut over" shape `/system/update` already established (ADR-0031). This is a smaller feature than a naive "build a restore mechanism" framing would suggest, precisely because it declines to duplicate logic that already exists.

**Every field is validated before any file is written**, mirroring `do_system_update()`'s "validate everything, then write" discipline exactly (each JSON-file field must itself parse as valid JSON; `pkg_recipes` must be an object of string values) — a malformed field must never leave the others half-applied, the same reasoning that already governs a combined root+kernel `/system/update` call.

## Consequences

- Verified end-to-end against a live, twice-restarted daemon (`test/test_system_backup.c`): a real persisted container, network, and DNS record created; `GET /system/backup` confirmed to embed matching content; the container then deleted entirely (live instance and persisted definition both gone); `POST /system/restore` with only the earlier-captured `container_defs` field; a real daemon restart afterward confirmed the deleted container came back — the actual proof that restore's on-disk write plus the *existing*, untouched boot-time replay path genuinely reconstructs state, not just that a write syscall succeeded. A malformed field confirmed rejected `400` with the real on-disk file provably byte-for-byte untouched. Restore confirmed to *not* hot-reload (the restored container stays absent from the live registry until an actual restart).
- A real, if minor, operational note surfaced while designing this (not itself a code change): a container-based backup trigger needs genuine network reachability to `cixd`'s own bind address (loopback by default; a real installed system's own static management IP otherwise) — through the operator's own routing, the same as any other cross-network traffic in their topology, or a host-level cron job as an equally valid, simpler alternative. This ADR does not change the daemon's bind/reachability posture; doing so would be a separate, real security decision, not something to bundle into a backup feature.
- A real, worth-remembering test-hygiene lesson from writing this feature's own test: a network created via `POST /v1/networks` creates a genuine, persistent kernel bridge interface — deleting only the JSON state file (`rm -rf networks.json`) between test runs leaves that real interface behind, causing the *next* run's `POST` of the same network name to fail. The correct, already-established convention in this codebase (`test/test_networks.c` has no `reset_state()` at all) is real API-driven `DELETE` for cleanup, not filesystem-level deletion of the state file alone — this test was fixed to follow that same convention rather than inventing a second cleanup idiom.
- No scheduled/periodic backup trigger is built — matching `/system/update`'s and `/pkg/update-all`'s own already-accepted "on-demand, operator- or cron-invoked" posture (Phase 16), not a gap specific to this feature.
