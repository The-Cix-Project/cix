# 0169 — Operator-chosen swap disk placement, reconciling `diskrole`'s `swap` role with ADR-0069's swap-file mechanism

## Status

Accepted

## Context

Issue #28, raised directly by the user: "today swap is presumably placed automatically (no operator control over which physical disk/partition backs it)." Confirmed by reading the code rather than assumed: ADR-0069's own real, working, on-demand host swap file (`daemon/src/swap.c`, `POST /v1/system/swap`) always writes to a single fixed path (`g_base_dir/swap/swapfile`) computed once at daemon startup — there was no way to place it on a different, operator-chosen disk.

`diskrole.h`'s own top comment had already anticipated and deliberately deferred exactly this: `"swap" is deliberately NOT one of the roles: ... a disk-level "swap" role would either duplicate that mechanism or need to be reconciled with it, a real design question with no answer yet, so it's left out rather than added as a role nothing can act on (No Stop-Gaps)`. This ADR is that reconciliation, now that the question has a real answer.

Directly related to issue #9 (partition-level disk management, large, deliberately not started) — a `swap` *partition type* depends on that landing first. This ADR covers only whole-disk placement, which can and does land independently, per issue #28's own scoping note.

## Decision

- **New `DISKROLE_SWAP` role** (`"swap"`), added to the existing closed role vocabulary (`container-storage`/`backup`/`state-storage`/`rebuildable-storage`/`log-storage`) — the same "daemon-wide singleton, multiple disks can carry it as eligible candidates but only one is ever active" shape `state-storage`/`rebuildable-storage`/`log-storage`/`backup` already have. Assigning the role itself has no side effect (matches every other role), same as today.
- **`STORAGE_KIND_SWAP`** added to `storageplacement.h` — reusing that module's existing pure "which disk is the active placement" pointer (already shared by `state`/`rebuildable`/`log`) rather than inventing a fourth parallel "which disk for X" mechanism (One Source of Truth). Deliberately **not** wired to `storagemigrate.c`'s live-migration machinery: unlike the three storage kinds, a swap file's own content is transient and discardable by definition — there is no existing data worth preserving across a placement change, so no migrate-job concept was added, and none is planned.
- **`POST /v1/system/swap` gains an optional `disk` field.** Given (and validated at that exact call — present, mounted, currently carrying the `swap` role, the same "operator names a disk, real validation happens at the point of real use" posture `backup-config`'s own disk field already established): `swap_repoint()` (a new function, matching this codebase's existing `*_repoint()` convention — `backupconfig_repoint()`, `logstore_repoint()`, etc.) retargets the file `swap_enable()`/`swap_disable()` act on to that disk's own mount path, and `storageplacement_set(STORAGE_KIND_SWAP, ...)` persists the choice. Omitted: repoints back to the default location and clears the placement — every call repoints, explicitly, rather than silently reusing whatever a previous call left in place.
- **A real ordering bug caught during implementation, not after**: an early draft called `swap_repoint()`/`storageplacement_set()` *before* checking whether swap was already enabled, meaning a call that was going to fail with `SWAP_ERR_ALREADY_ENABLED` anyway would still have corrupted `g_file_path` out from under the file `swapon(2)` was actually holding open. Fixed by adding `swap_is_enabled()` and checking it first, before either side effect — `swap_repoint()`'s own doc comment now states this precondition explicitly.
- **Boot-time reconciliation is deliberately soft-fail**, unlike `resolve_state_storage_placement()`'s own "refuse to start" posture for the other three: a swap file is not platform self-definition the way `STATE_DIR` is, and ADR-0069 already established swap's own startup reconciliation as best-effort ("never blocks startup if the file is somehow missing or stale"). The new `resolve_swap_placement()` mirrors that: if the configured disk is missing/unmounted/no-longer-role-carrying, it logs why and falls back to the default location for that boot, rather than refusing to start.
- **`is_active_storage_singleton_placement()`** (the existing 409 safety check guarding `DELETE /diskroles/{name}` and `POST /disks/{name}/format`) extended with the swap placement, exactly like the other four — pulling the role out from under, or reformatting, a disk currently backing active swap is refused, same protection every other singleton placement already has.

## Consequences

- `daemon/include/{diskrole,storageplacement,swap}.h`, `daemon/src/{diskrole,storageplacement,swap,main}.c` — the role/kind vocabulary, `swap_repoint()`/`swap_is_enabled()`, the REST handler's `disk` field parsing + validation + repoint-before-enable, boot-time `resolve_swap_placement()`, and the extended safety check. `cli/src/main.c` gains `swap enable --disk=NAME` and shows the configured disk in `swap`/`swap status` output even while disabled (previously showed nothing beyond "swap: disabled"). `docs/api/openapi.yaml`/`docs/api/README.md`/`docs/guides/cli-reference.md` updated together in the same change.
- Verified: full clean rebuild (`-Wall -Werror`, zero warnings). Regression sweep (`test_daemon`, `test_cli`, `test_storage_placement`, `test_backup_config`, `test_diskpart`, `test_disk_quota`) all pass unmodified. Live-verified the default (no-disk) path is byte-for-byte unchanged behavior (real `swapon(2)`/`swapoff(2)` round trip against a scratch daemon, `disk: null` correctly present) and both negative paths (a disk that doesn't exist; a disk that carries the role but isn't mounted) reject cleanly with a real `400`, without ever touching a real device. Role assignment/removal itself verified live too (non-destructive, per `diskrole_create()`'s own existing contract).
- **The full positive path (a real disk, actually `swapon()`'d) was deliberately not tested in the dev sandbox** — that sandbox's own visible block devices turned out to be the real, shared Proxmox host's own storage (confirmed directly with the user, who corrected an initial assumption that they were safe scratch disks), not isolated test disks; activating real swap on any of them without authorization would be an inappropriate, out-of-scope risk on shared infrastructure. The real positive-path verification happens on 192.168.15.95 (`sda`, a real 100GB QEMU virtual disk made for exactly this kind of test), tracked as the immediate next step, not skipped.
