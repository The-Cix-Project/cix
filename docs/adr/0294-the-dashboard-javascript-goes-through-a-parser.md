# 0294 — The dashboard JavaScript goes through a real parser

## Status

Accepted. Closes [#340](https://git.home.arpa/itdlabs/cix/issues/340), whose own option 1 this is. Extends the release gate to the one surface no compiler read, and records why the cheaper answer — a textual check in C — was rejected on evidence rather than on taste, so it is not re-proposed.

## Context

Every surface this project ships is read by a compiler before it reaches a
host. `cixd`, `cixctl`, `netplane`, the host tools, the installer, every test
and every recipe go through `tcc` with `-Wall -Werror`. `web/*.js` went
through nothing at all.

On 2026-09-08 that cost a live outage. A refactor removed one arm of an
`if`/`else` in `web/app.js` and left the `else` behind. The browser reported:

```
app.js:2967 Uncaught SyntaxError: Unexpected token 'else'
```

A file that does not parse runs **no** script at all, so the symptom was not
one broken feature — it was a blank dashboard on a deployed release. It was
found by the owner opening the page, which is the wrong way to find it.

`make web-syntax` was added at the time: `node --check` over `web/*.js`, in the
dev sandbox. That closed the sandbox half and nothing else. `SELFTESTS` runs
inside a build container on the box, and no JavaScript runtime existed there,
so the release build still shipped the dashboard unparsed.

## Decision

**A real JavaScript parser runs in `SELFTESTS`, linked into a test binary.**
`test/test_web_syntax.c` links `libquickjs.a` and asks it to compile each file
the dashboard serves with `JS_EVAL_TYPE_GLOBAL | JS_EVAL_FLAG_COMPILE_ONLY` —
parsed and turned into bytecode, none of it executed.

The files are what `web/index.html` actually loads (`api.js`, `vt.js`,
`app.js`) plus `index.html`'s own inline block, the pre-paint theme apply.
An absent file is a **failure**, not a skip: `web/api.js` is generated by
apigen and is a prerequisite of `build/cixd`, so by the time selftest runs it
exists, and a "note" there would be a pass that checked half the surface.

`quickjs` is a Cix package (`recipes/package/quickjs/2026-06-04-3`), built on
a Cix host with Cix's gcc, declared in the cix recipe's `pkg_build_depends`.
Library and header only; no `qjs`/`qjsc` binaries.

## Alternatives considered

**A textual check in C — rejected on evidence, and this is the load-bearing
rejection.** It is the cheap answer and it does not work for this class of
bug. The broken shape was an `else` whose preceding token is `;`, which is
perfectly legal after a braceless `if`, and this codebase uses braceless `if`
freely. `web/app.js` also carries regex literals, which is exactly where
hand-rolled JavaScript tokenizers go wrong. A release gate with false
positives is worse than no gate, because the response to it is to disable it.

**node, which is already packaged — rejected on cost.**
`recipes/package/node` exists (24.21.0-1) and has never been built: it
compiles V8 from source against this host's ~7.7 GiB of RAM. Hours, for a
syntax check.

**duktape — rejected on measurement.** It has no `async`/`await`. `web/app.js`
has 258 `async` functions and 401 `await`s, so duktape would report syntax
errors on valid code — precisely the false positive this gate must not have.

**quickjs — chosen.** ~600 KB of C, builds in seconds, implements ES2020,
which is what the dashboard actually uses (measured: 258 async functions, 401
awaits, 436 arrow functions, 33 template literals).

## Consequences

**The release build cannot ship a dashboard that does not parse.** That is the
whole point and it is now structural rather than procedural.

**A third-party library joins the release build's test path.** It is a normal
Cix package with a normal recipe, built by Cix's own gcc under ADR-0226, and
it ships in no artifact — `test_web_syntax` is built inside the build
container and thrown away with it. `pkg_toolchain="gcc"` is recorded with its
reason (quickjs's Makefile adds `-fwrapv` unconditionally, which TCC does not
implement), and `test_toolchain_policy` counts it.

**Static-only, against this platform's usual rule.** zlib, libsodium, zstd and
libarchive all refuse a static-only outcome because the platform links
dynamically always — but their consumers are things the platform *runs*. This
library's only consumer is a test binary that never leaves the build
container, and ADR-0251's finalize policy keeps an archive with no shared
counterpart for exactly this case.

**Two seams between gcc-built library and tcc-built consumer had to be closed,
and both are recorded here because the second one is the dangerous shape.**

- `quickjs.o`, which is always pulled in, referenced `__udivti3` and
  `__udivmodti4` — libgcc's TImode division helpers, emitted for
  `unsigned __int128`. `nm` over every archive in `tcc-0.9.28rc-29`, the build
  cix-builder uses, finds no TImode symbol at all, so nothing `tcc` links
  provides them.
- The *same* `__SIZEOF_INT128__` selects `JS_LIMB_BITS` in the **public
  header**, which sets the width of a `JSValueUnion` member. Built with gcc the
  library chose 64. The tcc binary contains the string `__SIZEOF_INT128__`
  zero times, while `__x86_64__`, `__linux__`, `__SIZEOF_POINTER__` and
  `__SIZEOF_LONG__` each appear exactly once — so tcc does not predefine it and
  the gate compiled that same header on the 32 arm: library and consumer
  disagreeing about a public type passed by value. Benign as it happens — the
  union also holds a `uint64_t`, a `double` and a `void *`, so `sizeof(JSValue)`
  is 16 either way, and only `__JS_NewShortBigInt`'s store width differs, which
  a parse-only consumer never calls — but it is the class of divergence that
  fails as wrong data rather than as an error.

**What was not observed, stated plainly: the link never failed on a TImode
symbol.** v2.57.191 died earlier, at `-ldl`, and never reached symbol
resolution; the helpers were removed before anything tried to resolve them. The
two measurements above say nothing tcc links could have provided them, which is
reasoning rather than a failure anyone saw. An earlier draft of this ADR, of
the recipe header and of the changelog all asserted the failure and even quoted
its error message. Note also that `__int128` itself appears in the tcc binary
three times, so "tcc has no `__int128`" — which those drafts also said — is not
established either; what is established is that it does not predefine the
macro and ships no TImode runtime.

`-U__SIZEOF_INT128__` closes both: gcc takes the arm tcc takes, so the header
means one thing on both sides and no helper is emitted. **Both sides are
gated.** The recipe checks the library's arm (`nm -u` shows no `__*ti[0-9]*`
symbol); `test_web_syntax.c` checks the consumer's with a
`_Static_assert(JS_LIMB_BITS == 32, ...)`, because the recipe's gate alone
would stay green if tcc ever grew `__SIZEOF_INT128__` while the ABI silently
diverged. The cost is 32-bit bigint limbs, in a library that
exists to parse and never runs a line.

**The general rule this yielded:** when a gcc-built archive is destined for a
tcc link, read its undefined symbols for anything outside libc *before*
building the consumer. One `nm` would have saved a build cycle here, and the
evidence was already in output that had been printed and skimmed past.
