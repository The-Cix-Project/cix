# 0052 — Server-side default DNS/PKI name qualification (revises ADR-0046)

## Status

Accepted

## Context

Direct follow-up in the same identity-focused conversation as ADR-0049/0050/0051: "since we are doing that, can we make the default DNS entries all postfix with site.domain_suffix? Can be over-ridden?"

ADR-0046 explicitly decided the opposite for the daemon side: *"no daemon-side code qualifies a name automatically -- that composition happens entirely client-side, in whatever UI chooses to offer it."* That decision was itself deliberate and reasoned (a retroactive-enforcement variant was considered and explicitly rejected there, to avoid breaking this project's own live demo topology's bare, unqualified names). This ADR does not reverse that reasoning -- retroactive *enforcement* (rejecting an unqualified name outright) is still not what's being built. What changes is narrower: a bare label with no dot at all, submitted to `POST /dns/records` or `POST /pki/certs`, now gets this site's own suffix appended *by default* -- still fully overridable by typing a dot, and still leaving every already-created bare, unqualified name (the demo topology's `cr-1`, `srv1`, `blah`, ...) completely untouched, since qualification only ever applies at creation time to a name with no dot in it.

**A deliberate departure from this project's own "supersede the whole ADR" convention (ADR-0000), stated explicitly rather than silently followed past its intent:** ADR-0046 is not marked `Superseded` here, because most of it remains exactly true -- the `instance_name`/`site_name`/`domain_suffix` subsystem, its shape, and its persistence are all unchanged. Marking the entire ADR superseded would misrepresent that only one specific claim within it (daemon-side qualification never happens) has changed. ADR-0046's own Status stays `Accepted`; this ADR is the record of the one line within it that's now different, and why.

## Decision

**New `siteconfig_qualify(label, buf, bufsize)`** (`daemon/src/siteconfig.c`/`.h`): if `label` contains no `.` **and `site_name` is non-empty**, composes `<label>.<site_name>.<domain_suffix>`; otherwise (a dotted label, or `site_name == ""`) returns `label` completely unchanged.

**Gated on `site_name` specifically, not on `domain_suffix` having any value at all -- found the hard way, not designed that way from the start.** The first version qualified whenever `domain_suffix` was non-empty, which is its default state (`"internal"`, ADR-0046) on every install from the moment it boots, configured or not. Run against this project's own test suite, that qualified bare names from the very first request, with zero operator action -- and broke tests immediately (`test_dns.c`'s own "shadow" record, created bare and later looked up by that same literal name, 404'd because it had silently become `shadow.internal`). `site_name` defaults to `""` ("no site tier," already an established, documented state in ADR-0046) and only becomes non-empty once an operator genuinely opts in via `PUT /system/site` -- the correct, much narrower trigger: a fresh, unconfigured install behaves identically to before this ADR, and this project's own extensive existing use of bare names (the live demo topology, the whole test suite) needed zero changes to keep working. Real behavior change begins exactly when an operator asks for one.

Called from exactly two places, both at the point a `name` is first accepted, before the value is used for anything else: `handle_dns_record_create()`'s `name` (`daemon/src/main.c`), and `handle_pki_cert_create()`'s `name` (both the CN and, when the caller doesn't supply an explicit `sans` array, the default SAN derived from it). **Not** applied to an explicitly-supplied `sans[]` entry -- an operator who lists exact SANs by hand has already opted into precise control there, the same "a dot means don't touch it" philosophy extended one level further rather than contradicted.

## Consequences

- `POST /dns/records {"name":"db"}` creates literally `db` on any install that has never set `site_name` (the default) -- identical to pre-ADR-0052 behavior, zero regression. Only once `site_name` is set does the same call start creating `db.<site_name>.<domain_suffix>`. Every existing bare name already in the system is unaffected either way; this only changes what a *new*, bare-labeled creation resolves to, and only after an operator opts in.
- The same rule now exists in two independent implementations (client-side JS `suggestedFqdn()`, server-side C `siteconfig_qualify()`) -- a real, accepted duplication, not a violation of One Source of Truth for the *rule itself* (which is simple and stable: no dot, and a site is configured, means qualify), traded off against the alternative of the web dashboard round-tripping through the server just to preview a suggested name before the operator has even submitted the form. `suggestedFqdn()` was updated to the identical `site_name`-gated condition in the same pass (it previously suggested a qualified name whenever `domain_suffix` merely had its default value, which is always -- the same bug this ADR's own server-side gate exists to avoid, caught and fixed here before it shipped inconsistent with the server).
- `cixctl`/raw API callers now get server-side default qualification for the first time once a site is configured -- previously only the web dashboard's own suggestion behavior existed, so a bare name via the CLI or a direct `curl` was stored exactly as typed regardless of site config. This is the fix for that inconsistency, not a new inconsistency of its own.
