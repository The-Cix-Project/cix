# 0034 — console login via a cixd-supervised cixctl, not a general shell

## Status

Accepted

## Context

Phase 18 gave the installed system a video console that displays text and gave `cixctl` an interactive REPL, but neither closed the actual gap: `cixd` runs as PID 1 with no getty, no login, and no shell of any kind on any console, and `cixctl` itself wasn't even staged into the installed root image. Booting the Phase 18 ISO on real Proxmox hardware surfaced this directly — the console showed text, but there was nothing to type a command into. Separately, the video console had display output but no keyboard input driver at all (a second, independent gap, closed by the kernel-config half of this same phase).

## Decision

**`cixd` (PID 1) directly `execve()`s `cixctl` on each console once boot is healthy, rather than spawning a general-purpose login/shell.** Cix has no general-purpose shell story at all — it's an appliance OS built around a single REST API surface, not a distro with a userland of standalone Unix tools. A getty+login+bash chain would be the first general-purpose shell this platform has ever needed, pulling in a real dependency (`bash`, PAM or `/etc/passwd`-style auth, `login(1)`) to solve a problem `cixctl`'s own existing interactive shell (Phase 18) already solves completely. Spawning `cixctl` directly keeps the console experience identical to running it remotely with `--host=`, and keeps the API-First Mandate intact: this is still a pure REST client talking to `cixd` over real HTTP (via `g_bind_addr`/`g_port`), just running on the same host it's talking to.

**No authentication gate on the console shell.** This daemon has zero authentication anywhere today — confirmed directly (`grep` across `daemon/src/` for auth/token/password/login turns up nothing) — the REST API is already fully reachable, unauthenticated, to anything on the network it binds to. Physical console access is at least as privileged a position as that already is. Gating the console behind a login this platform has no other use for would be security theater around an already-open door, not a real boundary; if/when this platform ever grows real API authentication, the console path should almost certainly grow alongside it rather than staying deliberately exempt, but that's a separate, larger decision this phase doesn't take.

**pidfd + epoll for reaping, timerfd for respawn delay — both already-established patterns, not new primitives.** `register_pkg_fetch_pidfd()`/`handle_pkg_fetch_event()` already give this reactor a way to learn "a plain `fork()`'d child exited" via ordinary `EPOLLIN`, and `arm_restart_timer()`/`handle_restart_timer_event()` already give it a way to defer work without blocking the single-threaded loop. `spawn_console_shell()`/`register_console_shell_pidfd()`/`handle_console_shell_event()`/`arm_console_respawn_timer()`/`handle_console_respawn_timer_event()` mirror both shapes closely rather than introducing a `SIGCHLD` handler this reactor has never needed — one source of truth for "how this daemon learns a child process ended," the pkg-build container, the restart-timer, and the console shell all going through the same two mechanisms.

**Each console gets its own independently-supervised instance.** `/dev/tty0` (video) and `/dev/ttyS0` (serial) are spawned separately, each with its own pidfd/respawn lifecycle — either could be the one an operator is actually watching on a given day (Proxmox's console viewer vs. `qm terminal`), and there's no reason to couple their lifecycles together.

**`setsid()` + first `open()` of the tty, not an explicit `TIOCSCTTY`.** Standard Linux tty semantics: a session leader's first `open()` of a terminal device without `O_NOCTTY` makes it that session's controlling terminal. This is what keeps a Ctrl-C typed at the console from ever reaching `cixd` itself — it lands on the console shell's own, separate session/process group only, the same isolation a real login shell gets for free.

**Console shells respawn on exit, after a fixed 2-second delay, forever.** Matches a real getty's own "keep trying" posture for a device that might be temporarily unready, and the delay exists specifically to stop a broken respawn (missing binary, unopenable tty) from spinning the reactor in a tight fork loop — not because a slower respawn is otherwise desirable.

## Consequences

- Verified end-to-end, not just that it compiles: `test/test_console_shell.c` boots a real QEMU guest with the new kernel and a `cixctl`-staged root image, scripts a real interactive session over the serial console (exit the first spawned instance, wait for the *respawned* instance's own genuinely new prompt — proving the pidfd-reap + timerfd-respawn path actually fired, not just that the first spawn worked — then confirms that respawned instance answers a real `health` call). Passes cleanly.
- `image/src/mkbootroot.c`'s contract changed (`cixctl_bin` is now a required argv) — every call site (5 test files, `README.md`'s documented build recipe) updated in the same pass, the same precedent already set when `firmware_dir` was added.
- **Known, deliberately out-of-scope limitation:** `cixd`'s own stdout/stderr stay attached to `/dev/console`, which resolves to `ttyS0` specifically (the *last* `console=` argument on the kernel command line wins that role). This means the serial console shell can occasionally see a stray daemon diagnostic line interleaved with its own prompt/output; the video console (`tty0`) has no such mixing, since `cixd`'s own fd 0/1/2 were never attached there. Fixing this properly means deciding where daemon logs go generally (a log file? syslog? nothing needed yet?) — a separate, real architectural question this phase doesn't take on.
- **Verification boundary, stated plainly:** actual keyboard-driven interaction on the video console — a human physically typing at Proxmox's console viewer and seeing it register — is not automatable in this sandbox (`qemu_boot_capture()` runs with `-monitor none`/`-display none`, no QMP channel to synthesize a keypress even in principle, and building one would be disproportionate engineering for this ask). This is the user's own final check, the same boundary GPU passthrough, Secure Boot, and the framebuffer console's own output already have. What *is* verified: the kernel's PS/2 (`i8042`/`atkbd`) and USB HID (`usbcore`/`usbhid`) driver stacks both confirmed binding in a real captured boot log.
