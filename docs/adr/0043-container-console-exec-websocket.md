# 0043 — an interactive shell into a running container, over a hand-rolled WebSocket

## Status

Accepted

## Context

Raised directly by the user while reviewing the redesigned web dashboard's left resource tree: it now has a place to open a console into a running container, but no such capability exists anywhere in Kanxeo — the daemon has no exec/attach primitive at all. Two mechanisms this codebase already has are close but genuinely don't fit: `spawn_console_shell()` (`daemon/src/main.c`) gives a login shell on the *host's own physical tty* (`/dev/tty0`/`/dev/ttyS0`, `--init-mode` only, never network-reachable, and it runs `kanxeoctl` itself, not an arbitrary command inside a container's own namespaces); `image/src/dual_console.c`'s PTY relay (ADR-0042) is install-time, host-console-only code with nothing to do with a running container. Per the API-First Mandate, this had to be built as a real, new daemon capability, not bolted onto the dashboard directly.

Building it surfaced that the daemon's own HTTP layer (`daemon/src/http.c`) is fully synchronous, one-request-per-connection (`Connection: close` hardcoded, no header parsing beyond `Content-Length`), and the CLI's HTTP client (`client/src/httpclient.c`) is equally one-shot with no socket handoff — neither has any notion of a connection that outlives one request/response. A real interactive terminal needs full-duplex, low-latency, bidirectional I/O; a poll-for-output-plus-separate-POST-for-input scheme was considered and rejected outright as exactly the kind of hack the Immutable Maxims rule out for something this latency-sensitive (tab completion, Ctrl-C, a shell prompt redrawing).

## Decision

**Transport: a minimal, hand-rolled RFC 6455 WebSocket**, not a framework or a vendored library — matching this project's own from-scratch-everything posture (`CLAUDE.md`'s Technology Stack) and this being a small, well-specified protocol, not the extreme scope xterm.js-class terminal *emulation* would be (see below). New `daemon/src/websocket.c`/`.h`: `ws_compute_accept()` shells out to `/usr/bin/openssl` (`dgst -sha1 -binary` piped to `base64`) for the handshake's SHA-1+base64 — the same "never link a crypto library, always shell to the real `openssl` binary" convention `pki.c`'s `run_openssl()` already established, verified against RFC 6455's own worked example (`"dGhlIHNhbXBsZSBub25jZQ=="` → `"s3pPLMBiTxaQ9kYGzzhZRbK+xOo="`). `ws_write_frame()`/`ws_conn_try_parse()` implement only what this endpoint's own traffic shape actually needs: no fragmentation (every frame sent or accepted is a complete single-frame message — keystrokes and modest output chunks never need more), payloads capped at 64KiB. `daemon/src/http.c`'s `find_content_length()` was generalized into a reusable `http_find_header()` (One Source of Truth) rather than writing a second, parallel header scanner for `Upgrade`/`Connection`/`Sec-WebSocket-*`.

**Exec mechanism: `setns()` + double-fork, mirroring `nsenter`/`docker exec`.** New `daemon/src/exec.c`/`.h`: given a running container's already-tracked `registry_entry.handle.pid`, `exec_into_container()` opens `/proc/<pid>/ns/{mnt,uts,net,pid}` (no `ipc` — containers never isolate it, `src/container.c`) — critically, **all four namespace fds are opened up front, before any `setns()` call**, confirmed the hard way: the first `setns()` (mnt) moves the calling process into the container's own mount namespace immediately, so opening the *later* fds by path afterward resolves against the container's own (often proc-less) `/proc`, not the host's — hit exactly this failure (`ENOENT` opening `ns/uts` right after the `ns/mnt` `setns()` had already succeeded) empirically against a real running container while building this, before the fix. A PTY is allocated in the daemon's own namespace, also before any `setns()` — the slave fd is simply inherited across `fork()`, so the exec'd process never needs a working `devpts` inside the container's own mount namespace (containers get no `devpts` mount at all today, confirmed). Namespace order: mnt/uts/net take effect on the caller immediately; pid only affects *future* children, so it's joined last, right before the `fork()` that needs it. A double-fork (intermediate child joins the namespaces then forks the real grandchild, which `setsid()`s, `TIOCSCTTY`s the pty slave, `dup2`s it onto stdin/stdout/stderr, and `execve()`s) is required because `setns(CLONE_NEWPID)` never moves the calling process itself into the new pid namespace, only children created after — the grandchild's pid, read back from the intermediate over a pipe, is a normal outer-namespace-visible pid (pid namespaces are hierarchical, the same reasoning that already makes `container_handle.pid` itself usable this way), needing no `pidfd_open()` gymnastics to track.

**Default exec command is `/usr/bin/bash`, not `/bin/sh`** — confirmed empirically (not assumed) against a real running container that this project's own package system stages everything under `usr/bin/`, with no `/bin` directory at all. `/bin/sh` would fail on every real Kanxeo image today. `X-Kanxeo-Exec-Cmd` (a request header, reusing the same `http_find_header()` primitive rather than inventing query-string parsing, which exists nowhere in this codebase) overrides it — a single executable path, no argument splitting; give a command interactively once inside.

**New `GET /v1/containers/{name}/console` (`docs/api/openapi.yaml`)**, documented as an Upgrade-required GET (OpenAPI 3.0 has no first-class WebSocket typing). `daemon/src/main.c`'s `try_console_upgrade()` intercepts this route in `handle_client_event()` *before* the ordinary `dispatch()` path — on success it repurposes the accepted connection in place (`CONN_CLIENT` → new `CONN_CONSOLE_WS`) instead of the usual dispatch-then-close-the-fd cycle every other request takes, and registers the PTY master fd as a second, paired `CONN_CONSOLE_PTY` connection. This is the first time this daemon has needed two independently-epoll-registered fds to represent one logical session that can tear each other down — a real hazard follows: a single `epoll_wait()` batch can report *both* halves ready in the same call, so freeing the first one processed on the spot would leave the second event's own `struct conn *` dangling for the rest of that batch. Solved with a small deferred-free queue (`g_pending_free`, drained once per batch, after every event in it has been dispatched) rather than freeing synchronously inside `console_session_teardown()` — a new, general pattern this codebase didn't need before, since every prior long-lived `conn` kind (`CONN_CONTAINER`, `CONN_PKG_FETCH`) tracked exactly one fd, never a pair.

**Web dashboard terminal stays hand-rolled, not xterm.js** — confirmed with the user directly: full ANSI/VT100 fidelity (vim, top, less rendering correctly) would need real terminal emulation, genuinely substantial to build from scratch and exactly what a library like xterm.js exists to solve, but vendoring one is a deliberate, explicit exception to ADR-0010's "no framework, no dependency" constraint the user set for this same dashboard one phase earlier. The user chose to keep the dashboard's own terminal minimal (plain output plus a small ANSI subset) rather than open that exception — `kanxeoctl console` (a real terminal, raw `termios` mode, full fidelity) is the fully-capable path; the web terminal is deliberately reduced.

## Consequences

- Verified in stages, each against real infrastructure, not mocks: `exec_into_container()` alone against this sandbox's own real, already-running `cr-1` router container (real `setns`/double-fork/PTY, real shell output relayed back, confirmed by real shell arithmetic evaluating, not just PTY input echo); the full WebSocket handshake + relay against the same real daemon and container via a hand-rolled raw-socket client (both a quick manual smoke test and the permanent `test/test_console_exec.c`, 5 consecutive clean runs); confirmed no leaked exec'd process survives session teardown (`find /proc` for a lingering bare `/usr/bin/bash` after close, none found).
- `test/test_console_exec.c` speaks the WebSocket handshake and frame format by hand over a raw socket — `client/src/httpclient.c` has no streaming/Upgrade support to test against, the same "no existing primitive fits, write the minimum needed directly in the test" precedent `test/test_dual_console.c` already set for Phase 28. Reuses `test/dual_console_child.c` (already a trivial line-echo stand-in for Phase 28's own test) as the exec target, staged into a real container image, rather than writing a near-duplicate child binary.
- **No new authentication/authorization layer** — this endpoint is exactly as protected as every other existing mutating endpoint today (network reachability only). A more sensitive capability than most (an arbitrary interactive shell inside a container's namespaces), worth naming plainly even though it isn't a gap this endpoint itself introduces — every other destructive endpoint (`DELETE /containers/{name}`, `/system/reboot`) already carries the same trust boundary.
- **No terminal resize propagation** (`SIGWINCH`/`TIOCSWINSZ`) in v1 — the pty gets a fixed default size. A real, deferred gap, not attempted half-right.
- Consoling into a container whose image has neither `/usr/bin/bash` nor whatever `X-Kanxeo-Exec-Cmd` names installed fails with a normal exec error — the same real limitation `docker exec` has against a scratch-based image, not a bug to work around.
- The web dashboard's own terminal (a separate, later piece of this same phase) inherits a known, accepted fidelity gap: no alternate screen buffer, no full cursor-addressing grid, so `vim`/`top`/`less` and similar full-screen-redraw programs render wrong or garbled there specifically — `kanxeoctl console` has no such limitation.
