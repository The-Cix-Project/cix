# 0057 — Self-hosted toolchain and control-plane rebuild

## Status

Accepted

## Context

[0056](0056-hostbuild-artifact-mechanism.md) built the generic hostbuild mechanism and proved it against `kernel.recipe`. The remaining half of the original goal (an operator rebuilding Kanxeo with no separate dev machine at all) is rebuilding `kanxeod`/`kanxeoctl`/`web` themselves — which, per this project's own Immutable Maxim, must be built with TCC, never GCC. That means the build-image needs a real TCC before anything else, and the source has to come from somewhere a fully network-isolated hostbuild container (`CLONE_NEWNET`, `net_count=0` — fetch always happens host-side via `curl` before the container starts) can actually reach.

## Decision

**TCC ships as an ordinary recipe**, installed via the unmodified `pkg install --image=<name>` flow — not baked into the shared build toolchain, not a hostbuild itself. `tcc.recipe` fetches the real upstream 0.9.27 release tarball from `download.savannah.nongnu.org` (matching this sandbox's own already-proven system TCC version) and patches one real, confirmed upstream bug: `lib/bcheck.c` unconditionally defines `CONFIG_TCC_MALLOC_HOOKS` on Linux, referencing glibc's `__malloc_hook`/`__free_hook`, which glibc 2.34 (2021) removed from `<malloc.h>` — TCC 0.9.27 predates that removal by four years. A `sed`-inserted glibc-version guard (mirroring the file's own existing BSD/Windows exclusion block) fixes it, matching how real downstream distro packages patch this exact issue.

**`kanxeo.recipe`'s source is Kanxeo's own self-hosted gitea archive-download endpoint**, not `git clone` (impossible with no network in the build container) and not a vendored tarball. The real, working URL shape is gitea's REST API (`https://git.home.arpa/api/v1/repos/{owner}/{repo}/archive/{ref}.tar.gz`) — this instance's reverse proxy only forwards `/api/*` and git-smart-http paths, so gitea's documented web-convention URL (`/owner/repo/archive/<ref>`) 404s even authenticated. `pkg_version="v1.4.0"` is a real, annotated git tag cut on the exact commit this recipe's own prior work landed at — a pinned snapshot, matching `git.recipe`'s own fixed-version discipline, and making a future tag bump the natural "new self-build available" signal. `extract_tarball()`'s existing `--strip-components=1` means `pkg_build()` runs with its CWD already at the repo root regardless of the archive's own top-level directory name — no new pkg.c behavior needed.

**Authentication uses a scoped gitea access token embedded in the source URL**, not a public repo. The org this repo lives under (`itdlabs`) has `visibility: limited`, which overrides an individual repo's own public/private setting for anonymous access — discovered only after making the repo itself public still left anonymous fetches blocked. Rather than widen the org's own access model (a bigger, unrelated change), a read-only (`read:repository`) token is embedded as the HTTP basic-auth password in `pkg_source`'s URL (`https://user:TOKEN@host/...`) — gitea accepts a token as the basic-auth password natively, so this needed zero daemon/`pkg.c` code changes. **The committed recipe never contains the real token** — `pkg/recipes/kanxeo.recipe` as committed carries a `REPLACE_WITH_REAL_TOKEN` placeholder, documented inline, mirroring this project's own already-established pattern for the ISO installer's signing key (gitignored, must exist locally, documented substitution). A real token is never printed or logged; it lives only in local operator state, substituted into the recipe at `pkg recipe add` time.

**`mkbootroot` runs server-side inside `kanxeod`, never CLI-invoked** — the API-First Mandate leaves no other option, and the daemon already forks subprocesses for `curl` during fetch, so this is the same pattern, not a new capability class. `kanxeo.recipe`'s own `pkg_build()`/`pkg_install()` produce `build/mkbootroot` itself alongside `kanxeod`/`kanxeoctl`/`web/`, making each hostbuild round self-contained — a freshly-deployed box has never had `mkbootroot` on it before (it was previously only ever a dev-machine build tool), so bootstrapping it from a prior round's own copy would be a hidden ordering dependency. `pkg_build_completed()` (`daemon/src/pkg.c`) gained a new `out_hostbuild_done_name` out-parameter, populated only when a hostbuild job named the completing package — `pkg.c` itself stays completely agnostic to what any package name *means*; the "kanxeo is special" business logic (spawning `mkbootroot`) lives entirely in `main.c`'s `handle_container_event()`, via a new `CONN_BOOTROOT_ASSEMBLE` conn kind that forks+execs+pidfd-tracks `mkbootroot` exactly like the existing `CONN_PKG_FETCH` pattern — non-blocking, epoll-driven, never stalls the daemon's single-threaded event loop even though `mksquashfs` itself may take real time.

**CLI `--deploy` for `name=="kanxeo"` does not poll the async assembly step.** It reads `<artifact_path>/kanxeod-root.squashfs` once the hostbuild job itself shows `installed` and calls the existing, unmodified `cmd_update()` with `--image=`. `state=="installed"` only means `pkg_build_completed()` ran, not that the follow-on `mkbootroot` child has finished — but bolting a second, ad-hoc polling loop onto the CLI for one specific recipe name would be exactly the kind of one-off the API-First Mandate exists to prevent. If the squashfs isn't there yet, `/system/update`'s own existing error handling for a missing/unreadable `image_path` is the honest answer.

## A real, load-bearing gap found and fixed along the way: TCC's own CRT search path

The first real hostbuild attempt against `kanxeo-builder` failed with `tcc: error: file 'crt1.o' not found` even though `crt1.o`/`crti.o`/`crtn.o` genuinely existed at `/lib/x86_64-linux-gnu/` — the exact path `libc-dev.recipe` already staged them at, chosen specifically to match GCC's own `LIBRARY_PATH` convention (confirmed via `gcc -v`). Root-caused by comparing `tcc -vv`'s own verbose search-path dump against vanilla upstream tinycc source (`tcc.h`'s `CONFIG_TCC_CRTPREFIX` macro, `libtcc.c`'s `tcc_split_path(s, &s->crt_paths, ...)`): TCC maintains a **separate, single-path** search list specifically for CRT startup objects, distinct from its broader "libraries:" list used for `-l`/general library lookups, and that single path defaults to `/usr/lib/x86_64-linux-gnu` (with triplet) — confirmed to be tinycc's own genuine upstream default, not a Debian-specific patch. `libc-dev.recipe`'s `pkg_install()` now stages a second copy of the six crt objects (`crt1.o`/`crti.o`/`crtn.o`/`Scrt1.o`/`gcrt1.o`/`Mcrt1.o`, not `libc.a`/`libc_nonshared.a` — those are already reachable via TCC's broader "libraries:" list, which does include `/lib/x86_64-linux-gnu`) at `/usr/lib/x86_64-linux-gnu`, satisfying both toolchains' differing conventions from the one shared recipe.

A second, related failure surfaced in the same build attempt: `/lib/x86_64-linux-gnu/libc.so.6: error: referenced dll 'ld-linux-x86-64.so.2' not found`. Root-caused via `tccelf.c`'s `load_dll()`: glibc ≥ 2.34's own `libc.so.6` carries a `DT_NEEDED` entry on `ld-linux-x86-64.so.2` itself, and TCC resolves every `DT_NEEDED` name it finds through its ordinary, general library-search-path list via `tcc_add_dll()` — which does not include `/lib64`, the one place this file was staged (`pkg_seed_image_baseline()`'s `runtime_libs[]` table in `daemon/src/pkg.c`, matching where a real dynamic loader genuinely lives). Fixed with a second `runtime_libs[]` entry copying the same file to `/lib/x86_64-linux-gnu/ld-linux-x86-64.so.2` too — a path TCC's general search list does cover. Both fixes are additive, idempotent second copies of files already correctly staged for their original purpose (GCC's `LIBRARY_PATH`, the real dynamic-loader path) — nothing about the existing convention was wrong, TCC simply has its own, narrower, genuinely different search-path defaults that a from-scratch TCC-only build image has to satisfy too.

## Another real gap: `kanxeo-builder` needed a real shell and coreutils

Built up incrementally, the same "confirm via a real failure, fix precisely" discipline as every prior recipe-catalog gap: the first real hostbuild attempt after fixing the CA/auth chain (below) failed with `execve failed` — `kanxeo-builder` had `tcc`/`make`/`libc-dev` but no `bash` at all, so the container's `/usr/bin/bash` shell (this project's own images have no `/bin`) didn't exist for `make` to invoke. The next attempt got further but failed with `mkdir: No such file or directory` — the root `Makefile`'s own `mkdir -p build` needs a real `mkdir` binary, and `kanxeo-builder` had no `coreutils` either. Both fixed by installing the already-existing `bash.recipe`/`coreutils.recipe` onto the image — no new recipes needed, just completing the minimal image's own dependency set the same one-at-a-time way `kanxeo-builder`'s tcc/make/libc-dev set was originally built up.

## A fourth gap: this sandbox's own stale system CA bundle

The first real archive-fetch attempt against `git.home.arpa` failed with `unable to get local issuer certificate` from plain `curl`, even though `git`'s own GnuTLS-backed TLS stack fetched the identical URL successfully. Root-caused: `git` reads individual cert files from `/etc/ssl/certs/` dynamically, while `curl` (OpenSSL-backed) reads only the static, pre-concatenated `/etc/ssl/certs/ca-certificates.crt` bundle — which was stale relative to an individually-present cert already on disk (`gibnet-im-root.crt`, the itdlabs internal CA). No `update-ca-certificates` tool exists in this sandbox to regenerate the bundle automatically. Fixed, with explicit user approval, by appending the missing cert directly to the bundle. This is a real fact about this specific development sandbox, not a Kanxeo behavior — a real deployed box's own trust chain is unaffected, and the daemon's own fixed curl invocation has no per-recipe CA-override capability regardless.

## Verification

No automated test can safely exercise "rebuild the box currently running the test suite with itself." Proven instead by one real, live, end-to-end operational round trip against a scratch verify daemon (`--data-dir=`-isolated, matching ADR-0044's own established isolation convention): `tcc`/`make`/`libc-dev`/`bash`/`coreutils` installed onto `kanxeo-builder` via ordinary `pkg install`; `pkg hostbuild kanxeo --build-image=kanxeo-builder --wait` fetched the real, tagged, token-authenticated gitea archive, built `kanxeod`/`kanxeoctl`/`mkbootroot` inside the container entirely with the just-installed TCC (confirmed via the daemon's own log showing the real `tcc -Wall -Werror ...` invocations, zero warnings), and reached `state=installed`; the daemon's own async `CONN_BOOTROOT_ASSEMBLE` step then ran `mkbootroot` server-side and logged `kanxeo bootroot assembly: succeeded`; the resulting `kanxeod-root.squashfs` was confirmed via `file` to be a genuine, valid squashfs image (`Squashfs filesystem, little endian, version 4.0, xz compressed`).

## Consequences

- `pkg.h`/`pkg.c`: `pkg_build_completed()`'s new `out_hostbuild_done_name` out-parameter is a minimal, generic completion-notification extension — `pkg.c` stays agnostic to package meaning, matching the same posture ADR-0056 already established for the hostbuild mechanism itself.
- `main.c` gained one new async subsystem shape (`CONN_BOOTROOT_ASSEMBLE`), directly mirroring the already-proven `CONN_PKG_FETCH` pattern rather than inventing a new one.
- `libc-dev.recipe` and `pkg_seed_image_baseline()`'s `runtime_libs[]` table are real, general fixes — any future TCC-only build image benefits from both, not just `kanxeo-builder`.
- The committed `kanxeo.recipe` carries a placeholder token, not a real secret; an operator must substitute a real, scoped gitea token before the recipe can actually fetch — documented inline in the recipe itself.
- Concurrent hostbuilds remain out of scope (unchanged from ADR-0056); no change to `/system/update`/`/system/reboot` themselves; GPU firmware re-staging on a kanxeo-only rebuild remains out of scope (`spawn_kanxeo_bootroot_assembly()` passes an empty firmware-dir argument deliberately — a control-plane-only rebuild needs no GPU firmware re-staging).
