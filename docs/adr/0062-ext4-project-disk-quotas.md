# 0062 — disk quotas: real ext4 project-quota enforcement, permanent project-id assignment

## Status

Accepted

## Context

Part 4 of the bare-metal-readiness plan: nothing in this project enforces a per-container disk-usage limit today — `overlay_upperdir_size()` (ADR-0054) only ever *reports* a container's real disk usage for `GET .../stats`, with no mechanism to cap it. On real hardware, a single misbehaving or malicious container writing unbounded data into its own overlay upperdir can exhaust the whole containers partition, starving every other container and the host itself. ext4's own real, kernel-enforced project-quota mechanism is the right tool: distinct from the ordinary per-uid/gid quota every Linux admin already knows, a *project* is an arbitrary group of inodes (here: one container's entire upperdir subtree) the kernel tracks and limits independently of which uid owns the files inside it — the correct model for this project, since every container process here already runs as the same uid regardless of which container it belongs to.

## Decision

**Kernel config**: `CONFIG_QUOTA=y` (which itself `select`s `CONFIG_QUOTACTL` — confirmed directly against the real kernel source's `fs/quota/Kconfig`, not assumed) and `CONFIG_QFMT_V2=y` (the vfsv0/vfsv1 on-disk quota-file format `mkfs.ext4 -O quota`'s own hidden quota inode needs to be readable at mount time at all).

**Enabled at mkfs time, not via a mount option** — a real, confirmed distinction, not an assumption: ext4's own `mount(8)` man page states `noquota|quota|usrquota|grpquota` are accepted but *ignored* mount options on ext4 (verified directly on this dev sandbox's own man page). The real mechanism is the on-disk `RO_COMPAT_QUOTA` feature bit and a hidden quota inode, both baked in once at filesystem-creation time via `mkfs.ext4 -O quota -E quotatype=prjquota` (`cix-install.c`'s `mkfs_ext4()`, now taking a `with_quota` parameter, applied only to the containers partition — the ESP and `cix-config` partitions never hold container overlay data). Verified empirically against this sandbox's own real `mkfs.ext4` binary (1.47.0): both the `quota` and `project` feature flags land correctly in the resulting filesystem (`dumpe2fs -h` confirmed), against a plain file image (this sandbox has no loop devices at all, so a real *mount* of a fresh quota-enabled ext4 filesystem could not be verified here — see Consequences). Once the feature bit and hidden quota inode exist, the kernel enables quota tracking automatically on every mount, with zero further mount-time configuration needed.

**Project-id tagging is real ext4/XFS-style `FS_IOC_FSSETXATTR`, not the older `FS_IOC_SETFLAGS`/`FS_PROJINHERIT_FL` pair** — a real, confirmed correction to this plan's own original phrasing (which named the old flag alongside the new ioctl): `struct fsxattr`'s `fsx_projid` + `fsx_xflags |= FS_XFLAG_PROJINHERIT` is the actual, modern API both ioctls this project uses expect (`FS_IOC_FSGETXATTR`/`FS_IOC_FSSETXATTR`, confirmed against `/usr/include/linux/fs.h` directly). `src/overlay.c`'s `overlay_create()` performs this tagging right after `mkdir(ov->upperdir, ...)` succeeds (child-side, post-`clone3()`, exactly where the plan specified) — `FS_XFLAG_PROJINHERIT` is not optional: without it, only the upperdir itself carries the project id, and every file a container later creates *inside* it (the overlay's whole reason to exist) would carry none at all, silently exempting all real container disk usage from the very quota this mechanism exists to enforce. Deliberately fails loud on `ioctl()` failure, unlike `cgroup_enable_io_accounting()`'s own best-effort posture elsewhere in this codebase — a quota that was requested but silently not applied is a correctness bug wearing a false promise, not a missing optional hardware capability.

**Project-id allocation is a new, small, persisted module (`daemon/src/quotamap.c`/`.h`), not folded into the existing in-memory-only `registry.c`** — a deliberate, confirmed split: `registry.c`'s own doc comment states its table is in-memory-only by design (every container dies via `PR_SET_PDEATHSIG` if the daemon exits, so there's nothing to reconcile on restart). A quota-project-id assignment is exactly the opposite: it must survive a daemon restart, because **`DELETE /v1/containers/{name}` does not remove the container's own upperdir at all** (confirmed directly by reading `handle_delete()` — it only tears down the registry entry, DNS/PKI ownership, and the persisted container definition; the real on-disk `<CONTAINERS_DIR>/<name>/upper` tree stays exactly where it was, ADR-0054's own pre-existing backup/restore design, e.g. `test_system_backup.c`'s "deleted, then restored" scenario). A permanently-deleted-looking container can still be holding real, quota-counted disk space.

**Project ids are therefore never reclaimed, reused, or recycled — a deliberate, explicit decision, not left implicit** (the plan's own instruction): reusing an id the instant a container is `DELETE`d would silently misattribute that id's now-orphaned-but-still-real disk usage to whatever new container happened to get it next. Since the underlying files simply never go away on delete (by this project's own existing, established design), the project id assigned to a given container **name** doesn't either — `quotamap_get_or_assign()` looks up an existing assignment before allocating a fresh one, so recreating a container under a name that previously had a quota naturally, correctly gets the same id back (the same logical container reoccupying the same on-disk path), while a genuinely new name always gets a fresh one from a persisted, monotonically-increasing counter (starting at 1000, since project id `0` is reserved — an untagged inode's `fsx_projid` reads back as `0`). `QUOTAMAP_MAX` (1024) is a considered, generous fixed bound matching this codebase's own established "no natural ceiling to mirror" convention — larger than `REGISTRY_MAX_CONTAINERS` (256, a ceiling on containers *live at once*) since this table instead accumulates one entry per distinct name that has *ever* requested a quota over the system's whole lifetime.

**Quota-limit enforcement (`quotactl(2)` `Q_SETQUOTA`) is host/daemon-side, order-agnostic with the child-side tagging above** — confirmed correct, not assumed: setting a limit for a project id via `Q_SETQUOTA` is independent of whether any inode has been tagged with that id yet (a completely normal, harmless no-op until one shows up), so there's no ordering race between `daemon/src/main.c`'s `set_disk_quota()` (called from `create_container_from_body()`) and `overlay_create()`'s own tagging inside the child. `dqb_bhardlimit`/`dqb_bsoftlimit` are set equal (no soft-limit/grace-period policy — this project has no mechanism to surface a grace-period warning to an operator anyway, so a hard cutoff the instant the real limit is hit is the honest, correct behavior, not an arbitrary simplification) and expressed in real quota *blocks* (always 1024 bytes each, confirmed against `sys/quota.h`'s own `struct dqblk` comment — not the filesystem's own block size), converted from the request's raw byte count with round-up.

**Device-path resolution is real and dynamic, not hardcoded** — this plan's own text explicitly flagged this as a real, unanswered question ("must be confirmed, not assumed"), and confirming it directly surfaced a real problem with the obvious hardcoded answer: `CONTAINERS_DEVICE` (`/dev/vda5`) is only correct under a genuine `--init-mode` boot; every daemon-linked test, and any `--data-dir=` override, instead points `CONTAINERS_DIR` at an ordinary directory on whatever filesystem the host/test environment's own root happens to be — a different, real device `quotactl(2)`'s own `special` argument must be told about correctly. `resolve_backing_device()` (`daemon/src/main.c`) resolves this for real by walking `/proc/mounts` and picking the longest-matching mount point for `CONTAINERS_DIR` — the same "find the owning mount" algorithm `findmnt`/`df` use internally — rather than assuming a fixed path that would be silently wrong in every non-`--init-mode` context this daemon actually runs in day to day.

## Consequences

- Verified real, empirically, within this sandbox's actual constraints: `mkfs.ext4 -O quota -E quotatype=prjquota` confirmed to correctly bake the `quota`/`project` feature flags into a real ext4 filesystem image (`dumpe2fs -h`, no mount needed for this check). `resolve_backing_device()` is exercised for real by this daemon's own normal `CONTAINERS_DIR` at every startup (not just under test) — it is the one real device-resolution path this daemon now always uses, not a test-only shim.
- **Not verified, per Zen — a real, structural constraint of this specific dev sandbox, not a design gap**: this sandbox has no loop devices at all (confirmed, an existing documented environment fact) and no access to the raw block device backing its own root filesystem (`tune2fs`/direct block-device access both confirmed to fail here), so a real, live *mount* of a freshly quota-enabled ext4 filesystem, and therefore a real `FS_IOC_FSSETXATTR`/`quotactl(2)` `Q_SETQUOTA` call actually succeeding end to end, and a real write past the limit genuinely failing with `EDQUOT`, cannot be exercised in this environment at all — confirmed directly: `FS_IOC_FSSETXATTR` against this sandbox's own real (non-quota-enabled) root ext4 filesystem returns `EOPNOTSUPP`, the expected, correct behavior for a filesystem that was never given the quota feature, not a bug. This is the same class of honest gap already documented for Part 3 (a full QEMU boot with real kernel modules loading) and Part 5 (a real self-built ISO) — real, live verification needs either a real installed system or a test environment with genuine block-device/loop-device access, neither available here. Deferred and batched with Parts 2/3's own kernel config additions into one combined rebuild+boot cycle, per this plan's own kernel-config-consolidation decision.
- `bnx2` firmware staging (Part 3's own open item) and Part 5 (ISO self-build) remain separately unstarted; this ADR does not touch either.
