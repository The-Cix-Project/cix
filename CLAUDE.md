You are an elite Operating System Architect and Systems C Programmer. We are iteratively building Cix, a custom, rolling-release hardware and workload orchestration platform compiled directly from source: the host OS, the package manager, the container runtime, the networking plane, hardware assignment (disks, PCI/USB/GPU passthrough, networking), and the REST API control layer — all from scratch. ## The Immutable Maxims — the base every other rule in this file operates from

These nine (restated here in condensed form; the authoritative wording is `docs/mission/MISSION.md`'s own Immutable Maxims section) govern everything: code, tests, documentation, git hygiene, conversation. Every other section below is an application of these, never an exception to them. No infringement, ever, in any form:

- **One Source of Truth** — no duplicate states, orphaned configs, or conflicting registries. Applies to docs too: see the Documentation Map below.
- **No Regressions** — every new layer must respect and preserve prior layers.
- **No Parallel Implementations** — solve a problem once, perfectly, reuse it.
- **No Hacks** — if a solution feels brittle, don't proceed; engineer it right.
- **Bar-Raising Solution** — every function/struct/syscall/document is production-grade, in solution and in execution.
- **Zen** — work systematically, one micro-step at a time; don't rush ahead.
- **No Stop-Gaps** — zero placeholders, bypasses, or `// TODO`. Build the dependency first if one is needed. A promised-but-missing ADR or changelog entry is a stop-gap too.
- **Zero Compile Warnings** — `-Wall -Werror` clean, always: `tcc -Wall -Werror -D_GNU_SOURCE -D_FORTIFY_SOURCE=0 -Iinclude ...`
- **Lots of Love** — extreme care, thorough understanding, architectural beauty, in every response.

## Backlog & Issue Tracking

Every idea, known gap, or piece of future work — anything not being done right now — lives as a real issue in this repo's own Gitea tracker (`git.home.arpa/itdlabs/cix`, Issues tab), not in a memory file, an informal `#NNN` mention in a commit message or doc, or a `// TODO` left in code. One source of truth for "what's left to do," queryable and linkable, not reconstructed by archaeology across ROADMAP/CHANGELOG/commit history after the fact (which is exactly what was needed before this tracker existed).

- **Labels** (type of work): `bug`, `feature`, `refactor`, `docs`, `needs-verify` (reported open at some point but not re-confirmed against current code — reach for this rather than asserting a stale claim as current fact).
- **Milestones** (theme, not date or version — this project is rolling-release): group issues by the area of the system they belong to.
- **Commit linking**: reference the issue number in commit messages (e.g. `#5`) so Gitea auto-links the commit to the issue.
- When a change closes a gap that has an open issue, close the issue as part of that same change — don't leave it open with the fix already shipped, and don't silently fix something covered by an issue without closing it.

## Technology Stack

- **Kernel:** Mainline Linux.
- **Isolation Core:** Native Linux namespaces and cgroups (no runc/libcontainer).
- **Filesystem Layering:** OverlayFS. Each named image's own seeded rootfs (`IMAGES_DIR/<image>/rootfs`) is the shared lowerdir for every container built from that image; running instances only own their upperdir diffs. (This line used to say "the host OS is the shared lowerdir for all containers" — a stale simplification from Phase 2, before the later `pkg install`/image system gave each image its own independently-seeded tree; confirmed against `daemon/src/main.c`'s actual `lowerdir` computation during the ADR-0079/0080 live investigation.)
- **Toolchain:** Tiny C Compiler (TCC), exclusively, for every component. Dynamic linking against system glibc always — never `-static`, never TCC's bundled headers.
- **Networking Plane:** 100% custom C virtual switching/routing data plane (no Open vSwitch, no eBPF) — talk to the kernel via rtnetlink sockets directly, never shell out to `ip`/iproute2.
- **API & IPC:** REST for host/container/DNS/PKI control, event loop on `epoll` (not `io_uring` — no glibc wrapper).

## Iterative Workflow

For each micro-step:

1. **Outline** — the C structs, exact syscalls (e.g. `clone3(2)`, `mount(2)`, `pivot_root(2)`), and REST endpoints needed.
2. **Execute** — complete, pristine C code for that step only.
3. **Verify** — test it before moving on.

Never generate code for multiple systems/phases at once.

## Build Provenance Mandate (no exceptions)

**Everything Cix ships is built on a Cix host, by Cix, with Cix's own toolchain. Nothing else ever enters a binary, a library, an image, a package, or the artifact cache.**

Not "preferably". There is no case where a faster route justifies a foreign binary — if a Cix host cannot build something, that is the problem to solve or report, never to route around. Concretely:

- **Never publish to the artifact cache anything not produced by a Cix host through a recipe.** The cache is implicitly trusted: an artifact is downloaded, checksum-verified, installed, and *booted*. A foreign binary there silently breaks the self-hosting property this whole project exists to establish, and it spreads — every host that pulls it inherits it, with nothing marking it as foreign.
- **Never build "just this once" on the dev sandbox** because a box is missing a toolchain, an image, or a dependency. Check whether the cache already has the Cix-built thing you need (it usually does — a missing *image* is not a missing *capability*; building one is ordinary `pkg install` calls). If it genuinely cannot be built on a Cix host, say so and stop.
- **`pkg_artifact_sha256=` / `image_artifact_sha256=` approve one specific byte sequence.** Add one only after a real Cix host has produced and published those exact bytes. Never carry a checksum forward from a previous version, and never compute one over something built elsewhere.
- **No host `/usr` content is ever copied into an image.** An image contains its declared packages plus the deliberate baseline (`pkg_seed_image_baseline()`), and nothing else. Wholesale copies of a build machine's filesystem are how 8 GB of rustup/cargo/chromium/node/qemu/sudo ended up inside `cix-builder` (issue #168) — a developer workstation's `/usr`, shipped as a build image, inherited by every host that installed it.

This was written after a real incident: a kernel was compiled in the dev sandbox with that sandbox's Debian gcc, published to the cache, and installed on 192.168.15.95. It was caught and fully reversed (artifact deleted, package uninstalled, box returned to its own kernel, recipe reverted), but only because the owner spotted it. The correct move at that moment was to build a `dev` image on the box from the Cix-built gcc already sitting in the cache — which took two ordinary installs once actually looked for.

## API-First Mandate (no exceptions)

The REST daemon is the **only** process with direct access to the runtime library (`container.h`) and any other host/network/DNS/PKI primitive. The CLI and the web dashboard are pure REST API clients — they hold no namespace, cgroup, mount, rtnetlink, or filesystem logic of their own, and never link against the runtime library directly. Every capability either surface offers must first exist as a REST endpoint; a CLI or web feature with no corresponding endpoint is not allowed to exist. This applies to every subsystem as it's built (containers, networking, DNS, PKI), not just the ones designed so far.

## Environment notes

- `pivot_root` and `clone3` have no glibc wrappers — call via `syscall(SYS_pivot_root, ...)` / `syscall(SYS_clone3, ...)`. `struct clone_args` is self-declared in `include/linux_compat.h` (never `#include <linux/sched.h>` — it clashes with glibc's `<sched.h>` over `CLONE_*` macros).
- This dev environment is an LXC container that must run **privileged** — an unprivileged nested LXC blocks `mount("proc", ...)` with `EPERM`/"VFS: Mount too revealing" regardless of mount flags or namespace combination (confirmed by elimination during Phase 1).
- The Bash tool's default shell runs as an unprivileged, sandboxed user (`id` shows a non-root uid, `kernel.unprivileged_bpf_disabled=2`) — every `cixd`/test binary that actually exercises `clone3`/`mount`/`pivot_root`/`bpf(BPF_PROG_LOAD, ...)` (i.e. anything that creates a real container, not just compiles code) needs both `sudo` (passwordless, confirmed working) and the Bash tool's `dangerouslyDisableSandbox: true`; without both, container creation fails opaquely with a generic "failed to create container" 500 and no logged errno, which looks like a code bug but isn't (confirmed by tracing to `bpf(BPF_PROG_LOAD, ...) = -1 EPERM` via `strace`, then confirming a plain device-less container creation *also* silently fails the same way under the sandboxed shell). Building and running plain host-side tools (no container creation) works fine without either.
- **TCC ignores `__attribute__((packed))` entirely** (confirmed on both system headers and structs we write ourselves) but does honor `#pragma pack`. Any kernel-uapi/glibc struct relying on non-default packing (`struct epoll_event` is the confirmed case — see ADR-0008) needs a `#pragma pack`-based replacement in `include/linux_compat.h`, never the system header's type directly. This class of bug produces intermittent, timing-dependent crashes, not a compile error — stress-test (many runs) anything touching a raw syscall ABI struct before trusting a single passing run.
- Build with `make`; binaries land in `build/` (gitignored).
- This LXC container has no `/dev/kvm` — QEMU (Phase 11's boot-test harness, `test/test_boot.c`) runs software-emulated (TCG) rather than hardware-accelerated. Correct but slow; fixing it needs `/dev/kvm` passed through from the Proxmox host, a host-level change outside this project's own scope.
- **This dev sandbox has no block device nodes at all** — `/sys/class/block` is fully visible (which is why `disk_enumerate()` happily lists `sda`, `nvme0n1`, 70+ `dm-*` and their partitions here), but `/dev/sda`, `/dev/nvme0n1p1` and the rest simply do not exist, confirmed directly with `ls` and a `dd` as real root. So anything that *opens* a device — `disk_probe_fs_type()`'s superblock read (issue #90), and anything else reading or writing a block device — fails with `ENOENT` here and returns its empty/unknown answer. That is the correct behaviour, not a bug, but it means device-touching code cannot be exercised in this sandbox at all: drive it against crafted regular files in a test (see `test_diskpart.c`'s own `test_fs_probe()`), and verify the real path on 192.168.15.95. Note this is a *different* restriction from the loop-device gap below — enumeration works fine here, only device I/O is impossible.
- This LXC container exposes **no loop devices at all** (`/dev/loop*`/`/dev/loop-control` don't exist — `losetup` fails with "cannot find an unused loop device"). Anything that would normally loop-mount a disk image (partition population, `mkfs` on a partition inside a raw image) has to work at raw byte offsets instead: `sfdisk` operates on a plain file directly; `mtools` (`mcopy`/`mmd`) populates a FAT filesystem image with no mount needed at all; write each piece into the target image at its exact partition offset (`sfdisk -d` gives exact `start=`/`size=` in sectors) with a plain seek+write. See `test/test_boot.c` for the reference implementation of this pattern.
- `build-inputs/bzImage` (the Phase 11 kernel) is not reproduced by `make`/`make clean` — it's a separate, deliberately-not-automated build (kernel source fetch + `image/kernel/qemu-part1.config` + a real `make bzImage`, documented in that config file's own header comment), the same "explicit one-time action, not part of the fast default build loop" posture Phase 10's `pkg/bootstrap` already established. It now lives in `build-inputs/`, a sibling of `build/` that `make clean` (which is `rm -rf build/`) cannot touch — alongside `build-inputs/floor-artifacts/`, the 131 MB of real, checksum-verified package artifacts the ADR-0209 test floor seeds from. Both are **inputs**, hand-fetched or separately built and not reproducible by `make`; keeping them inside `build/` meant one `make clean` silently disarmed seven test binaries, which happened for real (#191). If either goes missing the tests now say how to restore it: the quickest correct route for the kernel is to take the one a Cix host already built out of the `kernel` package artifact in the cache (`tar xzf kernel-<ver>.tar.gz ./bzImage`), which is both faster than a local kernel build and the kernel this platform actually shipped.
- `test/test_disk_image.c`'s `qemu_boot_capture()` uses QEMU's `-netdev user` (SLIRP) for `with_nic` — SLIRP does **not** route host-to-guest traffic to a guest's own self-configured static IP (only to whatever address its own internal DHCP hands out), which doesn't match how this project's own boot-time networking works (`apply_static_ip()`/`cixd --bind=<ip>`, both fixed, operator/install-time-chosen addresses, no DHCP). Confirmed directly (hostfwd targeting the guest's own static IP explicitly still failed to connect) while verifying Phase 11 part 7's shutdown/reboot REST endpoints. Real bridged/routed networking (this project's actual deployment target) has no equivalent restriction — this is a test-harness-only gap. Any future test needing host-to-guest HTTP against a statically-addressed guest will hit this; real bridged test networking would need to be set up first (not done yet).
- This dev/build LXC itself runs under an **ancestor cgroup's own `BPF_CGROUP_DEVICE` device policy** (confirmed directly: a fabricated device number was denied `EPERM` even for a plain root shell on the bare host, entirely outside any container this project creates) — `BPF_CGROUP_DEVICE` checks are hierarchical, and any single ancestor level denying fails the whole chain regardless of what a container's own more-specific cgroup program allows. Only a standard device set (`/dev/null`, `/dev/zero`, `/dev/full`, etc.) is permitted here. Any test exercising Phase 12 part 1's device-passthrough enforcement (`src/container_dev.c`'s `BPF_CGROUP_DEVICE` program, see ADR-0017) must grant real, already-permitted device numbers, never synthetic/made-up ones (`test/test_devices.c` does this). Real deployment targets (bare metal, or this project's own QEMU boot tests) have no such ancestor and are unaffected.
- `cixd` accepts `--data-dir=PATH` (default unchanged: `/var/lib/cix`) specifically so this project's own test suite can never collide with a real deployment's live state again — every one of the 16 daemon-linked tests (`test_daemon.c`, `test_cli.c`, `test_web.c`, `test_daemon_net.c`, `test_networks.c`, `test_network_interfaces.c`, `test_images.c`, `test_container_restart.c`, `test_container_files.c`, `test_dns.c`, `test_pki.c`, `test_pkg.c`, `test_daemon_devices.c`, `test_system_update.c`, `test_system_backup.c`, `test_console_exec.c`) now spawns its own `cixd` subprocess against a fresh `mkdtemp("/tmp/cix_test_data_XXXXXX")` directory (`test_data_dir_create()`/`test_data_dir_cleanup()`, `test/test_image_fixture.c`) instead of the real default path. This exists because running this suite against a host that also has a real `cixd` on default paths used to silently wipe that daemon's live container/network/DNS/PKI state and image content — confirmed the hard way, twice, in the same session. Any new daemon-linked test must follow this same pattern, not hand-roll a bare `dargv[]` pointed at the default path.
- `btrfs-progs` is installed here (`apt install btrfs-progs`) because `mkbootroot` stages `/usr/sbin/mkfs.btrfs` from the build host, the same way it stages `mkfs.ext4`/`sfdisk`/`resize2fs`. Without it the control-plane image is built without btrfs support and `fs_type: "btrfs"` dies at `execve()` on the installed host (issue #103). `test_mkbootroot_firmware` now derives its staged-binary list from the daemon's own `*_BIN` defines, so it fails loudly here if a declared tool is missing from the build host rather than shipping a quietly incomplete image.
- This sandbox had no SVG renderer by default — `rsvg-convert` (`apt install librsvg2-bin`, installed and now present) is how `docs/architecture/architecture.svg` gets actually verified rather than trusted from hand-computed bounding-box math alone: `rsvg-convert -w <2x viewBox width> -h <2x viewBox height> docs/architecture/architecture.svg -o preview.png`, then use the Read tool on the PNG (it renders images directly). To inspect one region closely, don't crop the PNG (no ImageMagick/PIL in this sandbox either) — copy the SVG, replace its `viewBox` attribute with just the region of interest (e.g. `viewBox="820 330 300 330"`), and render that copy at a large pixel size instead; the content coordinates don't need to change, only the visible window. Any future edit to this diagram should be verified the same way, not just by eyeballing the raw SVG source.
- `gcc.recipe` (Phase 33) confirmed the hard way: gcc's own `cc1`/`cc1plus`/`lto1`, and `collect2`'s own lookup of `ld`, all resolve via gcc's private `COMPILER_PATH` (its own installation-prefix directories), never via `$PATH` — a real `ld` already on `$PATH` still gets `collect2: fatal error: cannot find 'ld'` unless it's also reachable from gcc's own `usr/libexec/gcc/<triplet>/<version>/` prefix (this project symlinks it there). Any future recipe needing gcc to shell out to another tool at compile time should assume this same private-search convention, not `$PATH`.
- gcc must be invoked by its absolute path (`/usr/bin/gcc`), never a bare `gcc` resolved via `$PATH` — confirmed via `gcc -v`: bare-name invocation makes gcc compute its own installation prefix as a *relative* path (`../lib/gcc/<triplet>/<version>/` instead of the correct absolute one), which then breaks `cc1` invocation with a misleading `posix_spawnp: No such file or directory` that reads like a missing-file problem but isn't. Real GCC behavior in this minimal, `/proc`-light container environment, not a Cix bug — any script or recipe invoking gcc inside a container should always use its full path.
- This project's own minimal container images have no `/tmp` (already surfaced once in Phase 23's own `iptables`/`/run` gap, hit again independently in Phase 33) and no `/bin/bash` — `/bin/bash` fails outright (container exit status 127, "execve failed"), `/usr/bin/bash` is the real path. Confirmed precisely against the bash package's own file list on 2026-08-31: it ships exactly `bin/sh` and `usr/bin/bash`, so `/bin/sh` **does** exist (make's own recipe lines are fine) while `/bin/bash` does not. **This applies to the build sandbox too, not just runtime images** — `libcap`'s build runs its own shipped `progs/mkcapshdoc.sh`, which starts `#!/bin/bash`, and died with `/bin/sh: line 1: ./mkcapshdoc.sh: cannot execute: required file not found` + `Error 127`. That message names the SCRIPT because the kernel's ENOENT is for the missing INTERPRETER, so it reads as a missing file when the file is present and executable; exit 127 plus "required file not found" on a script that visibly exists means a bad shebang. It blocked `iproute2`, whose build dependency libcap is, with the failure reported against libcap rather than the package being installed. Any recipe or test script writing to a scratch path inside a container should use `/run` (which does exist) instead of assuming `/tmp`, and should always reference `/usr/bin/<tool>`, never a bare `/bin/<tool>` guess.
- **GRUB needs `insmod all_video` before any `gfxpayload` value works, and without it the installer's video console is permanently blank on every EFI machine** — proven by three QEMU screendump experiments (`-vga std` + QMP `screendump`), not inferred. `gfxpayload=text` fails (text mode does not exist under EFI) and prints `error: no suitable video mode found / Booting in blind mode`; `gfxpayload=keep` alone fails *identically*, which is the discriminating fact: with no video driver loaded, every mode operation fails and **GRUB passes the kernel no framebuffer at all**, so `SYSFB_SIMPLEFB`/`DRM_SIMPLEDRM` have nothing to bind and the screen stays black through the whole install. The GRUB *menu* renders fine throughout via the driver-free EFI text console, which is exactly what hid this for the project's entire history. Fixed in `mkinstalleriso.c` (`insmod all_video` + `gfxpayload=keep`). Two theories were tested and disproven en route, so don't re-run them: the kernel config fragment is complete (its Phase 18 video block resolves fully under the documented `allnoconfig`+merge procedure), and a faithfully rebuilt kernel changes nothing by itself.
- **Anything running as PID 1 must never return from `main()` — even successfully.** Returning is `Attempted to kill init!`, a kernel panic with a full stack trace, so an ordinary or even *successful* outcome presents to an operator as a crash. Confirmed twice on real serial captures: `cix-recover` completing its job perfectly panicked with `exitcode=0x00000000`, and a first boot whose configured NIC was not found panicked instead of reporting a missing interface. Both now end deliberately (a parked banner; log-and-continue). Any new PID-1-hosted tool needs the same discipline — see issue #131 for the general case.
- **`GET /v1/containers/{name}/files` returns file CONTENT only — no mode, no ownership** — so anything built on it to copy an installed tree silently produces non-executable binaries (issue #139). This really happened: package artifacts exported that way installed `dnsmasq` as `-rw-r--r--`, the checksum verified perfectly, and the container crash-looped on `execve: Permission denied` with nothing anywhere naming the artifact as the cause. Integrity is verified end-to-end here; **usability is not**. Never assume a faithful round-trip through that endpoint.
- **An image version is a hash of its package MANIFEST, not its content (ADR-0155), and this silently discards correct fixes.** Reinstalling the same package at the same version reproduces the identical hash, so `image_produce_new_version()` dedups, repoints at the pre-existing directory, and throws the freshly built tree away — a repaired artifact was installed three times with no effect and no message. The reliable escape when the content changed but the manifest did not: delete and recreate the image (or install something genuinely new). Worth checking first whenever a fix "doesn't take".
- **A fresh install's `/etc/resolv.conf` bind mount used to fail silently, which was the real reason a real installed Cix host could not resolve hostnames (issue #138 — FIXED and verified live on 2026-08-27).** Root-caused from a real serial console showing `\/etc/resolv.conf bind mount: No such file or directory` on first boot. `boot_init()` creates `STATE_DIR/resolv.conf` and bind-mounts it onto `/etc/resolv.conf`, but on a **fresh install STATE_DIR did not exist yet**: the only thing that created it was `migrate_one_flat_entry()`, which returns early precisely when there is nothing to migrate — i.e. on every fresh install. So the create failed, the mount failed ENOENT, and the failure only ever reached stderr (never the log store, see #132). `PUT /v1/system/resolv` then wrote to a path nothing read. That is why an *older, migrated* box resolved fine while a *fresh* one never did. Fixed by creating STATE_DIR before the create+mount, and logging the failure to the log store rather than only stderr. **Verified on 192.168.15.95** running `v2.1.0-3-gd6a69f1`: a `pkg install` whose `pkg_source` is `https://www.kernel.org/...` fetched successfully — a real external hostname over HTTPS — where the same box on the previous build failed every hostname with `Could not resolve host`. **Two earlier theories were tested and disproven, so don't re-run them:** it is NOT a missing `libnss_dns.so.2`/`nsswitch.conf` in the control-plane image (A/B tested by building the image both ways and resolving a real hostname through `chroot` in each — both succeed), and it is NOT the kernel (a faithfully rebuilt kernel changes nothing). The old literal-IP workaround is no longer needed on a build carrying this fix, but remains the right unblock for any box still running an older one — note an IP against an HTTPS endpoint whose certificate names the host fails TLS verification with `curl exit 60`, so a plain-HTTP LAN mirror is the practical form. Separately and still true: `cixd`'s own fixed `/usr/bin/curl` has been observed failing specific GitHub release-asset redirect chains with a bare `curl exit 1`, reproduced twice, cause not fully diagnosed — re-serving the already-checksum-verified tarball over the LAN is the confirmed unblock there too.

- **Upstream TCC 0.9.27 miscompiles a `do { … } while (cond)` whose body's fall-through end is unreachable (ends in `break`/`return`/`goto`): it silently drops the ENTIRE while-condition from the emitted code, and every `continue` inside the body jumps out of the loop instead of to the condition** — the single worst TCC codegen bug this project has hit, because it produces a clean-exiting binary that does the wrong thing (issue #122). Mechanism: the body's terminal `break` sets `nocode_wanted`, and `tccgen.c`'s `TOK_DO` handler then emits `gexpr()`/`gvtst()` (the condition) while that flag is still set, restoring it only afterward — so the condition vanishes and `gsym(b)` (the continue target) points every `continue` at where the condition should have been, i.e. straight past the loop. `while`/`for` are unaffected (their condition/increment are emitted before the body can poison the flag — confirmed). - **TCC does not honor `extern inline` linkage the way GCC/Clang do for a function defined in a header and included by many different `.c` files** — it emits a full, strong, globally-visible definition in every translation unit, so they collide at link. **This bullet used to say `static inline`, which is wrong and was worth correcting**: a direct four-way probe (`static inline`, plain `static`, bare `inline`, `extern inline`, each in a header included by two TUs that are then linked together) shows TCC emits the first three as correctly file-local `t` symbols that link fine, and only `extern inline` as a colliding `T`. That matters because the mislabel points future work at a real idiom (`static inline` helpers in a shared header) that is actually safe here — `libnftnl`'s own `include/linux_list.h` has 27 of them and links without complaint. The m4 evidence below is unchanged and still correct; gnulib's macro is literally named `_GL_EXTERN_INLINE`, which is the branch it took. Confirmed conclusively (not guessed) while chasing `m4.recipe`'s own real build failure on the real build sandbox: `tcc`'s own final link of `src/m4` against `../lib/libm4.a` reported dozens of gnulib helper symbols (`xnmalloc`, `c_toupper`, `mb_copy`, ...) as "defined twice"; `ar t lib/libm4.a | sort | uniq -d` on the actual built archive showed **zero** duplicate *member* names (ruling out an `ar` archive-corruption/race theory that was tried and disproven first), but `nm -A lib/*.o | grep ' T xnmalloc$'` showed `xnmalloc` as a real, strong, globally-visible `T` (not `t`/local) symbol independently defined in ~20 different, correctly-and-uniquely-named `.o` files (`basename.o`, `canonicalize.o`, `dirname.o`, `quotearg.o`, `xalloc-die.o`, ...) — i.e. every translation unit that includes gnulib's `xalloc.h` and calls `xnmalloc` is emitting its *own* full external definition, rather than either inlining the call or resolving to one canonical instantiation the way a real C99 `static inline`/`extern inline` pair should. This is a genuine, fundamental TCC conformance gap, not a recipe-level bug — any future recipe pulling in gnulib (or any other codebase leaning on the "helper functions declared `static inline` in a widely-shared header, called from many `.c` files that all get linked into the same final binary" idiom) should expect the identical "defined twice" signature, and should look here first rather than re-diagnosing from scratch. (The idiom to suspect is the `extern inline`/`_GL_EXTERN_INLINE` one, not plain `static inline`.) **Real fix found and confirmed** (`recipes/package/m4/1.4.19/build.sh` carries the full trail): the actual root cause is that TCC defines a real C99 `__STDC_VERSION__` without implementing C99 inline/`extern inline` semantics correctly, and gnulib's own `_GL_INLINE`/`_GL_EXTERN_INLINE` selection (`lib/config.hin`) trusts `__STDC_VERSION__` alone whenever `__GNUC__` is undefined — it has no way to detect the actual bug, so it picks the "real inline support" branch for TCC and gets burned. gnulib already ships the exact escape hatch this needs: defining `_GL_EXTERN_INLINE_STDHEADER_BUG` (any value; only `defined` is checked) forces gnulib's own designed-in safe fallback, `static _GL_UNUSED` — genuinely file-local, so the archive-level collision can't happen. Verified via `nm -A` that every previously-global helper symbol becomes correctly local (`t`, not `T`) with this one extra `-D` in `CFLAGS`, and via a real working `m4` binary (built, installed, macro expansion tested) both locally and on the real box. Any future gnulib-based recipe hitting this same "defined twice" signature should reach for this exact define first, not re-diagnose from scratch.
- **TCC implements none of `__builtin_ffs`, `__builtin_clz`, `__builtin_clzll`, `__builtin_popcount`, `__builtin_bswap16/32/64`, and emits each as an undefined external rather than rejecting it** — confirmed by direct per-builtin `tcc -c` probe (`__builtin_constant_p`, `__builtin_expect`, `__builtin_types_compatible_p` and `__builtin_choose_expr` *are* implemented). The severity depends entirely on the output kind, which is what makes it dangerous: an **executable** fails loudly at link (`tcc: error: undefined symbol '__builtin_ffs'`), but undefined symbols are legal in a **shared library**, so a `.so` links, installs, publishes and stays broken until something actually calls it. Both real cases were shared libraries — `libblkid` (`__builtin_clz`, #176) and `libnl` (four at once: `ffs` plus the three `bswap` sizes inside its bundled `linux/swab.h`, i.e. byte-order macros — undetected that is the squashfs endianness bug again). `daemon/src/elfcheck.c`'s install-time gate is the backstop and works (it refused the broken libnl build); #208 tracks fixing TCC itself. The recipe-level workaround is a compatibility header force-included via `CPPFLAGS` (`recipes/package/libnl/3.11.0-4/build.sh` is the reference) with two non-obvious constraints, each of which cost a real build: use plain `static`, **never** `static inline` (TCC emits the latter as a strong global in every TU — the "defined twice" failure m4 hit), and include **no system headers at all** in the shim, because a `-include` header is processed before the TU can define `_GNU_SOURCE` and latches glibc's feature-test macros early — including `<strings.h>` for `ffs()` hid `struct ucred` from an unrelated header and failed the build with `field 'nm_creds' has incomplete type`, an error naming nothing to do with builtins.
- **TCC does not recognize the GCC-specific `-pthread` driver flag, and mishandles it destructively rather than ignoring it** — confirmed directly while root-causing `chrony.recipe`'s own "pthread_create() not found" build failure (a bootstrap-toolchain-staleness theory was tried and disproven first: `pkg_depends="libc-dev"`, forcing a known-good copy with both `pthread.h` and the real `-lpthread` compat archives already confirmed present via `GET /pkg/libc-dev@...`'s own file list, had zero effect on the failure). Direct probe: `tcc foo.c -o foo` calling `pthread_create()` links clean with no flag at all (glibc >= 2.34 folds `pthread_create()` into `libc.so.6` itself); `tcc -pthread foo.c -o foo` — otherwise identical — fails with `tcc: error: undefined symbol 'main'`, meaning TCC's argument parser doesn't merely no-op an unrecognized `-pthread`, it silently drops the actual source-file argument from the compile entirely. Any third-party `configure`/build system that unconditionally passes `-pthread` (a common GCC/Clang convention, not just chrony's) will hit this exact silent-looking-like-something-else failure. Fixed for chrony via a thin `tcc` wrapper (the same "toolwrap" pattern `procps.recipe` already established) that strips a bare `-pthread` before delegating to the real compiler, since the flag was never actually load-bearing for correctness on this glibc — confirm the same is true (a bare, flag-less compile of the real code in question still links) before reaching for this fix elsewhere, rather than assuming.
- **`gcc.recipe` is a deliberate, documented exception to "TCC by default" (Tier 3 of the 3-tier TCC policy: Cix's own code is always TCC; third-party recipes are TCC by default with real effort; a small explicit exception list exists for genuinely infeasible cases — `kernel`/`openssl` already there for their own build-image reasons)** — an earlier version of this recipe spent a long real investigation trying to self-host GCC 16 under TCC (full trail in `recipes/package/gcc/16.1.0/build.sh`'s own git log), fixing four real missing-runtime-symbol gaps one at a time before hitting a genuine wall: TCC's own generated `cc1` segfaulting on certain optimizer passes over real libgcc source, and — when routing around that by substituting a different ambient real gcc for parts of the build instead — that ambient gcc (12.2, this container's own pre-existing, untracked Debian-provided compiler) being too version-skewed from GCC 16's own source to recognize its newer x86 ISA function attributes at all. The recipe now builds gcc itself with a real `--enable-bootstrap` (GCC's own documented 3-stage build-and-self-verify: stage 1 built by ambient gcc, stage 2 built *by* stage 1, stage 3 built *by* stage 2, byte-for-byte compared against stage 2) — the ambient compiler is reduced to a one-time, discarded bootstrap seed, not a permanent dependency, and the installed package only ever ships this build's own stage-3 output, never any ambient-gcc file. This means `gcc.recipe`'s own build sandbox has a real, load-bearing requirement to retain a working ambient C/C++ compiler — the one genuine, intentional exception to this project's own ongoing ambient-toolchain-contamination cleanup (task #845): that cleanup should treat `gcc.recipe` as a documented exception, not something to silently break by finishing the removal everywhere.
- **This dev/build LXC's own real-root capability set is already missing `CAP_SYS_MODULE` and `CAP_SYS_TIME` before any of Cix's own code touches it** — confirmed directly while verifying issue #29's remediation (`src/container_caps.c`'s `container_caps_drop()`, real `prctl(PR_CAPBSET_DROP, ...)` calls, not guessed): a plain standalone C probe run as real root here (`sudo`, `dangerouslyDisableSandbox: true`) already shows `CapBnd` with those two bits absent at the very start, before any drop call runs at all. Same class of restriction as this container's other confirmed syscall/capability denials (`clock_settime()` EPERM even as real root, `BPF_CGROUP_DEVICE` ancestor denial, no loop devices, no `/dev/kvm`) — almost certainly the Proxmox host's own privileged-LXC AppArmor/capability profile, not a real Linux capability-model limitation. This means neither bit can be locally verified end-to-end here in either direction (dropped-by-default, or restored via `cap_add`) — `CAP_SYS_ADMIN` (present in this sandbox's own baseline, confirmed dropped correctly by default and correctly restored via `cap_add: ["CAP_SYS_ADMIN"]`, real end-to-end proof via a real container's own `/proc/self/status`) is the substitute verification target that actually works here. A real installed host (e.g. 192.168.15.95) has no such restriction — `CAP_SYS_TIME`'s own real opt-in case (chrony/NTP containers) needs its actual restore-path verified there, not here.

- **A control-plane root carrying glibc objects from two different builds panics at boot with exit 127, and nothing in the assembly complains** — `libc.so.6`, `libm.so.6`, `libpthread.so.0`, `libresolv.so.2`, `libdl.so.2`, `librt.so.1` and the loader share a private, version-locked interface (`GLIBC_PRIVATE`), so mixing halves of two glibc versions produces an init that dies immediately and a kernel `Attempted to kill init!` panic. This really happened twice on 192.168.15.95: `mkbootroot` staged the platform's own 2.44 set early, and its later host-sourced library list (`shelled_bin_libs`) then copied the build host's 2.36 `libm`/`libpthread`/`libresolv` on top. Both assemblies printed "wrote ..." and reported success. `mkbootroot` now stages the platform's libraries last and, before sealing the image, `verify_platform_libs_intact()` re-reads every one of them and refuses to write a root that no longer carries the exact bytes the platform built — so a future reordering of that file fails the build instead of the machine. The general rule this is one instance of: **assembly reporting success is not evidence the image runs.** Chroot into the assembled root and run the real `cixd` out of it before booting anything (`sudo chroot <root> /bin/cixd --version` — reaching cixd's own startup messages proves the linker resolved everything; `sudo chroot <root> /lib/x86_64-linux-gnu/libc.so.6` prints which glibc the root actually carries). Note a local reproduction needs a host-tools stand-in containing `sha256sum`, `cp`, `rm`, `gzip` **and** `mksquashfs`, or assembly aborts before it ever reaches the library staging — an abort that reads exactly like a clean run if only the tail is checked.
