# Custom OS Project — Instructions

You are an elite Operating System Architect and Systems C Programmer. We are iteratively building thinC, a custom, rolling-release hardware and workload orchestration platform compiled directly from source: the host OS, the package manager, the container runtime, the networking plane, hardware assignment (disks, PCI/USB/GPU passthrough, networking), and the REST API control layer — all from scratch. See `docs/mission/MISSION.md` for the full charter (updated once Phase 11 proved the platform on real hardware — read it if the scope here seems narrower than what's actually being asked of you).

## The Immutable Maxims — the base every other rule in this file operates from

These nine (restated here in condensed form; the authoritative wording is `docs/mission/MISSION.md`'s own Immutable Maxims section) govern everything: code, tests, documentation, git hygiene, conversation. Every other section below is an application of these, never an exception to them. No infringement, ever, in any form:

- **One Source of Truth** — no duplicate states, orphaned configs, or conflicting registries. Applies to docs too: see the Documentation Map below.
- **No Regressions** — every new layer must respect and preserve prior layers.
- **No Parallel Implementations** — solve a problem once, perfectly, reuse it.
- **No Hacks** — if a solution feels brittle, don't proceed; engineer it right.
- **Bar-Raising Solution** — every function/struct/syscall/document is production-grade, in solution and in execution.
- **Zen** — work systematically, one micro-step at a time; don't rush ahead.
- **No Stop-Gaps** — zero placeholders, bypasses, or `// TODO`. Build the dependency first if one is needed. A promised-but-missing ADR or changelog entry is a stop-gap too.
- **Zero Compile Warnings** — `-Wall -Werror` clean, always: `tcc -Wall -Werror -D_GNU_SOURCE -D_FORTIFY_SOURCE=0 -Iinclude ...`
- **Lots of Love** — extreme care, thorough understanding, architectural beauty, in every response.

## Technology Stack

- **Kernel:** Mainline Linux.
- **Isolation Core:** Native Linux namespaces and cgroups (no runc/libcontainer).
- **Filesystem Layering:** OverlayFS. Each named image's own seeded rootfs (`IMAGES_DIR/<image>/rootfs`) is the shared lowerdir for every container built from that image; running instances only own their upperdir diffs. (This line used to say "the host OS is the shared lowerdir for all containers" — a stale simplification from Phase 2, before the later `pkg install`/image system gave each image its own independently-seeded tree; confirmed against `daemon/src/main.c`'s actual `lowerdir` computation during the ADR-0079/0080 live investigation.)
- **Toolchain:** Tiny C Compiler (TCC), exclusively, for every component. Dynamic linking against system glibc always — never `-static`, never TCC's bundled headers.
- **Networking Plane:** 100% custom C virtual switching/routing data plane (no Open vSwitch, no eBPF) — talk to the kernel via rtnetlink sockets directly, never shell out to `ip`/iproute2.
- **API & IPC:** REST for host/container/DNS/PKI control, event loop on `epoll` (not `io_uring` — no glibc wrapper).

## Iterative Workflow

For each micro-step:

1. **Outline** — the C structs, exact syscalls (e.g. `clone3(2)`, `mount(2)`, `pivot_root(2)`), and REST endpoints needed.
2. **Execute** — complete, pristine C code for that step only.
3. **Verify** — test it before moving on.

Never generate code for multiple systems/phases at once.

## API-First Mandate (no exceptions)

The REST daemon is the **only** process with direct access to the runtime library (`container.h`) and any other host/network/DNS/PKI primitive. The CLI and the web dashboard are pure REST API clients — they hold no namespace, cgroup, mount, rtnetlink, or filesystem logic of their own, and never link against the runtime library directly. Every capability either surface offers must first exist as a REST endpoint; a CLI or web feature with no corresponding endpoint is not allowed to exist. This applies to every subsystem as it's built (containers, networking, DNS, PKI), not just the ones designed so far.

## Environment notes

- `pivot_root` and `clone3` have no glibc wrappers — call via `syscall(SYS_pivot_root, ...)` / `syscall(SYS_clone3, ...)`. `struct clone_args` is self-declared in `include/linux_compat.h` (never `#include <linux/sched.h>` — it clashes with glibc's `<sched.h>` over `CLONE_*` macros).
- This dev environment is an LXC container that must run **privileged** — an unprivileged nested LXC blocks `mount("proc", ...)` with `EPERM`/"VFS: Mount too revealing" regardless of mount flags or namespace combination (confirmed by elimination during Phase 1).
- The Bash tool's default shell runs as an unprivileged, sandboxed user (`id` shows a non-root uid, `kernel.unprivileged_bpf_disabled=2`) — every `thincd`/test binary that actually exercises `clone3`/`mount`/`pivot_root`/`bpf(BPF_PROG_LOAD, ...)` (i.e. anything that creates a real container, not just compiles code) needs both `sudo` (passwordless, confirmed working) and the Bash tool's `dangerouslyDisableSandbox: true`; without both, container creation fails opaquely with a generic "failed to create container" 500 and no logged errno, which looks like a code bug but isn't (confirmed by tracing to `bpf(BPF_PROG_LOAD, ...) = -1 EPERM` via `strace`, then confirming a plain device-less container creation *also* silently fails the same way under the sandboxed shell). Building and running plain host-side tools (no container creation) works fine without either.
- **TCC ignores `__attribute__((packed))` entirely** (confirmed on both system headers and structs we write ourselves) but does honor `#pragma pack`. Any kernel-uapi/glibc struct relying on non-default packing (`struct epoll_event` is the confirmed case — see ADR-0008) needs a `#pragma pack`-based replacement in `include/linux_compat.h`, never the system header's type directly. This class of bug produces intermittent, timing-dependent crashes, not a compile error — stress-test (many runs) anything touching a raw syscall ABI struct before trusting a single passing run.
- Build with `make`; binaries land in `build/` (gitignored).
- This LXC container has no `/dev/kvm` — QEMU (Phase 11's boot-test harness, `test/test_boot.c`) runs software-emulated (TCG) rather than hardware-accelerated. Correct but slow; fixing it needs `/dev/kvm` passed through from the Proxmox host, a host-level change outside this project's own scope.
- This LXC container exposes **no loop devices at all** (`/dev/loop*`/`/dev/loop-control` don't exist — `losetup` fails with "cannot find an unused loop device"). Anything that would normally loop-mount a disk image (partition population, `mkfs` on a partition inside a raw image) has to work at raw byte offsets instead: `sfdisk` operates on a plain file directly; `mtools` (`mcopy`/`mmd`) populates a FAT filesystem image with no mount needed at all; write each piece into the target image at its exact partition offset (`sfdisk -d` gives exact `start=`/`size=` in sectors) with a plain seek+write. See `test/test_boot.c` for the reference implementation of this pattern.
- `build/bzImage` (the Phase 11 kernel) is not reproduced by `make`/`make clean` — it's a separate, deliberately-not-automated build (kernel source fetch + `image/kernel/qemu-part1.config` + a real `make bzImage`, documented in that config file's own header comment), the same "explicit one-time action, not part of the fast default build loop" posture Phase 10's `pkg/bootstrap` already established. If `build/` gets wiped, rebuild it from that recipe before running `test_boot`.
- `test/test_disk_image.c`'s `qemu_boot_capture()` uses QEMU's `-netdev user` (SLIRP) for `with_nic` — SLIRP does **not** route host-to-guest traffic to a guest's own self-configured static IP (only to whatever address its own internal DHCP hands out), which doesn't match how this project's own boot-time networking works (`apply_static_ip()`/`thincd --bind=<ip>`, both fixed, operator/install-time-chosen addresses, no DHCP). Confirmed directly (hostfwd targeting the guest's own static IP explicitly still failed to connect) while verifying Phase 11 part 7's shutdown/reboot REST endpoints. Real bridged/routed networking (this project's actual deployment target) has no equivalent restriction — this is a test-harness-only gap. Any future test needing host-to-guest HTTP against a statically-addressed guest will hit this; real bridged test networking would need to be set up first (not done yet).
- This dev/build LXC itself runs under an **ancestor cgroup's own `BPF_CGROUP_DEVICE` device policy** (confirmed directly: a fabricated device number was denied `EPERM` even for a plain root shell on the bare host, entirely outside any container this project creates) — `BPF_CGROUP_DEVICE` checks are hierarchical, and any single ancestor level denying fails the whole chain regardless of what a container's own more-specific cgroup program allows. Only a standard device set (`/dev/null`, `/dev/zero`, `/dev/full`, etc.) is permitted here. Any test exercising Phase 12 part 1's device-passthrough enforcement (`src/container_dev.c`'s `BPF_CGROUP_DEVICE` program, see ADR-0017) must grant real, already-permitted device numbers, never synthetic/made-up ones (`test/test_devices.c` does this). Real deployment targets (bare metal, or this project's own QEMU boot tests) have no such ancestor and are unaffected.
- `thincd` accepts `--data-dir=PATH` (default unchanged: `/var/lib/thinc`) specifically so this project's own test suite can never collide with a real deployment's live state again — every one of the 16 daemon-linked tests (`test_daemon.c`, `test_cli.c`, `test_web.c`, `test_daemon_net.c`, `test_networks.c`, `test_network_interfaces.c`, `test_images.c`, `test_container_restart.c`, `test_container_files.c`, `test_dns.c`, `test_pki.c`, `test_pkg.c`, `test_daemon_devices.c`, `test_system_update.c`, `test_system_backup.c`, `test_console_exec.c`) now spawns its own `thincd` subprocess against a fresh `mkdtemp("/tmp/thinc_test_data_XXXXXX")` directory (`test_data_dir_create()`/`test_data_dir_cleanup()`, `test/test_image_fixture.c`) instead of the real default path. This exists because running this suite against a host that also has a real `thincd` on default paths used to silently wipe that daemon's live container/network/DNS/PKI state and image content — confirmed the hard way, twice, in the same session. Any new daemon-linked test must follow this same pattern, not hand-roll a bare `dargv[]` pointed at the default path.
- This sandbox had no SVG renderer by default — `rsvg-convert` (`apt install librsvg2-bin`, installed and now present) is how `docs/architecture/architecture.svg` gets actually verified rather than trusted from hand-computed bounding-box math alone: `rsvg-convert -w <2x viewBox width> -h <2x viewBox height> docs/architecture/architecture.svg -o preview.png`, then use the Read tool on the PNG (it renders images directly). To inspect one region closely, don't crop the PNG (no ImageMagick/PIL in this sandbox either) — copy the SVG, replace its `viewBox` attribute with just the region of interest (e.g. `viewBox="820 330 300 330"`), and render that copy at a large pixel size instead; the content coordinates don't need to change, only the visible window. Any future edit to this diagram should be verified the same way, not just by eyeballing the raw SVG source.
- `gcc.recipe` (Phase 33) confirmed the hard way: gcc's own `cc1`/`cc1plus`/`lto1`, and `collect2`'s own lookup of `ld`, all resolve via gcc's private `COMPILER_PATH` (its own installation-prefix directories), never via `$PATH` — a real `ld` already on `$PATH` still gets `collect2: fatal error: cannot find 'ld'` unless it's also reachable from gcc's own `usr/libexec/gcc/<triplet>/<version>/` prefix (this project symlinks it there). Any future recipe needing gcc to shell out to another tool at compile time should assume this same private-search convention, not `$PATH`.
- gcc must be invoked by its absolute path (`/usr/bin/gcc`), never a bare `gcc` resolved via `$PATH` — confirmed via `gcc -v`: bare-name invocation makes gcc compute its own installation prefix as a *relative* path (`../lib/gcc/<triplet>/<version>/` instead of the correct absolute one), which then breaks `cc1` invocation with a misleading `posix_spawnp: No such file or directory` that reads like a missing-file problem but isn't. Real GCC behavior in this minimal, `/proc`-light container environment, not a thinC bug — any script or recipe invoking gcc inside a container should always use its full path.
- This project's own minimal container images have no `/tmp` (already surfaced once in Phase 23's own `iptables`/`/run` gap, hit again independently in Phase 33) and no `/bin` — only `/usr/bin` exists; `/bin/bash` fails outright (container exit status 127, "execve failed"), `/usr/bin/bash` is the real path. Any recipe or test script writing to a scratch path inside a container should use `/run` (which does exist) instead of assuming `/tmp`, and should always reference `/usr/bin/<tool>`, never a bare `/bin/<tool>` guess.
- **A real, installed thinC host has no outbound DNS resolution mechanism at all** — confirmed directly (`POST /v1/pkg/bootstrap` against a real internet hostname hung 150+ seconds before failing with `curl exit status 6`, `CURLE_COULDNT_RESOLVE_HOST`), and a full repo grep for `resolv.conf`/`nameserver` found zero hits anywhere in host-level code (`thinc-install.c`, `main.c`'s boot path). This project's own DNS mechanism (`dns.c`, `dnsmasq.recipe`) is entirely for the *internal* `.internal` thinC zone containers resolve against — it has never been wired to also serve the host process's own outbound `curl` fetches (pkg recipe multi-source, `pkg bootstrap --toolchain-url=`, `pkg hostbuild`'s git fetch). Any hostname-based fetch triggered by `thincd` itself on a real installed box will hang, then fail — only a literal IP works, **unless** the operator has first set real upstream resolvers via `GET`/`PUT /v1/system/resolv` (`thincctl resolv set --nameserver=...`, ADR-0076, since implemented) — a fresh, never-configured install still has this gap by default, but a box with real nameservers set (e.g. 192.168.15.95, configured this session) resolves real hostnames fine. The LAN-serve workaround (re-serving the needed content over the LAN by raw IP, `python3 -m http.server`) remains useful independent of resolver config: even with working DNS, `thincd`'s own fixed `/usr/bin/curl` (`PKG_CURL_BIN`) has been observed failing specific GitHub release-asset redirect chains (a 302 to `release-assets.githubusercontent.com`'s own time-limited signed blob URL) with a bare `curl exit 1` ("unsupported protocol") — reproduced twice against two different but structurally-identical such redirects (`openssl-3.0.20.tar.gz`'s own release asset, both via openssl.org's own redirecting `/source/` URL and the direct GitHub URL), while an equally-shaped redirect for a different package's release asset (`xz-5.8.3.tar.gz`) succeeded from the same box in the same session — cause not fully diagnosed (no shell access on the real box to inspect `curl -v` output directly), not blanket HTTPS/TLS brokenness (plenty of other real HTTPS fetches, including other GitHub-hosted ones, succeed). When a `pkg_source` fetch fails this way, re-serving the already-downloaded, checksum-verified tarball over the LAN and pointing a scratch/temporary recipe variant at that URL is the confirmed, working unblock.
- **This sandbox denies `clock_settime()` outright — `EPERM`, even as real root, even with `dangerouslyDisableSandbox: true`** (confirmed via a minimal standalone C program calling it directly, isolating the failure from any of thincd's own code). This blocks locally verifying the success path of the NTP subsystem's own clock-apply step (`ntp_time_set()`, `PUT /v1/system/time`, and a successful SNTP sync's own `clock_settime()` call in `daemon/src/ntp.c`) — the failure path (detecting and reporting the `EPERM`) *is* fully verifiable here and was. Same class of restriction as this container's other confirmed syscall denials (`BPF_CGROUP_DEVICE`, no loop devices, no `/dev/kvm`) — a real installed box (e.g. 192.168.15.95) has no such restriction. Any future host-clock-affecting feature needs its actual apply-succeeds path verified there, not in this dev sandbox.
- **A binary with a compiled-in default pidfile path under `/var/run/` will crash-loop silently on this project's own minimal container images** — confirmed the hard way with `dnsmasq.recipe`'s own container (`dns-1`/`dns-2` on 192.168.15.95): dnsmasq's real default pidfile is `/var/run/dnsmasq.pid`, but these images only ever have `/run` (no `/var/run`, no usrmerge symlink between them), so `open()` on that path fails and dnsmasq calls its own `die()` with `EC_FILE`, exit status 3 — instantly, on every single restart attempt, with zero REST-visible diagnostic at the time this was first found (ordinary run containers had no opt-in stdout/stderr capture yet, see task #676's own scope note) and the container vanishing from `GET /v1/containers` between backoff windows, which reads like the container was never created at all rather than what it actually is: a fast, silent crash-loop. Fixed by passing `--pid-file=` (empty — disables the pidfile write entirely, which nothing here needs since `thincd` already tracks the child by real PID) — `docs/api/README.md`'s own dnsmasq example command has been corrected to include this flag. Any future recipe wrapping a real, unmodified upstream binary that assumes a traditional `/var/run` should be checked for the same class of gap before trusting a first "it's running" response — a `POST /v1/containers` returning `"status":"running"` only proves the child successfully `execve()`'d, not that it stayed up past its own first-run file I/O. `capture_output` (task #652/#761, `POST /v1/containers`' own `"capture_output":true` field) closes the diagnostic gap this bullet originally described — any future silent-crash-loop investigation should reach for that first, not blind guessing.
- **A binary that looks up its own configured run-as user by name — even one that will never actually need to change UID, because it's already root and privilege-dropping is compiled out — will still fail on this project's own minimal images with no `/etc/passwd` at all**, not just no NSS module. Confirmed directly via `capture_output`, `chrony.recipe`'s own `chronyd` (built with `--with-user=root --without-libcap`, i.e. `-PRIVDROP` in its own feature summary, meaning it never calls `setuid()`): it still exited immediately with `Fatal error : Could not get user/group ID of root` on every attempt, because `getpwnam("root")` legitimately returns nothing when `/etc/passwd` has zero entries — `pkg_seed_image_baseline()`'s own general `libnss_files.so.2` + `/etc/nsswitch.conf` staging (ADR-0111, closing the earlier jumpbox-specific gap) only makes the `files` NSS backend *reachable*, it does not manufacture user records for it to find. Fixed by staging a minimal `/etc/passwd`/`/etc/group` (`root:x:0:0:root:/root:/usr/bin/bash` / `root:x:0:`) as ordinary `files[]` content at container-creation time, the same mechanism used for the binary's own config file — not a `pkg_seed_image_baseline()` change, since a real `/etc/passwd` is properly a container-instance concern (which accounts might exist), not an image-baseline one. Any future recipe wrapping a real upstream daemon that logs, prints, or validates its own configured user (even root) should be checked for this before trusting a first "it's running" response, same discipline as the pidfile bullet above.
- **TCC can't parse glibc's own `<regex.h>` `regexec()` prototype as written** — it declares its `regmatch_t` array parameter with a real C99 VLA-in-prototype size expression referencing the *next* parameter (`regmatch_t __pmatch[_Restrict_arr_ _REGEX_NELTS(__nmatch)]`), and TCC's simpler parser rejects it outright (`error: '__nmatch' undeclared`). Not a struct-packing issue (the `struct epoll_event`/`clone_args` class of bug) — the header's own `_REGEX_NELTS` macro already has an `#ifndef __STDC_NO_VLA__` branch for exactly this situation (a compiler without VLA support); `#define __STDC_NO_VLA__ 1` before `#include <regex.h>` (accurately — TCC really doesn't support this construct) steers the header onto that branch, which TCC parses fine, with zero hand-redeclaration of `regex_t`/`regmatch_t`/`regcomp`/`regexec`/`regfree` needed (unlike the packed-struct case, glibc's own real declarations are used as-is). See `daemon/src/logstore.c`'s own include-block comment for the confirmed repro.
- **The `thinc-builder` build image has no `binutils` (`ar`/`ranlib`) by default** — any `pkg_build()` step that ends up needing a real static-archive step (GNU Autotools/Libtool commonly build one internally as an unavoidable "convenience library" for a package with more than one source file, even with `--disable-shared --disable-static` passed — confirmed directly with `sysklogd.recipe`: identical `./configure && make` succeeds in a dev sandbox that happens to have `binutils` already installed, then fails with a real, reproducible build error against the real build image, which doesn't) will fail there specifically, not in every sandbox — this makes the failure look environment-flaky rather than a real, deterministic gap. `gcc.recipe`'s own `pkg_depends="binutils m4"` is the correct fix when the built package's own installed output will actually be used as a toolchain (worth the real cost of building the whole binutils tarball first). For a small package where pulling in the entire binutils toolchain as a build-only dependency would be disproportionate, `sysklogd.recipe` establishes the alternative: skip `make`/libtool entirely and compile+link the handful of needed `.c` files directly with `tcc`, bypassing the archive step altogether (see that recipe's own `pkg_build()` for the pattern). Prefer whichever the actual package shape justifies, but don't assume "it built in one sandbox" proves a recipe will build against the real image — the two environments are not guaranteed to carry the same base toolchain.
- **Direct `tcc`-only linking (no `make`/libtool driving it) can leave `__dso_handle` undefined** — confirmed live, again specifically on the real build image, not reproducible in every dev sandbox: glibc's own static-destructor/`__cxa_atexit` bookkeeping expects a `__dso_handle` symbol that the normal CRT/libtool-driven link path provides but a bare `tcc -o out a.o b.o ...` invocation sometimes doesn't, on some glibc builds. Fixed (see `sysklogd.recipe`) by compiling and linking in a one-line, `__attribute__((weak))` stub (`void *__dso_handle __attribute__((weak)) = (void *)0;`) alongside the real object files — `weak` means it's silently superseded wherever the toolchain already provides a real one (confirmed harmless in a sandbox where the bug never reproduces at all), and supplies the missing definition wherever it doesn't. A real, environment-specific TCC/glibc CRT gap, not something to patch into the third-party package's own source — the stub is compiled from this project's own recipe script, never a modification to unmodified upstream code.
- **The real build sandbox's (`__pkgbuild`, backed by the cumulative `g_pkgbuild_rootfs`) own bare `cc` can no longer be trusted to mean TCC** — confirmed the hard way via `openssh.recipe`'s own `-2` revision (`--with-pam`, ADR-0144 task #838): a `pkg_build()` with no explicit `CC=tcc` (the form nearly every recipe in this set uses, relying on this sandbox's own default) produced link commands literally spelled `cc`, carrying real GCC-family hardening flags (`-fstack-protector-strong -pie -Wl,-z,relro -Wl,-z,now -Wl,-z,noexecstack`) TCC does not understand or emit, and — despite `configure` correctly reporting "PAM support: yes" and `-lpam -lcrypt` genuinely present on the link line — produced an `sshd` binary with neither library actually recorded as a real ELF `DT_NEEDED` (confirmed via `readelf -d` against the real build output, captured through a live, intentionally-failing diagnostic build). A local from-scratch build in *this* dev sandbox with `CC=tcc` explicitly set, and a re-run of the same real-box recipe with `CC=tcc` forced, both produced the correct, fully-linked binary — proving the fix, not just the symptom. Almost certainly caused by `gcc.recipe`'s own toolchain output merging into the cumulative `g_pkgbuild_rootfs` sandbox at some point after most of this project's other recipes were last actually built there (that sandbox's cumulative nature is itself already documented above) — any recipe using `./configure` without an explicit `CC=tcc` is now at risk of silently picking up real GCC instead of TCC, not just this one. `sysklogd.recipe` was, until now, the only recipe in this set pinning `CC=tcc` explicitly; treat that as the correct default going forward for any `configure`-driven recipe, not an exception.
- **A dynamically-linked binary sourced from `thinc-hosttools` (ADR-0078) and directly `execve()`'d off the bare host (not inside a chroot/pivot_root, where a real container's own `/lib` is naturally on the search path) needs an explicit `LD_LIBRARY_PATH` pointed at that image's own lib directories, or the dynamic linker silently falls back to whatever the bare host already has there instead** (see ADR-0154). This fails *silently*, not loudly: a genuinely missing library aborts the process before `main()` runs (a real, easy-to-diagnose nonzero exit, already correctly handled) — but if the bare host happens to already have *some* same-named library at a normal system path, the linker just uses that one instead, with no error of any kind. The child reports a clean exit 0 while having run against a library it was never built or tested against. `image/src/mkbootroot.c`'s own `run_mksquashfs()` is the one confirmed real case (needs `liblzma.so.5`) and is the reference fix; any future host-tools binary added to a direct-exec call site (not just staged as a file the way `cp`/`rm`/`sha256sum`/`gzip` already are) needs the identical treatment.
- **TCC never predefines the bare `linux` compiler macro GCC always does on a Linux target** — confirmed directly via a trivial standalone `tcc -c` probe (`#ifdef linux` / `#else #error` / `#endif` fails to compile under TCC, compiles fine under GCC). This is a real, silent correctness hazard, not a build failure: any third-party source that branches real logic on `#ifdef linux`/`#ifndef linux` (not just feature-gates a declaration) will silently take the *other* branch under TCC, with no warning and often no build failure either — `squashfs-tools.recipe`'s own `endian_compat.h` is the confirmed real case (its entire byte-order detection branches on exactly this macro, so every TCC build was silently computing the host's own endianness wrong and byte-swapping every multi-byte on-disk field it ever wrote, `mksquashfs` still reporting a clean, successful exit throughout). Fixed there with `-Dlinux=1` on the command line — the correct, minimal fix wherever this exact pattern recurs is the same: confirm via the same trivial probe that a real third-party build genuinely relies on this legacy macro (don't assume; `__linux__`/`__linux` — the modern, non-legacy spellings — TCC *does* predefine correctly) before reaching for it, since supplying `-Dlinux=1` blindly on a recipe that doesn't actually need it is pure noise, not a fix.
- **`pkg_seed_image_baseline()`'s own "self-heals on its very next install" (ADR-0150's `/dev/ptmx` staging, and any future baseline addition) does not survive a same-manifest reinstall** — confirmed live, twice (ADR-0155): ADR-0108's image-version hash is a *manifest* hash (sorted `name@version` pairs), not a content hash, so uninstalling then reinstalling an already-present package at its own unchanged version reproduces the byte-identical manifest hash, and `image_produce_new_version()`'s own real, load-bearing dedup logic repoints `current_version` straight back to the pre-existing on-disk directory for that hash — the freshly re-seeded tree `install_mutate()` actually built is discarded, never becoming current. The self-heal only ever works when the resulting manifest is genuinely new. The real, repeatable unblock for an image caught by this: install a package it doesn't already have (any real one; needn't be permanent) rather than cycling an existing one.
- **A daemon-linked test binary killed mid-run by an external timeout (the harness's own command timeout, not the test's own `stop_daemon()` path) leaves its forked `thincd` child orphaned, still bound to that test's hardcoded port** — confirmed live during ADR-0157 Phase 4's own regression sweep: `test_pkg`'s port (7628) stayed held by a `thincd` from a run the test harness had killed after a 5-minute timeout, and every subsequent `sudo ./build/test_pkg` invocation appeared to succeed at "starting" its own daemon (the new process spawns fine) but was actually exercising the *orphaned* one instead — a different, incompatible `--data-dir` with none of the current run's freshly-written recipes, producing a cascade of failures that looked exactly like a real, non-deterministic regression (a different assertion failing on each rerun, eventually `stop_daemon()` itself reporting "did not exit cleanly on SIGTERM" since it was signaling the *new*, never-actually-bound process). `ps aux | grep thincd` is the fast way to tell this apart from a genuine flake before spending real effort chasing one: a leftover `thincd` still running from a prior invocation, `kill -9` it, then a single clean rerun settles the question — this project's own test suite has no port-reuse detection or startup-conflict error surfaced anywhere, so a stale daemon is silently indistinguishable from a fresh one until you look. Any test run that got killed by an external timeout (not its own clean exit) should be treated as a signal to check for and clean up orphaned daemons before trusting the *next* run's result, individually or in a batch.
- **TCC does not honor `static inline` linkage the way GCC/Clang do for a function defined in a header and called from many different `.c` files** — confirmed conclusively (not guessed) while chasing `m4.recipe`'s own real build failure on the real build sandbox: `tcc`'s own final link of `src/m4` against `../lib/libm4.a` reported dozens of gnulib helper symbols (`xnmalloc`, `c_toupper`, `mb_copy`, ...) as "defined twice"; `ar t lib/libm4.a | sort | uniq -d` on the actual built archive showed **zero** duplicate *member* names (ruling out an `ar` archive-corruption/race theory that was tried and disproven first), but `nm -A lib/*.o | grep ' T xnmalloc$'` showed `xnmalloc` as a real, strong, globally-visible `T` (not `t`/local) symbol independently defined in ~20 different, correctly-and-uniquely-named `.o` files (`basename.o`, `canonicalize.o`, `dirname.o`, `quotearg.o`, `xalloc-die.o`, ...) — i.e. every translation unit that includes gnulib's `xalloc.h` and calls `xnmalloc` is emitting its *own* full external definition, rather than either inlining the call or resolving to one canonical instantiation the way a real C99 `static inline`/`extern inline` pair should. This is a genuine, fundamental TCC conformance gap, not a recipe-level bug — any future recipe pulling in gnulib (or any other codebase leaning on the "helper functions declared `static inline` in a widely-shared header, called from many `.c` files that all get linked into the same final binary" idiom) should expect the identical "defined twice" signature, and should look here first rather than re-diagnosing from scratch. **Real fix found and confirmed** (`recipes/package/m4/1.4.19/build.sh` carries the full trail): the actual root cause is that TCC defines a real C99 `__STDC_VERSION__` without implementing C99 inline/`extern inline` semantics correctly, and gnulib's own `_GL_INLINE`/`_GL_EXTERN_INLINE` selection (`lib/config.hin`) trusts `__STDC_VERSION__` alone whenever `__GNUC__` is undefined — it has no way to detect the actual bug, so it picks the "real inline support" branch for TCC and gets burned. gnulib already ships the exact escape hatch this needs: defining `_GL_EXTERN_INLINE_STDHEADER_BUG` (any value; only `defined` is checked) forces gnulib's own designed-in safe fallback, `static _GL_UNUSED` — genuinely file-local, so the archive-level collision can't happen. Verified via `nm -A` that every previously-global helper symbol becomes correctly local (`t`, not `T`) with this one extra `-D` in `CFLAGS`, and via a real working `m4` binary (built, installed, macro expansion tested) both locally and on the real box. Any future gnulib-based recipe hitting this same "defined twice" signature should reach for this exact define first, not re-diagnose from scratch.
- **TCC does not recognize the GCC-specific `-pthread` driver flag, and mishandles it destructively rather than ignoring it** — confirmed directly while root-causing `chrony.recipe`'s own "pthread_create() not found" build failure (a bootstrap-toolchain-staleness theory was tried and disproven first: `pkg_depends="libc-dev"`, forcing a known-good copy with both `pthread.h` and the real `-lpthread` compat archives already confirmed present via `GET /pkg/libc-dev@...`'s own file list, had zero effect on the failure). Direct probe: `tcc foo.c -o foo` calling `pthread_create()` links clean with no flag at all (glibc >= 2.34 folds `pthread_create()` into `libc.so.6` itself); `tcc -pthread foo.c -o foo` — otherwise identical — fails with `tcc: error: undefined symbol 'main'`, meaning TCC's argument parser doesn't merely no-op an unrecognized `-pthread`, it silently drops the actual source-file argument from the compile entirely. Any third-party `configure`/build system that unconditionally passes `-pthread` (a common GCC/Clang convention, not just chrony's) will hit this exact silent-looking-like-something-else failure. Fixed for chrony via a thin `tcc` wrapper (the same "toolwrap" pattern `procps.recipe` already established) that strips a bare `-pthread` before delegating to the real compiler, since the flag was never actually load-bearing for correctness on this glibc — confirm the same is true (a bare, flag-less compile of the real code in question still links) before reaching for this fix elsewhere, rather than assuming.
