# recipes/

Git-tracked source for Cix's `pkg install`/`image apply-recipe`/`container apply-recipe` catalogs, split by kind (ADR-0149/ADR-0151) — not by topic, not by the phase that introduced a given recipe:

- **[`package/`](package/)** — 77 packages, each `<name>/<version>/build.sh`: real, from-source build recipes. Layout unchanged from ADR-0107 (filename per ADR-0120): `<pkg_name>/<pkg_version>/build.sh`, where both the directory names and the recipe's own internal `pkg_name=`/`pkg_version=` fields must agree exactly. A package can have more than one published version side by side (e.g. `curl/8.20.0/build.sh` and `curl/8.21.0/build.sh`) — recipe versions are immutable once published, never overwritten in place; fixing a mistake means publishing a new version. See [`docs/guides/writing-recipes.md`](../docs/guides/writing-recipes.md) for the complete authoring guide, with a real worked example.
- **[`image/`](image/)** — declarative per-image package-list manifests, `<name>/<version>/build.sh` (ADR-0123's format, ADR-0149's layout): each `build.sh` is `image_packages="pkgname:mode:version ..."`, not a shell script with `pkg_build()`/`pkg_install()` functions — the filename matches the package side purely for a uniform, predictable git layout, not because it executes as one. **The version directory here tracks the *recipe's own* revision history** (this declared package list changed, so it's a new version) — it is a completely separate concept from an image's actual build result, which is already content-addressed independently (ADR-0108). The daemon's own `image_recipe_add()` API stores exactly one current manifest per image name with no version parameter at all (ADR-0123's deliberate, unchanged design); `pkg sync` resolves which git version to publish by picking the highest per image name, the same "highest wins" rule an unpinned `pkg install NAME` already uses for package recipes.
  The images divide into two kinds, and ADR-0208 gives each one a single job so that a name can be wrong:

  | Image | Its one job |
  |---|---|
  | `cix-builder` | build Cix itself — **TCC only**, no gcc (ADR-0001) |
  | `kernel-builder` | build the kernel and its modules — the one image that legitimately holds gcc |
  | `iso-builder` | hold the ISO toolchain for `pkg hostbuild isotools` (renamed from `dev`) |
  | `gcc-tcc-bootstrap` | build GCC under TCC — the bootstrap rung |
  | `cix-hosttools` | **not a build image**: host-side binaries staged into the control-plane squashfs |
  | `chrony`, `dns`, `jumpbox`, `ldap`, `syslog` | workload images — what containers actually run |

  A manifest here is a *declaration of what the image is for*, not a snapshot of what some host happened to contain. The distinction is load-bearing: every one of these was originally captured from a running box, which is how `cix-builder` came to carry a gcc nobody chose and `dev` came to be prescribed for kernel builds it could not perform.

- **[`deployment/`](deployment/)** — a real `POST /v1/containers` body, verbatim, `<name>/<version>/container.json` (ADR-0151): everything an image recipe deliberately doesn't cover (`cmd`/`files`/network/restart-policy/sysctls). The version directory has the identical meaning the image side already established — the recipe's own revision history, unrelated to anything about the container's own runtime state (which has no version concept at all). May embed `{{SECRET:KEY}}` tokens inside any staged file's `content` string, substituted from a real value only at `POST /v1/deployments/{name}/apply` time — never commit a real credential to git.

**Prepared sources live in cix-cache, named `<name>-src-<version>-<release>` (#262).** Most recipes fetch upstream's own tarball, which stays where upstream put it. A few need a *prepared* tree first — a vendored Go module set, a submodule merged in, a generated shim — because a build container has no network at all and `pkg_build()` cannot fetch anything itself. That preparation is source work, not a build: it downloads and arranges source and compiles nothing, so it may be done in the dev sandbox, and the build still happens on a Cix host with Cix's own toolchain. What it must *not* do is land on whatever HTTP server happens to be up that day — `glauth` lost its prepared source exactly that way twice (`192.168.15.31:8904`, then `:8920`), and each time became unbuildable while still looking complete. The one durable, checksum-gated store every host already reaches is the artifact cache, so a prepared source is published there as `<name>-src-<version>-<release>-<arch>.tar.gz` (the cache stamps the arch; these bytes are not arch-specific), the recipe points `pkg_source` at it and `pkg_sha256` approves the exact bytes, and the recipe header records the assembly steps in full so that losing the store is recoverable rather than fatal. [`package/glauth`](package/glauth) is the worked example.

All three kinds are uploaded to a running daemon via `POST /pkg/recipes` / `POST /images/recipes` / `POST /deployments` (or `cixctl pkg recipe add`/`image recipe add`/`deployment add --file=PATH`) — these files are the *source* for a fresh deployment's initial catalog, never read directly off disk by `cixd` itself or baked into the installer ISO (see ADR-0040) — and, since ADR-0121 (package), ADR-0149 (image), and ADR-0151 (container), all three fetchable in bulk via `pkg sync` from a configured git repo instead of one-at-a-time uploads.
